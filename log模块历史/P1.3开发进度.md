### 2.2 已修 bug（★ 重要，别再踩）

**段文件必须预分配为定长 3984 B。**
首版 `flash_create_segment` 只写 16 B header，追加 9 条后文件为 1168 B
→ 重启扫描时 `size != LOG_SEGMENT_SIZE` 被判为损坏 → **整段丢失**
（实测 `valid=1, total_rec=31`，段 1 消失）。
修复：建段时把 header 之后的 3968 B 补零。未写入槽为全 0，其 CRC 必然校验失败，
因此天然表达"空槽"，无需额外标志位。

## 步骤 5：RAM → Flash safe handoff（已完成）

Commit：`feat(log): make persistent log drain loss-safe`

### 5.1 已实现（§22 / §23 / §24 / §27 / §28 / §30 / §39）

`log_task()` 由"先 pop 再写"改为 **窥视 → 分拣 → 单次 append → 按序提交** 四阶段：

| 阶段 | 内容 |
|---|---|
| 1 窥视 | 读第 `scanned` 条但**不推进 `s_rd`**；同时完成 routing 决策、stats 与 flush 请求 |
| 2 append | 本轮**唯一**的 Flash append 单元（§30），受 `LOG_FLUSH_RECORDS=8` 限制 |
| 3 按序提交 | 只有"已落盘"的前缀才计入 `commit`；遇首个未落盘记录即截断 |
| 4 提交 + 计 | 临界区内 `s_rd += commit`，并更新 `flash_append_ok/fail`、`flash_retry`、`flash_blocked_rounds`、`flush_honored` |

**关键不变量**：已落盘数 + 保留在环内的条数 == 已路由条数
⇒ WARN / ERROR / CRITICAL **不可能被静默丢弃**（§23）。

- **INFO（Flash NO）不依赖落盘**，天然可提交，不会被失败的 WARN 阻塞（§24）
- **CRITICAL 在同一轮内完成落盘**（§28 的"立即"= 本 LogManager 的下一次处理机会，
  不阻塞业务逻辑）
- `s_flush_requested` 在**本轮确有落盘**时视为已兑现并消费，计入 `flush_honored`（§27）
- Flash 未就绪 → 记录**保留**、`flash_blocked_rounds++`，下一轮再试；
  **无 `while(retry)`、无 delay、无独立 Task**（§29 / §39）

新增 stats（有界、`s_mux` 保护、不改旧字段含义，§38）：

| 字段 | 含义 |
|---|---|
| `flash_retry` | 因落盘失败而"保留 + 下一轮重试"的轮数 |
| `flash_blocked_rounds` | 队首记录无法被接收（Flash 未就绪）的轮数 |
| `flush_honored` | 被真正兑现的 CRITICAL flush 请求数 |

新增测试钩子（仅上板自测）：`log_flash_test_fail_next(n)` / `logt ffail <n>`
—— 令接下来 n 次 append 整批失败，不写入任何 record。

### 5.3 本步骤的坑 / 注意

1. **失败预算只被"真正发生的 append"消耗** —— 因此各项计数与 loop 时序无关，
   是确定性的（`fill N` 之后由 loop 自动 drain，注入的 N 次失败必被精确消耗）。
2. **不要用大预算去制造"持续失败"**：loop 每秒会跑成百上千轮 `log_task()`，
   任何有限预算都会在静默窗口内被耗尽，观测不到中间态。验证"保留"应改用
   **`fail` 与 `total` 的对照**（失败计数 ≫ 落盘计数 ⇒ 未丢失）。
3. `logt stats` / `ring` / `reset` 会**先排空 RAM 环**，不能用它们观测
   "尚未提交"的中间状态。
