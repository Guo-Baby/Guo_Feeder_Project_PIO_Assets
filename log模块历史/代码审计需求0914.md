# 四、Log 的目标

请按照以下实际使用场景来思考 Log：

这个设备大概率是：

> **长期联网运行的 IoT 设备。**

因此：

### 普通运行信息

原则上：

**不保存到 Flash。**

直接通过 Cloud 上传即可。

### Flash

Flash 是有限寿命资源。

因此：

> **不要为了保存普通运行日志而频繁写 Flash。**

只有确实值得在断网、重启、异常恢复后仍然保留下来的重要信息，才考虑 Flash 持久化。

# 五、暂定 Log 分级

本次审计先按照下面的四级体系分析：

## DEBUG

用于开发调试。

例如：

* HX711 原始读数
* BLE 原始广播
* MQTT loop
* JSON 解析细节
* 状态机每一次 poll
* 普通函数执行细节
* 高频传感器数据
* 调试变量

默认：

> **仅 Serial / Debug 输出。**

不上传 Cloud。

不写 Flash。

特别注意：

**高频数据绝对不能因为“方便诊断”而全部变成持久化 Log。**

---

## INFO

表示正常但有意义的业务运行信息。

例如：

* Workflow 开始
* Workflow 成功
* Workflow 正常完成
* Valve 正常打开/关闭
* Water Dispense 开始
* Water Dispense 达到目标
* WiFi Connected
* MQTT Connected
* NTP 同步成功
* Config 正常修改
* Device 正常启动

默认：

> **上传 Cloud。**

**不写 Flash。**

因为设备长期联网，正常运行信息没有必要消耗 Flash 寿命。

---

## WARN / ERROR

表示异常、异常恢复或者明确的错误。

例如：

* Water Dispense 超时
* HX711 读数异常
* 重量异常增加
* 重量异常下降
* Valve 行为异常
* Workflow 执行失败
* Workflow Storage 保存失败
* Config 保存失败
* MQTT 多次连接失败
* WiFi 异常断开
* Storage recovery
* 数据损坏后恢复
* 参数异常
* 硬件模块出现异常

默认：

> **上传 Cloud + Flash 持久化。**

原因是：

即使设备随后断网、重启，也希望这些重要异常能够留下历史证据。

但是请仔细判断：

**不是所有程序员意义上的 warning/error 都值得写 Flash。**

需要从产品和故障诊断角度判断其价值。

---

## CRITICAL

表示非常严重、可能影响设备继续正常工作的致命故障。

例如：

* 系统无法正常启动
* 核心 Storage 无法工作
* 关键数据损坏
* 核心硬件严重故障
* 严重内存异常
* 无法恢复的系统错误
* 发生需要重启才能恢复的严重故障
* 其他你认为必须留下永久故障证据的情况

默认：

> **立即上传 Cloud + Flash 持久化。**

其中 Cloud 上传应该具有最高优先级。

如果当前系统在 Critical 发生时无法联网，需要分析：

* 当前 Cloud Manager 能否发送
* 是否需要短暂等待 ACK
* 是否应该使用特殊 Critical Log 路径
* 是否应该先写 Flash 再尝试 Cloud
* 如何避免 Critical 本身造成系统阻塞

但这次只做分析，不实现。
