## 步骤 0：Flash scan invariant 核查（条件 3）—— 先决结论

### 0.1 被检验的假设

现有代码在两处使用**派生式** `last_seq`：

| 位置 | 表达式 |
|---|---|
| `flash_find_segment_of_seq()`（`log_manager.cpp`） | `last = first + records - 1` |
| `log_ack_segment_deletable()`（`log_ack.h:147`） | `last_seq = first_seq + records - 1` |

隐含不变量：**`s_seg_first_seq[seg] + i` 恒等于该段 slot i 中记录的 seq**（即 seq→slot 映射是**稠密**的）。

### 0.2 核查结果：不变量**不成立**，且违反是**常态**而非边界

决定性证据 —— `seq` 在 `log_emit()` 中**对除 DEBUG 外的每条记录**分配，**早于** routing 决策：

```cpp
// log_emit()（src/log_manager.cpp）
portENTER_CRITICAL(&s_mux);
    s_seq_last++;                 // ← 每条非 DEBUG 记录都消耗一个 seq
    rec.seq = s_seq_last;
    ...
// routing 决策发生在之后的 log_task() 阶段 1：
const bool to_flash = log_level_to_flash(lv);   // INFO → false（INFO 不落盘）
```

⇒ **每条 INFO 都消耗一个 seq，却从不写入 Flash**（`log_level_to_flash(INFO) == false`）。
⇒ Flash 流中的 seq 在每次 INFO 出现的位置**出现空洞**。
⇒ `flash_append_batch()` 只追加 Flash-routed 记录，段内 slot 0..k-1 的 seq ≡ `first, first+h₁, first+h₁+h₂, …`（h 为 INFO 空洞），**不是** `first, first+1, first+2, …`。

**因此派生式 `last_seq` 系统性偏小**（偏小量 = 该段内 INFO 空洞数）。

### 0.3 由该违反导出的两个**真实缺陷**（比审计描述更严重）

| 编号 | 缺陷 | 后果 |
|---|---|---|
| **CRITICAL-3a** | `cloud_replay_step()` 用 `idx = s_replay_seq - s_seg_first_seq[seg]` **反算 slot 下标**，并靠 `flash_find_segment_of_seq()` 判断"该 seq 在哪段" | 空洞处的 seq 命中"派生 last"⇒ 进入本该跳过的段；循环终止条件（`find == 0xFF`）会在 **`s_replay_seq > 派生 last` 时立刻触发** ⇒ **replay 在第一个段之后即永久终止**（`s_replay_done = true`，本次 Boot 不再启动）⇒ **其后所有段中从未确认的 WARN+ 全部静默丢失** |
| **CRITICAL-3b** | `log_ack_segment_deletable()` 用派生 `last_seq <= acked_seq` 判定可回收 | 派生值比真实末条 seq **小 H（空洞数）** ⇒ 段在**尚有未确认记录**时被判可回收 ⇒ 静默删除 |

**危害面**：INFO 在本系统属常规事件（`LOG_TIME_*` / `LOG_WIFI_*` / `LOG_MQTT_*` / `LOG_CFG_*` / Workflow 生命周期）。因此**只要一条 INFO 与 WARN+ 同段**，上述两条即成立。
⇒ 这也解释了为什么 P1.3/P1.4 上板用例全部通过：`logt fill warn N` 只产生 WARN（**无空洞**），而 replay 从未在硬件上跑过（P1.5 设备测试因开发板缺失全部 NOT TESTABLE）。
⇒ 原审计把 C-3 定为 MEDIUM **偏低**；正确评级：**3a = CRITICAL（静默丢失 WARN+）、3b = HIGH（提前回收）**。

### 0.4 结论：FIX-3 的形态（回答条件 3）

**不是"增加第二套状态源"，而是"修正一处错误的推导"** —— 但必须按下面的形态落地，否则确实会变成平行状态：

| 判定 | 内容 |
|---|---|
| 单一真相源 | **仍然是 Flash 上的段内容**（权威）。`s_seg_first_seq[]` / `s_seg_records[]` / `s_seg_last_seq[]` 三者同属**同一份"扫描派生缓存"**，必须由**同一组**函数整体重建 / 整体维护 |
| 重建点（唯一） | `flash_scan_all()`：`first_seq` 取自段头，`records` 取 `flash_scan_records()`，`last_seq` 取 **slot `records-1` 的 seq**（追加单调 ⇒ 末槽即最大） |
| 维护点（唯一） | `flash_append_batch()` 成功写入后一行：`s_seg_last_seq[seg] = recs[i].seq;`（与 `s_seg_records[seg]++` 同一处） |
| 失效点 | `flash_create_segment()` / `flash_drop_segment()` / `flash_drop_broken_segment()` 置 0（与现有 `s_seg_records[]` 处置完全一致） |
| 唯一消费者 | 回收判定与淘汰记账。**禁止**任何地方再从 `first + records - 1` 推导 |
| **强制配套** | **`DIR-1`：replay 必须改为"按 slot 遍历、用记录自身的 seq"**，删除 `flash_find_segment_of_seq()` 与 `idx = seq - first` 反算。若只加 `last_seq` 而不改 replay，则 3a 仍在 ⇒ **DIR-1 不是可选项** |
| 新增状态量 | `uint32_t s_seg_last_seq[16]` = **64 B**，属既有缓存的新增字段（非第二套） |

### 0.5 对 FIX-3 的其他修正

| 项 | 原设计 | 修正后 |
|---|---|---|
| 淘汰记账 `unacked` | 用 O(1) 公式 `records - (acked - first + 1)` | ❌ 该公式同样依赖稠密假设 ⇒ 改为**按 slot 读取该段记录、逐条比较 `seq > acked_seq` 计数**（≤31 次读，仅在环满淘汰这一本身已重 I/O 的路径上）；读取失败则**保守计 `records`**（宁可多报） |
| 受害者优先 | `last_seq <= acked_seq` | ✅ 保留，但 `last_seq` 取 `s_seg_last_seq[]`（真实值） |
| replay 游标失效处理 | 复位 `s_replay_seq` | ✅ `flash_drop_segment()` 后若 dropped seg == `s_replay_seg` ⇒ 复位游标并重新 arm |
| 溢出淘汰的 Flash-routed 记录 | 登记空洞 | ✅ 保留（FIX-2） |
