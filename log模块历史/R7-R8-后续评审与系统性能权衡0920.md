## 第一部分：R-8 重新评估

### 1.1 当前 `weight.cpp` 的采样窗口机制（事实）

已逐行核对 `src/weight.cpp`（711 行）。机制如下：

```
filter_samples[5]  ← 位置数组，无时间戳、无采样时刻字段
sample_index       ← 0..4 的写指针
每轮 weight_task():
    if(!scale.is_ready())  → 维护 not_ready_start，return
    raw = scale.read()
    filter_samples[sample_index++] = raw
    if(sample_index < 5) return                 ← 窗口未满，什么都不算
    sample_index = 0
    filtered = weight_filter()                  ← 去最大去最小取均值
    gram = (filtered - zero_offset) / scale_factor
    if(have_last_window) {
        delta = gram - last_window_value
        if(fabs(delta) >= 50.0f) weight_record_jump()
    }
    last_window_value = gram
    have_last_window = true
```

关键观察（全部为事实，非推断）：

1. **窗口是"位置窗口"而非"时间窗口"**：`filter_samples[]` 只存 5 个 `int`，**没有任何时间信息**。
2. **跳变基准 `last_window_value` 也没有时间**：它只代表"上一个完整窗口的滤波值"，
   代码天然假设"两个相邻窗口在时间上相邻"。
3. **代码注释自述的时间假设**（`weight.cpp:41-43`）：
   > `HX711 约 10Hz，每 5 次有效采样计算一次重量，约 0.5s 更新一次。`
   ⇒ 全部逻辑（跳变阈值 50 g、5 s 窗口内 5 次跳变、`WEIGHT_ERROR_WINDOW_MS`）
   **都建立在"窗口周期 ≈ 0.5 s"这个隐含前提上**，而该前提**从未被校验**。
4. **文件头注释明确写着禁止阻塞**（`weight.cpp:21`）：
   > `非阻塞设计: 禁止 while 等待 HX711`
   ⇒ 但实际使用的 `HX711::read()` **内部就是 `while` 等待**（见 1.2）。

### 1.2 阻塞期间 HX711 侧发生了什么（关键机理）

已核对库源码 `.pio/libdeps/*/HX711/src/HX711.cpp`：

```cpp
bool HX711::is_ready() { return digitalRead(DOUT) == LOW; }      // :88

long HX711::read() {
    wait_ready();      // ← :107 内部先调 wait_ready()
    ...
}

void HX711::wait_ready(unsigned long delay_ms) {
    while (!is_ready()) {      // ← :196 无限阻塞，delay() 默认 0
        delay(delay_ms);
    }
}
```

HX711 是**硬件自主转换**芯片：一旦被供电并使能，它以自身速率（本项目 10 Hz）
持续转换，转换完成即把 `DOUT` 拉低表示"数据就绪"。**芯片不会因为 MCU 忙就暂停**，
且**它只保留最新一次转换结果**（覆盖式，无 FIFO）。

因此当 loop 被 `flash_append_batch()` / `flash_create_segment()` 阻塞 T 毫秒时：

| 时长 T | HX711 侧状态 | loop 恢复后 `is_ready()` |
|---|---|---|
| T < 100 ms | 仅发生 0–1 次转换 | 立即为真，`read()` 不等待 |
| 100 ms ≤ T < 数秒 | 若干次转换被**覆盖丢弃**，`DOUT` 保持低 | 立即为真，但**读到的值已不是"上一次采样之后的那一个"** |
| T ≥ 数秒 | 同上，**且** `not_ready_start` 逻辑可能被跨越（见 1.4） | 立即为真 |

**核心结论：阻塞不产生"坏样本"，但产生"时间错位样本"。**
阻塞期间 HX711 输出的是**最新稳态物理值**，只是投喂给窗口的样本把
"阻塞前的物理值"和"阻塞后的物理值"**拼进了同一个 5 点窗口**。

### 1.3 是否可能产生假的 Δgram 跳变 —— 可以，且机理确凿

设：

- 阻塞前，秤盘负载为 W₁，窗口 `A` 由 5 个 W₁ 样本组成 → `gram_A = W₁`
- loop 被阻塞 T = 150 ms（`flash_create_segment` 的"几十 ms 量级"，或 8 条记录的
  open/seek/write/close 累积，或 BLE 扫描窗口期间的调度延迟 —— 见第三部分）
- 阻塞期间发生了一次**真实但极小**的物理变化（例如阀门关闭引起的水锤/管路应力释放、
  桌面振动、猫踩了一下又走开、水箱液面微动）
- 阻塞后，窗口 `B` 的前若干样本仍是阻塞前残留在 `filter_samples[]` 的老值，
  后若干样本是阻塞后的新稳态 → `gram_B = W₂`

若 `|W₂ - W₁| ≥ 50 g` ⇒ `weight_record_jump()` ⇒
`event_push(EVENT_WEIGHT_ERROR, CRITICAL, POLICY_STATE)` ⇒
`event_dispatch()` ⇒ `dispense_guard_event_callback` ⇒ **`valve_force_close()`**。

**这不是"多写几条日志"，而是"一次误触发强制关阀"。**
`R-8` 原登记（"实测 A 段 69 次 vs 静置 0.08 次/s"）只描述了**观测后果**
（CRITICAL 记录暴涨、放大 R-3 / R-7 夹具失准）；
**本报告补充的因果后果是**：它同时污染**安全链**——
`R-3`（跳变源致 dispense_guard 反复强制关阀）与 `R-8` 是同一个根因的两面。

#### 一个必须说清楚的边界：T 到底要多长才会误报

这里要给出**能被反驳的定量判据**，而不是"可能会"：

滤波窗口吞掉 5 个样本。若窗口内混入 k 个阻塞前样本、`5-k` 个阻塞后样本，
且 `WEIGHT_FILTER_WINDOW - 2 = 3` 个样本参与平均（去掉 1 最大 1 最小）：

- 当 `k = 0` 或 `k = 5`（窗口完全在一侧）：`gram` 是纯稳态值，**不会误报**（正常物理变化除外）
- 当 `k = 1..4`（窗口横跨阻塞边界）：去极值后仍会同时留下两侧的样本 ⇒ **混合值**，
  这正是误报窗口

**⇒ 误报的必要条件是"窗口跨越阻塞边界"**，而窗口跨界的概率与
「阻塞时长 / 采样周期」正相关。`T = 100 ms`（= 1 个采样周期）时，
窗口有 1 个样本落在另一侧——**刚好开始满足误报条件**；
`T ≥ 500 ms`（≥ 5 个周期，整窗换血）时，窗口**必然全部由阻塞后样本组成**，
反而**不再误报**。

**这是一个非单调关系：**
- `T < 1 个采样周期`：无跨界，不误报
- `1 个周期 ≤ T < 5 个周期`（**100 ms – 500 ms**）：**最危险区**，窗口跨界 ⇒ 假跳变
- `T ≥ 5 个周期`（> 500 ms）：整窗换血，不误报（但引入新的 `no_data` 风险，见 1.5）

**结论：R-8 的危险区间恰好是 100–500 ms 的中等阻塞。**
这解释了为什么"少量 Flash 写入造成的短暂停顿"（< 100 ms）确实无害
（符合用户的判断），也解释了为什么"明显卡顿"（数百 ms）反而最致命。
**用户"少量停顿可接受"的前提成立，但"停止点"比直觉更早（约 100 ms 而非数秒）。**

### 1.4 两项新发现（本轮首次确认，直接影响修法选择）

#### 发现 A：`not_ready` 超时路径在正常运行时**不可达**

这是本轮最重要的结构发现。`HX711::read()` 内部是**无限阻塞**的 `while(!is_ready())`。
因此：

- 一旦代码进入 `raw_value = scale.read()`，它**要么立刻返回，要么一直卡在这里**，
  **不存在"等一会儿回来再试"的可能**。
- 于是 `weight_task()` 里 `if(!scale.is_ready())` 这条分支，
  **只有在上一次 `read()` 已经返回之后**才可能被求值。
- 而 `read()` 返回意味着 `is_ready()` 为真 ⇒ **紧接着的这一轮 `is_ready()` 必然为真**。

⇒ `not_ready_start` 只能在**从"上次 `read()` 刚返回 → 下一轮硬件掉线"这个极窄窗口**中
被置位；正常运行下 `WEIGHT_NOT_READY_TIMEOUT_MS = 5000` 这条 5 秒超时**几乎不可能触发**。

**这与 `未修复的问题.md` 中 `NC-13` 的观察完全一致**：
> `NC-13`（部分解除）：`RATE_LIMITED` 仍未触发

**推论**：weight 模块的 `no_data` 保护**在实现上是失效的**——
它能拦住"HX711 彻底不响应"（`read()` 会永久卡死，此时 loop 全停、看门狗接管），
但拦不住"HX711 短时无数据"。而 `read()` 卡死是一条**独立于 R-8 的更严重路径**：

> ⚠️ **`scale.read()` 无限阻塞 = loop 可被永久挂起。**
> 若 HX711 掉线（DUOT 恒高），`weight_task()` 会永远卡在 `wait_ready()`，
> loop 完全停转 —— `system_command_task()`（唯一 `ESP.restart()`）、
> `valve_task()`、`event_dispatch()` 全部停摆。
> 这是一条 **P0 级隐患**，且**不属于 R-8**（R-8 是时间错位，这是永久挂起）。
> 本报告仅登记，建议单独立项（见第四部分 §4.3）。

#### 发现 B：`R-1`（同毫秒 ENTER/EXIT 抖动）获得了统一解释

`R-1` 原描述为"Weight 边沿同毫秒抖动，暂接受"。结合发现 A：

- `LOG_WEIGHT_ERROR_ENTER`(WARN) 的**唯一**产出点是
  `weight_refresh_error_state()` 中的 `err` 上升沿；
- `err` 的三个成因中，`jump_error` 需积攒 5 次、`raw_zero` 需 5 s 连续零，
  **只有 `no_data` 能在极短时间内翻脸**；
- 机制：`not_ready_start != 0` 后某一轮 `is_ready()` 为真（于是进入 `read()`），
  但 `read()` 内 `wait_ready()` 恰好跨过了 5 s 阈值 ⇒ 该轮 `now - not_ready_start ≥ 5000`
  在**下一次** `is_ready()` 判断为假时成立 ⇒ `no_data` 一瞬成立（ENTER）；
  紧接着 `read()` 返回、`not_ready_start` 清零 ⇒ 同毫秒 EXIT。

⇒ **`R-1` 不是独立缺陷，而是"`no_data` 计时器与实际采样时刻脱节"的又一表现**，
与 `R-8` 同源（都用处理时刻 `millis()` 近似采样时刻）。
**修正 R-8 的采样时刻记账，`R-1` 大概率一并消失**（待验证）。

### 1.6 判定

> ### ✅ **R-8 是真实缺陷，且优先级应高于原登记。**
>
> **理由（三条，均为可复核事实）**：
> 1. **机理确证**：窗口与跳变基准均无时间信息，代码显式依赖"窗口周期 ≈ 0.5 s"的
>    未校验前提（`weight.cpp:41-43`）；HX711 覆盖式输出 + 阻塞跨界 ⇒ 混合窗口。
> 2. **后果确证**：误报不是"多写日志"，而是经 `event_push(EVENT_WEIGHT_ERROR, CRITICAL, STATE)`
>    → `dispense_guard_event_callback` → **`valve_force_close()`**，即**污染优先级的第 2 位
>    （安全功能）**，与用户给出的优先级排序直接冲突。

>    这恰好是 `flash_append_batch()` 8 条记录、`flash_create_segment()` 4 KB 写、
>    以及 BLE 扫描调度延迟的**典型量级**。

## 第二部分：LogManager 性能模型复核

复核方法：逐条核对 `log_emit_internal()` / `log_emit()` / `log_task()` /
`flash_append_batch()` / `flash_create_segment()` / `cloud_poll()` / `cloud_replay_step()`。

### 2.1 `log_emit()` 是否完全非阻塞？

**结论：是（唯一有界例外已隔离）。** 逐段核对（`log_manager.cpp:1688-1871`）：

| 步骤 | 位置 | 是否阻塞 | 说明 |
|---|---|---|---|
| DEBUG 直接丢弃 | 开头 | 否 | 编译期开关 |
| 参数数量/长度校验 | 开头 | 否 | 纯计算，超限**整体拒绝**（无部分写） |
| `log_coalesce_filter()` | 中段 | 否 | 纯 RAM 状态读改（P2-I） |
| `memset` + 参数编码循环 | 中段 | 否 | 最多 8 项 × 6 B = **48 B**，栈上局部 |
| `time_get()` | 中段 | 否 | 读 RAM 快照 |
| `seq_reserve_next()` | **例外** | **是（Flash I/O）** | 每 256 条一次，**且已在 `portENTER_CRITICAL` 之外**，用 `s_seq_reserving` 门闩串行化 |
| `portENTER_CRITICAL(&s_mux)` 段 | 末段 | 否 | 见下 |

**临界区内容**：`s_seq_last++` → `log_crc32(128 B)` → 环形槽 `memcpy(128 B)` →
满环时 `s_rd++` + `ring_drop++` → `s_stats` 更新。

⇒ **临界区单次最长 ≈ 128 B CRC32 + 128 B memcpy + 少量计数**，
在 ESP32-S3 @240 MHz 上量级为**微秒级**（远小于 1 µs–10 µs 量级）。
**不持锁过久，无 Flash I/O，无 MQTT，无动态分配。**

> **判定**：`log_emit()` **完全非阻塞成立**。所谓"CPU 峰值"仅来自 CRC32 与两次
> 128 B 拷贝，属**可忽略量级**。`s_mux` 是 `portMUX_TYPE`（关中断临界区）而非 mutex，
> 因此**不存在优先级反转**，但有"关中断时长"约束 —— 当前微秒级完全安全。

⚠️ 唯一需注意：`s_mux` 关中断期间 WiFi/BLE 中断被延迟。微秒级无影响，
但**任何未来插入 `log_emit()` 临界区的耗时操作都会直接伤害 BLE 时序**——
这条应作为**维护红线**记入文档（而非本轮改动）。

### 2.2 `log_task()` 是否会一次处理过多记录 / 长时间占用 CPU？

**结论：不会，"一次处理过多"已被现有设计排除。** 核对 `log_task()`（:1877-2074）：

| 阶段 | 内容 | 上界 |
|---|---|---|
| 0 | `log_coalesce_tick()` | 纯 RAM |
| 1 | 窥视 + 分拣循环 | **`scanned < LOG_DRAIN_MAX_PER_TASK = 8`**；环空即 `break` |
| 2 | `flash_append_batch()` —— **本轮唯一 Flash append 单元** | `batch_n ≤ LOG_FLUSH_RECORDS = 8`；**单条失败即 `break`** |
| 3 | 按序提交前缀 | 纯计算，≤ 8 次 |
| 4 | 统一 `s_mux` 更新游标 + stats | 微秒级 |
| 尾 | `cloud_poll()` | 见 2.3 |

⇒ `LOG_DRAIN_MAX_PER_TASK` 与 `LOG_FLUSH_RECORDS` 都是 8，
**"每轮最多 8 条、每轮最多一个 append 单元"已在 §30 冻结语义下落实**。
`未修复的问题.md` 中"是否需要限制单次处理数量"的疑问，**答案已经存在于代码中**——
`LOG_DRAIN_MAX_PER_TASK` 就是那个限制器，且注释明确写着"对齐 `LOG_FLUSH_RECORDS`，
避免长时间占用 loop"。

### 2.3 Flash append 的最大耗时（当前唯一的真实峰值）

**Flash 侧两个热点**：

| 热点 | 位置 | 耗时构成 | 频次 |
|---|---|---|---|
| `flash_append_batch()` | :1213-1268 | **每条**：`LittleFS.open("r+")` + `seek` + `write(128 B)` + `close` ⇒ 8 条 = **8 次 open/close** | 每轮（有 WARN+ 时） |
| `flash_create_segment()` | :966-1030 | `exists`/`remove` + `open("w")` + `write(16 B header)` + **循环 `write(128 B zeros)` 补满 3984 B** ≒ **31 次小写 + 文件元数据更新** | **每 31 条记录一次** |

代码注释自述（:963）：
> `时间边界（§30）：仅在本段首次创建时发生，约 4 KB 写（几十 ms 量级），
> 属低频事件（每 31 条记录一次），因此可与本轮的 record 追加合为一个单元。`

⇒ **最大单轮 Flash 耗时 = 建段轮**（4 KB 写 + 31 次零填充）叠加 8 条记录追加，
落在**数十 ms 量级**。

**关键判断（本轮新增）**：

- 这个量级**低于** R-8 的最危险区间上界（500 ms），但**正好落在危险区间内**（> 100 ms）。
  ⇒ **建段轮是 R-8 误报的高发轮次**，与 `未修复的问题.md` 中"A 段（含 12 次 flush）
  69 次跳变"的观测完全吻合。
- `LittleFS` 的 `open/close` 含**文件元数据一致性开销**（LittleFS 是 copy-on-write，
  目录项更新涉及块级写）；`write(128 B zeros)` 循环 31 次比"单次 3984 B 写"慢得多
  （每次调用有固定开销）。⇒ **这里有一个零风险的优化点**（见 2.5），
  但**它不是本轮的必需项**（用户前提："少量 Flash 写入造成短暂停顿是可接受"）。

### 2.4 云上行路径是否阻塞 loop？

核对 `cloud_poll()`（:2818-2946）与 `cloud_replay_step()`（:2608-2720）：

| 环节 | 是否阻塞 | 上界 |
|---|---|---|
| ACK 落账 / 超时重试判定 | 否 | 纯 RAM |
| **节流 `LOG_TX_MIN_INTERVAL_MS = 500`** | 否 | **最快 1 批 / 500 ms** —— 天然的 CPU 预算闸门 |
| 离线跳过 | 否 | `!cloud_is_connected()` 直接返回 |
| `cloud_replay_step()` | 否（有界 I/O） | **`LOG_REPLAY_SCAN_MAX_PER_CALL = 32`** 条扫描 + `pushed < LOG_BATCH_MAX_RECORDS = 16` ⇒ 每步最多 1 段窗口、最多 16 次 `queue_push` |
| `cloud_collect_batch()` | 否 | ≤ 16 条 `memcpy`（`s_cloud_batch` 在 PSRAM） |
| `cloud_build_cbor()` | 否 | ≤ 16 × 128 B 编码 |
| `cloud_try_send_batch()` | **是（MQTT publish）** | ⚠️ 见下 |

⚠️ **`cloud_send_log()` 是 MQTT publish**。虽然库层通常是把数据交给协议栈后立即返回，
但在**离线边界 / 重连 / QoS 确认**场景下存在阻塞风险。
好在：`(4) 离线不消费` 已在最前面挡掉离线场景；`LOG_TX_MIN_INTERVAL_MS = 500`
把触发频次限制到 2 Hz。

**并且**：`BT-1`（云端从不回 `log_ack`）意味着当前**每个批次必然等到
`s_ack_timeout_ms` 超时才放弃** ⇒ 实际发送频次远低于 2 Hz（约 1 次 / 15 s，
由 `未修复的问题.md` 的 "14.76 s 必触发" 佐证）⇒ **当前云路径 CPU 压力比设计上限更低**。

**⇒ 偶然收益**：`BT-1` 未修复反而使设备侧云路径负载处于低位。
**一旦云端补上 ACK，发送频次会从 ~1/15 s 升到 2 Hz（30 倍）** ——
**这是一个需要在 BT-1 修复时同步评估的隐含回归风险**，本轮仅登记。

### 2.5 LogManager 是否需要性能限制？—— 结论

**逐条回答用户的三个子问题**：

| 用户问题 | 结论 | 依据 |
|---|---|---|
| 是否需要限制单次处理数量？ | **❌ 不需要新增。已存在** | `LOG_DRAIN_MAX_PER_TASK = 8` + `LOG_FLUSH_RECORDS = 8`，且 §30 保证"每轮一个 append 单元" |
| 是否需要分片执行？ | **❌ 不需要** | `log_task()` 已是 4 阶段流水线；`cloud_replay_step()` 已按 `LOG_REPLAY_SCAN_MAX_PER_CALL = 32` 分片；`flash_append_batch()` 单条失败即 `break` |
| 是否需要给 `log_task()` 自带时间预算？ | **🟡 可选，非必需；不推荐本轮引入** | 见下 |

**关于"时间预算"的详细论证**（这是本部分唯一需要判断的地方）：

- **当前实际上已经存在一个"隐式时间预算"**：`LOG_DRAIN_MAX_PER_TASK = 8` 是
  **条数预算**，它把单轮耗时锁定在"最多 8 条记录 I/O"。条数预算 =
  时间预算的**保守上界**（因为单条 I/O 耗时不会突变）。
- 引入 `millis()` 显式预算会带来**新问题**：
  1. 阶段 1（窥视分拣）与阶段 2（append）**必须原子**——
     若在阶段 1 中途因超时退出，`cloud_queue_push()` 已执行的记录会与
     Flash 提交游标（阶段 3/4）**失去同步**，需要引入额外的一致性推理。
     这是 **§22/§23 冻结语义的边界**，属于"不改变已有冻结项"的禁区。
  2. 时间预算的失效模式是**静默的**（"这轮没做完"），
     而条数预算是**可观测的**（`ring_used`、`flash_blocked_rounds`、
     `flash_retry` 这些 stats 已经在记账）。
- **⇒ 推荐做法：不引入显式时间预算，而是（a）保持 `LOG_DRAIN_MAX_PER_TASK = 8`
  不动，（b）把"单轮上限"这条不变量写进文档作为冻结项（它现在只是代码注释）。**
- **唯一值得做的 LogManager 侧优化**（**低优先、可延后**）：
  把 `flash_create_segment()` 中 31 次 `write(128 B zeros)` 循环
  改为 `static const uint8_t zeros[512]` + 8 次写（甚至直接在
  `LOG_SEGMENT_SIZE` 允许的前提下把 `LOG_SEGMENT_SIZE` 定义与
  `LittleFS` 写入路径对齐）。**这能把建段单次耗时降低约 3–4 倍**，
  直接缩小 R-8 的危险窗口。
  ⚠️ **但这改变了段创建路径的代码**，属"影响存储层"的改动，
  按用户约束**本轮不做**，仅登记为后续候选。

### 2.6 第二部分小结

> **LogManager 当前不需要新增性能限制。**
> `log_emit()` 非阻塞成立；`log_task()` 已有条数上限与单 append 单元语义；
> LittleFS 侧已有分片（replay 32 条/步）；云上行已有 500 ms 节流。
> **唯一真实峰值是 `flash_create_segment()` 的 4 KB 零填充（数十 ms，每 31 条一次），
> 它落在 R-8 的危险区间内，但修 R-8 的正确位置在 Weight 侧，不在 LogManager 侧。**

## 第三部分：BLE 与 LogManager 的资源竞争

### 3.1 架构事实（先纠正一个常见误解）

**BLE 与 LogManager 之间不存在"并发竞争"**，因为**两者共用同一个 loopTask**：

```cpp
// main.cpp:567-594
void loop() {
    system_command_task();
    wifi_task();  event_dispatch();  time_task();  cloud_task();
    command_manager_task();  config_task();
    workflow_task();  oled_task();
    weight_task();            // ← Weight 采样
    valve_task();
    computer_reset_task();
    MiThermometer_task();     // ← BLE 扫描状态机
    test_mqtt_task();
    log_task();               // ← LogManager 消费
    serial_debug_command_process();
}
```

⇒ **`MiThermometer_task()` 与 `log_task()` 在时间上天然串行，永不并发。**
LogManager 也**不创建独立 Task**（这是冻结项：LittleFS 单写者模型）。
因此**第三部分问的"是否需要对 LogManager 做低优先级策略"，
答案是：不需要，也无法做** —— 单线程顺序执行下没有"优先级"这一维度。

**真正的竞争是"三者对同一个 loop 周期时间的争夺"**：

```
BLE 扫描占用 → loop 周期被拉长（双方都在同一轮里排队）
LogManager Flash 写 → loop 周期被拉长
         ↓
Weight 采样间隔被打散、窗口跨界
         ↓
R-8 假跳变 → 安全链误触发
```

**⇒ BLE 与 R-8 是同一个根因（loop 节奏不稳）的两个施加者。**

### 3.2 BLE 的 CPU 压力（量化）

核对 `src/MiThermometer.cpp`：

| 参数 | 值 | 含义 |
|---|---|---|
| `pBLEScan->setInterval(160)` / `setWindow(160)` | 160 / 160 | **~100% 扫描占空比** |
| `MI_THERMO_SCAN_ON_MS` | **1000 ms** | 每次扫描 1 秒 |
| `mi_random_scan_off_ms()` | **1800–2301 ms** | 扫描关闭 1.8–2.3 秒 |
| `pBLEScan->start(0, true)` | duration=0, restart=true | **无限时长，由 task 主动 `stop()`** |
| LEVEL0 扫描窗口 | 15 min | 持续活跃期 |
| LEVEL1 扫描窗口 | 30 min | 持续活跃期 |
| SLEEP | 48–60 min | 完全停止 |

**关键事实**：

1. **`start(0, true)` 在 loopTask 内同步执行**（NimBLE-Arduino 的 `start` 是阻塞式 API，
   它启动扫描并等待 duration 到期；duration=0 表示不自动停止）。
   ⇒ **调用 `start()` 的那一轮 loop 会被显著拉长**，
   且启动 BLE 控制器是重量级操作（协议栈、射频校准、HCI 通道）。
2. **~100% 扫描占空比 × 1 秒 on / 2 秒 off**：在整个 15–30 分钟窗口期内，
   loop 节奏会被"扫描 on 期"与"扫描 off 期"交替扰动。
3. **`MiAdvCallback::onResult()` 在 BLE 协议栈任务（非 loopTask）内执行**（`MiThermometer.cpp:95-127`），
   内做 MAC 逐字节比较 + `payload.size()<29` 过滤 + `memcpy(6+31 B)` + `xQueueSend(...,0)`。
   ⇒ 它**不阻塞 loop**，但会与 loopTask 争抢双核 CPU（ESP32-S3 双核，
   但 NimBLE 主机任务与 Arduino loopTask 可能共用核或抢占）。
4. ⚠️ **`onResult()` 内有逐字节 hex 打印**（`MiThermometer.cpp:117-123`，
   即 `未修复的问题.md` 的 `P0-3`）：
   ```cpp
   Serial.printf("[MiThermo] ADV len=%d : ", payload.size());
   for(size_t i = 0; i < payload.size(); i++) Serial.printf("%02X ", payload[i]);
   Serial.println();
   ```
   **每条匹配广播 30+ 次 `Serial.printf`**。串口 @115200 下 **1 字节 ≈ 87 µs**，
   一行 ~90 字符 ≈ **7.8 ms**。若每秒来 10 个匹配包 ⇒ **78 ms/s 纯串口阻塞**。
   ⇒ **这是 BLE 侧最大的、且完全无价值的 loop 时间消耗**（调试代码）。
   **`P0-3` 与 `R-8` 有直接因果关系** —— 它把 BLE 活跃期的 loop 节奏拉长到
   R-8 危险区间内。

### 3.3 BLE 与 LogManager 的时间叠加

在 LEVEL0 活跃期（15 min）内，一个 loop 周期可能同时承受：

| 消耗源 | 量级 | 频次 |
|---|---|---|
| `MiThermometer_task()` 扫描 on 期 | 启动开销 + 调度扰动 | 1 s on / 1.8–2.3 s off |
| `onResult()` 串口打印（**P0-3**） | **~7.8 ms / 包** | 每匹配包 |
| `log_task()` 建段轮（`flash_create_segment` 4 KB） | **数十 ms** | 每 31 条记录 |
| `log_task()` 普通轮（`flash_append_batch` 8 × open/write/close） | 数 ms–十几 ms | 每轮有 WARN+ |
| `cloud_task()` / `wifi_task()` | 不定 | 每轮 |

**⇒ 最坏叠加**：BLE 扫描启动 + 建段 + 串口洪泛可能在同一轮内叠加到
**上百毫秒**，正好落在 R-8 的最危险区间（100–500 ms）。

**这解释了 `R-8` 观测中的"ISO 同 workload 实测额外记录"**：
`P2-H(26/5) = +15`（Valve crit=9、Weight≈6）——weight 侧的额外记录
正是这种叠加的结果。

### 3.4 是否需要对 LogManager 增加低优先级策略？

**结论：❌ 不需要，且不可实现。** 三条理由：

1. **架构上不可行**：LogManager **无独立 Task**（冻结项），
   与 BLE 共用 loopTask，**不存在"优先级"这一维度**。
   给它"降优先级"只能通过"减少每轮工作量"实现 —— 而 `LOG_DRAIN_MAX_PER_TASK = 8`
   已经就是这个机制。
2. **`log_task()` 已在 loop 末位**（仅早于 `serial_debug_command_process()`）：
   从"谁先跑"的角度，LogManager 已经是全场最低优先级 —— **它的产出
   不影响本轮的 weight 采样时机**（weight 在本轮已经跑完了）。
   ⇒ **LogManager 不加剧 R-8 的"当轮"误报**，它影响的是**下一轮**的起点。
3. **`log_emit()` 的临界区是微秒级**（关中断 <10 µs），
   对 BLE 射频时序的影响可忽略。

**⇒ 正确的资源竞争处置方向不是"给 LogManager 降优先级"，
而是"消除 BLE 侧无价值的 loop 时间消耗"** —— 即 `P0-3`。
这是一条**零风险、零行为变更、纯收益**的改动（删掉调试打印），
且**符合用户"降低 LogManager 自身性能而不是影响核心功能"的反向表述**：
这里连 LogManager 都不用动，只需删 BLE 的调试噪声。

## 第四部分：方案（不修改代码）

### 4.1 结论一：当前是否存在真实 R-8 缺陷？

> ### ✅ **存在，且优先级应从"风险登记"提升为"高优先级缺陷"。**
>
> | 维度 | 结论 |
> |---|---|
> | 机理是否成立 | ✅ 成立。窗口/跳变基准无时间信息，依赖未校验的"周期 ≈ 0.5 s"前提 |
> | 是否可复现 | ✅ `未修复的问题.md` 有定量：A 段 69 次 vs 静置 0.08 次/s |
> | 后果是否严重 | ✅ **严重于原登记**：不止多写日志，而是经安全链误触发 `valve_force_close()`，污染优先级第 2 位 |
> | 危险区间 | **100 ms – 500 ms 的中等阻塞**（非单调：< 100 ms 无害，> 500 ms 整窗换血也不误报） |
> | 是否属"Flash 写入是缺陷" | ❌ **不是**。Flash 写入合法；缺陷在 Weight 侧把"处理时刻"当"采样时刻" |

**附带发现（同样重要，建议单独立项）**：

| 编号（建议） | 内容 | 严重性 |
|---|---|---|
| **R-8-A** | `HX711::read()` 内部 `wait_ready()` 是**无限阻塞**（`while(!is_ready())`）⇒ HX711 掉线时 `weight_task()` **永久挂起**，`system_command_task()`（唯一 `ESP.restart()`）、`valve_task()`、`event_dispatch()` **全部停摆** | 🔴 **P0**，比 R-8 更危险，但**独立于日志** |
| **R-8-B** | `not_ready` 超时（`WEIGHT_NOT_READY_TIMEOUT_MS = 5000`）在正常运行时**不可达**（因 `read()` 无限阻塞 ⇒ `is_ready()` 求值时必为真）⇒ `weight.cpp:21` 注释声称的"非阻塞设计/禁止 while 等待 HX711"**与实现不符** | 🟠 与 `NC-13` 现象吻合 |
| **R-8-C** | `R-1`（同毫秒 ENTER/EXIT 抖动）获统一解释：`no_data` 计时器与采样时刻脱节。**修 R-8 时大概率一并解决** | 🟡 待验证 |

### 4.2 结论二：最小修改方案（R-8）

**设计约束（全部满足用户禁令）**：

- ❌ 不改 `WEIGHT_JUMP_DELTA_G`（50 g 不动）
- ❌ 不改 `WEIGHT_MAX_JUMP_EVENTS` / `WEIGHT_ERROR_WINDOW_MS`（保护灵敏度不动）
- ❌ 不改 `DispenseGuard`、不改 `EventManager`、不改 `EventId`/`ParamId`
- ❌ 不改 `log_manager.*`（LogManager 侧完全不动）
- ❌ 不新增配置项、不新增 enable 开关
- ✅ 只改 `src/weight.cpp` 的 `weight_task()` 采样分支与跳变判定段

#### 方案 R8-Fix-1（**推荐**）：采样间隔守卫 —— 跨界时重建窗口

**原理**：不引入时间戳数组，只记录**上一次成功 `read()` 的时刻**，
在每次成功采样后计算间隔 `gap`；若 `gap` 明显超过正常采样周期，
则**丢弃当前窗口的既有样本、从本次样本重新开始**，
并**放弃一次跳变判定**（`have_last_window = false`）。

**为什么这是最小且充分的**：

1. 误报的**必要条件**是"窗口跨越阻塞边界"（见 1.3）。
   **只要保证窗口内所有样本都来自"同一段连续采样"**，混合窗口就不可能出现。
2. 只在 `gap` 超常时重建 ⇒ **正常运行（10 Hz）时行为完全不变**（零开销、零行为变更）。
3. **不需要高精度时间戳**：用户已明确"目标是秒级异常检测"，
   因此用一个粗粒度 `millis()` 差值判断"这段间隔是否明显异常"即可。

**具体改动位置（三处，均在 `src/weight.cpp`）**：

| # | 位置 | 改动 |
|---|---|---|
| 1 | 静态变量区（约 `:52-56`） | 新增 `static unsigned long last_sample_ms = 0;` |
| 2 | 阈值常量区（约 `:63-69`） | 新增 `#define WEIGHT_SAMPLE_GAP_MAX_MS 150UL`（**建议值 150 ms = 1.5 个采样周期**，需上板标定） |
| 3 | `weight_task()` 成功 `read()` 之后、`filter_samples[]` 写入之前（约 `:412-425`） | 计算 `gap`；若 `gap > WEIGHT_SAMPLE_GAP_MAX_MS` 则 `sample_index = 0; have_last_window = false;`；然后更新 `last_sample_ms = now` |

**伪代码（示意，非最终实现）**：

```cpp
// —— 成功读取之后 ——
unsigned long now = millis();
unsigned long gap = (last_sample_ms == 0) ? 0 : (now - last_sample_ms);
last_sample_ms = now;

if (gap > WEIGHT_SAMPLE_GAP_MAX_MS) {
    // 采样间隔异常：既有窗口样本已与本次样本不同源
    // ⇒ 丢弃当前窗口，重新建立；同时放弃本次跳变判定（避免与旧基准比较）
    sample_index      = 0;
    have_last_window  = false;
}
// 之后照原样：filter_samples[sample_index++] = raw; ...
```

**关键设计点**：

- **`have_last_window = false` 是必需的**：仅重置 `sample_index` 不够 ——
  否则新窗口的第一个完整结果仍会与"跨阻塞前的旧基准"比较。
  这一条正是"丢弃异常间隔后的第一批样本"的用户建议的等价实现
  （`have_last_window = false` 使该窗口**不参与跳变判定**，
  但仍**正常更新 `current_weight` 与 `STATE_WEIGHT_VALUE`**，
  因此**不降低重量读数的可用性**）。
- **不触碰 `weight_record_jump()`**：函数体一行不改（不降灵敏度）。
- **不触碰 `weight_refresh_error_state()`**：异常状态机一行不改。
- **不触碰 `not_ready_start` / `raw_zero_start` 逻辑**：只加一个独立守卫。

**为什么阈值选 150 ms 而不是 500 ms**：

- 危险区间上界是 500 ms，但**危险区间下界是 100 ms**（1 个采样周期）。
- 150 ms ≈ 1.5 个周期，能在"误报开始"（100 ms）后立刻介入，
  同时**有 50% 余量容忍测量抖动**（`millis()` 粒度 1 ms、HX711 时序抖动、调度抖动）。
- **需上板标定**：建议用 `logt` 或串口观测正常运行时的 `gap` 分布，
  取 P99 值上浮 50% 作为阈值。

**备选方案 R8-Fix-2（更保守，不推荐但记录）**：
把 `filter_samples[]` 从 `int[5]` 升级为 `struct { int raw; uint32_t t; }[5]`，
在 `weight_filter()` 内按时间加权或剔除超时样本。
**不推荐理由**：改动面更大（触及 `weight_filter()`），
且**与 `WEIGHT_FILTER_WINDOW` 的去极值逻辑产生交互**（去掉最大/最小后
"哪个样本对应哪个时刻"的语义变复杂）；而 R8-Fix-1 已充分。

#### 架构影响评估

| 维度 | 影响 |
|---|---|
| 依赖方向 | ✅ **不变**。仅动 `src/weight.cpp` 内部静态状态，**不新增跨模块依赖** |
| 冻结项 | ✅ **不动**。`WEIGHT_FILTER_WINDOW` / 阈值 / 事件语义 全部保留 |
| 内存 | ✅ **零增量**（新增 1 个 `unsigned long` = 4 B） |
| Capability 边界 | ✅ **不变**。Weight 仍是 Capability，不触碰 Service/LogManager |
| 回归影响 | 🟡 **可预期**：`R-7` 的夹具失准中有一部分来自 Weight 侧额外记录（`+13`/`+15`）⇒ **修 R-8 应能减少 R-7 的 MISS 数**，但**不能完全解决 R-7**（R-7 的根因是测试隔离，见下文） |
| 风险 | 🟢 **低**。修改是"条件性重置"，不影响正常路径；最坏情况是"没生效"（退回现状） |

#### 验证方案（不新增测试资产的前提下）

- 定向注入：`logt flush` 制造 Flash 阻塞（沿用 R-8 原观测方法），
  对比修改前后 `weight jump` 计数与 `guard_rx` 计数；
- 静置对照：确认静置时行为无变化（无回归）；
- 建议把"gap 分布"以诊断方式临时输出（**不入库、不进 Flash**），标定阈值后移除。

### 4.3 结论三：LogManager 是否需要性能限制？

> ### ❌ **不需要新增性能限制。**
>
> | 检查项 | 现状 | 判定 |
> |---|---|---|
> | `log_emit()` 非阻塞 | ✅ 成立（临界区仅 CRC32 + 2×128 B memcpy，微秒级） | 无需改动 |
> | `log_emit()` 持锁过久 | ✅ 否（唯一 Flash I/O `seq_reserve_next()` 已在临界区外，每 256 条一次） | 无需改动 |
> | `log_emit()` memcpy/encode CPU 峰值 | ✅ 可忽略（≤48 B 参数编码 + 128 B CRC） | 无需改动 |
> | `log_task()` 一次处理过多 | ✅ **已由 `LOG_DRAIN_MAX_PER_TASK = 8` 排除** | 无需改动 |
> | `log_task()` 长时间占用 CPU | 🟡 峰值 = 建段轮（数十 ms，每 31 条一次） | 可接受；见下 |
> | LittleFS 单次处理量 | ✅ 已限制（8 条 / append 单元） | 无需改动 |
> | 是否需要分片 | ✅ 已有（replay 32 条/步，`LOG_REPLAY_SCAN_MAX_PER_CALL`） | 无需改动 |
> | 是否需要 `log_task()` 时间预算 | 🟡 **不推荐本轮引入** | 见 2.5：会撞 §22/§23 冻结边界，且条数预算已是更可观测的等价物 |
>
> **唯一登记的后续候选（低优先、可延后、本轮不做）**：
> 把 `flash_create_segment()` 的 31 次 `write(128 B zeros)` 循环合并为
> 更大块写（如 512 B × 8 次），可把建段耗时降低 3–4 倍，
> 从而**直接缩小 R-8 的危险窗口**。属存储层改动，需独立评审。

### 4.4 结论四：BLE 与 LogManager 资源竞争

> - **不存在并发竞争**：两者共用 loopTask，`MiThermometer_task()` 与 `log_task()`
>   时间上串行，且 `log_task()` 已在 loop 末位（实际最低优先级）。
> - **不需要给 LogManager 增加低优先级策略**：架构上无优先级维度；
>   `LOG_DRAIN_MAX_PER_TASK = 8` 已是它的"降载"机制。
> - **BLE 侧真正的 loop 时间消耗是 `P0-3` 的逐字节 hex 打印**
>   （`MiThermometer.cpp:117-123`，~7.8 ms/包）——
>   它把 BLE 活跃期的 loop 节奏拉长到 R-8 危险区间。
>   **删掉它是零风险纯收益**，建议与 R-8 同批处理。
> - **登记项**：一旦 `BT-1`（云端从不回 ACK）被修复，
>   云上行频次将从 ~1/15 s 升到设计上限 2 Hz（30 倍）；
>   **修复 BT-1 时必须同步评估设备侧 CPU 与 WiFi 负载。**

### 4.5 结论五：推荐下一步执行顺序

按"风险 × 收益 / 改动成本"排序：

| 顺序 | 项目 | 理由 | 成本 | 风险 |
|---|---|---|---|---|
| **P0-1** | **R-8-A：消除 `scale.read()` 无限阻塞** | HX711 掉线 ⇒ **loop 永久挂起**，连唯一的 `ESP.restart()` 都进不去。**这是全系统最严重的隐患**，且与 R-8 正交 | 小（改用 `wait_ready_retry(n, delay)` 或先判 `is_ready()`，配合已有 `not_ready_start` 逻辑） | 中（需确认 `HX711` 库 API 可用性；需评估"跳过本次采样"对窗口的影响） |
| **P0-2** | **R-8：采样间隔守卫（R8-Fix-1）** | 消除安全链误触发；同时缓解 `R-1` / `R-3` / `R-7` 的夹具失准 | 小（3 处，约 10 行） | 低 |
| **P0-3** | **删除 BLE 逐字节 hex 打印** | 零风险、零行为变更；直接缩短 BLE 活跃期 loop 周期 | 极小（删 ~5 行） | 无 |
| **P1** | **R-7：测试隔离方案** | 阻塞回归到 195/195；**但必须先有 R-8 与 P0-3 落地**（否则夹具仍在被真实的产品噪声干扰，无法区分"隔离成功"与"噪声减少"） | 中 | 中 |
| **P2** | `flash_create_segment()` 大块写优化 | 缩小 R-8 危险窗口；但 R-8 修好后已非必需 | 中（存储层） | 中 |
| **P2** | `BT-1`（云端补 `log_ack`） | 设备侧无解；**修复时须评估 30× 上行频次** | 在 Cloud Worker 侧 | 中 |
| 长期 | 把"单轮 Flash I/O 上限"从代码注释升格为**文档化冻结项** | 防止后续插桩破坏该不变量 | 极小 | 无 |

> **执行顺序的核心逻辑**：
> **先修"会把系统卡死/误动作的"（P0-1 / P0-2 / P0-3），再修"让测试失准的"（R-7）。**
> 顺序颠倒会导致 R-7 的隔离方案建立在"仍在抖动的噪声源"上，
> 无法判断隔离是否真正生效 —— 这正是 P2-I 已经踩过的坑
> （"改判据 = 降断言"的教训）。
