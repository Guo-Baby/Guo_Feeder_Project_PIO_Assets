# F0 —— 稀疏 seq 模型 + DIR-1 slot 遍历补发（★ 本次修复的存在前提）
#
# 目的：证明 global seq != flash slot，且补发**不再因 seq 空洞提前终止**。
#
# 构造（3 条命令即可造出空洞，不需要逐条 emit）：
#   fill warn 20   → Flash seq 连续
#   fill info 15   → **只进云队列、不落 Flash** ⇒ 在 Flash 的 seq 空间里留下 15 个空洞

#       seg1 的 first 更大）⇒ replay_done=true ⇒ **seg1 的 9 条永久丢失**

#       ⇒ ackst replay = **40**
#
# 补发节奏（确定性，已按代码推导）：
#   批1 = 16 条（seg0 slot 0..15）
#   批2 = 15 条（seg0 slot 16..30，每轮只扫一个段 ⇒ 到段尾停）

# F2-B —— 重启后补发 + 确认后才回收（★ 本修复的核心承诺）
#
# 重启 ⇒ acked_seq 归 0、空洞表清空（纯 RAM 态，无需任何 Flash 格式迁移）
# ⇒ 那 8 条 WARN 重新可补发 ⇒ ACK 后段被正常回收
#
# 预期：rarmed=1 → 注入 live ACK → **补发确实发生（replay > 0，★BT-9 判别）**
#       → 旧批次 ACK 未被吞（`ack ok boot=`）→ ACK 落账 → 旧段未回收（segdel=0）
#
#   ⚠️ 判据用「**非零**」而不是精确条数：可补发积压的条数取决于 Flash 里遗留了
#      几个 Boot 的记录（`cloud_collect_batch()` 在 boot_seq 变化处截断批次），
#      它**不是不变量**。详见本段尾部注释。
#
# ⚠️ 本段**不**期望 segdel/seg_del 增长：此时 Flash 里只有 1 个段，而它同时是
#    `s_append_segment`（追加目标）。`cloud_delete_acked_segments()` 明确跳过
#    追加目标（`if (seg == s_append_segment) continue;`）⇒ 该段**按设计永不可回收**。
#    "ACK 后段被回收"需要 ≥2 个段才有意义，由 F3-B / F7 覆盖。
# =====================================================
# ★★ 本段同时是 **BT-9 的验收场景**（旧 Flash 未确认日志 + live log 先被 ACK + 重启补发）
#
#   P2-A 之后每个 Boot 必然产生 ≥1 条 live WARN（实测
#   `[JStg][W] read: open failed: /config/.commit`），而补发 sweep 只在
#   `used == 0` 时推进 ⇒ 这条 live WARN 会先把补发挡住。
#
#   BT-9 的危害：它自己被 ACK 之后，单点水位 `acked_seq` 跳到**比旧记录更大的 seq**
#   ⇒ 旧记录被 `log_ack_should_replay(seq <= acked)` 判为"已覆盖" ⇒ 永久不再补发
#   （实测 `replay=0`、`qused=1`），且旧段会被 `segment_reclaimable` 误删。
#
#   因此本段**主动注入**这条 live ACK（而不是等云端：云端至今不回 log_ack，见
#   BT-1），把 BT-9 从"偶发"变成**确定性场景**。

# 拉长超时，避免 live 批次在本段中途 give-up；stats 顺带刷新 <BOOT>（取当前 boot_seq）

logt stats ||| boot=
# ★ 确定性制造一条 "live 尾巴"（boot_seq = 当前）
#
#   为什么必须显式造：注入的 ACK 只覆盖**当时的在途批次**。若队列在 ACK 后正好为空，
#   补发 sweep 会立刻推进；若还残留记录，sweep 就被 `used != 0` 挡住 ⇒ **同一个断言
#   会因"Boot 期记录落在哪一批"而时通时不通**。
#   ⚠️ 实测：P2-D 接入后新增 `LOG_MQTT_CONNECTED`（它比 WiFi 记录晚 ~4s 落地，
#      因为要等 TLS 握手）⇒ 队列里**必然**多出一条尾巴，本段因此由"通常通"变为"必失"。
#   用 cpush 显式补一条，使两种情形都收敛到同一条路径（不依赖时序）。

#    云端会做的事：每条批次各回一次 ACK）
logt ackauto 0 ||| acked=
#
# 此刻状态：acked = live 记录的 seq（**大于**旧记录），而旧记录一次都还没补发过。
#   修复前：单一水位 ⇒ 旧记录被跳过（replay 恒 0）＋ 旧段被判可回收。

# ★ 钳制下界已生效：`gcfloor` = Flash 现存记录的最低 seq

# F7 —— FIX-H2：ACK 落账阶段为"淘汰间隙"补齐空洞（FIX-1 × FIX-2 交界）
#
# 场景：send batch → ACK 只覆盖前缀 → 期间 overflow evicted > covered
#   ⇒ 下标 [covered, evicted) 的记录：已离开 RAM 队列 / 未被 ACK / 无空洞
#   ⇒ 后续水位推过它们后段可被回收 ⇒ 重启也补不回
#
# 构造（全部用 WARN = Flash-routed，否则无物理副本可保护）：
#   ⚠️ 起点**不是空队列**：`creset` 会 arm 补发并把 Flash 里未确认的 WARN 重新入队。
#      实测起点 used=20，loop 组出的 batch1 是 **n=8**（不是 16）。
#   ★ 与 F1 同一根因：**在途窗口宽度 = 批次的真实条数**，不是 16。
#
#   fill warn 20   → queue 20，batch1（**n=8**）在途
#   fill warn 62   → 再入队 62
#   fill warn 58   → 20 + 120 = 140 > 128 ⇒ 共淘汰 **12** 条
#                    窗口内偏移 0..7（宽 = 批次条数 8）⇒ evict_inf = **8**
#                    其余 4 条在窗口外                      ⇒ qdrop      = **4**
#                    8 + 4 = 12 = 140 − 128 ✅ 恒等式自洽
#   ackauto 1 4    → covered=4、evicted=12
#                    ⇒ H2(FIX-H2) 负责 [4, min(12,8)) = 下标 4..7 = **4 条 WARN**
#                    ⇒ hole_evict = **4**（修复前恒为 0）
#   rd = rd_base + max(4,12) ⇒ qused = 140 − 12 = 128
#
# ★ 判别断言：`hole_evict=4`（修复前**恒为 0**）+ `hovf=0` + 段不被回收。
#
# ⚠️ `holes` 的**条目数不作为不变量**：空洞有**两个独立来源** ——
#    ① `cloud_queue_push()` 的非在途分支（每条被淘汰的 Flash-routed 记录各 1 次调用）
#    ② `log_hole_protect_gap()`（FIX-H2，补齐 [covered, evicted)）
#    `log_hole_add()` 会把**相邻/重叠**区间合并；两来源是否合并取决于 seq 是否相邻
#    （本项目 seq 允许空洞）⇒ 本场景实测 **2** 条。故只断言"存在空洞且表未溢出"。
# ★ 效果断言：把水位推过 seg0 之后，seg0 仍**不得**被回收
#             （`segdel=0` / `seg_del=0`）—— 这正是空洞保护的意义。
#             seg0 = Flash 前 31 条；batch1 的前 12 条（含被淘汰的 4..11）
#             落在 seg0 内；水位到第 44 条时已超过 seg0 的末条 seq=31。

# F8 —— FIX-D1：补发 sweep 中删除"游标所在段"后继续前进
#
# 构造：
#   fill warn 40 + flush     → seg0=31 / seg1=9
#   creset + sonline 1       → acked=0、arm；**强制 online** 使 replay 流程可执行
#                              （replay 只在 used==0 时推进）⇒ 推 16 条后暂停，游标 = seg0@16
#   fcorrupt 0               → 段头损坏 → 扫描删除 seg0
#                              ⇒ D1：记下 seg0.first_seq 作为约束并重新 arm
#   sonline 1（幂等）+ ackauto 0 → 排空 16 条 ⇒ 补发**从 seg0 之后继续**
#                              ⇒ 命中 seg1，再推 9 条 ⇒ replay = 16 + 9 = 25
#   ackauto 0                → 再排空 9 条 ⇒ sweep 完成（rarmed=0）
#
# ⚠️ 本段验证的是"删除 replay **当前段**后的 after_seq 约束"，

#    真离线时 replay 根本不会执行 ⇒ 断言全 MISS 且 D1 的 re-arm 分支不会被触及。
#
# ⚠️ 诚实说明：本段验证的是**游标连续性与路径安全**（删除发生在 sweep 中时
#    不丢记录、不空转、不无限循环）。**旧行为在本场景下结果相同** —— 因为
#    游标只在 used==0 时前进 ⇒ 已扫描记录必已被 ACK ⇒ 即使回到最老段重扫，

#    故 D1 是**预防性**修改（消除无谓重扫，并防止将来不变量变化后退化为重复投递），
