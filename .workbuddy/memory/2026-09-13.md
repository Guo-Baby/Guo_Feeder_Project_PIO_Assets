### 最重要的语义变更：`p.id` = Slot

```text
p.id（整数 0..15）  → 唯一 Slot → Workflow object     【唯一定位键】
workflow.id（字符串）→ 用户业务 ID，允许重复          【不是主键】
stable_id            → Registry metadata，会整体重排   【不得长期引用】
```

**已移除**「按 workflow.id 搜索对象」的能力（`workflow_find_index_by_id`
只保留给 Registry 反查用，注解明确禁止用于云端定位）。

### 代码改动要点

- `command_manager.cpp`：`workflow_resolve_index()` → **`workflow_resolve_slot()`**
  （p.id 必须整数；越界/未占用 → error 5；非整数 → error 6）。
  list 改为**按 Slot 遍历**输出 `slot/id/variant/valid/stable_id`。
- `list` / `sync_info` 的 `count` 改为 **`workflow_get_occupied_count()`**
  （占用 Slot 数，含 valid=false），**不再是** `capability_get_workflow_count()`
  —— 因为 Registry 按 runtime_id **去重**，`workflow.id` 重复时两者不相等。
- 新增 `workflow_validate_workflow_json()`：type 必填 / steps≤16 / params≤8，
  超限**整体拒绝**（错误码 11），不截断、不默认 action。
  校验位置：create 在分配 Slot 之前、set 在幂等比较之前。
- `workflow_apply_workflow_json()` 同步收紧（Defence in Depth）。
- `delete` 幂等：`!workflow_is_valid()` → no-op（`deleted:false, noop:true`），
  不 variant++、不产生 Dirty、不 rescan。
- `workflow_save_transaction()`：成功者**立即清自己的 Dirty**，
  失败者保留，**循环不中断**；仅当 `!dirty_any()` 才 release Critical。

### 已知差异（保持现状，已写入文档）

§8.1 需求说 delete 后"进入 Dirty 状态"，实际是 `workflow_storage_delete()`
只置 `meta.valid=0` 并**立即写盘**、随后清本对象 Dirty。
原因：若保留 Dirty，后续 `save_transaction()` 会把对象写回并置
`valid=true` → 删除被撤销（源码注释已说明）。对 Cloud 的影响：
delete 后**不需要**再调 save。
