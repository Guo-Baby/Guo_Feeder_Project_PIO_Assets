### 最重要的语义变更：`p.id` = Slot

```text
p.id（整数 0..15）  → 唯一 Slot → Workflow object     【唯一定位键】
workflow.id（字符串）→ 用户业务 ID，允许重复          【不是主键】
stable_id            → Registry metadata，会整体重排   【不得长期引用】
```

**已移除**「按 workflow.id 搜索对象」的能力（`workflow_find_index_by_id`
只保留给 Registry 反查用，注解明确禁止用于云端定位）。

### 代码改动要点

- `command_manager.cpp`：`workflow_resolve_index()` → **`workflow_resolve_slot()`**
  （p.id 必须整数；越界/未占用 → error 5；非整数 → error 6）。
  list 改为**按 Slot 遍历**输出 `slot/id/variant/valid/stable_id`。
- `list` / `sync_info` 的 `count` 改为 **`workflow_get_occupied_count()`**
  （占用 Slot 数，含 valid=false），**不再是** `capability_get_workflow_count()`
  —— 因为 Registry 按 runtime_id **去重**，`workflow.id` 重复时两者不相等。
- 新增 `workflow_validate_workflow_json()`：type 必填 / steps≤16 / params≤8，
  超限**整体拒绝**（错误码 11），不截断、不默认 action。
  校验位置：create 在分配 Slot 之前、set 在幂等比较之前。
- `workflow_apply_workflow_json()` 同步收紧（Defence in Depth）。
- `delete` 幂等：`!workflow_is_valid()` → no-op（`deleted:false, noop:true`），
  不 variant++、不产生 Dirty、不 rescan。
- `workflow_save_transaction()`：成功者**立即清自己的 Dirty**，
  失败者保留，**循环不中断**；仅当 `!dirty_any()` 才 release Critical。

## ConfigManager `[CFG][E] version reload failed` 修复 + 文件系统初始基线

提交：`17b8823`（代码）/ `23889ac`（脚本）/ `f37ca8e`（报告）

### 根因（重要，易复发）

1. `data/config/`（uploadfs 源）只有 8 个模块 JSON，**没有 version.json**。
2. `config_init()` 步骤 3 无条件 `load_version_file()` → 文件不存在 → E 级日志，
   所有模块 `version = 0`。
3. **不会自愈**：`save_version_file()` 跳过 `version==0` 的模块（防 0 覆盖已有版本），
   于是只要没有模块被真正修改（version++ ≥ 1），version.json 永远不生成
   → 每次启动都报错；期间 `expect_version` 乐观锁恒为 0 而失效。

### 修复

- 新增 `bootstrap_version_file()`：为【已加载】模块置 version=1 并落盘。
- **顺序关键**：模块在步骤 5 才加载，自愈必须在模块加载**之后**（config_init
  新增步骤 6），否则 `loaded` 全 false 一个都处理不了。
- 日志级别：首次烧录/文件损坏属预期场景，`E` → `W`；仅写入失败才 `E`。
- 同样处理 `config_reload()` 与 `commit_recover_from_backup()`。

### 文件系统初始基线（data/ 被 gitignore，需脚本生成）

| 脚本 | 产出 |
|---|---|
| `tools/gen_config_version.py` | `data/config/version.json`（8 模块 version=1） |
| `tools/gen_workflow_bin.py` | `data/workflow/meta.bin` + `wfNN/stepMM.bin`（Meta v3 / Step v1） |

**uploadfs 会整分区擦除**（实测 `Flash will be erased from 0x00410000 to 0x00ffffff`）；
日常 `esptool write_flash 0x10000` **不碰** LittleFS。

⚠️ 若 `WF_STG_META_VERSION` 升级（v3→v4）必须同步 `gen_workflow_bin.py`，
否则设备 `VERSION_TOO_NEW` 拒绝 → 回退 `/workflow.json`（功能不丢）。

### 验证技巧（重要）

串口批量脚本**开串口会复位板子**，所以"烧录后的第一次启动"捕获不到 ——
自愈日志会丢失，误以为没生效。解法：
`esptool --after no_reset write_flash 0x410000 littlefs.bin`（留在 bootloader），
再开串口捕获，即可看到真正的首次启动日志。

### 实测

- 修复前：`[E][vfs_api] /littlefs/config/version.json does not exist` + `[CFG][E] version reload failed`
- 场景 A（镜像无 version.json）：`[CFG][W] ... will rebuild` → `[CFG][I] version file created (baseline)`，E=0
- 场景 B（镜像有 version.json）：无 W 无 E，versions 全 1
- `[OK] Workflow loaded from Flash BIN`（生成的 BIN 基线生效，未走 JSON 回退）
- BIN 内容往返正确（步骤类型 / 参数 / 中文名 UTF-8），4/4 断言，0 崩溃
