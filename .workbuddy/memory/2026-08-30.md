## Config Manager 稳定性增强（非重构，最小侵入）

依据用户《Config Manager / Command Manager 稳定性与健壮性修改需求》31 节文档。核心原则：**保持现有架构、公开接口、调用关系不变**，只做最小范围修复。

### 第 25 节强制检查：修改前的现状分析（A–F）

**A. Config Data 写入**
- 函数 `save_module(ConfigModule *m)`
- 路径：同步 `config_save()` → `save_module()`；异步 `config_task()` → `config_cmd_process_one()` → `exec_save()` → `save_module()`
- 顺序：① `rename(active → backup)` ② `write_atomic(active)` ③ RAM `version++` / `dirty=false`
- 成功：rename + write_atomic 均成功；失败：任一失败返回 false

**B. Version 写入**
- 函数 `save_version_file()`，在所有模块保存**之后**调用
- 成功：serializeJson 非 0 + write_atomic 成功

**C. Data / Version 顺序**：Data → Version ✓ 符合需求，不存在 Version 先写

**D. Backup 生成时机**：`save_module()` 第 ① 步，Data 写入**之前**。
- 内容 = 修改前的 active = **Last Known Good** ✓
- 新配置尚未证明成功，不会污染 Backup → 语义正确，本次**未改**

**E. Boot Flag**：`config_init()` 读取后立即 remove；`config_boot_validate()` 在 setup 末尾写回

**F. Rollback**：`recover_module()` = remove(active) + rename(backup → active)；由 `config_init()` 在 `last_boot_ok == false` 时对所有模块触发

### 本次实际修改（5 项）

1. **Restart Safe Delay 1000ms → 10000ms**（头文件 `CONFIG_RESTART_SAFE_DELAY_MS`）
2. **统一重启策略**：`config_set_weight_zero_offset()` 的 `schedule_restart` 从 false 改回 **true**。理由：模块间存在初始化依赖（Action/Trigger → Workflow），ConfigManager 不判断"某参数是否只需刷新 RAM"
3. **Version 一致性（核心）**：新增 `commit_recover_from_backup()`
   - 文件层 backup→active；RAM 层重新 load 丢弃未提交修改；version 回到文件可信值
   - `config_save()`：version 失败 → 回滚 + **return false**（原实现只记日志仍返回成功，违反需求）
   - `exec_save()`：Data 部分失败 **或** Version 失败 → 均回滚 + 返回明确错误
4. **XSetField 类型防御**：新增 `value_type_matches()`
   - bool 字段只收 bool；int 字段只收 int；float 字段接受 int/float；string 字段只收 string；字段不存在则接受标量
   - 检查**严格置于 `set_begin()` 之前** → 非法请求不污染 RAM、不写盘、不更新 version、不触发 restart
5. **ArduinoJson 返回值检查**：`exec_query_field/module/all` 与 `config_get_json()` 中，`set()` 在内存不足时返回 false，改为显式检查并报错（原先会静默把残缺 result 当成功交出）

### 未改动及原因（对照需求第 23 节）
- **Queue**：保留现有"找第一个空槽 + head 顺序标记"实现，未重构（需求明确要求）
- **Backup 轮换顺序**：当前语义即 Last Known Good，不改
- **Boot Flag / Rollback / CommandRuntime / CloudManager / WorkflowManager / MQTT 协议**：均未触碰
- **公开 API**：无改名、无改签名

## Version / Backup 稳定性增强（8 节需求，已完成）

### 1. Backup 恢复不再消耗 Backup
`recover_module()` 原实现 `rename(bak → active)` 会让 backup 消失，只剩一份数据。
改为：**读取 backup 内容 → 校验 JSON 合法 → `write_atomic(active)`**，backup 原样保留。
恢复后：active = backup 内容，backup 保持不变 → 连续多次恢复都安全。

### 2. Version 失败回滚保证三者一致
`commit_recover_from_backup()` 改为返回 bool，回滚后保证：
- active = backup 内容
- backup 保持不变
- RAM version = `load_version_file()` 读回的文件值（RAM 数据也重新 load）

### 3. recover_module 返回值全部检查
两处调用（config_init 启动恢复、commit_recover_from_backup 回滚）均改为判断返回值并 `cfg_log("E", ...)`。
注意：无 backup 的模块会先 `exists` 检查跳过，不会被误报为"恢复失败"。

### 4. commit 状态保护（新增）
- 新增标记文件 `CONFIG_COMMIT_FLAG_FILE = "/config/.commit"`，内容与 boot flag 无关：
  - **存在** = 上次提交未走完全流程；**不存在** = 无进行中提交或已完整完成
- 新增枚举 `ConfigCommitState` + 公开查询 `config_commit_state()`
  （NONE / DONE / PENDING / FAILED）
- 内部函数：`commit_mark_pending()` / `commit_mark_done()` / `commit_fail_and_rollback(stage)`
- 提交流程：**mark pending → Data 写入 → Version 写入 → mark done**

### 5. 多模块保存一致性
`config_save()` 与 `exec_save()`：任一模块 Data 失败即整批失败并回滚，
不允许"部分模块新、部分模块旧"。回滚成功则清除 commit flag（已回到一致状态）；
回滚失败则保留 flag，下次启动继续恢复。

### 6. 启动恢复
`config_init()` 同时检查两个标记：
- Boot Flag 缺失 → 上次启动未完成（初始化崩溃）
- Commit Flag 存在 → 上次提交未完成
任一满足即从 backup 恢复所有模块，然后清除 commit flag。
（backup 不被消耗，重复恢复幂等安全）

### 7. json_storage write_atomic 落盘确认
ESP32 `File::flush()` 返回 void 无法确认。改为 **rename 后重新打开正式文件读回大小**做最终校验，
不一致则返回 false。只读回大小，不分配任何缓冲区（不引入动态内存）。接口未变。

## 用户复核后的 4 项修正（已完成）

### 1. config_init 恢复失败时保留 commit flag
原实现无论恢复成功与否都改写/清除标记 —— 恢复失败时会导致下次启动误判状态正常。
改为：跟踪 `recover_ok`（无 backup 的模块跳过、不计失败）
- 恢复成功 → `commit_mark_failed()`（下次启动无需再恢复）
- 恢复失败 → **保持 PENDING**，下次启动继续恢复

### 2. 所有 load_version_file() 检查返回值
3 处调用（config_init / config_reload / commit_recover_from_backup）全部改为
`if (!load_version_file()) { cfg_log("E","version reload failed"); }`

### 3. commit_fail_and_rollback 检查状态写入返回值
- 回滚成功 → 写 **FAILED**（不是 DONE，回滚成功≠提交成功），并检查 `commit_mark_failed()` 返回值
- 回滚失败 → 保持 PENDING，严禁改写成"已处理完"

### 4（最重要）. .commit 从"存在/不存在"改为三态内容
原设计缺陷：用"存在=异常"无法表达"最后一步（写 DONE）失败"——
无论写入成功与否都只能呈现同一种状态，无法区分"提交成功但标记没写成"与"提交真失败"。

新设计：文件内容为状态字符串
- `"PENDING"` 提交进行中 → 启动时读到即恢复
- `"DONE"` 最近一次提交完整成功
- `"FAILED"` 提交失败且已回滚到 Last Known Good

新增 `commit_state_write(state)` / `commit_state_read()`；
`commit_mark_pending/done/failed` 三个入口统一转调 `commit_state_write`。
读取时 `content.trim()`；文件不存在 → NONE；内容无法识别 → **保守按 PENDING** 处理（交给启动恢复兜底）。
已删除不再使用的 `CONFIG_COMMIT_PENDING_BODY` 宏。

## ConfigManager 健壮性自检（自查 + 独立审查交叉验证，共修复 15 项）

方法：先自己扫描所有底层调用的返回值，再启动独立 Agent 做交叉审查（自查容易有盲区）。

### 自查发现（6 项）
1. `config_init` 中 `json_storage_remove(BOOT_FLAG)` 返回值忽略 → 清除失败会让下次启动误判"上次启动成功"而跳过恢复
2. `config_init` 模块加载失败无逐模块日志（只有末尾汇总 INFO）→ 补 W 级别日志
3. `commit_recover_from_backup` / `config_reload` 中 `load_module()` 返回值忽略
4. `value_slot_apply` 空槽位静默无操作，但 dirty/restart 已标记（状态污染）→ 改返回 bool + `exec_set_field` 前置拦截
5. `config_restart_pending` 只查 5 分钟倒计时，漏掉重启命令的 10 秒安全窗口
6. `exec_save` 中 `commit_mark_done()` 失败 message 不明确 → 改为说明"数据已保存但可能下次启动回滚"

### 独立审查发现（9 项，均核实后修复）
7. **[P1 最严重]** `commit_recover_from_backup` 中 `load_module(m, false)` → 回滚时若 recover 失败（Active 缺失、Backup 完好）无法回退 Backup，模块直接降级默认值。**改传 true**
8. **[P1]** `m->data[key] = value` 全部未检查返回值；且 **null 文档会序列化成 `"null"`（4 字节）骗过 `serializeJson()==0` 检查**，被原子写入 Active 清空配置（此时旧 Active 已轮转走无法回头）→ 检查所有赋值返回值 + `save_module` 加 `is<JsonObject>()` 根校验
9. **[P1]** `commit_state_write` 先改 RAM 后写文件 → 写失败时对外报 DONE、磁盘仍是 PENDING → 改为先写文件成功后再更新 RAM
10. **[P2]** `commit_recover_from_backup` 无条件置 FAILED，与"回滚失败保持 PENDING"矛盾 → 改为 `all_ok ? FAILED : PENDING`
11. **[P2]** `config_release_module` 只清 loaded 不清 dirty → 后续 save 会写空文档 → 补 `dirty=false`
12. **[P2]** `value_type_matches` 中 `is<float>()` 对整数同样为 true，**无法区分 int/float 字段**，原规则与注释矛盾 → 数值字段统一按 `is<double>()` 处理（真正要拦的是 string↔number↔bool 跨类型转换）
13. **[P2]** `value_slot_from_variant` 超 int 范围的整数会降级存成 float → 精度丢失且类型失真 → 改为直接拒绝（新增 `CONFIG_INT_VALUE_MAX/MIN`）
14. **[P2]** `config_cmd_enqueue` 参数复制失败不清理槽位 → 补清理
15. **[P2]** `config_init` 中 `load_version_file()` 失败后版本全 0，save 会把 0 写回文件抹掉真实版本 → `save_version_file` 改为以文件现有内容为基底，且**跳过 version==0 的模块**（保存过的模块必然 >=1）

### 审查确认正确的部分（无需改）
- `millis()` 全部用无符号差值，溢出安全
- 队列容量检查前置、槽位先释放再回调（允许回调内重入 enqueue）
- 文件不存在未被当错误处理
- `load_module` 解析失败后 `data.clear()` 到位

## CommandManager 异步命令路由适配（已完成）

### 关键前提调查（避免设计错协议）
- **`cloud_protocol.md` 描述的是目标新协议（v/mid/d/t/ts/dat），但代码里 CommandManager 用的是旧格式（cmd/id/ob/pl）**。按"不重新设计协议"约束，以代码实际格式为准。
- `cloud_manager.cpp:896 cloud_translate_command()` 决定映射：
  - 旧格式（无 "c" 字段）：`cmd/ob/pl` **原样透传**到 CommandMessage
  - 新格式（有 "c"）：`system` → `p.o` 作 object；`query` → `p.q`/`p.o`；其余透传
- 因此 config 命令挂在 **`system` 命令族**，用 `ob` 区分：`config_query` / `config_set` / `config_save` / `config_restart`。沿用 `system_router` 既有分支风格。

### 实现（仅改 src/command_manager.cpp，+441 行；.h 未改）
1. `command_manager_init()` 注册 `config_set_completion_callback(command_config_completion)`
2. `system_router` 新增 4 个 object 分支
3. 新增 4 个 handler：解析 payload → `command_runtime_insert(cmd, 60s)` → `config_cmd_enqueue_xxx()` → 返回 `accepted`（`CMD_RESULT_ACCEPTED`）
4. 新增 `command_config_completion()`：按 cmd_id 找 runtime → 生成 result → `command_report_result` → `command_runtime_release`
5. 辅助：`config_enqueue_report_error()`（区分 queue full / invalid / unavailable）、`config_parse_payload()`（允许空 payload）

### 异步与生命周期要点
- **严禁**直接调用 `config_set_xxx()` / `config_save()` / `ESP.restart()`，一律走 enqueue
- 入队失败立即 `command_runtime_release(rt)` 归还槽位，不做悬挂
- callback 中 `doc["data"].set(rv)` 是深拷贝（ArduinoJson 拷进目标内存池），不持有 ConfigManager 内部引用；result/message 仅在回调期间有效
- callback 结果以 runtime 中保存的原始 CommandMessage 为准（保证 cmd_id/command/object 关联），回调自带参数仅兜底
- runtime 已被超时清理时，迟到回调直接忽略并记 WARN
- 未使用的回调参数用 `(void)` 显式消警告

### 踩坑
- handler 定义在 `system_router`（1192 行）之后（1369+ 行），必须加**前向声明**（同 `command_system_wifi_config` 的既有做法），否则报 "was not declared in this scope"
