## JsonStorage 模块实现（Config 专项第 ① 步）

**分支**：从 main 建立并切换到 `wb`（未提交，保留用户原有未提交改动）。

**交付**：仅 `src/json_storage.h` + `src/json_storage.cpp`，未改动任何其他文件（遵循 jsonstorage开发架构.md 约束）。

### 关键实现决策
- **init 策略**：用 `LittleFS.totalBytes() == 0` 探测是否已挂载，仅未挂载时才兜底 `begin(false, ...)`。避免与 `main.cpp:31` 的 `begin(true, "/littlefs", 10, "littlefs")` 重复挂载；formatOnFail 固定 false（格式化是破坏性操作，不由底层决定）。
- **原子写**：tmp 完整写入 → 校验大小 → `rename(tmp, path)`；失败必清理 tmp。依赖 littlefs rename 的覆盖语义，不做 remove+rename 兜底（后者在失败时会丢失正式文件，更危险）。
- **write_chunk**：offset==0 用 `"w"`（新建/截断），offset>0 用 `"r+"` 且拒绝越界 offset（防空洞、暴露丢块）。单次 open，从已打开句柄取 size。
- **read_chunk**：offset==size 返回 true + bytes_read=0（EOF）；offset>size 返回 false（越界，与写侧严格性一致）。
- **read**：32KB 硬上限（JS_MAX_FULL_READ），超限拒绝，强制大文件走分块。
- **零业务语义**：不依赖 ArduinoJson；tmp 路径用定长 char 缓冲合成（不用 String，避免堆碎片）。
- **日志**：预留 `JsonStorageLogCallback`，静默默认，未来接 Log Manager。

### 独立审查发现并已修复的问题
1. [P1] write_chunk 在 offset==0 时不截断 → 新数据短于旧内容会残留尾部旧字节，产出损坏文件（已改 `"w"`）
2. [P1] init 重复 LittleFS.begin 违反架构约束（已改 totalBytes 探测）
3. [P1] read_chunk 越界与 EOF 混淆（已区分）
4. [P2] write_chunk 对同一文件开合三次（已降到一次）
5. [P2] 流式 open_* 会覆盖已打开句柄导致泄漏（已加保护）
6. [P3] exists/size 未初始化时静默返回 false，易被上层误读为"配置不存在"（已加日志）
7. [P3] read 无大小上限（已加 32KB 守卫）
未采纳：rename 前先 remove 目标再做 rename 的兜底建议 —— 失败时会丢失正式文件，比保留旧数据更危险。

## ConfigManager 异步命令队列改造（第三阶段，已完成，未动 CommandManager）

**前提**：用户已烧录验证并认可模块化 JSON、7 个配置文件、Active/Backup、Atomic Save、41 个 getter 兼容；旧 config.json 废弃，不做运行时迁移。

### 异步边界（核心设计）
```
MQTT → CloudManager → CommandManager → [enqueue] ConfigManager 队列
     → config_task()（每次 loop 取 1 个）→ JsonStorage（同步 IO）
     → completion callback → CommandManager → CloudManager → MQTT
```
异步只在 **CommandManager → ConfigManager**；**ConfigManager → JsonStorage 保持同步**，不再建第二层队列。

### 实现要点
- **队列**：`s_cmd_queue[8]` 固定数组 + head/count，无动态链表。满时返回 QUEUE_FULL，绝不静默丢弃
- **任务槽位**：自带定长缓冲（cmd_id 32 / command,object 24 / source 16 / module 16 / key 32 / value 字符串 96），约 250 B/槽，8 槽 ≈ 2 KB 固定 RAM
- **value 生命周期（关键）**：入队时 `value_slot_from_variant()` 把标量提取到 `ConfigValueSlot`（联合体 + char[96]），**任务不持有调用方 JsonDocument 的任何引用**。只接受 int/bool/float/string；null/object/array 在**入队阶段**即拒（INVALID），不拖到执行阶段
- **config_task 策略**：先 `restart_timer_check()`（避免队列积压拖久重启），再 `config_cmd_process_one()` 处理恰好一个任务
- **回调顺序**：执行 → 复制回调参数到栈 → **释放槽位** → 回调（回调里可再次 enqueue）→ 若重启命令则最后 `ESP.restart()`（保证 SUCCESS 先送达）
- **ACCEPTED / SUCCESS 分离**：enqueue 返回 `ConfigEnqueueResult`（ACCEPTED/INVALID/QUEUE_FULL/UNAVAILABLE）；最终成败经 `ConfigCommandCompletionCallback`（cmd_id/command/object/source/type/success/error/result/message）

### ArduinoJson 7 深拷贝语义（源码级验证，非推测）
`out["value"] = v` 与 `out.set(x)` → `Converter<JsonVariantConst>::toJson` → `copyVariant()` → 字符串走 `VariantData::setString()`：
- `isStatic()`（仅编译期字面量）→ `setLinkedString` 存指针（指向 Flash，永不过期，安全）
- `isTinyString()` → 内联进 variant（拷贝）
- 其余 → `resources->saveString()` **拷进目标文档内存池**（深拷贝）

配置值来自 deserializeJson（RAM 字符串）→ 走第三条 → **真实深拷贝**，故原实现无需改动。

### 修复
- **restart timer**：`restart_timer_start()` 去掉 `if (s_restart_since_ms == 0)` 判断，改为每次成功修改都重开完整 5 分钟倒计时
- `set_begin()` 增加 `schedule_restart` 参数：命令通道修改 = true；**称重校准（config_set_weight_zero_offset）= false**（校准后不该重启设备）
- 删除对外同步 `config_cmd_query_*` / `config_cmd_set_field`，改为内部 `exec_*` + 对外 `config_cmd_enqueue_*`

- RAM 38.9%（127536 / 327680，+2056 B）　Flash 59.7%（1251957 / 2097152，+2.0 KB）
- 未改动 command_manager / cloud_manager / json_storage；41 个 getter 签名语义不变
