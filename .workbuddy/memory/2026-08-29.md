## JsonStorage 模块实现（Config 专项第 ① 步）

**分支**：从 main 建立并切换到 `wb`（未提交，保留用户原有未提交改动）。

**交付**：仅 `src/json_storage.h` + `src/json_storage.cpp`，未改动任何其他文件（遵循 jsonstorage开发架构.md 约束）。

### 关键实现决策
- **init 策略**：用 `LittleFS.totalBytes() == 0` 探测是否已挂载，仅未挂载时才兜底 `begin(false, ...)`。避免与 `main.cpp:31` 的 `begin(true, "/littlefs", 10, "littlefs")` 重复挂载；formatOnFail 固定 false（格式化是破坏性操作，不由底层决定）。
- **原子写**：tmp 完整写入 → 校验大小 → `rename(tmp, path)`；失败必清理 tmp。依赖 littlefs rename 的覆盖语义，不做 remove+rename 兜底（后者在失败时会丢失正式文件，更危险）。
- **write_chunk**：offset==0 用 `"w"`（新建/截断），offset>0 用 `"r+"` 且拒绝越界 offset（防空洞、暴露丢块）。单次 open，从已打开句柄取 size。
- **read_chunk**：offset==size 返回 true + bytes_read=0（EOF）；offset>size 返回 false（越界，与写侧严格性一致）。
- **read**：32KB 硬上限（JS_MAX_FULL_READ），超限拒绝，强制大文件走分块。
- **零业务语义**：不依赖 ArduinoJson；tmp 路径用定长 char 缓冲合成（不用 String，避免堆碎片）。
- **日志**：预留 `JsonStorageLogCallback`，静默默认，未来接 Log Manager。

### 独立审查发现并已修复的问题
1. [P1] write_chunk 在 offset==0 时不截断 → 新数据短于旧内容会残留尾部旧字节，产出损坏文件（已改 `"w"`）
2. [P1] init 重复 LittleFS.begin 违反架构约束（已改 totalBytes 探测）
3. [P1] read_chunk 越界与 EOF 混淆（已区分）
4. [P2] write_chunk 对同一文件开合三次（已降到一次）
5. [P2] 流式 open_* 会覆盖已打开句柄导致泄漏（已加保护）
6. [P3] exists/size 未初始化时静默返回 false，易被上层误读为"配置不存在"（已加日志）
7. [P3] read 无大小上限（已加 32KB 守卫）
未采纳：rename 前先 remove 目标再做 rename 的兜底建议 —— 失败时会丢失正式文件，比保留旧数据更危险。

### 环境踩坑（重要，后续复用）
- 沙箱 `safe-delete` 会拦截 PlatformIO 删除 `.o` / `.elf`，导致**增量编译必然失败**（报 SAFE_DELETE_FAIL_CLOSED），这不是代码问题。
- 解法：用全新构建目录绕开删除需求。注意 PlatformIO 6 **没有 `--build-dir` 选项**，要用环境变量 `PLATFORMIO_BUILD_DIR=.pio/build/xxx pio run`。
- clangd 虽已配置 `.clangd`，但 LSP 工具未为 `.cpp` 绑定服务，无法做静态诊断，只能靠 pio run。
