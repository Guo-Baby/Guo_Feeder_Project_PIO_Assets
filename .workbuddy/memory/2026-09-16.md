## 三、Commit 5：RAM → Flash safe handoff（`2db00be`）

### 修的是什么（§22/§23）

原 `log_task()` 是 **"先 pop 再写"**：`s_rd++` 发生在 `flash_append_batch()` 之前。
append 失败时记录**已被移出 RAM 环** → WARN/ERROR/CRITICAL 静默丢失。
PR1.2 阶段可接受（当时没 Flash），P1.3 **不可接受**。

### 新实现：`log_task()` 四阶段

```
1 窥视    读第 scanned 条但【不推进 s_rd】；完成 routing 决策 + stats + flush 请求
2 append  本轮【唯一】的 Flash append 单元（§30，上限 LOG_FLUSH_RECORDS=8）
3 提交    只有"已落盘"的前缀才计入 commit；遇首个未落盘记录即截断
4 落地    临界区内 s_rd += commit（带可读量钳位）+ 更新全部计数
```

**核心不变量**：`已落盘数 + 保留在环内的条数 == 已路由条数`
⇒ WARN/ERROR/CRITICAL **不可能被静默丢弃**。

其它语义：
- **INFO（Flash NO）不依赖落盘**，天然可提交，**不会被失败的 WARN 阻塞**（§24）
- **CRITICAL 在同一 `log_task()` 内完成落盘**（§28 的"立即"，不阻塞业务）
- `s_flush_requested` 在**本轮确有落盘**时视为已兑现并消费 → `flush_honored`（§27）
- Flash 未就绪 → 记录保留 + `flash_blocked_rounds++`，下轮再试；**无 while/delay/Task**

### 新 stats + 新钩子

`flash_retry`（保留+重试轮数）/ `flash_blocked_rounds`（队首无法接收轮数）/
`flush_honored`（被兑现的 flush 请求数）；
`log_flash_test_fail_next(n)` + `logt ffail <n>`（令接下来 n 次 append 整批失败）。

### 上板证据（`test/log_flash_handoff_tests.txt`，56/56 PASS）

```text
H1    正常路径    ok=10 fail=0  retry=0 blocked=0 honored=0
F10   失败 2 轮   ok=8  fail=16 retry=2 blocked=0 honored=0   ← fail=16 而 total=8（没丢）
F10-b INFO 混排   ok=2  fail=2  retry=1                       ← INFO 不被阻塞
F10-c 预算耗尽    ok=5  fail=0  retry=0                       ← 自动恢复
F11   CRITICAL    ok=1  fail=0  retry=0 blocked=0 honored=1
```

### Commit 5 最终全矩阵（完整固件）

`log_flash_handoff 56` + `log_flash 92` + `log_core 66` + `log_flash_recovery 34`
+ `log_flash_corrupt 43` + `log_meta_a/b/c/d 39` = **330/330 PASS，0 MISS，0 崩溃**

### Commit 5 的坑

1. **失败预算只被"真正发生的 append"消耗** ⇒ 计数与 loop 时序无关，是确定性的。
2. **不要用大预算制造"持续失败"**：loop 每秒跑成百上千轮 `log_task()`，
   任何有限预算都会在静默窗口内耗尽，观测不到中间态。验证"保留"要用
   **`fail` 与 `total` 的对照**（失败计数 ≫ 落盘计数 ⇒ 未丢失）。
3. `logt stats`/`ring`/`reset` **会先排空 RAM 环**，不能用来观测"尚未提交"的中间态。
