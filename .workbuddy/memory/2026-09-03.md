## Workflow 模块接入 Critical Operation（Safe Restart V2 配套）

**背景**：按 `critical_operation接入规范.md` §3/§5 要求，为 Workflow 模块接入 Critical Operation，防止执行 Workflow / 临时 Action 期间系统执行重启。用户限定**本次只改 workflow.cpp**，不编译不烧录，需提交修改报告。

**改动文件**：仅 `src/workflow.cpp`（未动 workflow.h / system_command / command_manager）

### 核心设计
- **计数模型**：每个执行体（一个 Workflow / 一个临时 Action）各 acquire 一次、release 一次；并发多执行体时计数累加，全结束才归零。
- **持有标记**：`static bool workflow_critical_held[WORKFLOW_MAX_COUNT]`（与 workflows[] 下标对应）+ `TempActionItem::critical_held`。
  - 用平行数组而非改 `Workflow` 结构体，是为了满足"只改 workflow.cpp"的约束。
  - 作用：release 幂等（避免 `release underflow` 错误日志）、覆盖无 finish_callback 的 Workflow、覆盖强制终止路径。
- **统一收口函数**（关键）：
  - `workflow_terminate(wf, state)`：写状态 → release → notify。Workflow 的 6 条结束路径全部改调它。
  - `temp_action_complete(item, result)`：标记完成 → release → callback。临时 Action 的 3 条结束路径（成功/失败/超时）全部改调它。
- **踩坑规避**：release **不能**写进 `workflow_notify_finish()` 内部 —— 该函数在 `finish_callback == nullptr` 时提前 return，事件/定时器触发的 Workflow 无回调，会漏 release 导致**系统永久无法重启**。

### 具体接入点（行号以改动后文件为准）
- acquire：`workflow_start()` :1555、`enqueue_temp_action()` :1762。失败时放弃操作（不 release）。
- release：6 处 `workflow_terminate`（:1975 超时 / :1984 完成 / :2001 / :2045 trigger 失败 / :2062 / :2093 action 失败）
- release：3 处 `temp_action_complete`（:2128 超时 / :2142 实例空 / :2185 成功或失败）
- 强制终止补漏：`workflow_clear()` :1062、`workflow_disable()` :2328、`workflow_stop()` :2348
- 防御兜底：`workflow_temp_action_cleanup()` :1912

### 关键时序约束（易踩坑）
`workflow_init()`（main.cpp:57）**早于** `system_command_init()`（由 command_manager_init :71 调用）。
因此 `workflow_init()` 中只 `memset` 标记数组，**绝不调用** system_command API —— 避免自旋锁未初始化时触碰其内部状态。

### 另一发现
`workflow_reload()` 只拦截"有临时 Action 在跑"，**未拦截运行中的 Workflow**。因此 `workflow_clear()` 中的 release 是必须的关键补漏点。

## Workflow Critical Operation 覆盖完整性自查（下午）

按用户提供的自查需求文档做控制流级审计，产出 `workflow_critical_operation自查报告.md`。

### 结论
PASS WITH CONCERN → 修复 P0 后 PASS。审计确认入口/出口在单线程控制流下覆盖完整，但发现 1 处跨核竞争。

### 【P0】workflow_terminate() 顺序缺陷（已修复，commit d15c2db）
- **根因**：`workflow_start()` 跑在 **esp-mqtt 任务**（command_manager_execute 由 MQTT 回调同步调用），`workflow_terminate()` 跑在 **loop 任务**，双核并发。
- **原顺序**：先 `wf.state = state`，后 Release → 中间存在窗口：
  - loop 置 state=ERROR → mqtt 的 `state != RUNNING` 守卫通过 → acquire + flag=true + state=RUNNING → loop 恢复后 Release 把 flag 清成 false
  - **结果**：Workflow RUNNING 但 flag=false、count 残留 +1 → **Critical Operation 永久泄漏，系统永久无法重启**
- **修复**：改为「先 Release、后置 state」。Release 后 state 仍是 RUNNING，`workflow_start()` 的 RUNNING 守卫会拒绝新启动，窗口闭合。
- **安全性**：`system_command_task()` 与 `workflow_task()` 同在 loop 任务，`workflow_terminate()` 同步执行，不会因 count 提前归零误触发重启。

### 【P2】未修复 —— Temp Action 环形队列跨任务无同步（既有问题）
`queue_wr_ptr`（mqtt 写）/ `queue_rd_ptr`（loop 写）无 volatile/原子/临界区。
理论上 slot 被覆盖会导致旧 Item 的 critical op 永不释放。
**该问题在 Critical Operation 接入之前就存在**，本次接入只是让后果从"命令丢失"升级为"系统无法重启"。
修复需引入临界区，但 `enqueue_temp_action()` 持锁期间要跑 JSON 反序列化（耗时长），改造面与死锁风险需独立评估 → 建议单独立项。

### 【P3】`workflow_start_by_id()` 全仓无调用者（已 Acquire，仅记录）

### 审计中确认无误的项（避免重复排查）
- **入口只有 3 个**：command_manager.cpp:685、workflow.cpp:2418（event）、:2427（by_id），全部收敛到 `workflow_start()`。
- **Step0 Trigger 不独立启动 Workflow**：本工程 Trigger 在 `workflow_task()` 内驱动**已 RUNNING** 的 Workflow 的 step 0，等待期已被 `workflow_start()` 的 Acquire 覆盖。文档假设的"Trigger → Workflow Start"模型不存在。
- **`workflow_reload()` 实际会拦截运行中的 Workflow**（:1469-1478，之前误判为只拦截 temp action）。
- **`workflow_load_json()` 无云端命令入口**，仅 boot 期 + reload 两条路径，故 `workflow_clear()` 的 release 是纯防御冗余。
- **`item.completed = true` 全文件仅 1 处赋值**（在 `temp_action_complete()` 内），这是"Temp Action 必过收口函数"的证明依据。
- Slot 复用安全：Workflow release(:1062) 早于清空(:1065+)；Temp Action release(:1912) 早于 free(:1917) 与重置(:1933)，且 `critical_held=true`(:1885) 早于队列提交(:1886)。

## Computer Reset Action 新增（晚上）

按 `AI_Task.md` 新增 GPIO8 电脑重启模块，报告见 `computer_reset接入报告.md`。

### 新增 / 修改
- 新增 `src/computer_reset.h` / `src/computer_reset.cpp`
- `src/main.cpp`：include(:15)、setup 第四层 `computer_reset_init()`(:61)、loop `computer_reset_task()`(:120)、串口调试命令 `computer_reset` / `computer_reset_status`(:178-190)
- **未改** command_manager / cloud_manager / workflow / system_command / config / event / system_state / capability_registry。**未 git commit**（等编译验证）

### 关键设计
- **输出仲裁**：GPIO8 是单例硬件，用 `active_pulse_count` 而非每实例各自拉低；`>0` 保 HIGH，归零者负责拉低。`used` 标记保证 release 幂等。
- **安全兜底三层**：poll 到期释放 → reset 释放 → `task()` 在 `800+1200ms` 无条件 force_idle（覆盖 poll 不再被调用的强制回收路径）。
- **引擎差异（重要，易踩坑）**：
  - **临时 Action**（workflow.cpp:2172-2201）：`start()` 后**同轮立即** `poll()`
  - **Workflow Step Action**（workflow.cpp:2093-2100）：`if/else` —— 首轮只 start，次轮起才 poll
  - 两者 poll 都可能带着 `result != RUNNING` 被调用（如 start 失败），**不能**在此情况下做全局 force_idle，否则误伤并发实例。
- **Action ID 取 `COMPUTER_RESET`**（大写下划线，与 VALVE_OPEN 等一致），`module` 取 `computer_reset`。AI_TASK §11 字面写的是 `computer_reset`，与 §17.9"遵循现有代码风格"冲突，倾向前者，已在报告标注待用户确认。

### 云端命令（两种格式）
- 旧格式透传（无需 version/stable_id，推荐先测）：
  `{"cmd":"execute_action","id":"8010","ob":"COMPUTER_RESET"}`
- 新格式需先查 registry：`{"c":"registry","i":"8000","k":0}` → 取 `v` / `k` → `{"c":"action","i":"8002","v":<v>,"k":<k>}`
- **注意**：新增 Action 会令 action registry **version +1 且所有 stable_id 重排**，云端缓存的旧 mapping 必须重新拉取，否则被 `ERROR_VERSION_MISMATCH` 拒绝。

### 实测判据
- 串口必须成对出现 `[ComputerReset] GPIO8 = HIGH` / `= LOW`，间隔约 800ms
- 云端临时 Action 必须出现 `critical op acquired` → `critical op released`，count 回到 0
