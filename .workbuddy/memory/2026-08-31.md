## 上板实测：config_query 单字段查询失败（已修复 + 加诊断）

### 现象
云端下发查单字段：
`{"cmd":"system","id":"1001","ob":"config_query","pl":{"module":"wifi","key":"ssid"}}`
→ 返回 `{"s":3,...,"m":"key not found","e":4}`（CONFIG_ERR_KEY_NOT_FOUND）

但查模块、查全部都正常，且查全部返回的数据里 wifi 确实有 ssid。两种下行格式（旧格式/紧凑格式）都失败 → 系统性 bug，非数据问题。

### 排查过程
逐层核对调用链，三层均正确：
- CommandManager：`command_config_query` 分支判断 + `module.c_str(), key.c_str()` 传参顺序正确
- ConfigManager enqueue：`need_key` 校验、`copy_str` 复制正确（入队返回 accepted 说明 key 非空且复制成功）
- `exec_query_field`：走到 "key not found" 说明 `find_module` 成功、模块已 loaded，只有 `m->data[t.key]` 为 null

### 定位的真实隐患（ArduinoJson 7）
`JsonDocument::operator[]` 有两组重载：
- 非 const 文档 → 返回 **`MemberProxy`**（"get or set" 语义，既有 `getData()→getMember`，也有 `getOrCreateData()→getOrAddMember`）
- const 文档 → 直接 `data_.getMember(...)`，返回 `JsonVariantConst`（纯查找）

`exec_query_field` 原写法 `m->data[t.key]` 走的是**非 const MemberProxy 路径**；
而 `config_get_int` 等走的是 `module_ro()` 返回的 **const 引用**（纯查找）。这是两者唯一差异。

隐患不止于查询：
- `exec_set_field` 的类型检查里对**可能不存在的键**用了非 const 访问 `target->data[t.key]`，
  一旦触发 get-or-create，会往配置插入 null 成员，后续 `config_save()` 就把 null 写进文件。

### 修复
1. `exec_query_field`：改用 `const JsonDocument &data = m->data;` 再 `data[t.key]`，确保纯查找
2. `exec_set_field` 类型检查：同样改为 const 只读访问，避免插入 null 污染配置
3. 加入诊断日志（`Serial.printf`，不依赖 log 回调）：
   ```
   [CFG] key not found: module=[wifi] key=[ssid]
   [CFG]   available: [ssid]
   [CFG]   available: [password]
   ```
   若仍失败，据此一眼可判断是 key 传错还是查找路径问题。

### 同时修复：重启前未自动保存（用户指出，确为设计缺陷）
原设计 `config_set` 只改 RAM、需显式 `config_save` 才落盘，但 5 分钟倒计时一到就重启
→ **未保存的修改会丢失**。
修复：
- `restart_timer_check()` 倒计时到点：先 `config_save()` 再 `ESP.restart()`
- 主动重启命令（`request_restart`）：同样先 `config_save()` 再进入安全延迟
- 保存失败照常重启（config_save 失败会回滚到 Last Known Good，回到上一份可信配置也是安全结果）

`config_save` 命令仍有价值：用于"立即落盘"而不必等 5 分钟倒计时。

`PLATFORMIO_BUILD_DIR=.pio/build/wb_dbg pio run` → SUCCESS（109s），EXIT=0
- 零 error；唯一 warning 为既有 `cloud_manager.cpp:1041`

## 根因确认（第二轮，诊断日志定位）：ArduinoJson 定长数组长度陷阱

用户烧录后串口输出：
```
[CFG] key not found: module=[wifi] key=[ssid]
[CFG]   available: [ssid]        ← 键明明存在
```
→ 参数传递正确、数据也有这个键，问题在 ArduinoJson 查找本身。

### 真正的根因
`ArduinoJson/Strings/Adapters/RamString.hpp`：
```cpp
template <size_t N>
struct StringAdapter<const char (&)[N]> {
  static AdaptedString adapt(const char (&p)[N]) {
    return RamString(p, N - 1, true);      // ← 长度取 N-1（数组大小）！
  }
};
// 而指针版本用 strlen：
static AdaptedString adapt(const TChar* p) {
  return AdaptedString(str, str ? ::strlen(str) : 0);
}
```

`ConfigCommandTask.key` 是 `char key[CONFIG_KEY_NAME_MAX]`（32）定长数组。
`data[t.key]` 时 adaptString 匹配【数组引用重载】，按长度 **31** 去匹配键 `"ssid"`（实际长度 4）→ 永不匹配。

### 为什么其它路径没暴露
- `config_get_*` 系列：`d[key]` 的 key 是函数参数 `const char*`（指针）→ strlen → 正常
- `exec_query_all`：`out[s_modules[i].name]`，name 是 `const char*` 成员 → 正常
- `find_module(t.module)`：用 strcmp（遇 \0 停）→ 正常
- 只有【数组成员直接做 JSON 键/值】才踩坑

### 修复（3 处）
1. `exec_query_field`：`const char *key_ptr = t.key;` 再 `data[key_ptr]`；
   `out["module"].set(t.module)` 也受影响（会写入 15 字节含填充），同样需注意
2. `exec_set_field` 类型检查：`const char *key_ptr = t.key;` 再 `existing_data[key_ptr]`
   （此处若按数组长度查找，已有字段永远查不到 → 类型校验静默失效）
3. 保留 const 只读访问（避免 MemberProxy 的 get-or-create 污染，虽非本 bug 根因，但确为真实隐患）

### 经验（重要，以后写 ArduinoJson 代码必守）
**永远不要把定长字符数组（`char[N]`）直接传给 ArduinoJson 的 `operator[]` / `set()`。**
必须先退化成 `const char*`（或 `String`），否则长度按数组大小算，静默失配。

### 验证
`PLATFORMIO_BUILD_DIR=.pio/build/wb_fix3 pio run` → SUCCESS（110s），EXIT=0，零 error
待用户烧录复测 config_query 单字段。

## 第三轮：config_set 字符串值乱码（根因确认 + 修复）

### 现象
1. 新增字段 `skc="7"` → 查询返回 `"7"` ✓
2. 再改成 `skc="8"` → 返回乱码 `` ❌
3. 新增 skc1/skc2 后再改 → 全乱码
4. **整数值（sck=7）始终正常**，只有字符串乱码
5. 5 分钟自动重启流程本身正常

### 根因：两个问题叠加（都在 ConfigValueSlot 的 `char s[96]`）
1. **缓冲区未清零**
   `value_slot_from_variant` 只 `memcpy(out.v.s, src, len+1)`，
   联合体尾部 90+ 字节仍是上次残留在栈上的内容。
2. **同一个定长数组长度陷阱**
   `data[key] = slot.v.s` 直接传定长数组 → 走 `StringAdapter<const char(&)[N]>`
   → 长度取 `CONFIG_VALUE_STRING_MAX-1 = 95` 而非 strlen
   → 把尾部残留字节一起写进配置。

**为什么第一次正常**：首次栈区恰好较干净，残留多为 0，`\0` 在 JSON 里转义后不可见，看着正常；之后再写就带上真实垃圾 → 可见乱码。

**为什么整数正常**：`slot.v.i/b/f` 是标量赋值，不涉及字符串长度计算。

### 修复（4 处）
1. `value_slot_from_variant`：`memset(out.v.s, 0, sizeof)` 后再 `memcpy(out.v.s, src, len)`
2. `config_cmd_enqueue`：`ConfigValueSlot slot;` 后加 `memset(&slot, 0, sizeof(slot))`
3. `value_slot_apply`：`data[key] = (const char *)slot.v.s;`（转指针，走 strlen）
4. `exec_query_field`：`out["module"].set(module_ptr)`，module 同样需退化成指针

### 用户猜想核对
- 库/函数版本不符 → 否。ArduinoJson 7.4.3 行为符合其设计，是调用方式问题
- value 格式转换问题 → 部分相关（字符串长度取错）
- **数组清理 / 越界 → 正是根因** ✓

### 重要：乱码已写进 Flash
被污染的 `skc/skc1/skc2` 已存入 `/config/weight.json`，
**仅烧固件无法清除**，需重新上传文件系统：`pio run -t uploadfs`
（会把 data/config/*.json 恢复初始状态；旧 config.json 仍在但不被读取，无害）

### 验证
`PLATFORMIO_BUILD_DIR=.pio/build/wb_str pio run` → SUCCESS（109s），EXIT=0，零 error

## 用户实测 P0 + 现象分析 + P1 实现

### 用户实测结论
- config_delete / config_save / config_query 带 version / config_module 严格校验 / config_module 正常写入**全部工作**
- 验证了 merge 语义方向正确（用户确认：不完全替换，只替换下发的字段，否则会让原有字段消失）

### 现象：skc3~skc6 无故消失 —— 根因是"烧录固件触发 Backup 恢复"
用户烧录 P0 固件（未重刷 fs），开机后查询：只有 skc1，skc3~skc6 消失。
原因链：
1. **Boot Flag 机制**：`config_init` 先读 `/config/.bootok`，`last_boot_ok == false` 就触发"从 Backup 恢复所有模块"
2. **烧录固件 = 非正常关机**：设备被烧录时，上一次启动的 boot flag 已被 init 删除、新的还没写入（setup 未走完）→ 下次启动 `last_boot_ok = false`
3. Backup 是"上一次保存前"的版本（不含 skc3~skc6，因为那些是后来才保存的）→ 恢复后 Active 被旧 Backup 覆盖

**这是设计行为**（保护"配置导致崩溃"），但对"计划内烧录"是误伤。
**关键教训**：烧录固件 = 非正常关机，会触发恢复。要保留配置需先 `config_save`（把当前 RAM 落盘 + 刷新 Backup）。

### 诊断盲点修复
`cfg_log` 之前未注册回调就完全静默 → 恢复/回滚等关键事件看不到。
改为未注册回调时 `Serial.printf("[CFG][level] ...")` 兜底输出。
用户重烧后应能在串口看到：
```
[CFG][W] recovering (boot_ok=0, commit_state=0)
[CFG][W] recovered from backup, module=weight
```

### P1 实现（config_manager + command_manager）
1. **keys_only**：`config_query` 支持 `{"keys_only":true}` → 只返回模块名/字段名
   - query_all+keys_only → `{"modules":["wifi",...]}`
   - query_module+keys_only → `{"keys":["dt",...],"version":N}`
2. **expect_version 乐观锁**：set/delete/module 支持 `{"expect_version":N}`
   - `ConfigCommandTask` 增加 `check_version` / `expect_version`
   - `version_check_pass()`：不符 → 拒绝 + `out["current_version"]` 回给 UI
   - 新错误码 `CONFIG_ERR_VERSION_MISMATCH`
3. **config_reset / config_backup（factory）**
   - `CONFIG_FACTORY_DIR = "/factory"`，`module_factory_path()` → `/factory/<module>.json`
   - `config_backup`：当前模块 → factory（**不标记 dirty、不安排重启**）
   - `config_reset`：factory → 完全替换模块（走 set_begin，标记 dirty + 重启）
