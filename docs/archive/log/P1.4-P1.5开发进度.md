## 1. 需求要点摘录（避免回头再翻原文）

### P1.4（§15–§18）

- LogManager **不得直接调用 MQTT API**；必须走 CloudManager 提供的 Log send 能力
- **必须真实 EMQX**，不得只用 Mock / 只看 `Serial.printf("send success")`
- Batch `fmt=2`，**CBOR**，字段冻结为 12 个（`LOG_BKEY_*` 0..11）：
  `fmt / event_dict_ver / boot_seq / seq_from / seq_to / count /
   drop_ring / drop_overflow / drop_unacked / self_degraded / flags / records`
- 测试：INFO（MQTT 收到 & Flash 无）／WARN·ERROR（MQTT 收到 & Flash 有）／
  CRITICAL（Flash 立即 + Cloud 最高优先级下一批）

### P1.5（§19–§27）

- `log_ack` 走 `guo_feeder/down`，**旁路 CommandManager**（照 `change_msg_limit` 落点，
  `cloud_process_rx_message()` 内）
- `ACK_TIMEOUT_MS=15000`；最多 **5** 次重试；退避 **2/4/8/16/32 s**；上限 **60 s**
- **重试耗尽：不删除记录**
- **ACK 语义**：Cloud 已持久化该 seq 区间 —— **不是**"以后不会再收到"
  ⇒ 全系统 **at-least-once**，云端按 `(device_id, boot_seq, seq)` 幂等去重
- 重复 ACK → 无变化；**回退 ACK → 忽略**；**错误 boot_seq → 忽略**；
  **部分覆盖 → 不能删除仍含未确认 record 的 segment**
- Offline：WARN+ 继续落 Flash；恢复后 Flash backlog → `guo_feeder/log`
- 重启后未确认 Log 重新发送属**正常行为**，不算失败
- **不得实现 FORCE_ADVANCE 默认行为** ⇒ 默认 `GIVE_UP_NOT_ADVANCE`；
  仅在**环满**时 FIFO 淘汰，并累计 `drop_overflow` / `drop_unacked`

### 通用（§28–§30）

- CloudManager **优先纯新增**：不得重写 `cloud_send_up()` / 不重写 Up·Down /
  **不建统一 TX Queue** / 不改现有业务语义。Log 只新增 `CloudRoute::LOG`
  与对应 send API / callback / route
- 保留**四层递归防护**；`LogManager → CloudManager → Cloud error → LogManager`
  不得形成无限递归（必要时用 `self_degraded` 统计）
- **不接管** `set_log_callback()` / `Serial` / `printf` / `ESP_LOG` 文本日志

### 2.2 LogManager 云待发队列（关键设计）

**问题**：INFO 是 Cloud YES / **Flash NO**，无法从 Flash 补发；
而 WARN+ 离线时要靠 Flash 保命。两者都要能上云。

**方案**：PSRAM **云待发队列**（`LOG_CLOUD_QUEUE_SLOTS = 128` × 128 B = 16 KB）

```text
log_task() 阶段 1 窥视到 to_cloud 记录
        ↓
   追加到 s_cloud_pending[]（按 seq 有序；满则淘汰最旧 + drop_overflow）
        ↓
cloud poll（≤1 批 / 500 ms）
        ↓
 取队首 ≤16 条 → CBOR Batch → cloud_send_log()
        ↓
   标记在途（seq_from..seq_to、发送时刻、重试次数）
        ↓
   收到 log_ack（boot_seq 匹配且区间覆盖）→ 移除 + 推进 acked 高水位
        ↓
   删除"全部记录都已 acked"的 Flash segment
```

- **重启重放**：`s_cloud_acked_seq` 不持久化（重启归 0）⇒ 未确认记录自然重发；
  `log_init()` 时按 `seq > acked` 从 Flash 段环**回填**云待发队列（WARN+），
  INFO 因不落盘无法重放（**设计如此**）
- **重试耗尽**：不删记录、不推进；`self_degraded` 计数；等环满时被 FIFO 淘汰 →
  `drop_unacked++`

### 2.3 段删除条件（§23 部分覆盖）

扫描时记录每段的 **`s_seg_max_seq[seg]`**（不能假设段内 seq 连续 ——
区间预留会让 seq 出现空洞）。
删除条件：`s_seg_max_seq[seg] <= s_cloud_acked_seq` 且该段不是当前追加目标。

### 3.2 关键实现决定

1. **CBOR 手写，不用 ArduinoJson**
   - `JsonDocument` 缓冲只能落内部 RAM（ArduinoJson 无 PSRAM 支持），
     16 条 × 128 B 的 byte string 会白占 2 KB 内部 RAM；
   - 批次结构完全固定，手写 30 行即可，且能直接写进 PSRAM 缓冲。

2. **批次布局（冻结）**：CBOR **定序数组** 12 项，下标 = `LOG_BKEY_*` 0..11；
   `records` 每项 = **bstr(128 B)**，原样保留冻结的 `LogRecord` 布局。
   **头 21 B / 每条 130 B**（2 B bstr 前缀 + 128 B）。
   2 条批次 = 281 B。

3. **云待发队列独立于 Flash**
   - INFO 是 Cloud YES / **Flash NO**，没有 Flash 副本可补发；
   - 因此建立 PSRAM 云待发队列（128 槽 / 16 KB），INFO 与 WARN+ 都进；
   - WARN+ 同时在 Flash 有副本 ⇒ 重启后可从段环回填重放。

4. **同一批次必须是同一个 `boot_seq`**（批次头只有 1 个该字段）⇒
   `cloud_collect_batch()` 遇 `boot_seq` 变化即停止收集。

5. **入队去重靠 seq 守卫**：落盘失败被保留的记录下一轮会以相同 seq 再次出现，
   用 `s_cloud_q_last_seq` 挡住，避免队列里出现两份。

6. **P1.4 的推进是"乐观"的**（发布成功即推进）。P1.5 会换成"收到 `log_ack` 才推进"，
   并加入超时/重试/退避。代码里已用醒目注释标出替换点与 `s_cloud_inflight`。

### 3.3 ★ 离线验证范式：wasm32 跑 C++ 探针（本项目新增能力）

**问题**：本机 clang 22 没有 MSVC/CRT 库（`libcmt.lib` / `ucrt.lib` / `kernel32.lib`
全部缺失），**无法链接原生控制台程序**；也没有 g++/MinGW。

**解法**：`log_cbor.h` 做成**完全 freestanding**（连 `<string.h>` 都不用，
拷贝用本地字节循环）⇒ 可以零依赖编到 `wasm32`，用 **node 真实执行**：

```bash
clang++ --target=wasm32 -std=gnu++11 -nostdlib -fno-builtin -O1 -I src \
        test/log_contract/probe_cbor.cpp \
        -Wl,--no-entry -Wl,--export-all -o probe_cbor.wasm
node test/log_contract/run_cbor_probe.js probe_cbor.wasm
```

探针把结果写进静态缓冲，由 node 从 wasm 线性内存读出（**不需要 printf**）。

**这一步抓到了真实错误**：探针初版把批次头写成 23 B（误把 `0x58 0x80` 算进头里），
实测 `len=281` 而断言期望 279 ⇒ 2 条断言 FAIL。核对后确认**编码器是对的、断言写错了**，
头应为 **21 B**。修正后 16/16 全过。
> 教训：有了"真跑"的探针，连自己的算术错误都能当场抓住 ——
> 只做 `-fsyntax-only` 是不会有这个效果的。

### 4.2 关键实现决定

1. **判定与执行分离**（本阶段最重要的结构决定）
   `src/log_ack.h` 只做纯函数判定，`log_manager.cpp` 负责取数 / 调判定 / 落账。
   收益：在**没有开发板、没有 MQTT 对端**时仍能穷举验证 ACK 语义 ——
   这正是本设备当前的处境，否则 P1.5 将完全无法验证。

2. **`cloud_poll()` 七段式**（替换 P1.4 的乐观推进）
   `(1) ACK 落账 → (2) 在途超时/重发/放弃 → (3) 退避 → (4) 离线跳过
    → (5) 节流 → (6) Flash 补发 → (7) 取批发送`

3. **推进依据改为 ACK**：`s_cloud_q_rd` 只在收到覆盖该前缀的 ACK 时前进。
   PARTIAL 只推进被覆盖前缀，尾部留在队列里下轮重新组批（不丢、不重复记账）。

4. **段删除的单一判定点**：`log_ack_segment_deletable(first, records, acked)`
   —— 只有"末条 seq <= acked"才可删；并跳过**当前追加目标**与**补发游标尚未越过**的段。
   （因此首段要等追加目标移走后才回收，属刻意的保守行为。）

5. **去重守卫从"seq 单调"改为"(boot_seq, seq) 相等"**
   P1.4 的单调判定会让 Flash 补发在队列排空后**永远被拒绝**（补发的都是旧 seq）。
   重复只可能发生在相邻两次 push，故相等判定已足够。

6. **GIVE_UP_NOT_ADVANCE**：只把该批移出 RAM 云队列并计 `drop_unacked`，
   **ack 水位与 Flash 段都不推进**；同时记 `give_up_seq` 以免本轮无限重放，
   下次开机（acked_seq 归 0）会重新补发。

7. **离线行为**：`cloud_is_connected()` 为假时直接跳过，**不消费任何记录**，
   计 `cloud_offline_skip`。恢复后走 (6) 从 Flash 补发。

8. **两个可调测试旋钮**（`atimeout` / `abackoff`）
   默认值不变，仅测试钩子可缩短。理由：默认参数下"重试耗尽"需 ≈152 s 纯等待，
   超出单条命令 200 s 预算 ⇒ 该冻结语义将无法被验证。
