# 3. 第一阶段：P1.2 并发安全修正

## 3.1 修正 Stats 写入的并发保护

当前 `log_task()` 中以下统计字段是在离开 `s_mux` 后直接修改：

* `flash_routed`
* `cloud_routed`
* `consumed`
* `critical_seen`
* `flush_requests`

而：

* `log_emit()` 在 `s_mux` 内修改其他 stats；
* `log_get_stats()` 在 `s_mux` 内读取 stats；
* `log_stats_reset()` 在 `s_mux` 内修改 stats。

因此需要统一并发规则。

### 要求

所有 `s_stats` 的读写必须遵守同一个临界区保护规则。

可以采用：

1. 先在临界区内取出 Record；
2. Flash/MQTT 等未来耗时操作仍然必须在临界区外执行；
3. routing 决策完成后；
4. 只在很短的临界区内更新 stats；
5. 离开临界区后再继续其他工作。

**禁止：**

* 为了保护 stats 而把 Flash 写入放进 critical section；
* 为了保护 stats 而把 MQTT publish 放进 critical section；
* 引入阻塞 mutex 破坏当前 non-blocking 架构。

# 4. 第二个 P1.2 修正：Flush Request 并发安全

当前：

```cpp

```

的：

* `log_task()` 写入；
* `log_flush_requested()` 读取；
* `log_clear_flush_request()` 写入；

不是统一保护的。

### 要求

统一使用 `s_mux` 保护：

* `s_flush_requested`
* `flush_requests`

实现：

```text
log_flush_requested()
    ↓
critical section
    ↓
读取 bool
    ↓
critical section end
```

以及：

```text
log_clear_flush_request()
    ↓
critical section
    ↓
写 false
    ↓
critical section end
```

不得使用阻塞 mutex。

# 8. P1.3 Flash 存储固定规格

## 8.1 Flash 文件

使用：

```text
/log/meta.bin
```

以及：

```text
/log/s0000000.log
/log/s0000001.log
...
/log/s0000015.log
```

共：

```text
16 segments
```

---

# 9. Segment 固定结构

每个 Segment：

```text
16 B header
31 × 128 B LogRecord
---------------------
3984 B
```

即：

```text
16 + 3968 = 3984 B
```

### Header

固定 16 B：

```text
offset 0   magic      uint32
offset 4   seg_index  uint32
offset 8   first_seq  uint32
offset 12  crc32      uint32
```

CRC：

```text
CRC32(bytes[0..11])
```

不得增加字段。

---

# 10. Flash 总容量

：

```text
16 × 3984 B
= 63744 B
≈ 62.25 KiB
```

实际使用：

```text
16 个 segment
496 条 LogRecord
```

不得增加额外 Flash ring 文件。

---

# 11. LogRecord 不得修改

必须继续使用 P1.1 已冻结的：

```cpp
sizeof(LogRecord) == 128
```

不得：

* 增加字段
* 删除字段
* 改字段顺序
* 修改字段大小
* 增加 persist flag
* 增加 uploaded flag
* 修改 CRC 范围

CRC 仍然：

```text
bytes 0..107
```

---

# 12. Meta 文件

`/log/meta.bin`

固定：

```text
32 B
```

布局：

```text
0   magic           uint32
4   fmt_version     uint32
8   boot_seq        uint32
12  seq_reserved    uint32
16  corrupt_count   uint32
20  reserved
28  crc32
```

CRC：

```text
bytes 0..27
```

---

# 13. Sequence Reservation

必须使用：

```cpp
LOG_SEQ_RESERVE = 256
```

规则：

### boot

LogManager 初始化时：

```text
读取 meta
↓
seq_base = meta.seq_reserved + 1
↓
meta.seq_reserved += 256
↓
boot_seq++
↓
写回 meta
```

之后当前 boot 内的 seq：

```text
seq_base
...
seq_base + 255
```

用完后：

```text
再次 reservation 256
```

而不是每条日志写一次 meta。

---

# 14. Sequence Reservation 的核心目的

必须保证：

> 正常情况下不同 boot / 不同 reservation range 不会产生相同 seq。

允许：

```text
1001~1256
1257~1512
```

中间出现未使用号码。

例如：

```text
boot A:
seq 1001~1010

重启

boot B:
seq 1257~1265
```

中间：

```text
1011~1256
```

即使没有实际 LogRecord，也完全允许。

**禁止为了消除 holes 而重新设计 sequence allocator。**

---

# 15. Meta 写失败

如果 reservation 写入失败：

必须设置：

```text
s_seq_reliable = false
```

后续 Cloud Batch header：

```text
flags.bit0 = 0
```

表示 sequence 可能存在重复。

P1.3 阶段只负责记录该状态。

不要在 P1.3 实现 Cloud dedup。

---

# 16. Meta 丢失 / 损坏

如果：

```text
/log/meta.bin
```

不存在或 CRC 错误：

必须：

1. 扫描现有 Segment；
2. 验证 Segment header；
3. 验证 Record CRC；
4. 找到最大 seq；
5. 根据要求向上取整后重新建立 sequence reservation；
6. 将 sequence reliability 标记为当前恢复逻辑要求的状态；
7. 增加 `corrupt_count`。

不得简单：

```text
seq = 0
```

然后重新开始。

---

# 17. Segment 初始化

启动时扫描 16 个 Segment。

每个 Segment：

1. 检查文件是否存在；
2. 检查大小；
3. 验证 header magic；
4. 验证 header CRC；
5. 验证 `seg_index`；
6. 验证记录；
7. 找到有效记录数量；
8. 找到 append position。

---

# 18. Segment Header 损坏

如果 Header CRC / magic / index 无效：

该 Segment：

```text
删除
```

并：

```text
corrupt_count++
```

然后作为空 Segment 重新使用。

禁止继续向损坏 Header 的 Segment 追加数据。

---

# 19. Record CRC 损坏

扫描 Segment 中的 Record 时：

如果发现第 N 条 Record CRC 错误：

```text
Record N 无效
Record N+1 及之后不再认为有效
```

append point：

```text
N
```

即从第一条坏 Record 开始重新写。

原因：

LittleFS / 文件系统出现掉电或部分写入时，后面的数据不能假定连续有效。

---

# 20. Segment 满

一个 Segment：

```text
31 records
```

写满以后：

```text
创建 / 选择下一个 Segment
```

Segment ring 满时：

```text
删除最老 Segment
```

然后复用它。

顺序：

```text
oldest → delete → recreate → newest
```

不得增加额外 reserved segment。

---

# 21. CRITICAL 不保留专用 Segment

必须遵守：

> CRITICAL 没有专用 Flash segment。

Ring 满时：

```text
CRITICAL
```

仍然可能和 WARN/ERROR 一样被最老 Segment 淘汰。

不要自行实现：

* critical partition
* reserved critical segment
* priority segment
* special overwrite policy

这些都不在冻结契约中。

---

# 22. P1.3 最重要：RAM → Flash 安全交接

当前 P1.2：

```text
RAM ring
↓
pop
↓
consume
```

在 P1.2 是可以接受的，因为 Flash 还不存在。

P1.3 **不得简单复制这种逻辑。**

对于：

```text
WARN
ERROR
CRITICAL
```

Flash 是持久化责任。

必须保证：

```text
Flash persistence 成功
        ↓
RAM record 才可以正式认为完成消费
```

因此设计一个明确的：

```text
RAM → Flash handoff
```

边界。

---

# 23. Flash 写失败处理

如果：

```text
Flash append failed
```

不得：

```text
pop RAM
然后丢失 Record
```

必须保留 Record，等待下一轮重试，或者进入明确的受控 degraded 状态。

不得静默丢失：

```text
WARN
ERROR
CRITICAL
```

```text

```

因此 INFO：

```text

↓
被 log_task 取出
↓
认为已消费
```

P1.3 不需要为了 INFO 构造 Flash persistence。

# 25. DEBUG

DEBUG：

```text
Flash NO
Cloud NO
```

继续在 `log_emit()` 直接丢弃。

# 26. WARN / ERROR / CRITICAL

固定：

```text
WARN      Flash YES + Cloud YES
ERROR     Flash YES + Cloud YES
CRITICAL  Flash YES + Cloud YES
```

P1.3 当前只实现：

```text
Flash YES
```

Cloud route 仍然只是 P1.2 的统计 / routing 状态。

不要实现 MQTT。

---

# 27. Flush Request

CRITICAL：

```text
s_flush_requested = true
```

P1.3 可以利用该 flag 让 Flash drain 优先。

但是：

> CRITICAL 只代表“最高优先级的下一批处理”，不承诺秒级 SLA。

禁止写：

```text
critical <= 1s
critical <= 5s
critical <= 16s
```

之类未经冻结的硬实时承诺。

---

# 28. WARN / ERROR Flash Flush

按照冻结设计：

```text
WARN/ERROR:
    8 records
    或
    5 seconds
```

触发 Flash flush。

CRITICAL：

```text
立即 Flash
```

这里的“立即”指进入当前 LogManager 的下一次处理机会，不允许阻塞当前业务逻辑。

---

# 29. Non-blocking 要求

P1.3 必须保持：

```text
无 delay()
无 blocking while()
无等待 Flash 完成的死循环
无独立 FreeRTOS Log task
```

LogManager 继续由：

```cpp
loop()
    ↓
log_task()
```

驱动。

---

# 30. Loop 时间预算

`LOG_DRAIN_MAX_PER_TASK = 8` 仍然保留。

但是：

> “每次最多 8 条”不能被视为完整的时间预算保证。

P1.3 必须控制单次 `log_task()` 的 Flash 工作量。

默认目标：

```text
一次 log_task()
    最多处理一个 Flash append/flush 单元
```

不要在一次 loop 中：

```text
连续写几十个 Flash record
```

导致喂水、Workflow、BLE、OLED 等业务被长时间占用。

如果需要一次写多个 Record，必须有明确、可验证的时间边界。

---

# 31. PSRAM 使用要求

ESP32-S3：

```text
8 MB PSRAM
```

已经是本项目可用的大容量工作内存。

对于以下对象：

* Flash batch buffer
* Segment 工作缓冲区
* 大型临时数组
* LogRecord 批量数组
* 未来 CBOR batch buffer
* 大型解析/序列化工作区

应：

> **优先考虑 PSRAM。**

例如：

```cpp
heap_caps_malloc(size, MALLOC_CAP_SPIRAM)
```

或者项目现有的 PSRAM 分配方式。

---

# 32. PSRAM 使用边界

但是：

以下高频、极小、必须低延迟访问的对象不要为了“统一”强行放 PSRAM：

* ring index
* bool flag
* counters
* mutex / spinlock
* 小型状态变量
* 高频访问的控制状态

原则：

```text
大对象 / 批量 buffer
    → 优先 PSRAM

小型控制状态
    → Internal RAM
```

---

# 33. Flash 工作 Buffer

如果 P1.3 需要：

```text
LogRecord temp
```

或者：

```text
LogRecord batch[...]
```

等明显较大的工作区：

优先 PSRAM。

但单个 128B、生命周期极短的局部变量可以继续使用 stack，不需要为了“PSRAM”过度复杂化。

# 39. Degraded 状态

如果 Flash 长期不可用：

LogManager 不得：

```text

```

阻塞系统。

应该：

```text

↓

```

并允许后续：

```text

```

等 P1.4/P1.5 使用。

P1.3 不提前实现 Cloud degraded report。

```text
unacked records 保留
```

没有：

```text
5 retries
↓
30 min
↓
FORCE_ADVANCE
```

这一旧设计已经废止。

# 45. At-least-once

P1.3 必须保持数据模型能够支持：

> at-least-once

因此：

```text
Flash record
```

不能因为一次上传失败而被删除。

但：

> P1.3 本身不实现 Cloud ACK。

Flash record 的删除/segment 回收机制将在后续 ACK 逻辑中继续使用。
