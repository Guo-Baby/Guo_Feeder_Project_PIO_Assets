## 1. 问题确认（改动前体检）

按用户要求逐项核对三类"不必要输出"：

| 用户要求核对项 | 是否存在 | 证据 |
|---|---|---|
| **callback 中大量 Serial 输出** | ✅ **存在（本次主要问题）** | `MiAdvCallback::onResult()`（`src/MiThermometer.cpp:117-123`）运行在 **NimBLE 主机任务上下文**（**非 loopTask**），内含 `Serial.printf("[MiThermo] ADV len=%d : ")` + **逐字节** `for` 循环 `Serial.printf("%02X ", payload[i])` + `Serial.println()` |
| **高频 hex dump** | ✅ **存在（同一处）** | 同上循环。按 `payload.size()`（本项目 LYWSD03MMC 加密广播 **≥29 B**，典型 31 B）估算：**每包约 31 次 `Serial.printf`** ⇒ 串口 ≈ 3×31 ≈ **93 字符** |
| **不必要调试打印** | ✅ 存在（3 处） | ① `MiThermometer_task()` 内 `[MiThermo] decrypt OK`（每成功解密帧一次）② `lywsd03_decrypt()` 末尾 `[MiThermo] decode type=%d value=%.2f`（每成功解密帧一次）③ 状态机周期性节奏输出（`enter scan window` / `scan window finished` / `scan success` / `enter LEVEL1` / `wakeup from sleep`） |

### 1.1 `P0-3` 代价核算

`P0-3` 原登记为"≈7.8 ms/包"。本次核算其构成：

- **主项**：31 次 `Serial.printf` 调用开销（参数解析 + 缓冲区管理）**加上** `println` 换行
- **次要项**：`Serial.printf` 内部经 `vprintf` 家族 + `Print` 缓冲；115200 bps 下 93 字符 ≈ **8.1 ms 纯传输**（若缓冲写满会阻塞等待）
- ⇒ 两项**量级吻合**，原估算可信

### 1.2 为什么它在 callback 里格外危险

| 维度 | 说明 |
|---|---|
| **执行上下文** | NimBLE 主机回调由 **`NimBLE` 自己的任务**调用，非 loopTask |
| **优先级** | NimBLE 主机任务优先级高于 loopTask ⇒ callback 内长时间阻塞会**推迟主机协议栈处理**（可能丢广播 / 丢连接事件） |
| **期间 loopTask** | 被抢占期间 loopTask 停摆 ⇒ 与 `R-8-A` 类似的"整机节奏受影响"，但**程度轻得多**（毫秒级，非永久） |
| **频率** | 目标设备广播周期通常 1–2 s，且本项目扫描占空为"1 s 开 / 1.8–2.3 s 关" ⇒ 实际约 **每 3 s 一包** |
| **结论** | 属"**高频 + 阻塞式输出**"的典型反模式；**符合用户描述的"callback 中大量 Serial 输出"** |

## 2. 处置方案

### 2.1 设计原则（严格遵守用户约束）

| 用户约束 | 本方案如何满足 |
|---|---|
| **不改变 BLE 解码逻辑** | `lywsd03_decrypt()` 的**全部算法/分支/判据逐字未动**，只把末尾一行打印改为宏 |
| **不改变 System State** | `state_set_*` 调用**零改动**（`TEMP` / `HUMID` / `BAT_V` / `TEMP_TS` / `HUMID_TS` / `BAT_TS` / `VALID` / `ENABLE` 全未触碰） |
| **不改变数据流程** | `onResult()` 的 MAC 过滤 → payload 取用 → 长度过滤 → `RawAdvItem` 构造 → `xQueueSend()` **顺序与语义逐字未动**；`MiThermometer_task()` 的队列消费 → 解密 → `state_set` 流程未动 |
| **保留必要错误日志** | `scan failed count=… level=…`（判断温湿度计是否离线）、`LEVEL2: scanning disabled`（采集**永久停用**，需人工/云端介入）、`ERR mac or bindkey empty!`、`ERR xQueueCreate failed`、`init OK` **全部保留为常态输出** |
| **不删除调试能力，只降低默认输出** | 见 §2.2 —— 逐字节 hex dump 与逐帧诊断**完整保留在源码中**，一个宏即可全部恢复 |
| **禁止加测试模式开关 / 临时 enable 配置** | 本宏**不是**这些。详见 §2.3 的"合规性论证" |

### 2.2 机制：模块级**编译期**调试开关

```cpp
#ifndef MI_THERMO_DEBUG_VERBOSE
#define MI_THERMO_DEBUG_VERBOSE 0
#endif

#if MI_THERMO_DEBUG_VERBOSE
#define MI_THERMO_VLOG(...) Serial.printf(__VA_ARGS__)
#else
#define MI_THERMO_VLOG(...) ((void)0)
#endif
```

- **默认 `0`** ⇒ 所有归入 verbose 的输出被**预处理器彻底移除**（不是运行期 `if`）
- 需要排查 BLE 协议问题时，把 `#define MI_THERMO_DEBUG_VERBOSE 0` 改成 `1` **重新编译** ⇒ **逐字节恢复**全部原始输出

#### 2.2.1 归入 verbose 的输出（默认关闭）

| # | 位置 | 内容 |
|---|---|---|
| 1 | `onResult()`（callback 内） | `[MiThermo] ADV len=N : ` + **逐字节 hex** + 换行 |
| 2 | `MiThermometer_task()` | `[MiThermo] decrypt OK` |
| 3 | `lywsd03_decrypt()` | `[MiThermo] decode type=%d value=%.2f`（**保留在函数尾部，返回语义不变**） |
| 4 | 状态机节奏 | `enter scan window` / `scan window finished`（2 处）/ `scan success` / `enter LEVEL1` / `wakeup from sleep` |

> 注：#4 的 `enter sleep %u sec`（`mi_enter_sleep()`）与 #2 的 `stop scan` 系列**未动**——
> 他们分别属"进入长休眠"与"用户主动命令"的**低频可观测点**，保留有助于确认模块节奏。

### 2.3 合规性论证（对照用户"禁止事项"）

| 禁止项 | 是否触碰 | 论证 |

### 5.3 ⚠️ 本轮**未能**触发 callback 路径（如实登记）

**原因**：`onResult()` 内的 **MAC 过滤**要求广播源为**用户配置的目标温湿度计**
（`config_get_mithermometer_mac()`）。当前环境：

- 目标 MAC 未配置为实际存在的设备（或设备不在广播距离内）
- 且模块自身节奏为 `BOOT_DELAY 15 s → 扫描窗口 15 min`，**探针只跑了 75 s**
- ⇒ `onResult()` 的**过滤后**分支（含 hex dump 那段）**未被执行**

**这是"期望行为"而非缺陷** —— 但意味着**运行期证据缺失**。
因此 §6 改用**静态/二进制级证据**补足，且该证据**更强**（见下）。

## 6. 二进制级验证（V3，**本轮的决定性证据**）

> **方法论**：运行期"没看到 hex 输出"是**弱证据**（可能只是没触发）。
> 要证明"hex 打印**不可能**再发生"，必须看**编译产物的机器码**。
> 本节用 `objdump` 反汇编 `onResult()` 并解析**调用目标符号表**，
> 得到的是**无条件的结构性证明**。

### 6.1 `onResult()` 体积

```
符号：MiAdvCallback::onResult(NimBLEAdvertisedDevice const*)
地址：0x42002e98 → 0x42002f7c（下个符号 mi_enter_sleep 起始）
长度：228 bytes = 57 条指令
```

### 6.2 `onResult()` 内**全部**外部调用（重定位表解析，7 个）

| 序 | 目标符号 | 源码语义 |
|---|---|---|
| 1 | `NimBLEAdvertisedDevice::getAddress() const` | 取 MAC |
| 2 | `NimBLEAddress::getVal() const` | 取地址字节 |
| 3 | `NimBLEAdvertisedDevice::getPayload() const` | 取 payload |
| 4 | `memset` | `RawAdvItem item{}` 清零 |
| 5 | `memcpy` | 拷 MAC（6 B） |
| 6 | `memcpy` | 拷 payload（≤62 B） |
| 7 | **`millis`** | `item.timestamp` |
| 8 | **`xQueueGenericSend`** | **`xQueueSend()` 入队** |
| 9 | `__stack_chk_fail` | 栈金丝雀失败（异常路径） |

### 6.3 ★★ **`Print::printf` / `Print::println` 出现次数 = 0**

```
$ objdump -d -C firmware.elf | onResult 函数体内 grep "Print::|printf"
0
```

> **改动前**，同函数内应有 2 个打印调用点（`Serial.printf` 两处）+
> 一段以 `payload.size()` 为界的循环（每次迭代都进入 `Serial.printf`）。
> **改动后，函数内一个都没有。**

### 6.4 ★★ 关键路径：`millis()` → `xQueueSend()` **零函数调用**

```asm
42002f50:	call8  millis
42002f53:	s32i.n a10, a1, 72      ← item.timestamp = millis()
42002f56:	movi.n a13, 0           ┐
42002f58:	l32i.n a10, a5, 0       │ xRawAdvQueue
42002f5a:	mov.n  a12, a13         │ timeout = 0
42002f5c:	mov.n  a11, a1          │ &item
42002f5e:	l32r   a8, <xQueueSend> │
42002f61:	callx8 a8               ┘ xQueueSend(xRawAdvQueue, &item, 0)
42002f64:	（栈金丝雀校验）→ retw.n
```

**从"构造完成"到"入队完成"仅 6 条指令，且无任何间接跳转到打印函数。**
这是"**callback 内不再有串口输出**"的**机器码级证明**。

### 6.5 其余保留输出**依然存在**（反例对照，证明没有"顺手删干净"）

同一 ELF 中：

| 符号 | 含打印调用 | 说明 |
|---|---|---|
| `mi_enter_sleep()` | ✅ 有（`Print::printf`） | `enter sleep %u sec` 保留 |
| `ble_init()` | ✅ 有（`Print::println`） | `[BLE] init OK` 保留 |

⇒ **不是"把所有打印都删了"，而是"精准只去掉高频/逐帧那批"**。

## 7. 结论

| 项 | 结论 |
|---|---|
| **问题是否确认** | ✅ `P0-3` 成立：callback 内**每包 31 次 `Serial.printf` + 逐字节 hex**，≈7.8 ms/包 |
| **是否低风险清理** | ✅ 是。改动**只影响打印**，不参与任何判定分支 |
| **是否满足"只降低默认输出"** | ✅ 逐字节 hex dump **完整保留在源码**，宏改 1 即恢复（**且已验证 verbose 模式编译通过**） |
| **是否保留必要错误日志** | ✅ `scan failed` / `LEVEL2` / `ERR *` 全部保留 |
| **是否改变解码 / State / 数据流** | ❌ **均未改变** |
| **是否违反禁止事项** | ❌ 未触碰任何一条（详见 §2.3；宏与既有 `LOG_DEBUG_ENABLE` 同模式） |
| **运行期 hex 输出** | **0 次**（75 s 静置） |
| **结构性保证** | **`onResult()` 内打印调用 = 0**（机器码级证明） |
| **`R-7` 影响** | **无** —— 本模块**未接入 LogManager**，改动不产生任何日志记录 ⇒ 对回归夹具零干扰 |

### 7.1 预期收益

| 指标 | 改动前 | 改动后 |
|---|---|---|
| callback 内串口调用 | **31 次/包**（+2 次格式串） | **0 次** |
| callback 内输出字节 | ≈93 B/包 | **0 B** |
| callback 执行时间（输出部分） | ≈7.8 ms/包 | **≈0 ms** |
| NimBLE 主机任务被占用 | 7.8 ms/包 | 仅 `memcpy` 级（µs 级） |
| `decrypt OK` / `decode` 逐帧输出 | 2 行/帧 | **0 行** |
| 状态机节奏输出 | 6 类周期性 | **0**（保留 `enter sleep` 等低频点） |

> 换算：按目标设备 1–2 s 广播周期 + 本项目"1 s 扫描 / 1.8–2.3 s 关闭"占空
> ⇒ 约每 3 s 一包 ⇒ **节省 ≈2.6 ms/s 的 callback 占用**，
> 且这 2.6 ms/s 原本发生在**优先级高于 loopTask 的 NimBLE 任务**里。

### 7.2 残余风险

1. **BLE 协议级诊断能力下降**：默认看不到逐包 hex。**缓解**：宏改 1 重编译即可恢复（已验证）。
2. **`decrypt OK` 消失**导致"解密成功与否"不再有正面证据。
   **缓解**：`decode type=… value=…` 一并归入 verbose，
   正常情况下可通过 **`STATE_MI_THERMO_TEMP/HUMID` 的更新**间接观测。
3. **未触碰**：`NimBLE` 库自身的日志级别（`CONFIG_NIMBLE_CPP_LOG_LEVEL` /
   `CONFIG_BT_NIMBLE_LOG_LEVEL`）**保持不变** —— 属库级配置，
   修改会引入库行为变化，**超出"低风险清理"范围**，故不动。
   （登记为后续可选优化，见 `未修复的问题.md`。）

## 8. 与后续阶段的关系

- **Phase 3（埋点接入）**：BLE 相关埋点**仍暂缓** —— 本轮只做了"降低输出"，
  **未做** 用户要求的"事件筛选 / 聚合策略 / callback 上下文安全"设计。
  现在 callback 已**干净**（零打印、零阻塞），**为后续埋点提供了安全底座**。
- **`SYS-2` 结论依然成立**：BLE 与 LogManager 共用 loopTask ⇒ 无并发竞争。
  本轮的收益是**降低 NimBLE 任务占用**（而非 loopTask）。
- **Phase 4（Dispense）**：本改动与 Dispense 无耦合，不构成前置。
