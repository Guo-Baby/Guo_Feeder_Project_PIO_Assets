## 1. 调用链

### 1.1 库内调用链（**根因所在**）

```
HX711::read()                                  HX711.cpp:107
  └─ wait_ready()                              HX711.cpp:110   ← 无 timeout！
       └─ while (!is_ready()) { delay(delay_ms); }   HX711.cpp:196-199
            └─ is_ready() = digitalRead(DOUT) == LOW     HX711.cpp:88
                     ↑
              ★ 若 DOUT 恒为 HIGH ⇒ 死循环，永不返回
```

**三个等待 API 的实际实现（库均已在头文件公开）**：

| API | 实现 | 有界？ | 头文件声明 |
|---|---|---|---|
| `wait_ready(delay_ms=0)` | `while(!is_ready()) delay(delay_ms);` | ❌ **无限** | `HX711.h:51` |
| `wait_ready_retry(retries=3, delay_ms=0)` | `while(count<retries){ if(is_ready()) return true; delay(); count++; } return false;` | ✅ **有界**（次数） | `HX711.h:52` |
| `wait_ready_timeout(timeout=1000, delay_ms=0)` | `start=millis(); while(millis()-start<timeout){ if(is_ready()) return true; delay(); } return false;` | ✅ **有界**（时间） | `HX711.h:53` |
| `read()` | **先 `wait_ready()`（无参 ⇒ 无限）**，再读 24 bit | ❌ **无限** | `HX711.h:59` |

> **根因一句话**：`read()` 内部的 `wait_ready()` 是**无参调用**，因此走的是**无限**版本。
> 库**已经提供** `wait_ready_timeout()` / `wait_ready_retry()`，但 `read()` 没有用它们。
> ⇒ **我们无法通过参数让 `read()` 变有界；只能在调用 `read()` 之前自己保证 `is_ready()`。**

            │       └─ 5 s 超时 → event_push(EVENT_WEIGHT_ERROR, HIGH, STATE)
            │                    weight_refresh_error_state()

| 行 | 调用 | 说明 |

**⇒ 全项目只有这 2 个阻塞点，且两处都有 `is_ready()` 前置检查。**

### 1.3 `read()` 内部还会关中断（次要风险）

已核对 `HX711.cpp:127-170`：本平台（ESP32）走 `IS_FREE_RTOS` 分支

```cpp
portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;
portENTER_CRITICAL(&mux);          // ← 关闭中断
data[2] = SHIFTIN_WITH_SPEED_SUPPORT(...);   // 24 bit × delayMicroseconds(1)
…
for (i = 0; i < GAIN; i++) { digitalWrite(SCK,HIGH); delayMicroseconds(1); … }
portEXIT_CRITICAL(&mux);
```

`FAST_CPU` 分支 ⇒ 走 `shiftInSlow()`，每位 2 次 `delayMicroseconds(1)`。
**总计约 24×2 + 3×2 ≈ 54 µs 关中断**。⇒ 量级可接受（微秒级），**不是本次要解决的问题**，
但说明 `read()` 本身是一个"关中断 + 忙等"的临界区，**不应被无限拉长**。

## 2. 风险确认

### 2.1 ✅ 确认：无限阻塞风险真实存在

**关键在于 `is_ready()` 前置检查与 `read()` 之间存在"失效窗口"。**

| 检查点 | 代码 | 时刻 |
|---|---|---|
| 前置检查 | `if(!scale.is_ready()) { … return; }` | t₀ |
| 实际读取 | `raw_value = scale.read();` → 内部 `wait_ready()` | t₀ + Δ |

在 Δ 窗口内若 DOUT 由 LOW 变 HIGH（重新开始转换周期 / 芯片掉线 / 引线接触不良 / 电源跌落），
则 `read()` 内部的 `wait_ready()` 进入**等待一个永不到来的 LOW**。

### 2.2 ★ 硬件层面决定了风险的严重程度（本平台特有）

已核对 `HX711.cpp:71-75`：

```cpp
#ifdef ARCH_ESPRESSIF
#define DOUT_MODE INPUT          // ← ESP32 无内部上拉！
#else
#define DOUT_MODE INPUT_PULLUP
#endif
```

`HX711::begin()` 执行 `pinMode(DOUT, DOUT_MODE)` ⇒ **ESP32 上 DOUT 是纯 `INPUT`，无内部上拉**。

**HX711 芯片行为**（数据手册）：
- 数据未就绪 ⇒ **DOUT 输出 HIGH**（主动驱动高）
- 数据就绪 ⇒ DOUT 输出 LOW

⇒ **芯片在正常工作期间绝不会让 DOUT 悬空**（它是推挽输出），
因此"DOUT 恒 LOW ⇒ 误判就绪"的假就绪路径**概率极低**。

⇒ **真正的高概率触发场景 = 芯片脱离总线**：

| 场景 | DOUT 状态 | `is_ready()` | 后果 |
|---|---|---|---|
| 芯片正常，数据未就绪 | 芯片驱动 **HIGH** | false | ✅ 走 `return` 分支，安全 |
| 芯片正常，数据就绪 | 芯片驱动 **LOW** | true | ✅ 立即读到数据 |
| **芯片掉电 / 断线 / VCC 断 / 焊接开路** | **浮空**（无内部上拉） | **不确定**：若接外部上拉或寄生耦合 ⇒ HIGH ⇒ safe；**若浮空读 LOW ⇒ `read()` 进入无限等待** | 🔴 **loop 永久挂起** |
| DOUT 对 GND 短路 | **LOW（恒低）** | **恒 true** | ⚠️ 不会阻塞，但会**读到垃圾值**（不属 R-8-A） |

⇒ **风险确认：真实存在，触发条件 = "DOUT 浮空且被读为 LOW"**。
在"无内部上拉"的 ESP32 上，这一条件的概率**取决于外部电路**（是否加了上拉电阻）。

> ⚠️ **这一点需要硬件确认**（见 §5 待确认项）：若 DOUT 有外部上拉电阻，
> 则掉线时浮空被拉高 ⇒ **实际风险大幅降低**（虽非零）；
> 若没有外部上拉，则**风险显著**。

### 2.3 后果确认（为什么是 P0）

一旦 `weight_task()` 卡在 `read()` 内：

| 受影响 | 说明 |
|---|---|
| **`system_command_task()`** | 🔴 全系统唯一 `ESP.restart()`（`system_command.cpp:312`）**无法执行** ⇒ Safe Restart 彻底失效 |
| **`valve_task()`** | 🔴 阀门**安全超时检查停摆** ⇒ 阀门可能保持开启 ⇒ **溢水风险** |
| **`event_dispatch()`** | 🔴 `EVENT_WEIGHT_ERROR` → `dispense_guard` → `valve_force_close()` **链路断裂** |
| **`log_task()`** | 🔴 日志停写 |
| **`wifi_task()` / `cloud_task()`** | 🔴 断连、离线 |
| 唯一恢复途径 | **看门狗复位**（`delay(0)` 会喂狗 ⇒ 若走的是 `wait_ready()`，`delay()` 会喂 WDT ⇒ **甚至连看门狗都不会触发**！） |

> ⚠️ **最坏情况**：`wait_ready()` 内的 `delay(delay_ms)` 默认 `delay_ms=0`，
> 即 `delay(0)` —— 在 ESP32 Arduino 上 `delay(0)` 会调用 `vTaskDelay(0)` 并**让出 CPU**，
> 因此 **WDT 不一定触发**（任务在"让出"而非"死占"）。
> ⇒ **可能表现为"系统看起来还活着但不做任何事"** —— 这是**最难诊断**的失效模式。
> **这一点使 R-8-A 的严重性再升一级。**

## 3. 最小修改方案

### 3.1 核心设计：**"先确保就绪，再读" + 超时即走既有错误路径**

**原则**：不引入新机制，**复用已有的 `not_ready` 状态与 `EVENT_WEIGHT_ERROR` 流程**。

**修改本质**：把 `scale.read()`（无限等待版）替换为
`scale.is_ready()` 判定 + `scale.read()` 的**两段式**，
并在 `is_ready()` 为 false 时**直接走既有的 `not_ready` 分支**。

### 3.2 具体改动（**2 个阻塞点**）

#### 改动 ① `weight.cpp:406`（采样分支，主路径）

**现状**：
```cpp
    if(not_ready_start != 0)
    {
        not_ready_start = 0;
        last_not_ready_event_ms = 0;
    }

    // 成功读取新的 HX711 数据
    raw_value = scale.read();
```

**改为**（在 `read()` 前再确认一次就绪；不就绪则走既有 error 路径）：
```cpp
    if(not_ready_start != 0)
    {
        not_ready_start = 0;
        last_not_ready_event_ms = 0;
    }

    // ★ R-8-A：二次就绪确认。
    //   HX711::read() 内部的 wait_ready() 是**无限阻塞**（库未提供有界 read()）。
    //   故此处再确认一次就绪才读；不就绪则退回既有"无数据"路径，
    //   由 not_ready_start / WEIGHT_NOT_READY_TIMEOUT_MS 驱动既有错误流程。
    if(!scale.is_ready())
    {
        if(not_ready_start == 0)
            not_ready_start = millis();

        weight_refresh_error_state();
        return;
    }

    // 成功读取新的 HX711 数据
    raw_value = scale.read();
```

> ⚠️ **为什么这次不用 `wait_ready_timeout()`**：
> 若用 `wait_ready_timeout(5ms)` 等它，则在**真掉线**时会**每轮 loop 白等 5 ms**
> 而**永远不会进入错误状态**（因为它会一直 return false，但代码路径需要显式处理）。
> **直接不读、退回 `not_ready` 分支**才是语义最正确、开销最小的做法：
> - HX711 正常时：`is_ready()` 为 true ⇒ **行为与现在完全一致**（零额外开销，只多一次 `digitalRead`）
> - HX711 异常时：**立即 return**（不等待）⇒ **loop 继续运行** ⇒ 5 s 后触发既有 `EVENT_WEIGHT_ERROR`

#### 改动 ② `weight.cpp:312-314`（校准分支）

**现状**：
```cpp
        if(scale.is_ready())
        {
            cal_sum += scale.read();
            cal_sample_count++;
```

**改动**：**无需修改**。已确认该处 `if(scale.is_ready())` 与 `scale.read()` **紧邻**
（中间无任何代码），Δ 窗口是**纳秒级**（一次函数返回 + `digitalRead`），
**不存在实际操作空间**。⇒ **保持原样，最小化改动面**。

> 若审阅时希望"零遗漏"，可选加一行 `if(!scale.is_ready()) return;` 的重复检查，
> 但**收益接近于零、增加改动面** ⇒ **本方案不做**。

### 3.5 ⚠️ 残余风险（**必须如实说明**）

方案 A **不能 100% 消除**阻塞，因为存在**不可消除的 TOCTOU 窗口**：

```
t₀: if(!scale.is_ready())   →  true（就绪）
t₁: …（几条指令，无 I/O、无阻塞、无函数调用）
t₂: raw_value = scale.read()  →  内部 wait_ready() 再次检查
     ↑ 若 DOUT 在 t₀→t₂ 之间变 HIGH ⇒ 仍会无限等待
```

**量化评估**：Δ = t₂ - t₀ ≈ **数条指令 + 一次函数调用**（≈ 几十 ns ~ 1 µs）。
- HX711 转换周期 ≈ **100 ms**（10 Hz）⇒ 在这个 1 µs 窗口内恰好发生转换完成的概率
  约为 **1 µs / 100 ms = 1e-5**；
- 而且即使发生，**下一次转换完成后 DOUT 会再次变 LOW**（10 Hz）⇒ 阻塞会**在 100 ms 内自行解除**；
- ⇒ **只有当 DOUT 持续为 HIGH 时才会永久阻塞**，即**芯片掉线**场景 ⇒
  此时方案 A 的二次检查**已经能拦住绝大部分情况**（因为掉线后 `is_ready()` 恒 false）。

**⇒ 结论：方案 A 把"永久挂起"的概率从"掉线即挂起"降到"掉线初期恰好撞上 1 µs 窗口"，
属工程上可接受的残余风险。**

**若要求 100% 消除**，需额外手段（**本次不做，仅登记为可选加固**）：
- **看门狗式守卫**：记录 `read()` 的进入时刻，若下一轮 `weight_task()` 发现
  `millis()` 已跨越远超正常周期（如 > 2 s）⇒ 判定"上次读卡住" ⇒ 置 `STATE_WEIGHT_ERROR`
  并**跳过当轮**。但这**仍无法打断正在进行的 `read()`**（因为 loop 卡在里面），
  ⇒ 只能触发**看门狗复位**（需任务看门狗配置）而**无法优雅恢复**。
- **真正的根治**需改库（方案 C）或自写驱动（方案 E），**均超出"最小修改"范围**。

### 5.1 待硬件确认项（影响风险评估，不影响方案正确性）

| # | 待确认 | 为什么重要 |
|---|---|---|
| **Q1** | HX711 的 `DOUT` 引脚**是否有外部上拉电阻**（10 kΩ 至 3.3 V）？ | 库在 ESP32 上用 `INPUT`（**无内部上拉**）。有外部上拉 ⇒ 掉线时被拉 HIGH ⇒ `is_ready()` 恒 false ⇒ **风险大幅降低**（方案 A 基本可覆盖）；无上拉 ⇒ 浮空不确定 ⇒ 风险更高 |

### 8.9 残留风险（如实登记，未消除）

1. **TOCTOU 窗口**：二次 `is_ready()` 与 `read()` 之间仍有 **≈1 µs** 窗口。
   量化：以 1e-5 概率估算，且 **10 Hz 采样下该条件 100 ms 内自行解除**
   ⇒ 不构成实际风险。**彻底消除需改库**（方案 C），已明确否决。
2. **硬件侧更彻底方案（建议保留）**：既然已确认 **DOUT 有外部上拉**，
   则"掉线 ⇒ 读 HIGH ⇒ `is_ready()` false ⇒ 走 `not_ready` 路径"**已由硬件保证**
   ⇒ 软件修复（方案 A）与硬件上拉构成**双重保险**。
3. **方案 A 未覆盖的场景**：若 HX711 **未掉线但永久不再拉低 DOUT**
   （芯片假死但电平保持 HIGH）—— 同样被方案 A 覆盖（`is_ready()` 恒 false）。
   **真正未覆盖的只剩 TOCTOU**。
