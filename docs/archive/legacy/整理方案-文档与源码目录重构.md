### 2.3 ★ 关键技术点：123 处 include 怎么办（**这是本方案的核心**）

因为全部是裸文件名 `#include "xxx.h"`，把 `.h` 挪进子目录后**必须让编译器还能找到它们**。三种做法：

| 方案                          | 做法                                                 | 改动量                                   | 评价                 |
| --------------------------- | -------------------------------------------------- | ------------------------------------- | ------------------ |
| **① 加 `-I` 搜索路径**（**推荐先做**） | 在 `platformio.ini` 的 `build_flags` 里为每个子目录加一行 `-I` | **改 1 个文件、加 7 行；123 处源码 include 零改动** | ✅ 风险最低，固件行为零变化     |
| ② 改成路径限定写法                  | 把 123 处改成 `#include "services/config_manager.h"`   | **改 30 个文件 / 123 行**                  | 更规范，但 diff 大、易出笔误  |
| ③ 折中（**推荐落地方式**）            | **现在做 ①**；**以后新写的代码**用带路径写法，老代码不动，渐进迁移             | 1 + 增量                                | ✅ 兼顾"现在零风险"与"长期规范" |

**方案 ① 的具体改法**（`platformio.ini`）：

```ini
build_flags =
  -DARDUINOJSON_USE_CBOR=1
  -DARDUINO_LOOP_STACK_SIZE=16384
  ; ↓ 新增：源码分层后的头文件搜索路径（PlatformIO 已默认含 -Isrc）
  -Isrc/app
  -Isrc/automation
  -Isrc/services
  -Isrc/storage
  -Isrc/log
  -Isrc/cloud
  -Isrc/test
```

> **说明**：`-I` 路径是相对于工程根目录（PlatformIO 的标准用法）。加上之后，`#include "config_manager.h"` 这类裸名字仍然能被解析到 `src/services/config_manager.h`。  
> **唯一代价**：若将来出现**同名头文件**，include 路径的先后顺序会决定胜负。目前 49 个文件名**互不重名**，无风险；后续新增文件注意不要重名即可（② 的写法可以彻底消除这个隐患）。

**<u>为什么不用中文目录名</u>**<u>：`src/` 的目录名会进入 `platformio.ini` 的构建参数与 `compile_commands.json`。本项目已经踩过「Windows 下非 ASCII 脚本/路径被按 ANSI 解</u>码」的坑（`docs/scripts/setup-cloud-app-env.ps1` 首版直接 `ParserError`），**源码目录名一律用 ASCII**。`docs/` 不参与构建，可以自由用中文文件名（现状已如此）。

### 2.4 执行方式与验证

| 步骤 | 命令                                    | 目的                                       |
| -- | ------------------------------------- | ---------------------------------------- |
| 1  | `git mv src/xxx.h src/app/xxx.h` 逐批移动 | **保住 git 历史**（不要用 `mv`）                  |
| 2  | 编辑 `platformio.ini` 加 7 行 `-I`        | 恢复 include 解析                            |
| 3  | `pio run -t clean`                    | 清掉旧路径的对象文件                               |
| 4  | `pio run`                             | **必须全量编译通过**（唯一硬门槛）                      |
| 5  | `pio run -t compiledb`                | 重新生成 `compile_commands.json`（clangd 依赖它） |
| 6  | `pio run`（可再烧录实测）                     | 确认固件行为不变                                 |

> **回滚**：全过程只用 `git mv` + 一处 `platformio.ini` 编辑，`git reset --hard` 或 `git mv` 反向即可完全回退。**建议先打一个 tag 或 commit 作为锚点。**

### 2.5 风险清单

| 风险                                     | 等级               | 处置                                               |
| -------------------------------------- | ---------------- | ------------------------------------------------ |
| include 解析失败（漏加 `-I`）                  | 中                | 第 4 步全量编译会立刻暴露；补齐 `-I` 即可                        |
| 目录内 `.cpp` 未被编译                        | **低**（已核实递归默认开启） | 编译后确认符号数量不变（对比 build 输出的 object 数）               |
| 未来同名头文件冲突                              | 低                | 新代码用路径限定写法（§2.3 方案 ③）                            |
| clangd 索引失效                            | 低                | 重新 `pio run -t compiledb`；`.clangd` 无需改          |
| `extra_scripts = fix_compiledb.py` 受影响 | **无**            | 该脚本只设置 `COMPILATIONDB_INCLUDE_TOOLCHAIN`，与目录结构无关 |

### 4.2 ★ 必须先知道的一条 git 规则

> **`.gitignore` 只对"还没被跟踪"的文件生效。**  
> 文件一旦进入过索引，加 ignore **不会**让它消失，必须显式 `git rm --cached <file>`。

实测结果 —— 以下文件**当前已被跟踪**，因此现有 ignore 规则**对它们无效**：

| 文件                              | ignore 里有规则？      | 实际状态                               |
| ------------------------------- | ----------------- | ---------------------------------- |
| `data/`（11 个文件，含 `mqtt.json`）   | ✅ 有 `data/`       | ❌ **仍在仓库里**                        |
| `.workbuddy/memory/*.md`（12 个）  | ✅ 有 `.workbuddy/` | ❌ **仍在仓库里**（当初用 `git add -f` 加进去的） |
| `compile_commands.json`         | ❌ 无               | ❌ 在仓库里（5.1 MB）                     |
| `serial.log` / `serial_sys.log` | ❌ 无               | ❌ 在仓库里                             |
| `AI_RULES.md`                   | ✅ 有               | ✅ **确实被挡住了**（未跟踪）                  |
