## 2. P0-1 · D1 写入归因（做法与结论）

### 2.1 为什么不用 Analytics 归因

上一轮尝试按 `queryName` 维度归因，实测失败：`orderBy: rowsWritten_DESC` 不被接受、没有 `queryName` 维度，且 Analytics 有**独立**限流预算——反复重试会把排查本身变成新故障。⇒ 改为「静态语句清单 + 表级增量实测」两条腿，都可复核。

工具：`Cloudflare_Assets/scripts/d1_write_attribution.mjs`（输出留档 `docs/evidence/d1-write-attribution-2026-10-31.txt`）。

### 2.2 静态归因（代码里到底有哪些写点）

扫描 `guo-feeder-api/src` + `guo-feeder-pagesdev/functions`：**70 处写语句，涉及 20 张真表**。

| 表 | 写点数 | 主要来源 |
|---|---|---|
| `mqtt_browser_account` | 13 | 账号池（租约/轮换） |
| `device` | 9 | 设备注册 upsert（**有节流**）+ 绑定/凭据 |
| `device_credential` | 6 | 设备注册 |
| `device_binding` | 5 | 绑定 |
| `xiaomi_auth_pending` | 5 | 米家登录 |
| `device_event` | 4 | 注册/presence |
| `ui_session` | 4 | 浏览器会话（新建/touch） |
| `xiaomi_sync_cursor` | 4 | 米家同步（cron） |
| `command_audit` | 3 | 命令审计（**每下发一条命令 1 行**） |
| `log_boot_watermark` | 3 | 日志批次水位（每批 1 次） |
| `mqtt_messages` | 1 | **每条入站 MQTT 消息 1 行**（含 echo 回环行） |

### 2.3 实测归因（近 24h / 当日）

| 表 | 近 24h 新增 | 总行数 |
|---|---|---|
| `mqtt_messages` | **8,410** | 13,348 |
| `log_history` | 2,671 | 5,283 |
| `command_audit` | 1,480 | 1,886 |
| `ui_session` | 80（新建会话 79） | 92 |

逐小时看，`mqtt_messages` 的 8,410 中**只有 289 条是今天**（UTC 08:xx 前），其余 8,121 条集中在 **10-30 11:00–16:00Z**（峰值 1,704/h）——那是当天的联调/测试高峰，**不是生产常态**。

今日（UTC 00:00 → 08:00）：写入 **3,541 / 100,000（3.5%）**，读取 535,286 / 5,000,000（10.7%）；安静小时基线 **183–210 写/小时 ≈ 4.4–5.0k/天**。

> 结论：D1 写入的**结构性大头是 `mqtt_messages`（每条入站消息 1 行，EMQX 双规则各抓一次）**，属架构决定、非 bug；`command_audit` 随"每下发一条命令"线性增长。真正可压缩的是"测试/联调流量"而不是生产常态。

### 2.4 已实现的写入保护（可持续，不靠"等用户发现额度耗尽"）

1. **`src/d1-guard.js`**：`classifyD1Error()` 把错误分成 `quota_exhausted / constraint / network / d1_error / unknown`；`quota` 优先判定，避免把"额度"误判成"约束"。
2. **非必要写入闸门** `shouldSkipNonEssentialWrite()`：仅对 `quota` 生效、60 s 持留；被跳过的都是**可丢字段**（`device.last_seen`、`ui_session.last_seen_at`、池 journal）。**必要写入**（`mqtt_messages`/`log_history`/`telemetry_history`/审计）照旧尝试、失败照旧上报。
3. **主动监控工具** `tools/d1_usage.py`：每次现读 token（避免 wrangler 轮换导致 401），打印逐小时写入/读取与累计占比、额度重置时间；异常时以退出码 2/3/4 区分（2=接近阈值，3=已超，4=读取失败），可直接挂到任何守护/CI 里。
4. **`GET /api/admin/storage-health`**：**零 D1 访问**、只回非敏感观测值 `{ok,degraded,kind,hold_left_s,scope:"isolate"}`，供前端驱动全局横幅。

### 2.5 `log_boot_watermark.rewind_count = 1321/1643` 已查明

不是缺陷：`rewind_count` 是**观测计数**（每批"看到 `boot_seq` 低于水位"就 +1），语义明确标注为 `REWIND_CANDIDATE(not proof)`；该模块**不降水位、不删除、不拒绝**任何原始日志，因此**不存在数据丢失**。高比例主要来自迟到上传与重复投递（计数会放大）。若要把它变成可用指标，需要按 `(boot_seq, 批次)` 去重后再计数——属"指标优化"，本轮未做。

## 3. P1-1 · 米家 LAN 能力矩阵复核（如实说明）

- 实际可用的只有：**喂食器出粮（份数）**、**插座通电/通断电（含 60 s 自动断电）**、**状态查询**。
- **没有**实现、也不宣称：出粮克数、余粮、进食量实时读取、摄像头、喂食计划写入。
- 已知硬件/链路限制（沿用既有结论，本轮未改变）：米家设备对密集握手会丢包（需连续 ≥3 次失败且距上次成功 ≥120 s 才判离线）；错 Token 的真实表现是"无响应"而非"拒绝"。
- `XIAOMI_FEEDER_STATUS` / `XIAOMI_PLUG_STATUS` 是**只读状态刷新**，不是动作。
