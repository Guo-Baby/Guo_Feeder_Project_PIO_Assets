## D. 缺陷关闭证据

### D-1 首页刷新后模块消失（P1-1）

* **原始表现**：点刷新后除最底部"米家近七天"外全消失，只剩"加载中"；再点首页导航不恢复；只有整页刷新才行。
* **根因**：`gf-app.js::renderHome(opts)` 在 `cacheOnly` 分支**先**执行 `box.innerHTML = '加载中…'`（清空 DOM），**然后**才判断"缓存里没有快照"并 `return` ⇒ 页面永久停在空壳；而重复点同一导航不触发 `hashchange` ⇒ 点了也回不来。
* **修改**：`guo-feeder-pagesdev/assets/js/gf-app.js::renderHome` —— 无缓存 + 只读缓存 ⇒ **保持当前 DOM 不动**（既不闪空，也不额外打请求）。
* **回归测试**：`tests/ui/p2_p3_checks.test.mjs` + 生产浏览器 61/0。
* **生产证据**：真实 Chromium 375×812 反复刷新/切页/米家查询后模块保持完整。

### D-2 手动 MQTT 认证失败交互（P0/P1-2）

* **原始表现**：手动登录失败后只剩"退出手动连接"，输入框被清空，用户无法重试。
* **根因**：草稿只存在于 DOM，`renderManualMqtt()` 每次 `innerHTML` 重建 ⇒ 输入被抹掉；失败态没有独立存储 ⇒ 一闪即失。
* **修改**：`gf-app.js` —— 草稿与失败态移入**内存**（`_manualDraft` / `_manualFail`）；失败后弹**明确弹窗**（说明被 EMQX 拒绝、当前没有连接、可选两条路）；状态用**彩色徽标**（绿=已连接 / 黄=未连接 / 红=失败）；两个按钮**并存**；**绝不自动切账号池**、**绝不自动分配池账号**、**不清空输入**；凭据仍只在内存（30 分钟 TTL，从最后提交算起）。
* **回归测试**：`tests/pages/mqtt_manual_credential.test.mjs` 29/0（内存态、无 localStorage/sessionStorage/IndexedDB 痕迹）。
* **生产证据**：真实浏览器断言"未连接态下同时存在两个按钮"+"localStorage 无凭据痕迹" ✓。

### D-3 ConfigManager enable 键（P0-1，上一轮 OPEN）

* **原始表现**：`config_manager.cpp` 的键表**没有**声明 `xiaomi_lan.feeder_enable/plug_enable`；读点是 `xiaomi_lan.cpp:558` 的动态 `config_get_bool` ⇒ 云端 `config_set` 是否被接受**未知**。
* **根因**：ConfigManager 的"声明键表 / 默认值 / 类型校验 / 读写映射"没有这两个键的条目。
* **修改**：`config_manager.h/.cpp` —— 显式登记（模块 `xiaomi_lan`、键名、类型 BOOL、默认 **true**）；`config_init()` 给缺失的键补默认值并加载到内存；`xiaomi_lan.cpp` 只读 ConfigManager 的内存值（不再自行读 Flash）；云端 `config-spec.js` 的 fallback 同步改成 `true`（两侧必须一致）。
* **回归测试**：`tests/api/config_spec_parity.test.mjs` 改为**解析固件的 `kDeclaredKeys[]` 表**（不再用硬编码白名单自证），并正向断言这两个键确实在表里。

### D-4 Workflow 整份 pre-flight（P0-2）

* **原始表现**：存在"先执行前几步、走到某个米家动作才失败"的可能。
* **修改**：`src/automation/workflow.cpp` —— `workflow_start()` 的**第一步之前**遍历**整份**步骤，对每个动作检查其依赖模块的 enable（`state_get_bool(STATE_XIAOMI_FEEDER_ENABLE)` / `..._PLUG_ENABLE`），任一不满足 ⇒ **整份不执行**，并记录 slot / 步骤号 / 模块 / 原因码。

### D-5 米家历史增量同步（P1-1）

* **原始表现**：每点一次同步新增约 14 条，却重复处理 700+ 条。
* **根因**：米家云端 `multiGetFeedRecord` **只有上界**（startTime）没有下界；旧代码唯一的收敛条件是"本页无新增 且 已低于已知边界"⇒ **只要这轮有新记录，就会一路深翻到 90 天窗口尽头**，把上千条历史重新拉取并逐条尝试写库。
* **修改**（`sync-run.js::syncIncremental` + `sync.js`）：
  * 新增游标 `feeder_backfill_done`（写入**既有**表 `xiaomi_sync_cursor`，**不新增迁移**）；
  * **回溯段**（标记未置位）：翻到 90 天窗口边界后置位，一次性成本；
  * **增量段**：下界 = `newest − 2h`；单页从 20 起（缺口大时逐页加倍）；**早于下界的记录在写库前就被过滤**（不写、只计 skipped）；某页出现下界以下记录 ⇒ 窗口已覆盖 ⇒ 立即停；
  * 游标只在**写库成功后**推进；写失败抛出且不推进 ⇒ 可安全续跑。
* **回归测试**：`xiaomi_incremental_window.test.mjs` 37/0（首次/增量/无新/分页/边界重叠/同刻多条/中途失败/重试/游标恢复/90 天外历史保留）。
* **生产证据**（`scripts/verify_sync_incremental_prod.mjs`，10/0）：

|---|---|---|---|---|---|---|
| 第 1 次（回溯，一次性） | 4 | 1047 | 2 | 1045 | 0 | EMPTY |
| **第 2 次（增量）** | **1** | **20** | 0 | 2 | **18** | **REACHED_FLOOR** |

⇒ 上游请求 **4 → 1**，写库尝试 **1047 → 2**（≈ **500×** 减少）。这同时是 D1 额度的一笔直接节省。

### D-6 ★ 部署到生产的语法事故（本轮自查发现并修复）

* **原始表现**：第一次部署后，生产浏览器报 `Unexpected identifier 'section'`，**米家四个模块与首页图表全部不渲染**。
* **根因**：我在 `gf-xiaomi.js` 的 **CSS 模板字符串**（`const CSS = \`…\``）内部的注释里写了带反引号的 `section.mod-sec` ⇒ **模板字符串被提前闭合** ⇒ 后面的 CSS 全被当成 JS 解析。
* **为什么单测没抓到**：既有前端单测都是**读源码文本做断言**，从不**解析**它 ⇒ 一个语法错误能全绿通过。
* **修复**：清理模板串内全部反引号（8 处）。
* **新增防线（两级）**：
  1. `tests/ui/frontend_syntax.test.mjs` —— 对 Pages 目录下**全部 27 个 .js** 做语法解析（ESM 按 `.mjs` 解析），任一失败即红。**负向验证**：注入缺陷 → 26/1 报错；还原 → 27/0。
  2. **`guo-feeder-pagesdev/tools/deploy_pages.sh` 增加"语法门禁"** —— 部署前逐个解析暂存目录的 `.js`，不通过就 **exit 66 拒绝部署**。**负向验证**：注入缺陷 → `refusing to deploy`（exit 66）；还原 → exit 0。

## F. 用户测试指南（中文，逐步照做）

> ⚠️ 标了 **【物理动作】** 的步骤会真的让设备动起来，**请你在设备旁**执行并自己确认。
> 其余步骤都是只读或配置操作，随时可做。

### F-1 首页稳定性（对应 D-1）

1. 打开 `https://YOUR_PROJECT.pages.dev/app.html`，登录。
2. 在首页点 **「↻ 刷新数据」** 3 次 ⇒ 首页模块应**始终完整**（不应只剩"加载中"）。
3. 依次切到「控制页 → 首页 → 记录 → 首页」⇒ 模块应始终在。
4. 到控制页点「读取两台设备状态」，再回首页 ⇒ 模块不应消失。
5. **预期**：任何时候都能看到完整的首页；若出现"加载中"卡住 ⇒ 记录当时的操作步骤。

### F-2 首页布局（对应 P1-2 / P3-4）

1. 首页点 **「▤ 布局」** ⇒ 弹出区块列表，应有 **8 项**，其中一项是 **「米家 · 近 7 天（出粮/进食）」**。
2. 把「米家 · 近 7 天」用 ▲ **上移 3 格**，点「保存」。
3. **刷新浏览器** ⇒ 它应仍在你保存的位置（不是回到最底部）。
4. 点「恢复默认」⇒ 回到初始顺序。
5. **预期**：列表里**不应**再出现「米家喂食器」「米家智能插座」两个状态卡（读状态只在控制页）。

### F-3 自动化名称（P1-3）

1. 「自动化」页 ⇒ 手动/定时两个 Tab。
2. 看卡片标题：中文、英文、数字、emoji 都应**原样显示**（例如 `Daily feed`、`Test 1`、`WF_xxx`、`🎉投喂`）。
3. **名称为空**的才显示「自动化 N」。
4. 点开详情 ⇒ 副标题应是「序号 N · 内容版本 vN」，**不应**出现 `WF_` / `Daily` / `Test 1` 这类内部标识。
5. **预期**：你起的名字就是页面上显示的名字。

### F-4 定时 Workflow 加入快捷操作并手动运行（P1-4 / P1-5 / 固件 P0-2）

1. 「自动化」页切到 **定时** Tab ⇒ 选一条定时流程 ⇒「加入快捷操作」。
2. 回首页「快捷操作」⇒ 应能看到它（名称后带「（定时）」提示）。
3. **修改**这条自动化的**名称** ⇒ 刷新页面 ⇒ **快捷操作里的它不应消失**。
4. 点它 ⇒ 弹层里应**列出这次会碰到的米家设备** ⇒ 确认。
5. **预期**：改名不丢快捷操作；定时流程可以手动跑。
   > 若该流程含米家动作，**固件**会在第一步之前做整份预检：设备未启用/不在线 ⇒ 整份不执行并给出原因。
   > 这里若涉及出粮/通电，请**由你本人**在设备旁执行。

### F-5 米家设备启用状态与配置持久化（对应 D-3）

1. 设备页「Config」⇒ 找到「米家喂食器启用」「米家智能插座启用」。
2. 把 **米家喂食器** 关掉 ⇒ 保存 ⇒ **控制页**应显示该设备"已停用"（不是"未查询"）。

4. **重启设备**（设备页的「重启」按钮）⇒ 等设备重新上线 ⇒ 再看控制页，启用状态应与重启前一致。
5. **预期**：启用状态**不是**"读状态"推出来的，而是**真实配置**；重启后不丢。
   > 自动化已经替你验证过一轮（写 false→读 false→写回 true→重启后仍是 true）。
