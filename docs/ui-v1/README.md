## 一句话结论

功能级真机缺口只剩 `stepper` / `vibration`，与 UI 无耦合；
但**命令通路有两个硬缺口**必须先补，否则控制界面无法诚实反馈：
**① `cloud_api` 无鉴权**、**② 没有任何端点能读到设备回帧**。

## 待裁决（进入实施前必须回答）

1. **会话吊销**：加 `ui_session` 表（推荐）还是只缩短 TTL？
2. **写入口的 D1 故障策略**：fail-closed（拒绝，推荐）还是 fail-open？
3. **限流阈值**：采用建议值（命令 20/min、危险 6/min、读 120/min）还是另定？
4. **审计保留期**：90 天（推荐）/ 永久 / 其它？
5. **参数元数据来源**：接受"云端元数据目录 + 漂移检测"（推荐，不改固件），
   还是要求固件新增 `query_action_schema`（需改固件，本轮禁止）？
6. **页面划分**：日志与审计合并为一页两个 tab（推荐）、Workflow 三级（列表/详情/编辑）是否认可？
7. **`Unknown` 交互**：危险操作在结果未知时，是否接受"禁止自动重发、必须人工确认"？

## 三个最容易踩的坑（提前写下来）

1. **`message` 字段 100% NULL** —— 现有看板的日志"消息"列本来就是空的，
   不是加载失败。要可读必须先解码 `payload`。
2. **`registry` 只给"名字↔数字"，不给参数** —— 编辑器**不能**从设备推导表单，
   约束（如 `0 < gram ≤ 300`）只存在于固件描述符的自由文本里。
3. **"30 秒内重复 cmd_id"的表现是"完全没回应"** —— 与设备离线无法区分；
   所以重试策略必须靠"复用同一 id + 人判断"，不能靠"再发一次试试"。
