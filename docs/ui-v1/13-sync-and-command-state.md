# 命令状态、在线时长与能力同步

> 日期：2026-10-23 · 对应需求 §3.8 / §3.3 / §3.9
> 前置事实：`10-technical-contract.md` §2（cmd_id）、§3（Registry 字段与四类数据）
> 命令九态的完整定义在 `05-command-lifecycle.md`；本文件负责**用户可见的四态映射、保留策略、同步算法**。

## 1. 在线时长（§3.3）

### 1.1 数据源的真相（必读）

| 想要的 | 有没有 | 说明 |
|---|---|---|
| 设备真实开机时长（uptime） | ❌ **没有现成字段** | `LogRecord` 里有 `uptime_ms`，但埋在 `payload` 的 base64 CBOR 里，且只有产生日志时才有 |
| 本次 MQTT 连接建立时间 | △ **可推算** | 最近一条 `device_event(type='online')` 的时间 |
| 最后存活时间 | ✅ | `device.last_seen` |

⇒ **UI 上必须叫「在线时长」= 自最近一次上线至今，不能叫「运行时长/开机时长」**。
两者的差异在重启后立刻显现：设备重启 3 次，连接时长会归零，开机时长不会。

### 1.2 presence 的三个态（必须正确渲染）

`presence.js` 的派生态：

| 派生 | 含义 | UI 显示 |
|---|---|---|
| `online=true, stale=false` | 有新鲜存活证据 | ● 在线 · `<时长>` |
| `online=true, stale=true` | 最新事件不是 offline，但 `last_seen` 已老化 | ◐ 在线（数据可能滞后）· `<时长>` + 文案「最近无上行」 |
| `online=false` | 最新事件是 offline 且不早于 `last_seen` | ○ 离线 · **最后在线 `<相对时间>`** |

★ **`stale=true` 不得显示成"离线"**（长连接 + 无周期上行是正常态，MEMORY 有实测记录）；
★ **`online=false` 时禁止继续递增时长**，只显示"最后在线 X 前"。

### 1.3 格式规则

| 时长 | 格式 | 例 |
|---|---|---|
| < 60 s | `N 秒` | `42 秒` |
| < 60 min | `M 分钟 S 秒` | `4 分钟 12 秒` |
| < 24 h | `H 小时 M 分钟 S 秒` | `3 小时 4 分钟 12 秒` |
| ≥ 24 h | `D 天 H 小时 M 分钟 S 秒` | `3 天 4 小时 12 分钟 8 秒` |
| ≥ 365 天 | `D 天`（其余省略） | `400 天` |

- **单位取 0 值省略中间项**：`3 天 0 小时 12 分钟` → `3 天 12 分钟`（不要出现 "0 小时"）
- **分钟以上只在最后一个非零单位带秒**，但需求明确要"天 + 时 + 分 + 秒"同显 ⇒ **保留秒**，仅省略 0 项
- 数字用 `tabular-nums`，避免每秒跳动时宽度抖动
- 刷新：**每 1 s 本地递增**（不用轮询服务端），每 30 s 与服务端 `presence` 对齐一次
- 上限保护：若 `now < onlineAt`（时钟偏差/时区问题）⇒ 显示 `--`，不显示负数

### 1.4 数据获取

- 现有 `snapshot` 返回 `device`（含 `state`/`last_seen`）+ `event_recent`
- **缺口**：`snapshot` 不自带 `onlineAt`（最近 online 事件时间）⇒ 要么从 `event_recent` 里挑最新 `online`，
  要么阶段 2 在 snapshot 里加 `presence: {online, stale, online_at}` 字段（**拟议，成本极低**）

## 2. 命令状态（§3.8）

### 2.1 九个底层态 → 四个用户态

| 用户态 | 底层态（`05` 定义的九态） | 颜色 | 文案示例 |
|---|---|---|---|
| **进行中** | `REQUESTING` / `PUBLISHED` / `ACKED` / `ACCEPTED` / `RUNNING` | 蓝 | 「已下发，等待设备」／「设备已受理，执行中」 |
| **成功** | `DONE` | 绿 | 「已完成 · 用时 45.4 s」 |
| **失败** | `FAILED` / `REJECTED` | 红 | 「设备拒绝：registry 版本不匹配」 |
| **Unknown** | `TIMEOUT` / `SUPERSEDED` / `UNPARSEABLE` | 橙 | 「结果未知 · 请核实设备状态」 |

★ **`ACCEPTED` / `RUNNING` 绝不能显示为"成功"** —— 这是本项目已踩过的坑（`accepted` 只是"已受理"）。

### 2.2 每条命令显示什么

```
[图标] 开阀                          进行中 · 已下发，等待设备
       14:32:05 · cmd_id a7f3...        [详情 ›]
```

| 字段 | 位置 | 说明 |
|---|---|---|
| 用户可读名称 | 主行 | 「开阀」而不是 `VALVE_OPEN` |
| 当前状态 | 主行右 | 上面四态 + 一句人话 |
| 发起时间 | 副行 | 本地时间，秒级 |
| 设备反馈/失败原因 | 副行或详情 | `e=3 s=4 "registry version mismatch"` → 翻译成中文 |
| `cmd_id` | **只在详情面板** | 需求明确"不必始终占据主界面" |

### 2.3 保留策略（明确数字，不允许"无限占屏"）

| 位置 | 显示 | 规则 |
|---|---|---|
| 首页 | 最多 **1 条**「当前进行中」条 | 无进行中则不显示 |
| 控制页 | 最近 **5 条** | 终态且超 **5 分钟**的自动折叠进「更早」 |
| 命令详情页 | 单条完整（含九态时间轴、原始帧） | 常驻，可分享 `cmd_id` |
| 操作审计页 | **全部** | 保留 **90 天**（可配置，属待裁决项） |

- **进行中的命令永不折叠**，即使超过 5 分钟（说明设备可能掉线，更要看见）
- 超过 `COMMAND_MAX_AGE`（建议 10 分钟）仍未终态 ⇒ 自动转 `Unknown` 并标注"设备未回执"

### 2.4 页面刷新后的恢复

| 场景 | 恢复方式 |
|---|---|
| 刷新时仍有未终态命令 | 从**服务端**按 `cmd_id` 查（需 P0-C 端点）；本地 `sessionStorage` 只存"我在等哪些 cmd_id" |
| 服务端查不到（端点未上线/超时） | 显示「状态未知（未能查询）」→ **不得显示为"命令不存在"** |
| 组件卸载 / 切页 / 轮询失败 | **不影响**服务端记录；UI 恢复时重新拉取 |
| 前端本地列表丢失 | 从审计页按时间倒序重建最近 5 条 |

★ **硬规则**：历史记录的唯一真相在服务端。前端数组**不是**权威，
不能因为"我没收到"就判命令失败。

### 2.5 危险操作的 Unknown 处置

| 操作类型 | Unknown 后允许 |
|---|---|
| 读类（查询/同步） | ✅ 自动重试（幂等） |
| 幂等写（关阀、停止、急停） | ✅ 允许重试（安全方向） |
| **非幂等写（开阀、出粮、振动启动、强制重启）** | ❌ **禁止自动重发**，必须人工"核实状态 → 再决定" |

## 3. 能力同步（§3.9）

### 3.1 四类数据，四套策略（不要一个 TTL）

| # | 数据 | 版本依据 | 缓存位置 | 失效条件 | 拉取成本 |
|---|---|---|---|---|---|
| **D1** | 静态参数元数据（名称/单位/范围/默认值） | 云端 `meta_version` | 服务端 + 前端内存 | 应用发版 | 0（随包） |
| **D2** | 设备能力映射（stable_id ↔ runtime_id） | 设备 `registry.version` + `checksum` | 前端内存 + `sessionStorage` | version/checksum 变；boot_seq 变 | 1 次命令 |
| **D3** | Workflow 内容 | `workflow.sync_info` 的 `registry_version` + `checksum` + `dirty` | 前端内存 | 上述三者任一变化 | 1 次轻量 + 按需 get |
| **D4** | 设备当前配置值 | **无版本** | **不缓存**（每次进详情页读） | 任何 `config_set/save` | 每次 1 次命令 |

### 3.2 八个触发时机 → 各自要做什么

| # | 时机 | D1 | D2 | D3 | D4 | 说明 |
|---|---|---|---|---|---|---|
| 1 | 应用首次打开 | 随包 | 拉 | `sync_info` | 进入页面时 | 见 §3.3 |
| 2 | 登录成功 | — | 后台拉 | 后台 `sync_info` | — | 不阻塞登录 |
| 3 | 页面回前台（`visibilitychange`） | — | **不拉**（用缓存，见 §3.3） | 不拉 | 若在详情页则重读 | 节流 ≥30 s |
| 4 | 设备重新上线（presence `online`） | — | **拉**（可能换了固件/配置） | `sync_info` | — | 上线 = 最可信的"变了"信号 |
| 5 | 版本不匹配（收到 `e=3 s=4`） | — | **强制重拉一次** | — | — | 只重拉一次，防抖环 |
| 6 | Workflow 保存成功 | — | **必须重拉**（`v` 会 +1） | 重拉 | — | `workflow.save` 已返回新 `registry_version` |
| 7 | Config 修改并保存 | — | **必须重拉**（`enable` 切换会改 registry） | — | 重读 | `config_save` 后设备会重启 |
| 8 | 设备重启（boot_seq 变） | — | 拉 | `sync_info` | 重读 | ⚠ **boot_seq 尚不存在**，见 §3.5 |

### 3.3 首次打开的算法（避免"每次开页面都发一堆命令"）

```
1. 读本地缓存 { registry:{version,checksum,entries}, workflows:{version,checksum,list}, savedAt }
2. 若缓存 < 12h 且 有 device.last_seen 变化不大：
     → 直接渲染（标记"缓存"）
     → 后台发 1 条 query_action_registry + 1 条 workflow.sync_info 做比对
     → 版本/checksum 变了 ⇒ 静默替换 + 轻提示"能力已更新"
3. 若缓存缺失/过期/无缓存：
     → 阻塞式：先 registry → 再 sync_info（→ 不一致再 list）
     → 期间控制页按钮显示骨架屏，不可点
4. 任何一步超时（>8s）：
     → 显示「暂无法同步设备能力」+「重试」+「以缓存只读展示」
     → ★ 只读模式：允许看数据，**禁止**发起控制命令
```

**为什么首次不无条件全拉**：一次 registry + 一次 sync_info 已经 2 条消息；
再叠加 config_query（每模块 2 帧）× 10 = 20+ 帧，会把日志通道的 2 条/秒上限挤爆（见 MEMORY 的放大铁律）。

### 3.4 版本不匹配的自动恢复（只做一次）

```
收到 result: e=3 s=4 "... registry version mismatch"
  → 判定：本地 D2 过期
  → 拉一次 registry（新 version）
  → 用新 stable_id 重新组帧，提示用户"已更新能力，请重试"
  → 若第二次仍 mismatch：停止自动重试，显示「设备能力与云端不一致，请检查固件」
    + 提供「重新同步」按钮（人工）
```

★ 防抖：同一 `cmd_id` 只自动重试 **1 次**；两次失败后进入人工态。

### 3.5 缺口：没有 `boot_seq`

需求要求"设备启动标识变化时失效"。现状：

| 候选 | 有吗 | 可否用作 boot 标识 |
|---|---|---|
| registry `version` | ✅ | ❌ 重启不变 |
| registry `checksum` | ✅ | ❌ 重启不变 |
| `mqtt.last_connect_time` | ✅（State 键） | △ 语义像，但不是 boot 唯一标识 |
| `log_history.boot_seq` | ✅（设备侧有） | ❌ 云端要解码 payload 才有，且靠日志 |
| **`boot_seq` 状态键** | ❌ | **需新增**（`11` §4.4 的 F-6/F-7） |

**在 `boot_seq` 存在前**：用「presence 的 online 事件 + `mqtt.last_connect_time` 变化」**近似**判定重启，
并在 UI 上把这种判定标为**推断**（不用于安全结论，只用于触发刷新）。

### 3.6 同步中 / 同步失败的用户可见状态（原型必须有）

| 状态 | 控件 | 行为 |
|---|---|---|
| 同步中 | 控制页顶部黄条「正在同步设备能力…」+ 按钮 `disabled` | 阻止不兼容操作（需求原文） |
| 同步成功 | 黄条消失，若能力有变化则 toast「已更新：新增 2 个操作」 | |
| 同步失败 | 红条「无法同步（超时）」+ 重试 + **只读模式** | 禁止一切控制命令 |
| 版本冲突（两次 mismatch） | 红条 + 「查看详情」→ 显示本地 v 与设备 v | 提供人工重同步 |

★ **绝不允许**"同步失败后继续用旧数据发命令" —— 这是需求明写的红线。
