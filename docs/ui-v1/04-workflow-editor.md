# Workflow 编辑器设计

> 前置结论（先说清能力边界，再谈界面）：
> **当前 Registry 不足以生成参数表单。** 详见 §2。
> 因此编辑器采用 **"云端参数元数据目录 + 严格校验 + 未知即禁用"** 的路线，
> 并且**不发明任何固件不支持的字段**。

---

## 1. 入口与操作可实施性

| 操作 | 现有协议 | 可实施 | 说明 |
|---|---|---|---|
| 列表 | `workflow.list` / `query_workflows` | ✅ | 含 `state` / `current_step` / `step_count` |
| 详情 | `workflow.get p.id` | ✅ | 返回完整定义（`id/name/enable/timeout_ms/steps[]`） |
| 创建 | `workflow.create p.workflow` | ✅ | `k` 由设备分配；`variant` 由设备产生 |
| 编辑 | `workflow.set p.id + p.workflow` | ✅ | **整份替换**；`variant+1`、`dirty=true`、**registry v+1** |
| 复制 | `get` → 改 `id` → `create` | ✅（组合） | **无原生复制接口**，标"组合实现" |
| 删除 | `workflow.delete p.id` | ✅ | **只置 `valid=false`**，需在 UI 说明"不是物理删除" |
| 保存 | `workflow.save p{}` | ✅ | **会重启设备（约 40 s）** |
| 运行 | `{"c":"workflow","v":<registry>, "k":<slot>}` | ✅ | **内部跳过第 0 步** |
| 中断 | —— | ❌ | **MQTT 侧无 stop 命令**（G-5）。只能等 `timeout_ms` 超时 |
| 重命名 | `set` 改 `name` | ✅ | 无独立接口 |
| 排序 | `set` 重写 `steps[]` | ✅（组合） | **无 `reorder` 接口** |

**硬限制（来自固件常量）**：`WORKFLOW_MAX_STEP = 16`、`WORKFLOW_MAX_PARAM = 8`、
`WORKFLOW_MAX_COUNT = 16`（全设备最多 16 个流程）。

## 2. ★ Registry 元数据缺口（本轮最重要的结论之一）

### 2.1 现状：只有"名字 ↔ 数字"

| 来源 | 返回 | 有参数吗 |
|---|---|---|
| `{"c":"registry","k":0}` | `{v, n, d:[["0","COMPUTER_RESET"], …]}` | **没有** |
| `query_capabilities` | `{action:{version,checksum,count,entries:[{stable_id,runtime_id}]}, …}` | **没有** |
| `query_actions` | id/名字 | **没有** |

结论：**云端无法从设备得知"这个 Action 有几个参数、什么类型、什么范围"。**

### 2.2 固件内部其实是有的，但没暴露

```c
// workflow.h:157
struct WorkflowParam {
    const char *name;         // "gram"
    WorkflowParamType type;   // PARAM_INT / FLOAT / BOOL / STRING
    const char *unit;         // "克"
    const char *description;  // "重量减少目标（克），合法范围 0 < gram <= 300"
};
```

- **有**：名字、类型（4 种）、单位、自由文本描述
- **没有**：`min` / `max` / `default` / `required` / `enum 取值` / 是否危险
- 约束只存在于**描述字符串里**，靠人读

### 2.3 三条可选路线（本轮只采用 B，其余列为待裁决）

| 路线 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 固件新增命令暴露 schema**（如 `query_action_schema`） | 真·单一事实源 | 需改固件 + 冻结契约评审 + 重新烧录；且 `min/max` 目前固件里**也没有**，要先给描述符加字段 | **长期正解，本轮不可做**（禁止改固件） |
| **B. 云端元数据目录（版本化）** | 手写一份 `action-catalog.json`：中文名/分组/参数 schema/风险级别/验证状态；带 `catalog_version` 与 `fw_compat` 范围 | 会与固件漂移，需人工维护 + 漂移检测 | **本轮采用** |
| **C. 从名字猜参数** | 按 `STEPPER_ROTATE_STEPS` 猜出 `pulses` | 高概率出错 | **明令禁止** |

### 2.4 目录长什么样（拟议结构）

```jsonc
{
  "catalog_version": 1,
  "fw_compat": { "app_min": "0.7", "note": "对应固件描述符 2026-10-23" },
  "actions": {
    "STEPPER_ROTATE_STEPS": {
      "label": "步进指定脉冲旋转",
      "group": "dispense",
      "risk": "medium",              // low | medium | high
      "hw_verified": false,           // 真机是否验证过
      "params": [
        { "name": "pulses", "type": "int", "unit": "step",
          "required": true, "min": 1, "max": null,
          "help": "1 ~ max_pulses（上限由设备 pulse 计划决定）" },
        { "name": "direction", "type": "enum", "values": [0, 1],
          "labels": ["出粮方向", "反向"], "required": true, "default": 0 }
      ]
    },
    "VALVE_OPEN": { "label": "电磁阀开", "group": "water", "risk": "high",
                    "hw_verified": true, "params": [] }
  },
  "triggers": { "weight_decrease": { "params": [ { "name": "gram", "type": "float",
      "unit": "克", "required": true, "gt": 0, "lte": 300, "default": 21 } ] } }
}
```

★ 目录里的每个 `min/max` 都必须**能在固件描述符的 `description` 里找到出处**
（例：`"0 < gram <= 300"`），并在目录里用 `source` 字段记原文，便于复核。

## 3. 列表页

```
┌───────────────────────────────┐
│ Workflow                 [+ 新建] │
├───────────────────────────────┤
│ 开阀-减重21g-关阀         slot 3 │
│ ● 空闲 · 4 步 · 已启用           │
│                    [运行] [详情] │
├───────────────────────────────┤
│ 每日开阀测试              slot 0 │
│ ● 空闲 · 4 步 · 已启用           │
│                    [运行] [详情] │
└───────────────────────────────┘
```

- 状态色：`IDLE` 灰、`RUNNING` 绿（带进度 `第 2/4 步`）、`TIMEOUT` 橙、`ERROR` 红、`WAITING` 蓝
- `RUNNING` 时 **`运行` 按钮禁用**（设备会返回 `e=10`，因为 `state==RUNNING` 被拒）
- `TIMEOUT` 时给"上次超时结束"的副标题（**否则会误以为还在跑**）
- 卡片左滑（移动端）/ 右侧菜单（桌面）：复制、删除

## 5. 添加步骤：选择器

**两级**（先类别，再动作），类别来自元数据目录的 `group`：

| 分组（拟议） | 含 |
|---|---|
| 供水 | `VALVE_OPEN` / `VALVE_CLOSE` |
| 称重 | `WEIGHT_ZERO` + Trigger `weight_decrease` |
| 出粮 | `STEPPER_DISPENSE_ROTATE` / `STEPPER_ROTATE_STEPS` / `STEPPER_EMERGENCY_STOP` |
| 振动 | `VIBRATION_START` / `VIBRATION_STOP` |
| 时序 | Trigger `delay` / `timer` |
| 环境 | `MI_THERMO_START_SCAN` / `MI_THERMO_STOP_SCAN` |
| 排障（默认折叠） | `MQTT_TEST` / `TEST_STEPPER_START` / `TEST_STEPPER_STOP` / `COMPUTER_RESET` |

选择器行为：
- 只列出**当前 registry 里存在**的项；目录里有但 registry 没有 ⇒ 灰显 + "设备未注册（模块可能被禁用）"
- registry 有但目录没有 ⇒ 灰显 + "本版 App 未支持"
- 已被 `WORKFLOW_MAX_STEP(16)` 限满 ⇒ 添加按钮禁用并说明

## 6. 步骤卡片

### 6.1 有参数

```
┌────────────────────────────────────┐
│ ③  重量减少                     ⋮  │
│    目标 [ 21 ] 克                   │
│    合法范围 0 < gram ≤ 300          │
└────────────────────────────────────┘
```

### 6.2 无参数（必须简洁，不占屏）

```
┌────────────────────────────────────┐
│ ②  电磁阀开                     ⋮  │
└────────────────────────────────────┘
```
一行搞定；**不显示空表单**、不显示"0 个参数"。
（注意：固件里 `stepper_no_params` 有一个占位 `_unused`，但 `param_count=0` ⇒
渲染必须按 `param_count`，**不能按数组长度**，否则会出现一个莫名其妙的 `_unused` 输入框）

### 6.3 第 0 步的语义标记

第 0 步卡片右上角常驻灰标 **"运行时不执行"**，并在页脚说明：
「设备执行 Workflow 时会从第 2 步开始；第 1 步仅在设备串口手动启动时执行。」

## 7. 参数表单规则

| 类型 | 控件 | 校验 | 非法提示 |
|---|---|---|---|
| `int` | 数字输入（`inputmode=numeric`）+ 可选步进 | 必须是整数；`min`/`max`（目录给的）；`pulses` 额外提示"上限由设备决定" | 就地红字："必须是 1 以上的整数" |
| `float` | 数字输入（`inputmode=decimal`） | `gt`/`lte`；**重量类强制 `0 < x <= 300`** | "必须大于 0 且不超过 300 克" |
| `enum` | 分段控件（不是下拉，2 个值时） | 值必须在枚举内 | 不可达（控件保证） |
| `bool` | 开关 | — | — |
| `string` | 文本框 | 长度；`timer.type` 用分段控件（once/daily/weekly） | 按类型给具体提示 |

**必填**：目录里 `required: true` 的项为空 ⇒ **保存按钮禁用**，并在字段下说明"必填"。

**默认值**：`weight_decrease.gram` 默认 21（与当前生产流程一致）；
`TEST_STEPPER_START.hz` 默认 100、`direction` 默认 0；
其余无默认 ⇒ 必须由用户填，**不预填猜测值**。

**★ 最重要的提示**：`gram` 非法时固件**不报错，而是静默回落到 20 g**。
⇒ 表单必须在校验失败时**阻止下发**，并在 help 里写明这条行为，
否则用户会以为"我设的 300"。

## 8. 排序

### 8.1 桌面 / 触屏

长按卡片出现拖拽柄 → 拖动 → 松手落位；拖动时显示插入位置指示线。

### 8.2 移动端替代（必须有，不能只依赖拖拽）

每张卡片的 `⋮` 菜单里提供 **上移 / 下移 / 删除 / 在此下方插入**。
理由：拖拽在长列表 + 小屏 + 系统手势边缘容易误触发；且**可访问性**上必须有非拖拽路径。

### 8.3 顺序的语义

**顺序 = 执行顺序**。固件没有依赖声明，也没有并行。
⇒ UI 不能暗示"可以并行"，也不能自动排序（例如按类型分组）。

---

## 9. 删除 / 编辑 / 撤销

| 操作 | 行为 |
|---|---|
| 删除步骤 | 立即从草稿移除，**不立即下发**；顶部出现"已删除 1 步 [撤销]" |
| 撤销 | 5 分钟内可撤销最近一次结构改动（本地栈，最多 20 步） |
| 编辑参数 | 就地编辑；失焦即校验 |
| 取消整个编辑 | 有改动 ⇒ 二次确认（"放弃 N 处改动？"） |
| 设备态保护 | **编辑器全程只改本地草稿**，只有"保存到设备"才发 `set` |

★ 这一条是为解决 **G-6**（无草稿概念）：如果不做本地草稿，
用户一次误删就写进了设备内存（虽然还没 `save` 落盘，但 `set` 已经改了运行态）。

## 10. 保存流程（两阶段 + 重启提示）

```
[保存到设备]
   ↓
① 本地校验（必填/范围/步骤数/未知 Action）
   ↓ 失败 → 就地标红，不发送
   ↓ 通过
② 二次确认弹窗：写明后果
   「将写入 slot 3 并重启设备（约 40 秒）。
     重启期间无法控制设备，正在运行的流程会被中断。」
   ↓
③ workflow.set  → 等回帧（s=0，含 variant / dirty）
   ↓ 失败（e≠0）→ 显示设备原文 m/e
   ↓ 成功
④ workflow.save → 设备重启
   ↓
⑤ 页面进入「设备重启中」：倒计时 + 自动轮询 snapshot
   ↓ 恢复在线
⑥ 重新拉 registry（v 可能 +1）→ 刷新页面数据 → 顶部"已保存"
```

**保存失败处理**：

| 失败点 | 表现 | 处理 |
|---|---|---|
| `set` 返回 `e≠0` | 显示 `m` 原文 + 错误码中文解释 | 保留草稿，允许重试 |
| `set` 成功但 `save` 超时 | **结果未知**（可能已落盘） | **禁止自动重发**；提示"请刷新确认真实状态" |
| `save` 后设备未在 90 s 内上线 | 显示"设备未恢复"，给"重试查询 / 现场检查" | 不自动重发 `save`（会导致二次重启） |

## 11. 失效与不匹配的提示（三类必须区分）

| 情况 | 判定依据 | 提示 |
|---|---|---|
| **设备未注册该 Action** | 名字不在 registry | 卡片标红"设备未注册"，运行按钮禁用；说明"可能是对应模块被 `enable=false`" |
| **本版 App 不支持** | 名字在 registry、不在元数据目录 | 卡片标灰"未知能力"，**只读展示、不可编辑参数**、禁止保存 |
| **registry 版本与草稿不一致** | 打开时 `v` ≠ 保存时 `v` | 弹窗"设备能力已变化（v3→v4），请重新校验"，并提供"重新校验"按钮 |

★ 第三类是真实高频场景：今天 `v` 从 2→3→4 变了三次。

## 12. 风险提示（不能只看按钮文字）

### 12.1 静态风险（由元数据目录标注）

- `risk: high` ⇒ `VALVE_OPEN`、`STEPPER_DISPENSE_ROTATE`
- 若 Workflow 含 `VALVE_OPEN` 且**其后没有** `VALVE_CLOSE` ⇒ **红色横幅**：
  "本流程会开阀但不会关阀，只能依赖设备的 300 秒安全超时强制关闭。"
- 若含 `weight_decrease` 且前一步不是 `VALVE_OPEN` ⇒ 橙色提示：
  "减重触发器前面没有开阀，流程可能一直等待直到超时。"

### 12.2 运行时风险（保存前动态计算）

| 检测 | 依据 | 提示 |
|---|---|---|
| 最长运行时间 | `timeout_ms` vs 各步估算 | 显示"最长 360 s" |
| 与阀门安全超时的关系 | `valve.safety_timeout_sec`（1~300，**300 是硬上限**） | 若 `timeout_ms > 300 s` 且含开阀 ⇒ "阀门会在 300 s 被强制关闭，流程随后会继续等待" |
| 重复执行 | 同一 Workflow 连续两次运行 | 提示"上次运行在 xx 前结束（状态 xxx）" |
| 可能持续放水 | 含 `VALVE_OPEN` 且 `timeout_ms` > 60 s | 黄条 + 运行确认框里再次强调 |

### 12.3 运行确认框（危险 Workflow）

```
┌──────────────────────────────┐
│  ⚠ 运行「开阀-减重21g-关阀」    │
│                              │
│  将真实打开电磁阀，直到重量减少   │
│  21 克（上次实测约 45 秒）。    │
│                              │
│  设备安全保护：300 秒后强制关阀  │
│  无法从 App 中断本次运行        │
│                              │
│  [取消]        [我已确认，运行] │
└──────────────────────────────┘
```
**"我已确认，运行" 需要 800 ms 延迟后才能点**（防误触双指连击）。

## 13. 执行后的反馈与审计

| 阶段 | 界面 | 数据来源 |
|---|---|---|
| 已提交 | 卡片状态 → "已下发" | Worker 响应（**当前只有 `"OK"`，需改造**） |
| 设备已确认 | → "设备已确认" | `mqtt_messages` 里的 `c:"ack"` 帧（**需新端点**） |
| 执行中 | → "运行中 第 2/4 步" + 已开阀计时 | `query_workflows` 轮询（30 s） |
| 成功 | → "完成，用时 45 s" | 终态 `result` + 设备侧 `WF_FINISHED` 日志 |
| 失败 | → "失败：第 3 步触发器失败" | `e` + `m`，或 `query_workflows` 的 `state=ERROR` |
| 超时 | → "超时（360 s）" | `state=TIMEOUT` |
| 未知 | → "状态未知，请核对" | 无回帧 |

**审计写入点**：M1 建表 `command_audit`；每次运行写一条
`{cmd_id, kind:"workflow", object:"wf_valve_20g", slot:3, result_s, result_e, actor_ip_hash}`，
并允许从审计条目跳回日志页看那次运行的设备事件。

## 14. 明确"不做"的事（防止过度设计）

| 不做 | 理由 |
|---|---|
| 可视化流程图画布（节点连线） | 固件是**线性步骤数组**，没有分支/并行；画布会暗示不存在的能力 |
| 条件表达式 / 变量 | 协议没有表达式引擎 |
| 从 App 创建 Trigger 类型的第 0 步自动触发 | 只有 `event_*` 前缀的 trigger 才能被事件自动启动（`workflow_event_callback`），当前无此类 trigger |
| 批量编辑多个 Workflow | 一次 `set` 只能改一个，批量会产生多次 `dirty` 与一次重启 |
| 版本历史 / 回滚 | 设备只有 `variant` 计数，没有历史快照 |
