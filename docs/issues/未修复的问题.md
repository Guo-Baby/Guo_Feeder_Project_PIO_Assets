### 判定：`R-8` 是**真实缺陷**，优先级应从"风险登记"升格为**高优先级缺陷**

> ⚠️ **后续修正**：本节判定出自 2026-09-20 凌晨的技术评审；同日**产品侧复审后改判** ——
> 重量检测目标是**秒级控制**而非高速实时控制，HX711 10 Hz 偶降频**可接受**，
> 故 `R-8` **不作为产品缺陷处理**（`DEFERRED`）。下表作为**技术事实记录保留**，
> 但不构成待修项。

| 维度 | 结论 |
|---|---|
| 机理 | `filter_samples[5]` 与 `last_window_value` **均无时间信息**；代码显式依赖未校验前提"窗口周期 ≈ 0.5 s"（`weight.cpp:41-43`） |
| HX711 行为 | **覆盖式输出**（只保留最新转换值，无 FIFO），芯片不因 MCU 忙而暂停 ⇒ 阻塞期间数值被丢弃而非损坏 |
| 误报条件 | **窗口跨越阻塞边界** ⇒ 混合窗口（既含阻塞前样本、又含阻塞后样本） |
| **★ 危险区间（本轮新定量，非单调）** | `< 100 ms` 无害 ｜ **`100–500 ms` 最危险**（1–5 个采样周期，窗口跨界）｜ `> 500 ms` 整窗换血反而不误报 |
| **★ 后果（比原登记严重）** | 不止多写日志 —— 经 `event_push(EVENT_WEIGHT_ERROR, CRITICAL, STATE)` → `dispense_guard_event_callback` → **`valve_force_close()`**，**污染优先级第 2 位（安全功能）** ⇒ `R-3` 与 `R-8` 是同一根因的两面 |
| 是否属"Flash 写入是缺陷" | ❌ **不是**。`flash_append_batch()` / `flash_create_segment()` 的写入代价是"定长段 + 预分配 + 定偏移覆写"冻结设计的必然代价（每 31 条一次建段）。**缺陷在 Weight 侧把"处理时刻"当成"采样时刻"** |
| **★ 实际安全性（V3/V4 实测）** | 误报**不会造成危险后果**：V3 实测跳变 → `DispenseGuard` → `Valve FORCE CLOSE` 是**安全方向**（关阀）；且 **V4 实测自动恢复**（20 s 计数零增长）。⇒ 这是"**误报**"而非"**漏报**"，且**产品可接受** |

## ✅ R-8-A 修复记录（2026-09-20，Phase 1 完成）

> 完整分析 + 实施 + 验证：`docs/archive/log/R8A-HX711阻塞分析0920.md`（375 → 544 行）

### 调用链（根因）

```
loop() → weight_task() → scale.read()          weight.cpp:441（原 :406）
   → HX711::read()                              HX711.cpp:107
      → wait_ready()        ← ★ 无参版本        HX711.cpp:111
         → while(!is_ready()) delay(0);         HX711.cpp:192-199   ← 无限阻塞
```

> 库虽提供有界版本 `wait_ready_retry()`（次数上界）/ `wait_ready_timeout()`（时间上界），
> 但 **`read()` 用的是无参无限版**，且**无法通过参数让其变为有界**。
> 全项目 `scale.*` 仅 5 个调用点：`:312 is_ready()`（校准前置）/ **`:314 read()`（阻塞点①）** /
> `:373 is_ready()`（采样前置）/ **`:406 read()`（阻塞点②）** / `:663 begin()`。

### 方案 A 实施（唯一改动）

在采样分支 `read()` **之前**增加**二次 `is_ready()` 确认**：

```cpp
    if(!scale.is_ready())
    {
        if(not_ready_start == 0)
            not_ready_start = millis();

        weight_refresh_error_state();
        return;
    }

    // 成功读取新的 HX711 数据
    raw_value = scale.read();
```

**关键设计点**：该分支**刻意不发 not-ready 事件**，只做状态维护 ——
因为事件发布需要"距上次发布 ≥ `WEIGHT_NOT_READY_TIMEOUT_MS`"的节流
（由上方既有分支的 `last_not_ready_event_ms` 承担）；
若在此复制该逻辑会**引入重复计数**。下一轮 loop 即由既有分支以同一时间基准接管，
**事件时序完全不变**。

**刻意不改**：校准分支（`:312-314`）—— `is_ready()` 与 `read()` **紧邻**
（Δ 为纳秒级，无可操作空间），且是非常规路径 ⇒ 遵循最小修改不动。
