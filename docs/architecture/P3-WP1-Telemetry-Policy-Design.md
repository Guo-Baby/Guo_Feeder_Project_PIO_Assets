## 1. Telemetry Policy 唯一权威位置

### 1.1 铁律

> **降频规则只能有一套，且位于「唯一权威位置」。**
> **禁止**设备侧 / EMQX / Worker **三层同时实现**降频规则 —— 三层各写一套必然导致
> **口径漂移、难以排障、无法验证**（同一个"变化"在三层可能是三个不同的判定）。

### 1.2 三层职责（**谁定义 / 谁执行**）

| 层 | **唯一职责** | **不做什么** |
|---|---|---|
| **设备侧（★ 唯一权威位置）** | **采样决策**：决定**采样频率**、**阈值**、"**何时算变化**"、以及"**是否值得上报**" | 不做存储、不做转发过滤 |
| **EMQX** | **只执行过滤**：按数据集成规则 SQL `WHERE` 做**转发前过滤** | **不重新定义阈值语义**（只应用设备侧已定口径） |
| **Worker（ingest）** | **只负责存储**：接收 → 边界校验 → 批量写入 → 幂等 → 持久化 | **不判断"该不该存" / 不做任何业务语义判断 / 不实现降频**（见 `P3-History-D1-Plan.md` WP-4） |

### 1.3 采样决策属于哪一层（**明确回答**）

| 问题 | 答复 |
|---|---|
| **采样决策属于哪一层？** | **设备侧** —— 设备是**唯一**知道"当前读数是否真的变了"的一方（它持有原始采样与时间窗） |
| **EMQX 的定位？** | **执行过滤** —— 把设备侧已定的口径翻译成 SQL `WHERE`；**不新增语义** |
| **Worker 的定位？** | **只负责存储** —— **原样归档**；**不得**成为"第三套 telemetry policy" |

### 1.4 反模式（**明确禁止**）

| 反模式 | 后果 |
|---|---|
| 设备侧按阈值上报 **＋** EMQX 又按自己的阈值过滤 | 双重阈值 ⇒ 实际口径 = 两者交集，**不可解释** |
| Worker 内再判一次"重量变化是否有效" | **第三套 policy** ⇒ 三层不一致，且 Worker CPU 预算被业务逻辑吃掉 |
| 三层都实现"变化检测" | 排障时**无法定位**是哪一层丢的数据 |

> **⇒ 设计结论**：**唯一权威位置 = 设备侧**；EMQX / Worker **只执行、不定义**。
> （该结论与 `P3-History-D1-Plan.md` WP-1「★★ 架构约束（R2 新增）」一致。）

## 2. 历史数据分类（**全量 8 类**）

下表为 P3 需要处理的**全部历史数据类别**（与 `§7.3` 表的 6 行 + `cloud_protocol.md` §12.5 属性映射对齐）：

| # | 类别 | 典型来源 | 数据性质 |
|---|---|---|---|
| **1** | **EVENT / ERROR** | `EVENT_*` · `VALVE_ERROR` · 安全事件 | 事件驱动、低频、**高价值** |
| **2** | **Valve action** | `VALVE_OPEN` / `VALVE_CLOSE` · `0x0505` · `water/valve` | 动作驱动、中低频 |
| **3** | **Weight** | `weight.value` · `water/weight` · `water/weight-error` · `water/zero` | 连续、**高频** |
| **4** | **Water** | 水位 / 水量（**注：见下**） | 连续、高频 |
| **5** | **Temperature / Humidity** | `climate/temperature` · `climate/humidity` · `climate/battery`（Mijia `LYWSD03MMC`） | 连续、中高频 |
| **6** | **Online state** | `$state`（`§12.3`）· `system/mqtt-connected` · 连接生命周期 | 状态迁移、低频 |
| **7** | **Heartbeat** | 周期性保活/心跳 | 周期、**高频** |
| **8** | **Log** | LogManager 结构化日志批次（`§8.2` log Topic 预留） | 可抑制批量流、级别相关 |

> **★ 关于「Water」的现状说明（不得臆造）**：
> `§7.3` 列出「水位/温湿度」；但**当前 Device Model 的 `water` node 只有 `valve` / `weight` / `weight-error` / `zero`**
> （`cloud_protocol.md` §12.5）—— **没有独立的"水位"属性/sensor**。
> ⇒ 本设计**不假设存在水位传感器**；「水量」目前**由 Weight 派生**（水箱重量）。
> 若未来引入独立水位传感器，**归入本类**并按 §3.4 处理。

## 3. 逐类策略定义（5 维）

> **通用口径**：下表的**频率/行数均为「理论估算」**（非实测）；**实际消耗须由 WP-6 实测确认**（`P3-History-D1-Plan.md` WP-6）。
> 单设备目标 **< 1200 行/天**（**保留**该目标）。

### 3.1 EVENT / ERROR（故障 / 安全事件）

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是（100%）** |
| **采样频率** | **事件驱动**（非周期）；低频 |
| **降频方式** | **不做阈值降频**（本身稀疏）；**但必须做「去重 / 边沿」**（见下注） |
| **生命周期倾向** | **长**（故障诊断 / 安全追溯） |
| **成本影响** | **低**（理论 **< 100 行/天**） |

> **注（既有登记）**：`R-3` 已登记「跳变源导致 `dispense_guard` 反复强制关阀」（成对 ×2、峰值 6 次/s）⇒
> 事件类**若直接全量落库会产生风暴**。⇒ **去重 / 边沿策略**是本类的**前置设计项**（属设备侧决策层）。

### 3.2 Valve action（供水动作）

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是（100%）** |
| **采样频率** | **动作驱动**；中低频 |
| **降频方式** | **不降频**（每次开/关都是有意义的动作）；可考虑 **open/close 配对**为一条（**待定，不预设**） |
| **生命周期倾向** | **长**（供水行为追溯） |
| **成本影响** | **中低**（理论 **< 500 行/天**） |

### 3.3 Weight（重量）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（仅"有意义的变化"） |
| **采样频率** | **高频**（连续采样） |
| **降频方式** | **阈值 + 抽样**：变化 **> Xg** 才记；或**每 N 分钟**至少一条 |
| **生命周期倾向** | **短**（高频运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**）—— **强烈依赖 `X` / `N` 取值** |

> **★ `X` / `N` = `HUMAN_REQUIRED`**（见 §5 H-W1-1 / H-W1-2）。

### 3.4 Water（水位 / 水量）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（若独立水位传感器存在）；**当前无该传感器** ⇒ 由 Weight 派生，**避免重复落库** |
| **采样频率** | **高频**（若存在） |
| **降频方式** | **每 5–15 分钟一条** 或 **变化超阈值** |
| **生命周期倾向** | **短**（高频运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**，若存在）；**当前 = 0（无传感器）** |

### 3.5 Temperature / Humidity（温湿度）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（Mijia 可用时） |
| **采样频率** | **中高频**（Mijia 广播采集） |
| **降频方式** | **每 5–15 分钟一条** 或 **变化超阈值** |
| **生命周期倾向** | **短**（环境运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**） |

> 注：`climate/battery` / `scan-enabled` 属**设备元数据**而非遥测 ⇒ **默认不落库**（如需，单列）。

### 3.6 Online state（在线状态）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（**仅状态迁移时**） |
| **采样频率** | **状态驱动**；低频 |
| **降频方式** | **仅记录 `$state` 迁移点**（`init`→`ready`、disconnect、LWT `lost`）；**不记录稳态** |
| **生命周期倾向** | **中 / 长**（可用性审计） |
| **成本影响** | **低**（理论 **< 50 行/天**） |

> **★ "在线状态是否落库（persistence）" = `HUMAN_REQUIRED`**（见 §5 H-W1-4）。

> **⚠️ 重要**：P1-6 已确立「**`last_seen` 超时不再产生 `offline`，只标 `stale`**」⇒
> **不要**用"周期性 offline 事件"当作在线状态历史；**唯一可信的迁移点**是 `$state` / 连接事件。

### 3.7 Heartbeat（心跳）

| 维度 | 定义 |
|---|---|
| **是否落库** | ❌ **否**（仅内存 / 在线态） |
| **采样频率** | **高频（周期）** |
| **降频方式** | **不落库**（"降频到 0"） |
| **生命周期倾向** | **N/A**（不进入历史库） |
| **成本影响** | **0**（**这是把总量压到 < 1200 行/天的关键一项**） |

> **★ heartbeat policy = `HUMAN_REQUIRED`**（见 §5 H-W1-3）。

### 3.8 Log（日志）

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是**，**但受 `BT-1` 门禁**（`G-4` / `B-2`）；且仅 **WARN / ERROR / CRITICAL** 落设备 Flash |
| **采样频率** | **可抑制的批量流**（`§8.2`：批 ≤16 条 / 单条 ≤4096 B） |
| **降频方式** | **级别过滤**（INFO 不落 Flash）+ 设备侧**发送限流**（`LOG_TX_MIN_INTERVAL_MS`） |
| **生命周期倾向** | **长**（故障诊断）；**`payload` 须有体积上限**（`P3-History-D1-Plan.md` WP-2） |
| **成本影响** | **高**（`R-4`：修 `BT-1` 后上行升至 **2 Hz（×30）**，日志量可能远超预估） |

> **⇒ `Log` 是本设计里**唯一**"落库前必须等前置修复"的类别**（`BT-1`）。

## 4. 汇总矩阵（8 类 × 5 维）

| # | 类别 | 落库 | 采样频率 | 降频方式 | 生命周期倾向 | 理论成本（行/天） |
|---|---|---|---|---|---|---|
| 1 | **EVENT / ERROR** | ✅ 100% | 事件驱动 / 低 | 无阈值；**去重/边沿** | **长** | **< 100** |
| 2 | **Valve action** | ✅ 100% | 动作驱动 / 中低 | 不降频（或配对，待定） | **长** | **< 500** |
| 3 | **Weight** | ⚠️ 条件 | 高频 | **阈值 `X` + 抽样 `N`** | **短** | **< 300** |
| 4 | **Water** | ⚠️ 条件（当前无传感器） | 高频 | 5–15 min 或超阈值 | **短** | **< 300 / 当前 0** |
| 5 | **Temp / Humidity** | ⚠️ 条件 | 中高频 | 5–15 min 或超阈值 | **短** | **< 300** |
| 6 | **Online state** | ⚠️ 条件（仅迁移点） | 状态驱动 / 低 | 仅记录迁移点 | **中 / 长** | **< 50** |
| 7 | **Heartbeat** | ❌ 否 | 周期 / 高 | **不落库** | N/A | **0** |
| 8 | **Log** | ✅ 是（**受 `BT-1` 门禁**） | 可抑制批量流 | 级别过滤 + 限流 | **长** | **高** |

> **⇒ 目标**：单设备 **< 1200 行/天**（**保留**）。
> **⚠️ 全部数字为「理论估算」**：11 台合计与免费额度占比**只能作数量级预测**，**实际须由 WP-6 实测确认**（**不得据估算下"安全"结论**）。
