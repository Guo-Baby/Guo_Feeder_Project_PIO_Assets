## 1. 验收方法

### 1.1 触发方式（可控、可重复、无硬件副作用）

通过**生产链路**下发只读命令 `system.config_query`（查 `valve` 模块）：

```
Pages /api/command → Worker cloud_api → EMQX → 设备
```

该命令在固件中会触发 `LOG_CMD_APPLIED`（`INFO`）⇒ 产生**一条真实日志** ⇒ 设备上传 `/log` ⇒
Worker 入库并回 `log_ack` ⇒ 设备处理 ACK。整链无需喂食/出水/重启/改配置。

共两轮，命令 ID 分别为 `bt11792420492`、`bt1b1792420703`（每次全新）。

### 1.2 串口采集方式

- 端口 `COM8`，115200，**只读**（脚本不写串口）。
- 打开前先置 `dtr=False` / `rts=False`，避免 CH343 上的 DTR 跳变触发复位。
- 两轮分别捕获（不并发占用同一 COM 口），捕获期间**无任何启动横幅**（`rst:` / `ESP-ROM` / `boot=` 命中 0）⇒ **设备未被复位**。

- `floor=0` ⇒ 无空洞阻挡。

## 5. 非打印证据：设备确实"消费"了 ACK

**原理**：若设备未处理 ACK，会按 `15 s + 退避 2/4/8/16/32 s` 的**重发阶梯**继续重投同一记录
（这正是 `BT-1` 修复前的现网症状：同一 `/log` 帧重复 6 次，间隔 `17/19/23/31/47 s`）。
每次重投都会再次触发云端 ACK（云端按"键是否存在"判定，重复投递仍会回 ACK —— 历史 `ack:21:5168/5169` 各有 2 条即为此现象）。

**实测**（`14:38:30` 之后观察 2 分 40 秒，覆盖完整阶梯窗口）：

| 检查 | 结果 |
|---|---|
| `mqtt_messages` 中新增 `log_ack`（seq ≥ 5174） | **0 条** |
| `mqtt_messages` 中新增任何消息 | **0 条** |
| `log_history` 新增（seq ≥ 5176） | **0 行** |
| 串口新增 `[Cloud LOG]`（重发） | **0 次** |

⇒ 设备在收到 ACK 后**没有继续重发**，即 ACK 已被消费。**该结论不依赖打印**：
重发一旦发生，云端必然再次回 ACK 并落一条 `log_ack` 记录，而实测为 0。

> 附注：该窗口内 EMQX `recv_cnt/send_cnt` 各 +3。经核对**无任何对应云记录**（无 `mqtt_messages`、无 `log_history`、无新 ACK），
> 判定为协议层保活/确认类报文，**不是** `/log` 重发。此点不影响上述结论。
