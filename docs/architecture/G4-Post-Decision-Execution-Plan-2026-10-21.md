### 0.2 ★ 我上一轮说错了一句，先更正

我说「85% 也会因 `minimum_free` 单向恶化而**必然**触发」——**说过头了**。

`minimum_free = ESP.getMinFreeHeap()` 是**本次 boot 内**的最低水位，**重启即重置**，不是永久单调。
所以 85% 的真实含义是：**单次 boot 内峰值一旦破过 85%，该 boot 剩余时间判 FAIL，重启可复测**。

| 已实测峰值 | 85% 余量 |
|---|---|
| 空载 `77.08%` | **+7.92 pp** |
| 压力 `77.16%` | **+7.84 pp** |

**85% 可用**，但不是"随便就过"——后续加功能会真实吃掉这 8 个百分点。这正是 `90%` 备选值存在的理由。
（真正需要修的仍是**分母口径**：`internal.total`≈251 KB 与 SRAM 327 680 两个口径混用，见 §1.2。）

**为什么这个方案绕开了原来卡住的 403**：原 C-1 卡在"改鉴权需要知道 EMQX 走哪个入口"。**校验器不关心谁来调**——它只看 `topic`/`payload` 是否合法，所以**不需要读 EMQX 配置**。

**设计（带开关，一次部署、可随时翻转）**：

```
环境变量 INGEST_VALIDATION = "observe" | "enforce"     # 默认 observe

EMQX 分支（body.topic）：
  S2 校验失败 ⇒
     observe 模式：照旧写入，但 console.warn 记 {reason, topic, clientid} 并 ++counter
     enforce 模式：400 {error:"invalid_topic", reason:...} 且 **不写库**
  S2 通过 ⇒ 原逻辑不变（resolveIngestDeviceId / dedup_key / insert）

cloud_api 分支：已在用 isValidDeviceId() 强校验（400 invalid_device_id），**不动**
```

| 风险 | 评估 |
|---|---|
| 误判合法消息 ⇒ 断流 | **已量化：0 条**（S2 只命中 9 行历史垃圾） |
| EMQX 发非 `guo_feeder` 主题 | 全库 0 行先例（`n_suffix_other=9` 全是空 topic）⇒ 概率极低；且 `observe` 模式先兜底 |
