## 1. 现行 DRAM 门禁的历史定位（必须先讲清楚）

### 1.1 原文与出处

| 项 | 内容 |
|---|---|
| 出处 | `BT-1-Log-ACK-Read-Only-Investigation-and-Fix-Plan.md` **§6.2 第 11 行** |
| 原文性质 | **"建议阈值"**（措辞即如此） |
| 批准记录 | ❌ **从未有人工批准记录** |
| 因此当前状态 | **`HUMAN_REQUIRED`** —— 不是既成门禁，是待裁决的工程建议 |

### 1.2 ★ 关键事实：该阈值在本设备**从未被满足过**

| 测量 | 分母 | 分子 | 占用率 | 判定 |
|---|---|---|---|---|
| 更早一次 | — | — | **82.8%** | FAIL |
| boot 22 空载基线 | `total=251 060` | `minimum_free=57 544` | **77.08%** | FAIL |
| boot 22 压力后 | `total=251 172` | `minimum_free=57 356` | **77.16%** | FAIL |
| boot 23 空载 | `total=250 428` | `minimum_free=55 180` | **77.97%** | FAIL |

> 公式：`占用率 = (total − minimum_free) / total`（分母 = `system.memory` 的 `internal.total`，**不是** PlatformIO 报的 SRAM 总量 327 680）

**这不是"这次跑坏了"，而是"空载即超标"** ⇒ 若继续把它当硬门禁，`G-4` 将**永久卡死**，且**无法反映**真实风险变化（压力只让占用率 +0.09 pp，被 77% 的基数完全掩盖）。

### 1.3 三个口径缺陷（调查已证实）

| # | 缺陷 | 说明 |
|---|---|---|
| D-1 | **分母不统一** | `internal.total`（heap ≈ 251 KB）vs PlatformIO 构建报告 40.5% 用的 SRAM 总量 **327 680** ⇒ 同一台设备两个"占用率" |
| D-2 | **`minimum_free` 被当"峰值占用"用** | 它是**单向历史最低水位**（`esp_get_minimum_free_heap_size()`），随运行单调下降，**不是**某时刻的峰值占用；用它算"占用率"是口径错配 |
| D-3 | **阈值从未满足**（见 §1.2） | 门禁失去区分能力 |

## 5. 未来观测能力设计（6 项字段）

> 设计目标：**可观测、可解释、可测试**；不追求"看起来全面"。
> 每项给出：定义 / 单位 / 采样时机 / 生命周期 / 当前可观测性 / 测试方式。

### 5.1 `free` —— 当前剩余内部 DRAM

| 项 | 内容 |
|---|---|
| 定义 | `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`（当前空闲内部堆字节数） |
| 单位 | 字节 |
| 采样时机 | **查询时即时读取**（非缓存） |
| 生命周期 | 瞬时值，随分配/释放波动 |
| 可观测性 | ✅ **已有**：`system.memory` → `internal.free` |
| 测试方式 | 分配 N 字节后立即查询，断言 `free` 减少 ≥ N |

### 5.2 `largest_free_block` —— 最大连续空闲块

| 项 | 内容 |
|---|---|
| 定义 | `heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL)` |
| 单位 | 字节 |
| 采样时机 | 查询时即时读取 |
| 生命周期 | 瞬时值；**碎片化的直接度量** |
| 可观测性 | ✅ **已有**：`system.memory` → `internal.largest_free_block` |
| 测试方式 | 分配/释放交替若干轮后，断言该值不持续单调下降 |

> ★ 这是**比占用率更贴近失效模式**的指标：分配失败由"有没有连续块"决定，而不是"总共剩多少"。

### 5.3 `minimum_free` —— 本 boot 周期最低空闲 DRAM

| 项 | 内容 |
|---|---|
| 定义 | `esp_get_minimum_free_heap_size()` 的内部 RAM 对应量 |
| 单位 | 字节 |
| 采样时机 | 硬件自动维护（**单向**低水位） |
| 生命周期 | **每个 boot 周期重新累计**；重启清零 |
| 可观测性 | ✅ 已有：`system.memory` → `internal.minimum_free` |
| 测试方式 | 施加已知大分配，断言低水位下探到预期值；**重启后断言其回到接近 `free`** |

> ⚠️ **铁律**：① 它是**历史低水位**，不是当前值；② **不得跨 boot 比较**；③ 下降**不等于**泄漏（可能是正常的瞬时大分配）。

### 5.4 稳态内存漂移（**新增设计**）

| 项 | 内容 |
|---|---|
| 定义 | 在**无外部命令、无突发日志**的静置窗口内，`free` 的**线性回归斜率** |
| 单位 | 字节 / 30 min |
| 采样时机 | 由**云端/上位机**按固定间隔连续查询 `system.memory` 后离线计算（**固件不保存历史序列**，避免新增静态内存） |
| 生命周期 | 每个采样窗口独立计算 |
| 可观测性 | ❌ **当前不可用**（需采集流程，非固件改动即可实现） |
| 测试方式 | 静置 30 min、`free` 采样 ≥ 60 点，拟合斜率；**注入已知泄漏**验证能检出 |

> 优点：**零固件改动**即可获得；缺点：依赖采样纪律（窗口内不得改配置/执行动作）。

### 5.5 分配失败计数（**新增设计**，`H-4`）

| 项 | 内容 |
|---|---|
| 定义 | `heap_caps_malloc()` 返回 `nullptr` 的**累计次数**（分 SPIRAM / 内部 RAM 两类） |
| 单位 | 次 |
| 采样时机 | 每个**显式分配调用点**失败时自增（单次 `++`，无锁或用原子） |
| 生命周期 | 本 boot 周期累计；重启清零。**只读，不提供清零命令** |
| 可观测性 | ❌ **需新增代码 + 烧录** |
| 测试方式 | 宿主机单测：注入分配失败，断言计数自增且不影响控制流 |

### 5.6 `loopTask` 栈高水位（**新增设计**，`H-5`）

| 项 | 内容 |
|---|---|
| 定义 | `uxTaskGetStackHighWaterMark(NULL)` —— `loopTask`（栈 16 KB）的剩余栈最小值 |
| 单位 | 字节 |
| 采样时机 | 查询时即时读取（也可周期记录最小值） |
| 生命周期 | 任务生命周期内单向下降 |
| 可观测性 | ❌ **当前无出口**：仓库内 3 处 `uxTaskGetStackHighWaterMark` 仅打在**串口日志**（`workflow.create` / `CapRegistry.sync`），**不经命令暴露** |
| 测试方式 | 构造已知栈深度的调用，断言 HWM 下降到预期区间 |

## 6. ★ 分配失败计数的覆盖边界（**必须明示，不得宣称全覆盖**）

> 任务书要求：先盘点现有分配调用点及可覆盖范围，
> **不得**宣称未覆盖的 `new`、第三方库或其它分配路径也已被完整监控。

### 6.1 盘点结果（`src/` 全量，已剥离注释；`2026-10-20`）

| 类别 | 数量 | 是否**可**被 H-4 计数覆盖 | 说明 |
|---|---|---|---|
| `heap_caps_malloc()` 显式调用 | **22 处 / 6 文件** | ✅ **可**（逐点包裹） | 多数**成对**：先 `MALLOC_CAP_SPIRAM`，失败回退 `MALLOC_CAP_8BIT` |
| ├ `log_manager.cpp` | 12 处 | ✅ | 含最大单笔 16 384 B（队列，DRAM 回退路径） |
| ├ `workflow.cpp` | 3 处 | ✅ | |
| ├ `capability_registry.cpp` | 2 处 | ✅ | |
| ├ `workflow_storage.cpp` | 2 处 | ✅ | |
| ├ `homie_bridge.cpp` | 2 处 | ✅ | |
| └ `config_manager.cpp` | 1 处 | ✅ | |
| `new` 运算符 | **0 处** | — | 精确匹配（`(?<!\w)new\s+\w+\s*[(\[]`）后确认为 **0**；此前"9 处"是 `newData` 等变量名误匹配，**已更正** |
| `std::vector` | 1 处 | ⚠️ 部分 | 内部走 `new`，需重载 `operator new` 才能覆盖 |
| **Arduino `String`** | **498 处 / 26 文件** | ❌ **不可** | 内部走 `malloc`/`realloc`；**不改 `String` 类或重载全局 `operator new` 就无法逐个埋点** |
| **第三方库** | — | ❌ **不可** | ArduinoJson、esp-mqtt、**mbedTLS(TLS 握手)**、BLE、LittleFS、WiFi 驱动 —— 全在库内部 |
| 任务栈 | — | ❌ 不适用 | 栈不是堆分配，走 H-5 |

### 6.2 覆盖结论（**诚实表述**）

- ✅ H-4 能覆盖：**本项目 `src/` 内的 22 处显式 `heap_caps_malloc`**（≈11–13 个逻辑分配点）——这包括了**最大的几笔**（16 384 B / 4 096 B / 3 984 B / 1 024 B）。
- ❌ H-4 **不能**覆盖：Arduino `String`（498 处）、第三方库（含 TLS）、`std::vector` 内部、`new`（当前为 0 处但若将来引入则默认不覆盖）。

⇒ **因此"分配失败计数 = 0"只能表述为"本项目显式分配点未失败"，**
**不得**表述为"系统无任何分配失败"，**更不得**推导为"不存在内存风险"。
若要覆盖 `String` / `new`，需**重载全局 `operator new`** 或劫持 `malloc` —— 属**更大范围改动**，本阶段**不实施**。
