## 1. 历史预算来源（Q1）

### 1.1 冻结条文原文（`P2-0-…-freeze.md` §17.2，:973–985）

| 项 | 预算 | **该行给出的依据（原文）** |
|---|---|---|
| 新增 DRAM 静态数组 | 0 B | 「铁律；所有表 `const` → Flash」 |
| Flash `.rodata`（Device Model 表 + 字符串） | **+1.2 … 2.5 KB** | 「**约 20 属性**」 |
| Flash `.text`（投影 + Facade 代码） | **+3 … 6 KB** | 「**估 400–700 行**」 |

| DRAM 堆 / 栈 / CPU / MQTT | 0 / ≤512 B / <5 ms / ~21 取值/loop / ≤4096 B 不分片 | — |

### 1.2 与 §5.3 的交叉印证（同一文件、同一轮冻结）

> §5.3「存储位置与开销（FROZEN）」：**单个 property 条目 ≈ 44–52 B + 字符串常量；20 个属性 ≈ 1.2–2.0 KB Flash**。

⇒ **`.rodata` 预算是有「每属性字节数 × 属性数」推导的**（44–52 B × 20 + 字符串），不是拍脑袋。
⇒ 而 **`.text` 预算只有「行数」一个变量**，**没有任何按模块的分解**。

### 1.4 ★ 预算中**没有出现**的东西（这是缺口所在）

| 未列入预算的因素 | 后来在 P2-0 中成为 | 实际代价 |

## 3. Flash 根因（定量）

### 3.1 增量的构成（`p27on − base` = 12,548 B）

| 段族 | 字节 | 占比 |
|---|---:|---:|
| 真实代码（`.text.*`） | **8,447** | 67.3% |
| 只读字符串 / 数据表（`.rodata.*`） | 2,730 | 21.8% |
| `.eh_frame`（异常展开表，位于 `.flash.rodata`） | 580 | 4.6% |
| `.literal`（Xtensa 地址常量池） | 460 | 3.7% |
| `.gcc_except_table` | 82 | 0.7% |
| 残差（库 / 对齐 / appdesc） | 249 | 2.0% |
| **合计** | **12,548** | 100% |

> `.xt.prop` / `.xt.lit`（`.o` 内约 2 KB 松弛元数据）**全部落在 “Discarded input sections” ⇒ 不占 Flash**（无元数据泄漏型浪费）。

### 3.2 ★★ 预算超限的**唯一**根因

```
冻结假设：.text +3…6 KB（400–700 行）
实测：    .text +9,264 B（真实代码 8,447 B + .literal 460 B + 库侧 357 B）
⇒ 超出上限 6 KB 达 +3,120 B（+51%）；按行数比 = 实测算 2.9–5.1×
```

**超预算的 3,844 B 全部落在 `.text` 一侧**：
- `.rodata` 3,284 vs 预算上限 2,560（2.5 KB）⇒ 超 724 B；
- `.text` 9,264 vs 预算上限 6,144（6 KB）⇒ **超 3,120 B**。
- ⇒ `.text` 贡献了 **81%** 的缺口。

**且 `.text` 的超额不是"写得差"，而是"要写的东西比估算多"**：
- 新增模块 **3,111 行 / 2,049 SLOC** vs 假设 **400–700 行**；
- 其中 **1,891 raw（`device_model.*` 932 + `homie_projection.h` 979）属于 P2-0 新造的独立层**，**完全不在上游 250–350 行的估算对象内**。

### 3.3 「实现低效」的三条反证（为 §6 归因铺垫）

| 反证 | 证据 |
|---|---|
| **代码密度正常** | `homie_bridge.cpp`：5,887 B 代码 / 422 SLOC = **13.9 B/SLOC**（嵌入式 C++ 正常区间 10–20） |
| **符号级可完全对账** | Homie Bridge 的 5,887 B 代码 = 命名符号之和，**零未归因残差**；Device Model 1,258 B 同样可逐符号对上 |
| **无结构性浪费** | ① `.xt.prop/.xt.lit` 全被 GC；② `--gc-sections` 已启用，Homie=off 时 Homie 体确被剔除；③ `homie_projection.h` **无跨 TU 重复**（仅 `homie_bridge.cpp` include）；④ P2-2 的队列/注册表全是 **bss（DRAM）不占 Flash**；⑤ 已做过一轮 `6775bb3` 收敛（−768 B），`hp_u64_dec` 四份重复循环已合一 |

### 3.4 全局编译开关无法弥补（算术性结论）

`Δ' ≈ Δ·(1 − f)`（f = 全镜像缩减比例）⇒ 补 3,844 B 需**全镜像缩小 30.6%**。
实测 `-fno-exceptions`：全镜像 **−5.7%**（text −22,596 / rodata −50,888），在 Δ 口径只换 **−824 B**。
LTO 在本工程 **构建失败**（`undefined reference to app_main`）；`-fno-stack-protector` 经 `PLATFORMIO_BUILD_FLAGS` **实测无效**（两侧 `firmware.bin` md5 相同）。

## 5. 重新冻结建议（Q4 + Q6）

### 5.1 Q4 — 保持**全部**已验收功能 / 诊断 / 严格校验 / retained 语义 / Device Model 能力时的合理区间

| 档位 | 数值 | 推导 |
|---|---:|---|
| **Minimum** | **10.5 KiB（10,752 B）** | 现状 12,548 − 「行为不变」优化上限 2,200（低+中风险，见 `P2-6-Optimization-Feasibility-Audit.md` §9.1）= 10,348 → 取整留薄余量。**零增长余量** |
| **Recommended** | **13 KiB（13,312 B）** | Minimum + P2-7/8 增长上限 1,150 + 工程余量 ≈ **13.0 KiB**。**不要求任何 trade-off** |
| **Upper bound** | **14 KiB（14,336 B）** | **不做任何进一步优化**的现状 12,548 + 增长 1,150 + ≈8% 安全余量 |

> ⚠️ **注意**：`Minimum` 需要完成约 700–1,100 B 的中等风险重写（打磨 description 发射器 / 数值格式化特化 / `/set` 解析收敛 / 门控表并入 DM）。**若不做这些，实际下界就是 Recommended。**

| | **Option A** | **Option B（推荐）** | **Option C** |
|---|---|---|---|
| 预算 | **12 KiB（12,288 B）** | **14 KiB（14,336 B）** | **16 KiB（16,384 B）** |

| margin（含 P2-7/8 增长 1,150） | **−1,410 B（必然再超）** | **+638 B（4.5%）** | **+2,686 B（16.4%）** |
| 是否需附带优化 | ✅ **必须** ≥260 B（另建议 ~1 KB 低风险项） | ❌ 不要求（附带则余量升至 ~2.2 KB） | ❌ 不要求 |
| 风险 | **高** —— 预算仍低于实测；P2-7 后必然二次超标；且 P2-7 一旦发现小修就无路可走 | **低** —— 覆盖增长后仍有正余量；不逼迫任何 trade-off（不必关异常、不必删诊断） | **低** —— 但对**1 MB 级固件**而言 31% 余量偏松，可能掩盖后续低效实现（与本次教训反方向的漂移） |
| 生命周期 | ≈ 到 P2-7 结束（数周） | **P2 全程 + P3 初期小幅扩展** | P2 全程 + P3/P4 初期 |
| 对冻结架构/安全的影响 | 需压缩实现（可能诱使删诊断/削校验） | **无** | **无** |

**推荐 = Option B（14 KiB）。** 理由：它是**唯一一个「不需要任何 trade-off、且能吸收 P2-7/P2-8 增长」**的选项；12 KiB 会立刻复现本次事故（预算 < 实测），16 KiB 则对 2 MB app 分区而言过于宽松。

### 5.3 物理能力核对（说明"预算"完全是自设约束）

| 当前 Homie 构型 `firmware.bin` | **1,401,888 B**（**66.9%**） |

⇒ **三个选项在物理上都远未逼近任何限制。** 争议 100% 发生在**自设的 §17.2 数字**上。

## 6. 坚持旧预算（≤8,704 B）的代价（Q7）

### 6.1 必做清单（每项量化）

| # | 动作 | 可省（B） | 后果 |
|---|---|---:|---|
| ① | **删除全部 Homie 诊断**（21 个调用点 + `homie_log` 18 + `homie_log_outcome` 54 + ≈450 B 字符串） | **650** | 完全丧失可观测性；**与 §15.3 AD-15a「必须包含 `LOG_HOMIE_DESC_STALE` 哨兵」直接冲突**（冻结文本修订） |
| ② | **全工程 `-fno-exceptions`** | **824** | `bad_alloc` → `abort`；unwinding 清理路径失效；**可靠性语义变化**（全镜像 −73.5 KB） |
| ③ | **Device Model struct 重排去 padding**（56 → 44 B/项） | **192** | 触犯 `device_model.h:83`「字段顺序即冻结契约」（冻结文本修订） |
| ④ | **删除 pending 表 + 6 态结果分类** | **300–450** | 删除 **P2-4 阶段 B 已验收功能** |
| ⑤ | **删除 description fingerprint 哨兵**（AD-15a） | **150–250** | 删除已验收功能 + 冻结文本修订 |
| ⑥ | **删除 HomieGate 门控表**（`kGates` 80 + `gate_find` 50 + 调用点） | **175** | 门控语义改回隐式推断（§12.4 明令禁止"隐式推断"） |
| ⑦ | **属性 16 → 10**（回到 plan 时代规模），86 B/属性 | **516** | **削减功能面**；且**违 §5.4「一旦发布即视为 ABI」**（删 6 个已发布属性会让 UI 控件失联） |
| ⑧ | **严格数值校验降级**（`dm_parse_float_strict` 273 + `dm_range_check` 182 + `dm_parse_num_segment` 104） | **300–450** | 契约倒退（§13.2 两层校验失效） |
| ⑨ | **删除跨设备 namespace / ID 校验**（`homie_id_valid` 109 + `/set` 解析守卫） | **175** | **安全倒退**（跨设备隔离削弱） |
| ⑩ | **删除 retained `/set` 丢弃守卫**（AD-14a） | **60** | **安全倒退（§14 明令禁止）** |
| | **合计** | **3,342 – 3,742** | |
| | **12,548 − 合计** | **→ 8,806 – 9,206 B** | **仍然超标 102 – 502 B** |

### 6.2 ★ 结论：**≤8,704 B 不可达**

即使**同时**执行上述全部 10 项（含 **2 项安全倒退**、**2 项冻结文本修订**、**1 项已发布 ABI 削减**、**1 项已验收功能删除**），落到 **8.8–9.2 KB**，**仍然超过 8,704 B**。

要把剩下的 100–500 B 也挤出来，只剩两条路：
1. **再削 2–6 个属性**（86 B/个）⇒ 功能面进一步削减；
2. **动 P2-2 的冻结行为**（Transport Facade / 分片重组 / 订阅注册表 / foreign 队列，**1,716 B**）⇒ **破坏 P2-0 架构**（违反 §6.4 单向依赖、§7.1 单 client 契约、§17 的 P2-2 范围）。

⇒ **`≤8,704 B` 与「P2-0 冻结架构 + 已验收功能 + 安全语义」不可同时成立。** 这不是实现问题，是**约束集本身矛盾**。

## 7. 归因判定（Q3 + Q8）

### 7.1 逐项证据

| 候选 | 判定 | 证据 |
|---|---|---|
| **A. 实现低效** | ❌ **排除** | ① 代码密度 **13.9 B/SLOC**（正常区间）；② 符号级 **100% 对账**、零未归因残差；③ 无元数据泄漏（`.xt.prop` 全丢弃）、无跨 TU 重复、无重复 buffer；④ 属性/节点/命令数与 §12.2 冻结表**逐条一致**（16 / 4 / 6）；⑤ §12.3 排除项（Workflow / 事件 Trigger / `*_TS` / `LAST_ERROR` / `WIFI_STATE` / 设备级 `name`）**全部未被投影** —— 无"顺手多做"；⑥ 已做过一轮收敛（−768 B） |
| **B. 预算估算过低** | ✅ **主因** | `.text` 预算只有「**400–700 行**」一个变量，而实际新增 **3,111 raw / 2,049 SLOC**（**2.9–5.1×**）；差额 3,844 B 中 **81% 来自 `.text`**。且**凡是有按量推导的预算项（数据表 1.2–2.0 KB、description ≤2048 B）实测全部落在范围内** ⇒ 低估**只发生在行数口径上** |
| **C. 功能范围超过 P2-0 原定义** | ⚠️ **部分成立，但责任在 P2-0 自身** | 相对 **P2-0 冻结范围**：**未超**（16 属性 = §12.2 表；排除项全部遵守）。<br>相对 **预算所依据的上游范围**（`Cloud-APP-Platform-Plan.md` §4.2：8–10 属性、无 Device Model 层、无 Transport Facade、250–350 行）：**已超**——P2-0 新增了 **Device Model 独立层（2,844 B）+ Transport Facade/MQTT Routing（1,716 B）+ 分片重组 + 订阅注册表 + foreign 队列 + pending 结果分类 + fingerprint 哨兵**，属性数 8–10 → **16**；**但 §17.2 的行数没有随之重估** |
| **D. 预算与功能共同漂移** | ✅ **最终判定** | B 与 C 同时成立且**相互叠加**：范围在 P2-0 内被扩大（C），而行数基准仍沿用扩范围之前的上游数字（B，未重估） |

### 7.2 判定（Q8）

> ### **D. 预算与功能共同漂移**
> **`A. 实现失败` 明确排除**；`B. 预算错误` 是主因；`C. 功能范围变化` 成立但**变化由 P2-0 设计阶段自身引入**，不是实现阶段的范围蔓延。

**一句话**：**P2-0 在冻结"做什么"的同时扩大了范围，却没有同步重估"要多少字节"；实现忠实且高效地完成了扩大后的范围，于是撞上了一个按旧范围写的预算。**
