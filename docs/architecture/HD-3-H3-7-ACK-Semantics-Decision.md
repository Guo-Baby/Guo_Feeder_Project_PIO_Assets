# `H-3-7` 决策材料：冲突记录的 ACK 语义

> **状态**：`HUMAN_REQUIRED`（**本项未改任何代码**）
> **冻结边界**：ACK 协议 / HTTP 四字段响应体 / 设备端重试语义 **均未改动**
> 依据：`HD-3-A1-B3-Independent-Review.md` §6 `B3-04`；`H-3-7`（`HD-3-A1-B3-Implementation-Record.md` §7）
> 关联：`BT-1` `T02j`（响应体恰四字段）· `G-4`（`WP-5` 门禁）

---

## 1. 事实基线（不改动，仅陈述）

### 1.1 云端现状（`src/log-ack.js:651-700`）

| 判定 | 是否 ACK | 含义 |
|---|---|---|
| `same_content` | **ACK** | 键存在 + 五字段全等 ⇒ 合法重试已证 |
| `collision` | **ACK** | 键存在 + 至少一字段不等 ⇒ 候选碰撞 |
| `content_unverified` | **ACK** | 键存在但无法比较（缺列/类型异常） |
| `unpersisted` | **不 ACK** | 既未新增、也无法证明键存在（含查询失败） |

★ ACK 的唯一语义是 **"该 `(device_id, boot_seq, seq)` 在 D1 中有行"**，**不是**"该内容已被接受"。

### 1.2 设备端现状（`src/log/log_manager.cpp`）

| 机制 | 行为 |
|---|---|
| ACK 作用 | 推进 `acked_max` 水位 ⇒ 该 seq 及之前的段可被回收（GC） |
| 未 ACK | 按 `MAX_RETRY` 指数退避重投；超过门槛置 `s_cloud_gave_up`（**不阻塞主循环**） |
| 未 ACK 的代价 | ① 重投流量（每轮一次 `/log` 上行）；② 段不被回收 ⇒ 容量压力；③ 环形段最终仍会被覆盖 |
| 缓冲区满 | RAM 环满 ⇒ `ring_drop`（丢弃最旧）；Flash 环满 ⇒ 淘汰最旧段（**不等待 ACK**） |

### 1.3 关键推论

1. **冲突记录的"真实内容"在云端已经丢了**（`INSERT OR IGNORE` 保留首行）。ACK 与否都**不能**把内容找回来。
2. 不 ACK 会让设备**反复重投同一条冲突记录**，每次重投都会**再次**命中同一次比较 ⇒ `collision` 计数按重投次数**线性放大**。
3. 因此"不 ACK"唯一可能的收益是"让该记录在设备上多留一会儿"，但它**没有任何上行通道**能把内容以别的形式送出。

## 2. 三个判定分别该怎么处理（推荐方案 = `A`）

### 方案 A（**推荐**）：保持 ACK，把 `collision` 升级为**持久告警**

| 判定 | ACK | 附加动作 |
|---|---|---|
| `same_content` | 是 | 无（现状） |
| `collision` | **是**（不变） | ① 每批 `console.error` 一行（**已实现**，`B3-02` 同伴改动）；② 建议增 **持久冲突计数**（需新表 ⇒ 需 migration 授权） |
| `content_unverified` | 是 | 每批 `console.error`（**已实现**） |

**理由**：
- ACK 语义（"键有行"）本身**未被违反** —— 行确实存在，只是内容不是本条；
- 保住"有界重投 + 段可回收"，不引入缓冲区压力；
- 避免 `collision` 计数随重投放大（一次冲突 = 一次计数）；
- 冲突的本质是"设备序号分配器坏了"的**诊断信号**，而不是数据恢复问题 ⇒ 应当**告警**而不是**重试**。

**残余缺口**：`collision` 目前只落在 Worker 日志（有保留期）。一个已发生的冲突在日志过期后**不可追溯**。补法 = 新增 `log_conflict` 表（`device_id, boot_seq, seq, first_seen_at, count`）或把计数并入既有 `device_event`：

| 补法 | 需要 | 影响 |
|---|---|---|
| 新表 `log_conflict` | **migration（新文件，不改 0003）** | 零协议影响；D1 行数增长可控（仅在真碰撞时写） |
| 复用 `device_event` | 新 `event_type` 枚举 | 需确认该表语义允许 |
| 复用 `log_history` 加列 | **改 0003 ⇒ 禁止** | 不可行 |

---

### 方案 B：`collision` **不 ACK**（改为 `unpersisted` 语义）

| 项 | 评估 |
|---|---|
| 好处 | 设备不会"以为已送达"；冲突记录在设备上多留 N 轮 |
| 代价 1 | 每条冲突记录多 N 次 `/log` 上行（`MAX_RETRY` 轮），`collision` 计数 × N |
| 代价 2 | 段无法回收 ⇒ 容量压力（`LOG_SEGMENT_COUNT × 31` 条上限）；最终仍被环形覆盖 |
| 代价 3 | 设备端**没有**"另存后重发"的通道 ⇒ 多留也救不回内容 |
| 结论 | **不推荐**：成本确定、收益为零 |

### 方案 C：把 `collision` 写进 HTTP 响应体

| 项 | 评估 |
|---|---|
| 好处 | 上游（EMQX Action / Pages 中转）可直接看到 |
| 代价 | **违反 `T02j`（响应体恰四字段）** ⇒ 需修订 `BT-1` 冻结契约 + 所有消费方同步 ⇒ 属协议变更 |
| 结论 | **仅在**未来确有"上游需要区分"的需求时才考虑；当前无此需求 |

## 3. 兼容性影响

| 方案 | 协议 | 设备固件 | 云端 schema | 消费方 |
|---|---|---|---|---|
| **A（推荐）** | 不变 | **不变** | 可选新增表（需授权） | 不变 |
| B | 不变 | 重试/容量语义变化 | 不变 | 不变 |
| C | **变更**（四字段 → 五字段） | 不变 | 不变 | **需同步升级** |

## 4. 不处理的后果

1. 冲突（= 设备序号复用）只体现在 Worker 日志里，**随日志保留期过期而消失**；
2. `A-1` 若在某条路径上失效，云端**只剩一个短期窗口**能发现；
3. 最坏组合（已在独立审查 §9.3 记录）：格式化后 `ts=0` + 内容确定的启动期事件 ⇒ 判 `same_content` ⇒ ACK ⇒ **`collision` 仍为 0，完全静默**。
