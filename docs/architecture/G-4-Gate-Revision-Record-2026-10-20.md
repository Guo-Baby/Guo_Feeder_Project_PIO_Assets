## 1. 旧定义（正式 `G-4`，**继续有效**）

| 项 | 内容 |
|---|---|
| 出处 | `docs/architecture/BT-1-Acceptance-Report.md` **§6.4 / §6.5 `GATE-WP5` ②** |
| 指标 | 内部 DRAM **峰值占用率** |
| 阈值 | **< 70%** |
| 计算口径 | `峰值占用率 = (internal.total − internal.minimum_free) / internal.total`<br>`internal.total = ESP.getHeapSize()`（本设备实测 **251 060 – 251 172 B**，随 boot 小幅浮动）<br>`internal.minimum_free = ESP.getMinFreeHeap()`（分配器维护的**单调历史最低值**，不依赖采样） |
| 判定方式 | 单一绝对阈值；不区分"空载基线"与"压力增量" |

### 1.1 历史结果（**不得追溯修改**）

| 时间（UTC） | 场景 | 峰值占用 | 按旧定义 |
|---|---|---|---|
| `2026-10-19 15:31` | 方案 A（35 条突发） | `(251 xxx − 43 168)/…` = **82.8%** | `FAIL` |
| `2026-10-19 16:30` | `system.stats` 烧录后**空载基线**（boot 22，uptime 158 s） | **77.08%** | `FAIL` |
| `2026-10-19 16:50` | 四级压力后（105 条命令） | **77.16%** | `FAIL` |

> ★ **关键事实（促成修订的原因）**：**空载基线 77.08% 已远超 70%** ⇒ 该阈值在本设备**从未也不可能被满足**。
> 它测不出"压力是否造成退化"，只能恒定输出 `FAIL`。这是**判据缺陷**，不是设备缺陷。
> 但**历史结果照旧记为 `FAIL`**（§1.1 三行不改），避免"为了让门禁好看而改写历史"。

## 2. 新定义（**并行判据**，仅限「个人试运行准入」）

> 名称：**`TRIAL-DRAM` 综合内存判据**（四项**全部**满足才算通过）。
> 适用对象：`G-4` 门禁中的「内部 DRAM 峰值」一项，**且仅用于个人试运行准入评估**。

| # | 判据 | 阈值 | 理由 / 观测方式 |
|---|---|---|---|
| T-1 | **绝对内存（静置态）** | `free` 与同 boot 周期基线之差 ≤ **512 B**，且不得低于基线 − 2 KB | 反映"是否留下永久占用"；用 `system.memory.internal.free` |
| T-2 | **压力增量（峰值）** | `minimum_free` 相对同 boot 周期基线**下探 ≤ 1 024 B**（≈ `total` 的 0.41%） | 才是"突发把内存压了多少"的真实度量；用 `minimum_free` 差分 |
| T-3 | **最大连续空闲块** | `largest_free_block` **不得下降** | 碎片化的直接指标；比占用率更能反映后续分配失败风险 |
| T-4 | **恢复能力** | 静置 ≥ 5 min 后 `free` 回到 T-1 容差内，且 `minimum_free` **不再下探** | 区分"瞬时峰值"与"泄漏" |

### 2.1 与旧定义的关系（**不是替换**）

```
正式 G-4 判定  ── 仍用  < 70%（绝对阈值）→ 历史与未来均记 FAIL
个人试运行准入 ── 改用  TRIAL-DRAM（T-1…T-4）
两者并行存在；任何一方变更都必须追加本记录的新版本（不覆盖本文件）
```

> ⚠️ **`2026-10-21 03:00` 补注（不改上文）**：上面代码块第 1 行「仍用 `< 70%`」**已失效** ——
> 正式阈值经 `R-3`（§5）改为 **`< 85%`**。该代码块保留为 `2026-10-20` 时点的决策快照。
> 现行判定**只看 §5.2**。

### 2.2 新定义的固有局限（必须随结论一起引用）

- **只覆盖"同 boot 周期"**：`minimum_free` 是 per-boot 的历史最低值，**跨 boot 不可比**（本记录不解除该约束，见 `G4-M1`）。
- **只覆盖内部 RAM**：PSRAM 单独观测（本设备 PSRAM 全程逐字节未变，但新判据未设阈值）。
- **不能替代 `loop()` P99**：该项仍为 `NOT VERIFIED`，见 §3。
- **不构成"无泄漏"证明**：仅覆盖数十分钟、单一负载形态。

## 5. ★ `R-3`：正式门禁阈值改为 **85%**（`2026-10-21` 批准 · **取代 §1 的 70%**）

> **编号说明（透明起见）**：本文件原本**没有** `R-n` 编号。为满足 `2026-10-21` 任务书的引用方式，
> 现按修订次序事后编号并显式声明 —— `R-1` = §1（旧定义 `<70%`）· `R-2` = §2（`TRIAL-DRAM`，并行判据）·
> **`R-3` = 本节**。这三个编号是**本次追加的索引**，不改变任何既有正文。

### 5.1 批准与效力

| 项 | 内容 |
|---|---|
| 批准来源 | 用户书面裁决（`2026-10-21 03:00`）：**「改成 85% 这个阈值再去考虑，如果实在不行的话，我们改成 90% 也可以」** |
| 效力 | **正式 `G-4` 门禁**的「内部 DRAM 峰值占用」一项，阈值由 `< 70%` 改为 **`< 85%`** |
| 与 `R-1` 的关系 | **取代** —— 未来判定一律用 85%，不再用 70% |
| 与 `R-2` 的关系 | **并行保留** —— `TRIAL-DRAM`（T-1…T-4）仍用于个人试运行准入，不与 85% 互相替代 |
| 备选值 | `90%`（用户预留，**仅在 85% 实测不可用时另行裁决生效**，本记录**不**预先启用） |

### 5.2 固定判据（**唯一口径**）

```
DRAM occupancy % = (internal.total − minimum_free) / internal.total × 100
```

| 符号 | 定义 | 单位 / 取值 |
|---|---|---|
| `internal.total` | `ESP.getHeapSize()` —— **唯一允许的分母** | 字节；本设备实测 `250 428 – 251 172`（随 boot 浮动） |
| `minimum_free` | **本次 boot 内**观测到的最低可用 internal heap（`ESP.getMinFreeHeap()` / `internal.minimum_free`） | 字节；**per-boot 单调**，重启重置 |
| 判定 | **严格 `< 85%` ⇒ PASS；`≥ 85%` ⇒ FAIL** | — |
| 数据来源 | `system.memory` → `internal.{total,minimum_free}` | 只读命令 |

**❌ 明确禁止的分母**：`327 680`（SRAM 总量，PlatformIO 构建报告用的口径）、`internal.free`（某一时刻瞬时值，不是峰值）。
⇒ 任何"PlatformIO 说 40% / 门禁说 77%"的对照**必须先声明分母不同**，否则属假矛盾。

### 5.3 语义边界（**必须随结论一起引用**）

| 边界 | 说明 |
|---|---|
| **测量的是"单次 boot 内峰值占用"** | `minimum_free` 是 per-boot 历史最低值 ⇒ 跨 boot **不可比**；重启后重新开始测量 |
| **不可用于判断泄漏** | 只反映"掉到过多低"，不反映"是否持续下降"；泄漏看 `system.memwatch.drift.dram.slope_per_hour` |
| **不可替代 P99 / 连续块** | `loop()` P99 与 `largest_free_block` 是独立判据，85% 通过**不**代表它们通过 |
| **不覆盖 PSRAM** | 8 MB PSRAM 单独观测，本判据不设阈值 |

**数据无效即不判 PASS**：出现下列任一情况，该项记 `NOT VERIFIED`（**不得**记 `PASS`）——
`internal.total` 缺失或为 `0` · `minimum_free` 缺失 · `minimum_free > internal.total` ·
采样窗口不足 `G-4` 规定时长（§6 的 2 h + 30 min）· 配置非生产形态（`S-3-O3` 的教训）。

### 5.4 历史结果（**继续保留 `FAIL@70%`，不追溯修改**）

§1.1 三行（`82.8%` / `77.08%` / `77.16%`）**原文不动**，且**仍记 `FAIL`**——它们是在 70% 规则下的正确判定。

> **`2026-10-21` 补注（不改数、不改判）**：若把这三次测量代入 `R-3` 的 85% 阈值，
> `82.8%` 仍 `FAIL`；`77.08%` / `77.16%` 转为 `PASS`。
> ★ 这是**口径换算的说明**，**不是**重新判定，**不得**用于宣称"`G-4` 已通过"。

### 5.5 已知余量（供后续功能取舍参考）

| 基线测量 | 占用率 | 距 85% |
|---|---|---|
| boot 23 空载 | `77.97%` | **+7.03 pp** |
| boot 22 空载 | `77.08%` | +7.92 pp |
| boot 22 压力后 | `77.16%` | +7.84 pp |

> 余量约 **7 个百分点**（≈ 17 KB of `internal.total`）。后续功能（Homie 2641 行启用、`heartbeat` 周期上报、
> OLED 真实刷新）会真实吃掉这块余量 ⇒ 每次上板都应重测 `minimum_free`，不要假设余量不变。

### 5.6 `R-3` **不**做什么

- **不**解除 `G-4`：`loop()` P99 仍 `NOT VERIFIED`（需 2 h + 30 min 窗口），连续块 / 栈高水位仍未测。
- **不**解除 `WP-5`：`WP-5` 前置是 `G-4`，`G-4` 整体状态仍 `BLOCKED`。
- **不**解除 `STOP-R1`。
- **不**把 `2026-10-20` 那次 10.4 分钟的 `loop_stats` 样本当作满足未来 `G-4` 窗口的证据。
