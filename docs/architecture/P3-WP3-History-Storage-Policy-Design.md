## §5 Telemetry History Storage Policy

> **适用对象**：`telemetry_history`（`WP2:§3` 冻结 schema）。**9 类落库判定不得改**（`WP1:§4`）。

### 5.1 保存周期（retention）＋ 容量依据（**`FROZEN` = 90 天**）

| 项 | 内容 |
|---|---|
| **机制** | 按 `ts` **窗口保留**；`ts < now - W_telemetry` 的行**进入删除候选** |
| **设计期候选（历史留痕）** | 30 天 / 90 天 / 180 天 |
| **★ 冻结值（`FROZEN`）** | **`telemetry_history` retention = 90 天** |
| **粒度** | **秒**（`I-10`）；窗口以**天**为单位表达即可 |
| **裁决依据** | **`H-WP3-01` = `CLOSED` / `PASS`**（承接 `H-WP2-9`，见 §11.1） |
| **与实测的关系** | **`计划:WP-6` 容量实测用于「校验」容量假设**；若实测显著偏离，**须以新的人工裁决调整**（**不自动变更**，`P3-plan-§6:R-1`） |

> **★ 冻结说明**：**90 天**是在「**成本可控**」与「**趋势可用**（≈ 一个季度）」之间取的折中值（原为推荐基线，**已由人工裁决转为冻结值**）；它**收敛了** `WP2:§6.2`（telemetry 候选 90 天）与 `计划:WP-7`（Telemetry 偏短）之间的**方向张力**。

#### 5.1.1 ★ 容量依据（retention ↔ 容量控制的关系）

> **模型**：`稳态行数 = 设备数 × 单设备日行数(R) × 保留窗口(W)`；`稳态存储 = 稳态行数 × 单行字节(≈0.25 KB，见 §9.1)`。
> **⇒ 结论**：**在 R 与规模固定时，`W` 是唯一「线性可控」的硬杠杆** —— 调整 `W` 即**等比例**调整稳态容量。

**单设备日行数（按上限）**：`R ≤ 1200 行/天`（`I-8`；**上限估算，典型值应更低**）。

**retention × 规模 的稳态存储（telemetry，≈0.25 KB/行）**：

| 规模 | **W = 30 天** | **W = 90 天（★ 冻结值）** | **W = 180 天** |
|---|---|---|---|
| **1 台** | ≈ 9 MB | **≈ 27 MB** | ≈ 54 MB |
| **100 台** | ≈ 0.9 GB | **≈ 2.7 GB** | ≈ 5.4 GB |
| **1,000 台** | ≈ 9 GB | **≈ 27 GB** | ≈ 54 GB |
| **10,000 台** | ≈ 90 GB | **≈ 270 GB** | ≈ 540 GB |

> **⇒ 读法**：**窗口翻 3 倍（30 → 90 d）⇒ 稳态存储翻 3 倍** —— retention 与容量**严格线性**。
> **⇒ 另一面**：**不做 retention（S-A）⇒ 年增长 1.1 TB（10,000 台）** ⇒ **窗口 = 容量控制的唯一手段**。
> **⚠️ 全部数字为「理论估算」**；完整模型与口径声明见 **§9**；**实际须由 `计划:WP-6` 实测确认**。

### 5.2 删除执行形状（**概要 —— 硬规则见 §7.4**）

> **★ 关键约束（`I-9`）**：`telemetry_history` **无单列 `ts` 索引** ⇒ **全局 `DELETE ... WHERE ts < ?` 会全表扫描**。
> ⇒ **删除必须按 `device_id` 逐设备执行**，以命中 `ix_th_device_ts (device_id, ts DESC)`。

| 步骤 | 设计（**仅设计，不实现**） |
|---|---|
| **① 目标集合** | 遍历已知 `device_id`（来源 = `device` 表 / 或近期有写入的设备集合） |
| **② 单设备删除** | `DELETE FROM telemetry_history WHERE device_id = ? AND ts < ?` —— **走 `ix_th_device_ts`** |
| **③ 分批（batch）** | 单次删除**限制行数**并循环 ⇒ **不做大事务**；批大小见 `H-WP3-08`（**冻结原则，不冻结具体 batch size**） |
| **④ 确定性（deterministic）** | 谓词**只依赖 `ts` 与 `device_id`**（**不含 `rowid` / 随机 / 时间竞态**）⇒ **结果可重复** |
| **⑤ 幂等 / 可重入** | 删除谓词为纯 `ts` 谓词 ⇒ **天然幂等、可中断续跑** |
| **⑥ 不阻塞 ingest** | 删除**不在 ingest 请求路径**执行（`I-1`）—— 由**独立调度**（Cron）承担（§7） |

> **★ 硬规则全文见 §7.4**（批处理 / 禁大事务 / deterministic / 不依赖不存在索引 / 不改 WP-2 冻结索引）。

### 5.3 是否按 `device_id` 逻辑分区

| 项 | 结论 |

### 5.4 是否需要时间窗口清理

## §7 清理机制设计（**仅设计，不实现**）

### 7.1 四个候选

| # | 候选 | 形态 | 触发点 |
|---|---|---|---|
| **A** | **定期 Worker Cron 清理** | Cloudflare **Cron Triggers** → 定时 Worker → `DELETE ... WHERE device_id = ? AND ts < ?`（分批） | **时间驱动**（独立于请求路径） |
| **B** | **写入时触发清理** | `/api/ingest` 处理中**顺带**删除 | **请求驱动**（在 ingest 路径内） |
| **C** | **按设备访问时惰性清理** | 查询某设备历史时**顺手**删除其超窗行 | **读驱动** |
| **D** | **混合策略** | A（Cron 批量）**为主** + 可选补充（按写入量触发 / 按设备配额触发） | 组合 |

### 7.2 逐项评价

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A Cron** | ✅ **与 ingest 解耦**（不污染 `I-1` Worker 边界）· ✅ 可批量、可分批、可重入 · ✅ **`计划:WP-7` 已规划此手段** | ⚠️ 需要 Cron 配置（实施阶段）· ⚠️ 删除窗口有**延迟**（T+0 到 T+周期） | ✅ **推荐（主机制）** |
| **B 写入时** | 清理"及时" | ❌ **违反 `I-1`**（Worker = ingest/validation/idempotency/persist，**不含运维删除**）· ❌ 拉高 ingest 延迟 / CPU 预算 · ❌ 删除量不可预测 | ❌ **不推荐** |
| **C 惰性** | 无独立调度 | ❌ **无法约束"长期不活跃设备"**（不被访问 ⇒ 永不清理）· ❌ 与 `I-8`/容量目标**冲突** · ❌ 读路径被写操作污染 | ❌ **不推荐** |
| **D 混合** | 可兼顾及时性与解耦 | ⚠️ **复杂度 + 双触发点一致性**风险 | ⚠️ **可接受为 A 的演进**（**仅在出现明确需求时**） |

### 7.3 ★ 推荐 = **A（Cron 定期清理）为基线**，**允许演进为 D**

| 项 | 内容 |
|---|---|
| **推荐方案** | **A** —— 独立 **Cron 调度** → 定时 Worker → **逐 `device_id` 分批删除**（§7.4） |
| **不推荐方案** | **B**（污染 ingest 路径，违 `I-1`）· **C**（不约束冷设备，违容量目标） |
| **D 的定位** | **不是基线**；仅在「Cron 周期过长 ⇒ 删除滞后不可接受」或「需 per-device 配额硬顶」时**升级为 D** |
| **执行频率 / 批大小** | **候选**（如 每日 1 次 / 每小时 / 每 6 h）—— **`H-WP3-08`（冻结原则，不冻结具体 batch size）** |
| **幂等性** | 删除谓词为纯 `ts` 谓词 ⇒ **天然幂等、可重入、可中断续跑** |
| **失败处理（设计层）** | 删除失败**不得**影响 ingest / 查询；**只记日志 / 告警**（**不重试风暴**） |
| **★ 裁决（`H-WP3-03`）** | **`CLOSED` / `PASS`** —— **`scheduled cleanup job`**（= 方案 **A**） |

> **★ 与 `计划:WP-7` 一致性**：`P3-History-D1-Plan.md` WP-7 明示「**D1 无原生 TTL ⇒ 用 Cloudflare Cron Triggers 删除超期行 / 或归档**」⇒ **本推荐与计划逐条一致**。

### 7.4 ★★ D1 / SQLite 删除执行硬规则（**R2 新增 · 强制**）

> **★ 以下 5 条为删除的「硬约束」，实施阶段（`计划:WP-7`）必须遵守；违反任一条 ⇒ 删除设计作废。**

| # | 硬规则 | 依据 / 理由 |
|---|---|---|
| **D-1** | **DELETE 必须批处理（batched）** | 单次删除**限定行数**并循环（`LIMIT N` / 分批循环）⇒ 避免一次性删除海量行导致**页锁定 / 超时 / 写放大** |
| **D-2** | **不允许大事务删除（no large transactions）** | **禁止**把整窗口删除包成**单个长事务**；须分成**多个小事务**提交 ⇒ **可中断、可续跑**（配合幂等） |
| **D-3** | **删除必须 deterministic** | 谓词**只依赖 `device_id` + `ts`**（**不含** `rowid` / 随机 / `now()` 竞态 / 执行顺序依赖）⇒ **同一输入 ⇒ 同一结果**，可重复验证 |
| **D-4** | **不依赖不存在的索引（no phantom index）** | **禁止**设计依赖「单列 `ts` 索引」等**冻结索引集中不存在**的索引（`I-9`）；查询 / 删除**必须能命中实际存在的索引**（`(device_id, ts DESC)`） |
| **D-5** | **不修改 WP-2 冻结索引（no schema change）** | **不得**新增 / 删除 / 变更任何索引 —— 索引集合已随 **`G-3` 冻结**（`WP2:§5`）；**`H-WP3-10` 已裁决 = `no additional index`** ⇒ **本阶段确定不新增索引** |

> **★ D-4 的具体后果**：`telemetry_history` / `log_history` **均无单列 `ts` 索引** ⇒ **`DELETE ... WHERE ts < ?`（不带 `device_id`）会全表扫描** ⇒ **删除必须按 `device_id` 分批**（§5.2 / §6.1）。
> **★ D-5 的具体后果**：**`H-WP3-10` 已裁决 = 不新增索引** ⇒ 删除**只能**走既有 `(device_id, ts)`；不得以「新索引」为前置。
> **★ 配套**：**`H-WP3-08` 已裁决 = 冻结「原则」（本节 `D-1…D-5`），不冻结具体 batch size**（批大小属实施期可调参数）；删除失败**不得**触发重试风暴（§7.3）。

## §8 数据聚合策略（**P3 vs 后续阶段边界**）

### 8.1 三类数据的归属

| 项 | 是否 P3 | 归属 | 理由 |
|---|---|---|---|
| **原始 telemetry 长期保存** | ⚠️ **否（有窗口）** | **P3 = 窗口内保留**；**长期**保留 → **不在 P3** | 长期原始保存与 `I-8` + 成本冲突；**须靠窗口** |
| **小时级聚合** | ❌ 否 | **后续阶段**（`H-WP3-04` = **`DEFERRED`**） | **无查询消费者**（APP = P4）；且引入第三套 retention/索引 |
| **日级聚合** | ❌ 否 | **后续阶段**（同上） | 同上 |

### 8.2 明确声明

> - **P3 = 原始粒度 + 固定窗口**；**不建立任何聚合表 / 降采样流**。
> - **聚合的启动条件（前置）**：**出现真实查询需求（P4 Web UI 的长期趋势页）** 且 **窗口已不足以覆盖趋势跨度**。
> - **聚合若启用**：须同时裁决 **① 聚合粒度（h/d）· ② 聚合表 retention · ③ 聚合表索引 · ④ 与原始表的窗口关系** —— **属后续阶段（`H-WP3-04` `DEFERRED`）的独立设计**。
> - **★ 不得在 P3 预留「空聚合表」** —— **无消费者的空表 = 纯成本**。

### 8.3 与窗口的耦合（**重要**）

| 项 | 含义 |
|---|---|
| **窗口已冻结 = 90 天** | 趋势可覆盖 ≈ 一个季度；**超 90 天无法直查原始表** |
| **聚合 = `DEFERRED`** | 长期趋势（> 90 天）**当前无支撑** ⇒ 属后续阶段议题 |

> **★ ⇒ 结论（R3）**：`H-WP3-01`（窗口 = 90 天）**已冻结**、`H-WP3-04`（聚合）**已 `DEFERRED`** ⇒ **「> 90 天的长期趋势」是本阶段明确接受的缺口**，须在 **P4（Web UI 长期趋势页）** 立项时**一并评估**。

## §9 容量模型（**估算 —— 非 `PASS`、非实测**）

> **★ 口径声明**：以下**全部为「理论估算」**。① 行数用 `WP1:§4` 的**上限**（**非典型值**）；② 字节/行用**经验区间**；
> ③ **D1 免费额度的具体阈值以 Cloudflare 官方为准，本文件不引用具体数字**（沿用 `WP2:§7.3` 口径）。
> **⇒ 实际消耗须由 `计划:WP-6` 实测确认**（`P3-plan-§6:R-1`）；**不得据估算下"安全"结论**。

### 9.1 单行尺寸估算（**经验区间**）

| 表 | 组成 | 估算 / 行（含索引摊销） |
|---|---|---|
| **`telemetry_history`** | 数据行（9 列，小型文本）+ **3 个索引**（`ux_th_dedup` / `ix_th_device_ts` / `ix_th_device_type_ts`） | **≈ 0.25 KB**（区间 **0.2 – 0.35 KB**） |
| **`log_history`** | 数据行（含 `message` + `payload`）+ **2 个索引** | **≈ 0.5 – 2.5 KB**（**典型 0.5 – 1 KB**） |

> **★ 说明**：`telemetry_history` 索引数（3）多于 `log_history`（2）⇒ **单行摊销更高** —— 这也是 `WP2:§5` **只保留必要索引**的理由。

### 9.2 `telemetry_history` 容量（**按上限 1200 行/设备/天**）

| 规模 | 行/天 | 增长/天 | 年增长（**不删**） | 稳态 @30 天 | 稳态 @90 天（★ 推荐） | 稳态 @180 天 |
|---|---|---|---|---|---|---|
| **1 台** | 1,200 | **≈ 0.3 MB** | ≈ 110 MB | ≈ 9 MB | **≈ 27 MB** | ≈ 54 MB |
| **100 台** | 120,000 | **≈ 30 MB** | ≈ 11 GB | ≈ 0.9 GB | **≈ 2.7 GB** | ≈ 5.4 GB |
| **1,000 台** | 1,200,000 | **≈ 300 MB** | ≈ 110 GB | ≈ 9 GB | **≈ 27 GB** | ≈ 54 GB |
| **10,000 台** | 12,000,000 | **≈ 3 GB** | ≈ 1.1 TB | ≈ 90 GB | **≈ 270 GB** | ≈ 540 GB |

> **计算式**：`稳态 = 台数 × 行/天 × 窗口天数 × 0.25 KB`（与 §5.1.1 一致）。
> **★ 提醒**：`1,200 行/天` 是**上限估算**（`WP1:§4` 已声明各类上限**不可相加**且**不会同时发生**）⇒ **典型值应显著低于此**；**实际值须 `计划:WP-6` 实测**。

### 9.3 `log_history` 容量

**（a）普通情况**（**~20 – 50 行/设备/天**，`≈ 1 KB/行`）

| 规模 | 行/天 | 增长/天 | 稳态 @90 天 | 稳态 @180 天（★ 推荐） |
|---|---|---|---|---|
| **1 台** | 30 | ≈ 30 KB | ≈ 2.7 MB | **≈ 5.4 MB** |
| **100 台** | 3,000 | ≈ 3 MB | ≈ 270 MB | **≈ 540 MB** |
| **1,000 台** | 30,000 | ≈ 30 MB | ≈ 2.7 GB | **≈ 5.4 GB** |
| **10,000 台** | 300,000 | ≈ 300 MB | ≈ 27 GB | **≈ 54 GB** |

**（b）异常爆发情况**（**★ 关键风险**）

| 场景 | 估算 | 说明 |
|---|---|---|
| **节流上限（理论）** | `LOG_TX_MIN_INTERVAL_MS = 500` ⇒ **2 Hz** ⇒ **≤ 172,800 行/设备/天** | `WP1:§3.8` · `P3-plan-§6:R-4` |
| **单设备满速 1 小时** | ≈ **7,200 行** ≈ **7 MB**（`BT-1` 修复后） | **短时爆发**，非持续 |
| **满速折合 1 KB/行** | ≈ **170 MB/设备/天** | **不可能长期持续**（受级别过滤 + Flash 段约束），但**足以为单设备打满配额** |

> **★ 风险结论**：修 **`BT-1`** 后上行可升至 **2 Hz（×30）**（`issues:BT-1`）⇒ **日志量可能远超"普通情况"预估**（`P3-plan-§6:R-4`，**等级 🔴 高**）。
> ⇒ **缓解手段（本文件设计层）**：① **级别过滤**（INFO 不落库，`I-7`，已冻结）· ② **`payload` 体积上限 + 截断**（§6.4，**`H-WP3-06` = `DEFERRED`** ⚠️ 未闭环）· ③ **log 独立窗口**（`H-WP3-02`）· ④ **爆发期上限保护**（可选，`H-WP3-09`）。
> ⇒ **`BT-1` 修复须与设备侧负载评估同批**（`计划:WP-5`）—— **不在本文件范围**。

### 9.4 多设备数据增长控制（汇总）

## §10 D1 查询成本控制原则（**设计原则**）

> **★ 目的**：约束 **future APP / Worker 查询**，使成本可预测。**本节只定原则，不实现。**

| # | 原则 | 说明 |
|---|---|---|
| **Q-1** | **一切历史查询必须带 `device_id`** | 命中 `(device_id, ts)` / `(device_id, type, ts)` 前缀；**禁止无 `device_id` 的全表扫描** |
| **Q-2** | **必须带时间范围** | 强制 `ts BETWEEN ?`；**禁止无界 `SELECT`**（**必须 `LIMIT`**） |
| **Q-3** | **不做跨设备聚合**（P3） | 冻结索引**已删除 `(type, ts)`**（`WP2:§5.1`）⇒ **跨设备按度量聚合 = 全表扫描** ⇒ **P3 禁止** |
| **Q-4** | **删除按 `device_id` 分批** | 见 §5.2 / §7.4；**避免长事务与写放大** |
| **Q-5** | **索引不增**（已裁决） | 索引已冻结（`I-9`）；**`H-WP3-10` = `no additional index`** |
| **Q-6** | **查询成本与写入成本分账** | **读**：走前缀索引 + 时间窗；**写**：批量 INSERT（`计划:WP-4`）；**清理**：Cron 分批 |
| **Q-7** | **不做「查询时计算」的聚合** | 若需趋势 ⇒ **用聚合表**（§8），**不要**在查询期对海量原始行做实时聚合 |
| **Q-8** | **不引入跨表 JOIN 的历史查询** | `telemetry_history` 与 `log_history` **物理分离**（`I-6`）⇒ 各自独立查询，**不 UNION / 不 JOIN** |
