## §3 存储策略总体方案（方案空间与推荐）

### 3.1 三种取向

| # | 取向 | 形态 | 评价 |
|---|---|---|---|
| **S-A** | **无界保留**（不删除） | 历史表只写不删 | ❌ **不可接受** —— 见 §8 容量模型：10000 台一年即 1.1 TB 量级，且**无界增长不可运维** |
| **S-B** | **固定窗口 TTL**（按 `ts` 定期删除超窗行） | 定期清理，窗口内保留**原始数据** | ✅ **推荐为 P3 基线** |
| **S-C** | **分层 + 聚合**（原始短保留 + 聚合长保留） | 原始行短窗删除；小时/日级聚合行长保留 | ⚠️ **不在 P3** —— 聚合需**查询消费者**（APP 未实现）⇒ **过度设计**；延 **P4/P5**（§7） |

### 3.2 ★ 推荐方案 = **S-B（固定窗口 TTL）· 双域各自独立窗口**

| 决策 | 内容 | 状态 |
|---|---|---|
| **总体取向** | **S-B**：两表**各自**设保留窗口；超窗**分批删除**；**窗口内保留原始粒度** | **推荐（候选）** |
| **窗口数值** | **不冻结** —— `telemetry` 见 `H-WP3-01` · `log` 见 `H-WP3-02` | **`HUMAN_REQUIRED`** |
| **域间差异** | **Telemetry 偏短 / Log 偏长**（方向沿用 `P3-plan` WP-7；**具体天数待裁决**） | **推荐方向** |
| **聚合** | **P3 不引入聚合表**（延 P4/P5） | **推荐（候选）** |
| **归档** | **P3 不引入冷热分层 / R2 归档**（延 P4/P5） | **推荐（候选）** |
| **清理机制** | **Cron 定期清理**（§6 推荐 A） | **推荐（候选）** |

> **★ 不推荐 S-A**：与 `I-8`（容量目标）**冲突**，且无界增长会导致**查询退化 / 存储打满**。
> **★ 不推荐 S-C（本轮）**：聚合表的**唯一价值 = 长期趋势查询**；而 **APP 未实现（P4）** ⇒ **无消费者** ⇒ 属**过度设计**（任务明确要求避免）。
> **★ 与 WP-2 §6.2 候选值的张力（见 §11 / Review `F-3`）**：`WP2:§6.2` 列出的候选为 **telemetry 90 天 / log 30 天**（即 Telemetry **长** / Log **短**），与计划 WP-7 的「**Telemetry 短 / Log 长**」**方向相反** ⇒ **两者不可同时成立**，须人工在 `H-WP3-01` / `H-WP3-02` 中一并裁决。

## §4 Telemetry History Storage Policy

> **适用对象**：`telemetry_history`（`WP2:§3` 冻结 schema）。**9 类落库判定不得改**（`WP1:§4`）。

### 4.1 保存周期（retention）

| 项 | 内容 |
|---|---|
| **机制** | 按 `ts` **窗口保留**；`ts < now - W_telemetry` 的行**进入删除候选** |
| **候选窗口** | **30 天 / 90 天 / 180 天**（**三者均为候选**，**不预设结论**） |
| **粒度** | **秒**（`I-10`）；窗口以**天**为单位表达即可 |
| **裁决项** | **`H-WP3-01`**（承接 `H-WP2-9`） |
| **依赖** | 窗口取值**必须在 WP-6 容量实测之后再定稿**（`P3-plan` WP-6 / `R-1`）—— **估算不能代替实测** |

> **★ 纪律**：**本文件不裁决天数**。上表三项**仅为候选**；裁决归 `H-WP3-01`。

### 4.2 删除策略（执行形状 —— **须适配冻结索引**）

> **★ 关键约束（`I-9`）**：`telemetry_history` **无单列 `ts` 索引** ⇒ **全局 `DELETE ... WHERE ts < ?` 会全表扫描**。
> ⇒ **删除必须按 `device_id` 逐设备执行**，以命中 `ix_th_device_ts (device_id, ts DESC)`。

| 步骤 | 设计（**仅设计，不实现**） |
|---|---|
| **① 目标集合** | 遍历已知 `device_id`（来源 = `device` 表 / 或近期有写入的设备集合） |
| **② 单设备删除** | `DELETE FROM telemetry_history WHERE device_id = ? AND ts < ?` —— **走 `ix_th_device_ts`** |
| **③ 分批（batch）** | 单次删除**限制行数**（如 `LIMIT N` 循环）⇒ 避免**长事务 / 超时 / 写入放大**；批大小见 `H-WP3-08` |
| **④ 幂等 / 可重入** | 删除按钮**可重复执行**（删除条件为纯 `ts` 谓词 ⇒ 天然幂等） |
| **⑤ 顺序** | 先删**索引可覆盖**的行（`ts`），**不做行级随机删除** |
| **⑥ 不阻塞 ingest** | 删除**不在 ingest 请求路径**执行（`I-1`）—— 由**独立调度**（Cron）承担（§6） |

> **★ 反模式（禁止）**：在 `/api/ingest` 的请求处理内做删除（违反 `I-1` 的 Worker 边界 + 拉高 ingest 延迟）。

### 4.3 是否按 `device_id` 逻辑分区

| 项 | 结论 |
|---|---|
| **物理分区 / sharding** | ❌ **不做** —— D1 为单库 SQLite；**P3 不引入分库分表** |
| **逻辑隔离** | ✅ **`device_id` 为一级隔离字段**（`WP2:§3.1`），**所有查询 / 删除均以其为前缀** |
| **多设备增长控制** | 靠 **① 统一 retention 窗口**（§4.1）· **② `(device_id, ts)` 前缀索引**（查询/删除高效）· **③（可选）per-device 配额**（见 §8.4 / `H-WP3-09`） |
| **分区收益评估** | 11 台规模**无必要**；即便 1000 台，**TTL + 前缀索引**已足够 ⇒ **不引入分区复杂度** |

### 4.4 是否需要时间窗口清理

> **结论 = 需要（✅）** —— 与 §4.1 / §4.2 一致：**时间窗口 = 唯一的删除维度**。
> 理由：`telemetry_history` 无「逻辑删除」语义（无 `is_deleted` 列，且**不得新增**，`I-9`）⇒ **物理删除按 `ts` 窗口**。
> **执行机制**见 §6。

### 4.5 是否需要冷热数据策略

| 项 | 结论 |
|---|---|
| **P3 是否引入冷热分层** | ❌ **不引入** —— D1 **无存储分层**；且**本阶段无归档目标** |
| **热数据** | = 窗口内数据（**查询 / 删除均走 `(device_id, ts)` 索引**） |
| **冷数据** | = 超窗数据 ⇒ **直接删除**（**不归档**），P3 基线 |
| **归档（R2 / 对象存储）** | **延 P4/P5**（见 `H-WP3-07`）；届时形态 = 「**导出 → 校验 → 再删**」 |
| **风险** | 若未来需要"**长期审计留存**"，则**必须在删除前建立归档**，否则**数据不可恢复** ⇒ **window 值须与审计需求一并裁决** |

### 4.6 是否需要聚合 / 降采样

> **结论 = P3 不需要（❌）** —— **理由**：① **无查询消费者**（APP = P4）；② 聚合表**又是一套 retention + 索引**（成本）；③ 属**过度设计**。
> **⇒ 归属划分见 §7**（小时级 / 日级聚合 → **P4/P5**）。
>
> **★ 但保留一条"前置记录"**：若 `H-WP3-01` 判定的窗口**很短**（如 30 天），则**长期趋势**必然依赖**聚合**；
> ⇒ **聚合与否与窗口取值强耦合** ⇒ 两者**应在同一次人工裁决中一并考虑**（`H-WP3-04`）。

## §5 Log History Storage Policy

> **适用对象**：`log_history`（`WP2:§4.2` 冻结 schema；`payload` = `TEXT(JSON)`）。

### 5.1 retention

| 项 | 内容 |
|---|---|
| **机制** | 按 `ts` 窗口保留；超窗删除（同 §4.2 的执行形状，**逐 `device_id`**、走 `ix_lh_device_ts`） |
| **候选窗口** | **30 天 / 90 天 / 180 天**（**候选**） |
| **方向** | **Log 偏长**（故障诊断 / 安全追溯，`WP1:§3.8` 生命周期倾向 = **长**） |
| **裁决项** | **`H-WP3-02`**（承接 `H-WP2-10`） |

### 5.2 ERROR / WARN / INFO 级别分级策略

> **★ 前置冻结（`I-7`）**：**云端 `log_history` 存储级别 = `{WARN, ERROR, CRITICAL}`** —— **INFO 不落库**（`WP1:§3.8` · `F-6`）。
> ⇒ **「级别分级策略」的讨论范围 = 三个已落库级别之间**，**不涉及 INFO**。

| 方案 | 形态 | 评价 |
|---|---|---|
| **L-A** | **统一窗口**（三级同保留期） | ✅ **推荐为 P3 基线** —— 简单、删除走 `(device_id, ts)` 单维谓词 |
| **L-B** | **分级窗口**（`CRITICAL`/`ERROR` 长，`WARN` 短） | ⚠️ **不在 P3 默认** —— ⚠️ **技术障碍**：冻结索引**无 `(device_id, level, ts)`** ⇒ 分级删除需 `WHERE level IN (...)` **行内过滤**（`I-9` 约束）；且**分级会放大清理复杂度** |

| 项 | 结论 |
|---|---|
| **P3 推荐** | **L-A 统一窗口**（与 `WP2:§5.2`「`(device_id, level, ts)` **暂缓**」**方向一致**） |
| **L-B 保留可能** | 若人工认为 `CRITICAL` 需更长留存 ⇒ **须同时裁决是否补 `(device_id, level, ts)` 索引**（新 migration，`H-WP3-10` 相邻项） |
| **裁决项** | **`H-WP3-06`** |

> **★ 不得混淆（`I-7`）**：本节讨论的是 **① 云端 `log_history` 存储级别**；
> **绝不改动** **② 设备 Flash Log 保存级别**（`{WARN, ERROR, CRITICAL}`，`WP1:§3.8`，**设备侧行为**）—— **两者独立可调**。

### 5.3 `payload` 生命周期

| 项 | 内容 |
|---|---|
| **与行同寿命（默认候选）** | `payload` 随 `log_history` 行**同一窗口**删除 —— **简单、单一删除谓词** |
| **`payload` 先于行清理（备选候选）** | 超窗后先 `payload = NULL`（或置空串），**保留 `message` / `level` / `code`** ⇒ 便于**超长窗口保留"骨架"** |
| **评价** | **P3 推荐「与行同寿命」**（避免引入"两段式删除"复杂度）；备选方案保留为 `H-WP3-03` 的一个选项 |
| **裁决项** | **`H-WP3-03`** |

### 5.4 大 `payload` 控制策略（**承接 `H-WP2-8`**）

> **★ 背景**：`WP2:§4.2` 已冻结 `payload` **存储格式 = `TEXT(JSON)`**；**体积上限 = `DEFERRED` → 本文件**。
> **★ 上游约束**：`cloud_protocol.md` **§8.2** —— **批 ≤ 16 条 / 单条 ≤ 4096 B**（上行单条日志上限）。

| 项 | 候选 | 说明 |
|---|---|---|
| **上限口径** | **① 与上行一致（≤ 4096 B）** / **② 更严（如 ≤ 1024 B / ≤ 2048 B）** | ②的理由：`payload` **不建索引**但**计入存储**；D1 行越大 ⇒ 页分裂与读取成本越高 |
| **超限处置候选** | **A 截断**（保留前 N 字节 + 标记 `"truncated":true`）· **B 丢弃**（`payload = NULL`，保留 `message`）· **C 仅保留键**（剥离值，仅存 key 列表） | **A 最保信息**；**B 最省**；**C 折中（可诊断"哪些字段曾存在"）** |
| **`message` 上限** | **候选 ≤ 256 B 截断**（人读摘要，`WP1:§3.8`） | — |
| **裁决项** | **`H-WP3-03`** | — |

> **★ 纪律**：**本文件不预设数值上限，也不预设处置方式** —— 上表**全部为候选**。
> **★ 硬要求（无论取值如何）**：`payload` **不得是无界字段** —— **上限 + 超限处置必须同时确定**（`P3-plan` WP-2「`payload` 体积限制策略（必须明确）」）。

### 5.5 是否需要摘要化

| 项 | 结论 |
|---|---|
| **P3 是否摘要化** | ❌ **不做** —— 「体积上限 + 截断」（§5.4）**已足以约束**单行体积；摘要化（日志聚类 / 去重 / 滚动聚合）**需要消费者**（P4） |
| **已有的"摘要"** | `message` 字段**本身即人读摘要**（`WP2:§4.2`）—— **非新增机制** |
| **归属** | 摘要化 / 日志聚类 → **P4/P5** |
| **裁决项** | **`H-WP3-05`**（是否引入摘要化 —— 建议 P3 不引入） |

### 5.6 ★ 边界重申：设备 Flash Log ≠ 云端 `LogHistory`（**`I-7`**）

> **必须保持两个独立策略，不得混淆**：

| 维度 | **① 设备 Flash Log** | **② 云端 `log_history`** |
|---|---|---|
| **保存级别（冻结）** | `{WARN, ERROR, CRITICAL}`（INFO 不落 Flash） | `{WARN, ERROR, CRITICAL}`（**默认与设备一致，但独立可调**） |
| **存储介质** | 设备 SPIFFS/LittleFS 段（**496 条容量**，写满**淘汰未确认记录**） | D1 `log_history` 表 |
| **生命周期** | 依赖 `log_ack` 推进 `acked_seq` ⇒ **段回收**（受 **`BT-1`** 影响） | 依赖 **本文件 §5.1 retention** |
| **上限约束** | 段容量 496 条 | **retention 窗口 + `payload` 上限**（本文件） |
| **是否由本文件管理** | ❌ **否**（设备侧行为） | ✅ **是** |

> **⇒ 规则**：本文件**只设计 ②**；**不触碰 ①** —— 调整任一者**须独立裁决**（`WP1:§3.8`）。

## §6 清理机制设计（**仅设计，不实现**）

### 6.1 四个候选

| # | 候选 | 形态 | 触发点 |
|---|---|---|---|
| **A** | **定期 Worker Cron 清理** | Cloudflare **Cron Triggers** → 定时 Worker → `DELETE ... WHERE device_id = ? AND ts < ?`（分批） | **时间驱动**（独立于请求路径） |
| **B** | **写入时触发清理** | `/api/ingest` 处理中**顺带**删除 | **请求驱动**（在 ingest 路径内） |
| **C** | **按设备访问时惰性清理** | 查询某设备历史时**顺手**删除其超窗行 | **读驱动** |
| **D** | **混合策略** | A（Cron 批量）**为主** + 可选补充（如按写入量触发的轻量清理 / 按设备配额触发） | 组合 |

### 6.2 逐项评价

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A Cron** | ✅ **与 ingest 解耦**（不污染 `I-1` Worker 边界）· ✅ 可批量、可分批、可重入 · ✅ **`P3-plan` WP-7 已规划此手段** | ⚠️ 需要 Cron 配置（实施阶段）· ⚠️ 删除窗口有**延迟**（T+0 到 T+周期） | ✅ **推荐（主机制）** |
| **B 写入时** | 清理"及时" | ❌ **违反 `I-1`**（Worker = ingest/validation/idempotency/persist，**不含运维删除**）· ❌ 拉高 ingest 延迟 / CPU 预算 · ❌ 删除量不可预测（突发写入 ⇒ 突发删除） | ❌ **不推荐** |
| **C 惰性** | 无独立调度 | ❌ **无法约束"长期不活跃设备"**（不被访问 ⇒ 永不清理）· ❌ 与 `I-8`/容量目标**冲突** · ❌ 读路径被写操作污染（读写放大） | ❌ **不推荐** |
| **D 混合** | 可兼顾及时性与解耦 | ⚠️ **复杂度 + 双触发点一致性**风险 | ⚠️ **可接受为 A 的演进**（**仅在出现明确需求时**） |

### 6.3 ★ 推荐 = **A（Cron 定期清理）为基线**，**允许演进为 D**

| 项 | 内容 |
|---|---|
| **推荐方案** | **A** —— 独立 **Cron 调度** → 定时 Worker → **逐 `device_id` 分批删除**（§4.2 执行形状） |
| **不推荐方案** | **B**（污染 ingest 路径，违 `I-1`）· **C**（不约束冷设备，违容量目标） |
| **D 的定位** | **不是基线**；仅在「Cron 周期过长 ⇒ 删除滞后不可接受」或「需 per-device 配额硬顶」时**升级为 D** |
| **执行频率 / 批大小** | **候选**（如 每日 1 次 / 每小时 / 每 6 h）—— **`H-WP3-08`** |
| **幂等性** | 删除谓词为纯 `ts` 谓词 ⇒ **天然幂等、可重入、可中断续跑** |
| **失败处理（设计层）** | 删除失败**不得**影响 ingest / 查询；**只记日志 / 告警**（**不重试风暴**） |
| **裁决项** | **`H-WP3-05`**（机制选择 —— 本文件推荐 A） |

> **★ 与计划 `WP-7` 一致性**：`P3-plan` WP-7 明示「**D1 无原生 TTL ⇒ 用 Cloudflare Cron Triggers 删除超期行 / 或归档**」⇒ **本推荐与计划逐条一致**。

## §7 数据聚合策略（**P3 vs P4/P5 归属划分**）

### 7.1 三类数据的归属

| 项 | 是否 P3 | 归属 | 理由 |
|---|---|---|---|
| **原始 telemetry 长期保存** | ⚠️ **否（有窗口）** | **P3 = 窗口内保留**；**长期**保留 → **不在 P3** | 长期原始保存与 `I-8` + 成本冲突；**须靠窗口** |
| **小时级聚合** | ❌ 否 | **P4 / P5** | **无查询消费者**（APP = P4）；且引入第三套 retention/索引 |
| **日级聚合** | ❌ 否 | **P4 / P5** | 同上 |

### 7.2 明确声明

> - **P3 = 原始粒度 + 固定窗口**；**不建立任何聚合表 / 降采样流**。
> - **聚合的启动条件（前置）**：**出现真实查询需求（P4 Web UI 的长期趋势页）** 且 **窗口已不足以覆盖趋势跨度**。
> - **聚合若启用**：须同时裁决 **① 聚合粒度（h/d）· ② 聚合表 retention · ③ 聚合表索引 · ④ 与原始表的窗口关系** —— **属 P4/P5 的独立设计**。
> - **★ 不得在 P3 预留"空聚合表"** —— **无消费者的空表 = 纯成本**。

### 7.3 与窗口的耦合（**重要**）

| 若 `H-WP3-01` 判定的 telemetry 窗口为… | 对聚合的含义 |
|---|---|
| **长（≥ 180 天）** | **趋势可直查原始表** ⇒ 聚合**更无必要** |
| **短（≤ 30 天）** | **长期趋势无法直查** ⇒ 聚合**成为 P4 的硬前置** ⇒ **应尽早（P4 初）立项** |

> **★ ⇒ 结论**：**窗口与聚合须同批裁决**（`H-WP3-01` 与 `H-WP3-04` 联动），**避免"窗口定短 + 无聚合 ⇒ 趋势永久丢失"**。

## §8 容量模型（**估算 —— 非 `PASS`、非实测**）

> **★ 口径声明**：以下**全部为「理论估算」**。① 行数用 `WP1:§4` 的**上限**（**非典型值**）；② 字节/行用**经验区间**；
> ③ **D1 免费额度的具体阈值以 Cloudflare 官方为准，本文件不引用具体数字**（沿用 `WP2:§7.3` 口径）。
> **⇒ 实际消耗须由 WP-6 实测确认**（`P3-plan` WP-6 / `R-1`）；**不得据估算下"安全"结论**。

### 8.1 单行尺寸估算（**经验区间**）

| 表 | 组成 | 估算 / 行（含索引摊销） |
|---|---|---|
| **`telemetry_history`** | 数据行（9 列，小型文本）+ **3 个索引**（`ux_th_dedup` / `ix_th_device_ts` / `ix_th_device_type_ts`） | **≈ 0.25 KB**（区间 **0.2 – 0.35 KB**） |
| **`log_history`** | 数据行（含 `message` + `payload`）+ **2 个索引** | **≈ 0.5 – 2.5 KB**（**典型 0.5 – 1 KB**；`payload` 大时逼近上限） |

> **★ 说明**：`telemetry_history` 索引数（3）多于 `log_history`（2）⇒ **单行摊销更高** —— 这也是 `WP2:§5` **只保留必要索引**的理由。

### 8.2 `telemetry_history` 容量（**按上限 1200 行/设备/天**）

| 规模 | 行/天 | 增长/天 | 年增长（**不删**） | 稳态 @30 天 | 稳态 @90 天 |
|---|---|---|---|---|---|
| **1 台** | 1,200 | **≈ 0.3 MB** | ≈ 110 MB | ≈ 9 MB | ≈ 27 MB |
| **100 台** | 120,000 | **≈ 30 MB** | ≈ 11 GB | ≈ 0.9 GB | ≈ 2.7 GB |
| **1,000 台** | 1,200,000 | **≈ 300 MB** | ≈ 110 GB | ≈ 9 GB | ≈ 27 GB |
| **10,000 台** | 12,000,000 | **≈ 3 GB** | ≈ 1.1 TB | ≈ 90 GB | ≈ 270 GB |

> **计算式**：`稳态 = 台数 × 行/天 × 窗口天数 × 0.25 KB`。
> **★ 提醒**：`1,200 行/天` 是**上限估算**（`WP1:§4` 已声明各类上限**不可相加**且**不会同时发生**）⇒ **典型值应显著低于此**；**实际值须 WP-6 实测**。

### 8.3 `log_history` 容量

**（a）普通情况**（假设 **~20 – 50 行/设备/天**，`≈ 1 KB/行`）

| 规模 | 行/天 | 增长/天 | 稳态 @90 天 |
|---|---|---|---|
| **1 台** | 30 | ≈ 30 KB | ≈ 2.7 MB |
| **100 台** | 3,000 | ≈ 3 MB | ≈ 270 MB |
| **1,000 台** | 30,000 | ≈ 30 MB | ≈ 2.7 GB |
| **10,000 台** | 300,000 | ≈ 300 MB | ≈ 27 GB |

**（b）异常爆发情况**（**★ 关键风险**）

| 场景 | 估算 | 说明 |
|---|---|---|
| **节流上限（理论）** | `LOG_TX_MIN_INTERVAL_MS = 500` ⇒ **2 Hz** ⇒ **≤ 172,800 行/设备/天** | `WP1:§3.8` · `P3-plan-§6:R-4` |
| **单设备满速 1 小时** | ≈ **7,200 行** ≈ **7 MB**（BT-1 修复后） | **短时爆发**，非持续 |
| **满速折合 1 KB/行** | ≈ **170 MB/设备/天** | **不可能长期持续**（受级别过滤 + Flash 段约束），但**足以为单设备打满配额** |

> **★ 风险结论**：修 **`BT-1`** 后上行可升至 **2 Hz（×30）**（`issues:BT-1`）⇒ **日志量可能远超"普通情况"预估**（`P3-plan-§6:R-4`，**等级 🔴 高**）。
> ⇒ **缓解手段（本文件设计层）**：① **级别过滤**（INFO 不落库，`I-7`，已冻结）· ② **`payload` 体积上限 + 截断**（§5.4，`H-WP3-03`）· ③ **log 独立（可更短）窗口**（`H-WP3-02`）· ④ **爆发期上限保护**（可选，`H-WP3-09`）。

## §9 D1 查询成本控制原则（**设计原则**）

> **★ 目的**：约束 **future APP / Worker 查询**，使成本可预测。**本节只定原则，不实现。**

| # | 原则 | 说明 |
|---|---|---|
| **Q-1** | **一切历史查询必须带 `device_id`** | 命中 `(device_id, ts)` / `(device_id, type, ts)` 前缀；**禁止无 `device_id` 的全表扫描** |
| **Q-2** | **必须带时间范围** | 强制 `ts BETWEEN ?`；**禁止无界 `SELECT`**（**必须 `LIMIT`**） |
| **Q-3** | **不做跨设备聚合**（P3） | 冻结索引**已删除 `(type, ts)`**（`WP2:§5.1`）⇒ **跨设备按度量聚合 = 全表扫描** ⇒ **P3 禁止**（若 P4 需要 ⇒ 届时新增索引） |
| **Q-4** | **删除按 `device_id` 分批** | 见 §4.2 / §6；**避免长事务与写放大** |
| **Q-5** | **索引不增**（本轮） | 索引已冻结（`I-9`）；**新增索引须新 migration + 人工裁决**（`H-WP3-10`） |
| **Q-6** | **查询成本与写入成本分账** | **读**：走前缀索引 + 时间窗；**写**：批量 INSERT（`P3-plan` WP-4）；**清理**：Cron 分批 |
| **Q-7** | **不做"查询时计算"的聚合** | 若 P4 需要趋势 ⇒ **用聚合表**（§7），**不要**在查询期对海量原始行做实时聚合 |
| **Q-8** | **不引入跨表 JOIN 的历史查询** | `telemetry_history` 与 `log_history` **物理分离**（`I-6`）⇒ 各自独立查询，**不 UNION / 不 JOIN** |
