## 0. 为什么要合并（而不是先做 P1-2 再做 P1-4）

注册（**发现设备**）与签发（**给设备身份**）是同一闭环的两半：

- 只做 P1-2 ⇒ "能授权但没有触发点"，凭据签给谁不明确；
- 只做 P1-4 ⇒ "能发现但不能授权"，设备永远停在 `CLAIM_PENDING`。

⇒ Phase C **一次打通闭环**，并同时把"防抢注"这条安全主线的落点确定下来。

## 2. 继承的冻结约束（不可违背）

| 来源 | 约束 |
|---|---|
| **P1 Architecture Freeze #1** | `username` = `dev_<device_id>`（已由 D1 CHECK 强制） |
| **Freeze #2** | 设备侧 NVS namespace `gfcred`，双 slot + `ACTIVE/TESTING/INVALID` |
| **Freeze #4** | 首次绑定获得 owner，但**必须先经过可信注册**；`CLAIM_PENDING` **不得自动**升级 |

| **P0 容量约束** | Worker/D1 额度紧张 ⇒ 本闭环属**低频控制面**，不得引入轮询 |

## 3. 闭环总览

```
 设备（现用 P0 过渡凭据）          EMQX                Worker（控制面）              D1
      │                            │                        │                       │
 (1)  │── CONNECT + PUB up ───────►│                        │                       │
      │    (上线通告 / 任意上行)     │── 规则引擎(异步) ─────►│                       │
      │                            │   device_id = topic    │── upsert device ─────►│
      │                            │   的 2 级路径           │   state=CLAIM_PENDING  │
      │                            │                        │                       │
 (2)  │                            │                        │◄── 准入判定（§5.4）────│
      │                            │                        │   未通过 ⇒ 停在 PENDING │
      │                            │                        │   通过   ⇒ 走 (3)      │
      │                            │                        │                       │
 (3)  │                            │◄── POST /users ────────│  建账号                │
      │                            │◄── PUT  .../rules ─────│  写 ACL                │
      │                            │                        │── INSERT credential ─►│
      │                            │                        │   state=PROVISIONING   │
      │                            │                        │   acl_ready_at=NULL    │
 (4)  │◄──────── down: system.credential_set ──────────────│  下发（TLS 8883）       │
      │  写 NVS TESTING slot（P1-3）│                        │                       │
      │                            │                        │                       │
 (5)  │── CONNECT(新凭据) ────────►│  CONNACK ok            │                       │
      │── PUB up: credential_set result(generation) ───────►│                       │
      │                            │                        │── UPDATE credential ──►│
      │                            │                        │   PROVISIONING→ACTIVE  │
      │                            │                        │   acl_ready_at=now     │
      │                            │                        │   device.state=REGISTERED
      │                            │                        │── device_event ───────►│
```

**要点**：`(5)` 才是"ACL 真的生效了"的**唯一硬证据** —— 见 §6.3。

## 4. 状态与落库映射

### 4.1 `device.state`

```
FACTORY ──首次上行被云端发现──► CLAIM_PENDING ──准入通过 + 凭据 ACTIVE──► REGISTERED
                                   ▲                                        │
                                   └──── 准入未通过：**原地不动**（不得自动升级）
```

- Phase C 只负责 `→ CLAIM_PENDING` 与 `→ REGISTERED` 两个转移。
- `BOUND / UNBOUND / REVOKED` 属 Phase E（P1-5）。

### 4.2 `device_credential.state` 与"三态可检测"映射

D1 Schema 只定义了 4 个状态，**不新增 `FAILED` 状态**（避免动已 apply 的 `0001`）。
"成功 / 待定 / 失败"三态用**现有字段组合**表达：

| 语义 | 判定表达式 | 含义 |
|---|---|---|
| **PENDING（待定）** | `state='PROVISIONING' AND provision_error IS NULL` | 已建账号 + 已写 ACL（或尚未），**尚无就绪证据** |
| **FAILED（可检测失败）** | `state='PROVISIONING' AND provision_error IS NOT NULL` | 某一步失败，`provision_attempts` 记录重试次数 |
| **OK** | `state IN ('TESTING','ACTIVE')` | 已有 `acl_ready_at` 证据（D1 CHECK 强制） |

> 若后续确实需要独立的 `FAILED` 状态，走 `0002_*` 迁移（不在本阶段）。
> **`provision_error` 必须写入可读原因**（如 `emqx_put_acl_500`），不得留空却是失败。

### 4.3 状态机（凭据）

```
                  (首次签发)                        (轮换)
   ［新建］──► PROVISIONING ──设备 CONNACK 自证──► ACTIVE
                    │                              ▲
                    │                       （无旧凭据时直达）
                    │
                    └──设备 CONNACK 自证──► TESTING ──切主（旧→REVOKED）──► ACTIVE
                                              ▲
                                        （有旧 ACTIVE 时先并存）

   PROVISIONING / TESTING / ACTIVE ──回收或退役──► REVOKED（终态）
```

- **为什么首次签发不经过 `TESTING`**：`TESTING` 的语义是"已自证可用，但因**旧凭据仍占着 ACTIVE** 而处于并存期"。首次签发没有旧凭据，直接 `ACTIVE`。
- `acl_ready_at` 的**定义**（本文件冻结）：**"该凭据被证明可用于连接的时刻"**，证据来源见 §6.3。

### 4.4 `device_event` 写入点

| 动作 | `type` | `actor` |
|---|---|---|
| 首次上行建档 | `register` | `device` |
| 签发请求受理 | `credential_issue` | `cloud` |
| 账号创建 / ACL 写入（可分条） | `acl_update` | `cloud` |
| 凭据自证成功升 ACTIVE | `credential_activate` | `device` |
| 轮换 | `credential_rotate` | `cloud` |
| 回收（未激活即废弃） | `credential_revoke` | `cloud` |
| 退役：改 ACL | `acl_update` | `cloud` |
| 退役：踢会话 | `session_terminate` | `cloud` |

> `acl_update` 与 `session_terminate` **成对出现**才构成完整 revoke（§Design Impact Freeze）。

## 5. P1-4 注册流程（发现与建档）

### 5.1 触发点

**唯一入口**：既有 ingest 通道（EMQX 规则引擎 → HTTP Action → Worker）。
**不得**新增轮询、不得让设备额外上报"我上线了"以外的信息。

| 项 | 设计 |
|---|---|
| 触发条件 | 收到任一 `guo_feeder/<device_id>/up`（或 `log`）消息，且该 `device_id` **不在** `device` 表 |
| `device_id` 来源 | **仅** 从 topic 的 2 级路径取（V3 已固定），不信任 payload |
| 首条动作 | `INSERT ... ON CONFLICT(device_id) DO UPDATE SET last_seen=...`（幂等） |
| 顺带更新 | 已存在设备 ⇒ 只刷 `last_seen` / `fw_version`（若载荷含），**不改 `state`** |

### 5.2 幂等要求

1. **重复上行不得重复建档**（`ON CONFLICT DO UPDATE` 天然满足）。
2. **不得**因为"消息重复投递"而重复触发签发（签发另有幂等键，见 §6.5）。
3. 控制面写入必须能承受 ingest 的**至少一次投递**语义。

### 5.3 防抢注（安全主线）

> `device_id` 由 MAC 派生、**可从 topic 读出**；P0 过渡凭据是共享的 ⇒ 任何拿到过渡凭据的人
> 都能"代替"任意 `device_id` 上行。所以：

**硬规则（冻结）**：`CLAIM_PENDING` **绝不自动**变 `REGISTERED`。
建档只表示"云端见过这个 id"，**不授予任何身份**。

### 5.4 准入判定端口（**接口固定，形态待裁决**）

Phase C 定义一个**抽象判定**，实现形态在 §15-Q1 裁决后填入：

```
claim_authorized(device_id) -> {
    authorized : bool,
    reason     : string,          // 审计用："manifest_hit" / "admin_approved" / "no_rule"
    source     : "manifest" | "admin" | "token" | "none"
}
```

| 候选实现 | 说明 | 风险 |
|---|---|---|
| **A. 管理员显式 approve**（受保护端点） | 设备一律停在 `CLAIM_PENDING`，管理员逐台/批量 approve | 人工成本；无自动化但**最安全** |
| B. 产线 manifest 预置 | 出厂时把 `device_id` 批量写入 D1（`state='FACTORY'`） | 需要产线流程配合 |
| C. claim token（P1 **不选型**） | 一机一码，首次注册凭码自证 | 形态未定，属「生产流程设计」 |

> **本阶段建议（待你拍板，见 §15-Q1）**：P1 采用 **A + B 并存**（manifest 命中自动放行，否则等人工 approve），
> 把 C 留到后续「生产流程设计」。
> **无论选哪种**，`claim_authorized()` 的返回结构与审计字段（`reason`/`source`）都不变 ⇒ 后续替换不掉接口。

## 6. P1-2 凭据签发链路

### 6.1 顺序硬约束（不可颠倒）

```
① POST /users                      建账号（EMQX 内置库，密码由 EMQX 哈希）
        ↓
② PUT  /authorization/sources/.../rules/users/{username}   写 ACL
        ↓
③ 就绪判定（retry / wait，见 §6.3）   ← ★ 不可跳过
        ↓
④ INSERT device_credential (state=PROVISIONING, acl_ready_at=NULL)   落库
        ↓
⑤ down: system.credential_set      下发（TLS）
        ↓
⑥ 设备 CONNACK 自证 → 回转 result
        ↓
⑦ UPDATE credential → ACTIVE, acl_ready_at=now；device.state=REGISTERED
```

**为什么 ① 必须早于 ②**（继承 C-2 白名单模式）：ACL 兜底规则是 `全部用户 # → deny`，
**任何凭据必须先有 ACL 才能用** ⇒ 先写 ACL 再建账号会出现"账号存在但无规则"的窗口。

**为什么 ③ 不可跳过**：`PUT` 返回 2xx 只代表**规则已写入配置**，不代表**已生效**。
白名单模式下未生效 ⇒ 设备订阅落 `# deny` ⇒ **`subscriptions=0`（能连不能收）**，
而固件日志照样打 `MQTT subscribed`（那只是协议层 SUBACK）—— 这是 P0 已记录的排障陷阱。

### 6.2 每一步的具体动作

| 步 | 调用 | 幂等性 |
|---|---|---|
| ① | `POST /api/v5/authentication/password_based:built_in_database/users`（端点名以 P1-2 实施时实测为准） | 账号已存在 ⇒ 视为成功（**需实测确认返回码**，见 §15-Q5） |
| ② | `PUT .../rules/users/{username}`，body **必须是对象** `{"username":u,"rules":[...]}`（**裸数组 400**）；规则项只传 `{topic,permission,action}` | 全量覆盖，天然幂等 |
| ③ | 见 §6.3 | — |
| ④ | `INSERT`（`UNIQUE(device_id,generation)` 保证幂等） | 重复请求返回既有行 |
| ⑤ | MQTT publish 到 `guo_feeder/<device_id>/down` | **每次新 `i`**（去重缓存 10 项/30 s，重复 id 被静默丢弃） |

**规则内容（每个设备账号）**：

```
allow  subscribe  guo_feeder/<device_id>/down
allow  publish    guo_feeder/<device_id>/up
allow  publish    guo_feeder/<device_id>/log
（其余一律落到兜底 deny）
```

> 注意：**不要**给设备 `subscribe` 自己 `up`/`log` 的权限，也**不要**允许通配符订阅（X-1 用例）。

### 6.3 ★ 就绪判定：为什么"设备 CONNACK 自证"是唯一硬证据

| 候选判据 | 能否证明"已生效" | 结论 |
|---|---|---|
| `PUT` 返回 2xx | ❌ 只证明配置已写入 | 不可用 |
| 等待固定时长（如 3 s） | ⚠️ 概率性（实测 1.32–1.40 s，无长尾，但**非保证**） | 只作**下限保护**，不作判据 |
| `GET` 反查 ACL 规则 | ❌ 与 `PUT` 读同一份配置，**自证循环** | 不可用 |
| **用该凭据真实建连并订阅** | ✅ 唯一硬证据 | **采用**（由设备执行） |
| Worker 侧 TCP 探针（`connect()` 开 MQTT） | ⚠️ 理论可行，需手写 MQTT 握手且与 EMQX Serverless 的 TLS/ALPN 兼容性未知 | **不采用**（成本/风险不成比例） |

**⇒ 冻结结论**：
**ACL 就绪的最终证据由设备侧 CONNACK 反证**，云端只保证"规则已写 + 已过等待窗口"。
这正是 **P1-3 双 slot 模型（`ACTIVE/TESTING`）存在的理由** —— 没有设备侧试连，
云端无法区分"ACL 没生效"和"网络问题"，也无法安全地把新凭据升级为唯一有效凭据。

**等待窗口取值（冻结）**：`≥2 s`，**保守取 3 s**（依据 P1-0 A-1c：收紧 1.35 s / 恢复 1.37 s，3 轮极差 ≤0.08 s）。
实现上 = "写 ACL 成功后至少等 3 s 才下发"（可与 ④⑤ 并行，不额外增加总时长）。

### 6.4 下发（Protocol 草案，实现属 Phase D）

复用既有 **`system` 命令**，新增对象 `credential_set`（**不新增顶层命令名**）。

下行（新格式；`c:"system"` **不需要** `v`/`k`）：

```json
{
  "c": "system",
  "i": "cred_288485896ce4_g2",
  "t": 1785514668,
  "p": {
    "o": "credential_set",
    "action": "install",
    "username": "dev_288485896ce4",
    "password": "<32 字符高熵随机串>",
    "generation": 2,
    "slot": 1
  }
}
```

旧格式等价写法（调试用，`cmd` 原样透传）：

```json
{"cmd":"system","ob":"credential_set","id":"cred_288485896ce4_g2",
 "pl":{"action":"install","username":"dev_288485896ce4","password":"<...>","generation":2,"slot":1}}
```

设备 ACK（**绝不回显 password**）：

```json
{"s":"accepted","c":"system","i":"cred_288485896ce4_g2","o":"credential_set",
 "p":{"username":"dev_288485896ce4","generation":2}}
```

设备自证成功后的上行（**用新凭据连接发出**）：

```json
{"c":"system","i":"cred_288485896ce4_g2","s":"success","o":"credential_set",
 "p":{"generation":2,"username":"dev_288485896ce4","connack":"ok"}}
```

| `action` | 语义 | 归属 |
|---|---|---|
| `install` | 写入 TESTING slot 并试连 | **Phase D 实现** |
| `confirm` | （保留）管理端显式确认，用于设备不在线的兜底 | 可选 |
| `rollback` | 丢弃 TESTING slot 回到旧凭据 | **Phase D 实现** |

**约束**：
- `password` **只允许**出现在下行报文中；设备 ACK、上行、日志、D1 **均不得出现**（D-5 负向 grep 用例）。
- `generation` 必须单调递增；设备侧拒绝 `generation ≤ 当前` 的下发（防重放）。
- 每次下发必须换新 `i`（否则被 30 s 去重缓存静默丢弃）。
- 业务错误码沿用既有 1–13；凭据相关新增 **14/15/16**（提案：`CRED_INVALID_PAYLOAD` / `CRED_NVS_WRITE_FAIL` / `CRED_GENERATION_STALE`，Phase D 实施时定稿）。

### 6.5 幂等键与重入

| 操作 | 幂等键 | 重复请求行为 |
|---|---|---|
| 建档 | `device_id` | `ON CONFLICT DO UPDATE`，不重建 |
| 签发 | `(device_id, generation)`（D1 已有唯一索引） | 返回既有行，**不重复建账号 / 不重复下发** |
| 写 ACL | `username` | 全量覆盖 |
| 下发 | `i`（命令 ID） | **每次必须新**；同 `i` 重复会被设备静默丢弃 |
| 升级 ACTIVE | `(device_id, generation, state=PROVISIONING)` | 条件更新，重复到达无副作用 |

### 6.6 并发控制

同一 `device_id` 的签发必须**串行**（否则可能建出两个账号或两条 `PROVISIONING` 行）。
D1 无跨请求事务锁 ⇒ 采用：

1. **D1 唯一索引兜底**：`UNIQUE(device_id, generation)` + `UNIQUE(device_id) WHERE state='TESTING'` 已提供硬约束；
2. **软锁**：签发前先 `INSERT` 占位行（`PROVISIONING`），**占位成功者才继续**，失败者直接返回"进行中"；
3. 占位行超时（建议 60 s）由对账任务回收（§8）。

## 7. 失败模式与恢复矩阵

| # | 阶段 | 失败表现 | 系统状态 | 恢复动作 |
|---|---|---|---|---|
| F-1 | ① 建账号 | API 5xx / 超时 | 无账号；`PROVISIONING` + `provision_error` | 重试（幂等），`provision_attempts++` |
| F-2 | ① 建账号 | 账号**已存在** | 幂等成功 | 继续 ②（**不得**判失败） |
| F-3 | ② 写 ACL | 400（body 格式错） | **能连不能收**（C-4 复现） | 修 body（对象而非数组）；重写 |
| F-4 | ② 写 ACL | 5xx | 同上 | 重试 |
| F-5 | ③ 就绪窗 | 设备在窗口内就试连 ⇒ 被拒 | 设备侧**假失败** | **P1-3 必须**：网络/授权失败不得误判为凭据失败（D-2b） |
| F-6 | ④ 落库 | D1 写失败 | 账号与 ACL 已存在但云端无记录 | 以 EMQX 为准对账（列出 `dev_*` 账号 diff D1）；补写记录 |
| F-7 | ⑤ 下发 | 设备离线 | 行停在 `PROVISIONING`（无 `provision_error`） | 等下次上行时重发（或超时告警） |
| F-8 | ⑥ 自证 | 长时间不 confirm | 半成品 | 超时（建议 **300 s**）⇒ 写 `provision_error='confirm_timeout'` + 告警 + 可回收 |
| F-9 | 全链路 | 重复投递 | — | 由 §6.5 幂等键吸收 |
| F-10 | 退役 | 只改 ACL 未踢连接 | **设备继续可用**（最长到自然断线） | 必须执行 `DELETE /clients/{clientid}`（Freeze 强制） |

### 7.1 回收（未激活即废弃）

`PROVISIONING` / `TESTING` 行确认失败后：
```
DELETE ACL rules → DELETE user → UPDATE credential SET state='REVOKED', revoked_at=now,
                                             provision_error=<原因>
```
> 回收 `PROVISIONING` 不需要踢连接（该凭据从未被成功使用）。

### 7.2 退役（已激活）

```
UPDATE .../rules/users/{u}  (收紧为 deny)
+ DELETE /clients/{clientid}       ← 缺此步 revoke 不成立
+ UPDATE device SET state='REVOKED'
+ device_event: acl_update + session_terminate + retire
```

## 8. 对账（Reconcile）与可观测性

| 任务 | 判据 | 动作 | 频率建议 |
|---|---|---|---|
| 半成品超时 | `state='PROVISIONING' AND issued_at < now-60` 且 `provision_error IS NULL` | 重试或标记超时 | 低频（可用定时 Automation，**不引入常驻轮询**） |
| confirm 超时 | `PROVISIONING` 且已下发 > 300 s | `provision_error='confirm_timeout'` + 告警 | 同上 |
| 孤儿账号 | EMQX `dev_*` 账号 ∖ D1 `username` | 记录并告警（**不自动删**） | 手工触发 |
| ACL 缺失 | D1 `username` 存在但 EMQX 无对应规则 | 重写 ACL | 手工触发 |
| 无效会话 | 已 REVOKED 但仍有在线会话 | 踢连接 | 手工触发 |

**可观测性（必须可查）**：
- `GET /api/device/<device_id>` 返回 `device.state` + **凭据三态**（§4.2 的判定结果）+ `provision_error` + `acl_ready_at`。
- 每条签发链路都要能在 `device_event` 里**按时间轴复盘**（哪一步成功/失败）。

**容量**：本闭环全部为低频控制面动作（每设备一生 ≈ 数次），远低于 P1 容量约束（§2.5：< 100 行/天/11 台）。

## 9. 凭据（密码）的安全边界

| 环节 | 规定 |
|---|---|
| 生成 | 云端 CSPRNG，**32 字符**，建议 base62（EMQX 字符集几乎不限，A-4 已验；避开引号/反斜杠便于 MQTT 载荷） |
| 存在性 | 明文**只**存在于：① Worker 内存（生成 → 下发）② 一次下行报文 ③ 设备 NVS |
| D1 | **不存明文，也不存任何可离线穷举的派生值**（P1-1 已用 DDL 层保证） |
| 日志 | Worker 日志 / 审计 / `device_event.payload` **一律不得包含 password**（payload 只放 `username`/`generation`/结果） |
| 仓库 | 明文凭据**永不入库**（沿用 P0 §8 安全约定） |
| 串口 | 设备侧**不得**打印明文凭据（D-5 负向 grep） |
| 轮换 | P0 遗留共享凭据（`GuoFeederDevice`）在 P1 全量切到「一机一密」后**必须吊销并踢线**，见 §15-Q6 |

## 10. API 契约草案（设计级，Phase C 实施时落地）

### 10.1 端点

| 方法 | 路径 | 鉴权 | 作用 |
|---|---|---|---|
| `POST` | `/api/ingest` | `WEBHOOK_SECRET`（**P0 遗留待启用**） | EMQX 数据集成入口：建档 / 刷 `last_seen` |
| `POST` | `/api/admin/device/<id>/claim` | Admin token | 准入（§5.4-A）：放行后触发签发 |
| `POST` | `/api/device/<id>/credential` | Admin token（P1；APP 授权延后） | 签发 / 重发（幂等键 `(id,generation)`） |
| `POST` | `/api/device/<id>/credential/rotate` | Admin token | 轮换（Phase D 联调） |
| `POST` | `/api/device/<id>/revoke` | Admin token | 退役（§7.2 三步） |
| `GET`  | `/api/device/<id>` | Admin token | 状态查询（含凭据三态与失败原因） |

> **P1 不实现用户登录 / JWT**（P1 冻结 #3：APP 授权模型延后）⇒ 管理端点先用**单一 Admin 静态 token**（Worker Secret），
> 并在路径上明确标注 `admin`，避免后续与 APP 端点混淆。

### 10.2 请求 / 响应示例（签发）

```jsonc
// POST /api/device/288485896ce4/credential
{ "generation": 2, "reason": "initial_claim" }

// 200
{
  "device_id": "288485896ce4",
  "username": "dev_288485896ce4",
  "generation": 2,
  "state": "PROVISIONING",          // 三态：PROVISIONING(PENDING) / ACTIVE(OK) / REVOKED
  "acl_ready_at": null,             // null ⇒ 尚无就绪证据（等待设备 CONNACK 自证）
  "dispatched": true,               // 下行是否已发出
  "provision_error": null
}
```

**错误码（云端业务层，与设备侧 1–13 无关，独立命名空间）**：

| code | 含义 |
|---|---|
| `400` | 载荷非法 / `generation` 非递增 |
| `404` | `device_id` 不存在 |
| `409` | 该设备签发/轮换**正在进行中**（占位行未释放） |
| `422` | `device.state` 不允许签发（如 `REVOKED`） |
| `502` | EMQX API 失败（附 `stage`: `create_user` / `put_acl`） |
| `504` | 下发超时 |

## 12. 给 Phase D（P1-3）的接口冻结

Phase C 只**定义**、Phase D 才**实现**：

| 项 | 冻结内容 |
|---|---|
| 下行对象 | `system.credential_set`，字段 `action/username/password/generation/slot` |
| 上行确认 | 复用 `result` 帧，`o:"credential_set"`，`p.generation` |
| 设备侧存储 | NVS namespace `gfcred`，双 slot，状态 `ACTIVE/TESTING/INVALID` |
| 失败判定纪律 | **网络失败（超时/DNS/TLS）≠ 凭据失败** ⇒ 不得因一次连不上就弃用 `ACTIVE`（D-2b） |

| 明文纪律 | 串口/日志不打印密码 |

## 14. Phase C 完成判据（DoD）

1. 未知 `device_id` 上行 ⇒ 建档且**停在 `CLAIM_PENDING`**（无任何自动升级路径）。
2. 准入通过后，签发链路 ①–⑦ 全程可复盘（`device_event` 时间轴完整）。
3. `PROVISIONING`（含 `provision_error`）→ `ACTIVE` 的**每一次转移都有证据**（`acl_ready_at` 非空）。
4. 故意只建账号不写 ACL ⇒ **能连不能收** 可复现，且**检测手段能发现**（C-4）。
5. 退役路径 **同时**含 ACL 与踢连接（C-6）。
6. 全链路日志 / D1 / 仓库中**无明文密码**（负向 grep 通过）。
7. P0 身份链路零回归：`device_id` / topic 渲染结果不变（D-6）。
