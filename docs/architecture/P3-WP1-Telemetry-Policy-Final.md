## 1. Telemetry Policy 唯一权威位置（**架构铁律**）

> **铁律**：**降频规则只能有一套，且位于「唯一权威位置」。**
> **禁止**设备侧 / EMQX / Worker **多层重复定义** telemetry policy —— 各写一套必然导致**口径漂移、难以排障、无法验证**。

| 层 | **唯一职责** | **不做什么** |
|---|---|---|
| **设备侧（★ 唯一权威位置）** | **采样决策**：决定**采样频率**、**阈值**、"**何时算变化**"、"**是否值得上报**" | 不做存储、不做转发过滤 |
| **EMQX** | **只执行过滤**：按数据集成规则 SQL `WHERE` 做**转发前过滤** | **不重新定义阈值语义**（只应用设备侧已定口径） |
| **Worker（ingest）** | **只负责 ingest / storage**：接收 → 边界校验 → 批量写入 → 幂等 → 持久化 | **不判断"该不该存" / 不做任何业务语义判断 / 不实现降频** |

**⇒ 冻结结论**：**采样决策 = 设备侧**；**过滤 = EMQX（执行者）**；**ingest / storage = Worker（执行者）**。
（与 `P3-History-D1-Plan.md` WP-1「★★ 架构约束」· WP-4 边界**逐条一致**。）

**禁止的反模式**：

| 反模式 | 后果 |
|---|---|
| 设备侧按阈值上报 **＋** EMQX 又按自己的阈值过滤 | 双重阈值 ⇒ 实际口径 = 两者交集，**不可解释** |
| Worker 内再判一次"重量变化是否有效" | **第三套 policy** ⇒ 多层不一致，且 Worker CPU 预算被业务逻辑吃掉 |
| 多层都实现"变化检测" | 排障时**无法定位**是哪一层丢的数据 |

## 2. 数据分类（**9 类**）与边界声明

| # | 类别 | 典型来源 | 数据性质 |
|---|---|---|---|
| **1** | **EVENT / ERROR** | `EVENT_*` · `VALVE_ERROR` · 安全事件 · **System health 异常**（见 §3.9） | 事件驱动、低频、**高价值** |
| **2** | **Valve action** | `VALVE_OPEN` / `VALVE_CLOSE` · `0x0505` · `water/valve` | 动作驱动、中低频 |
| **3** | **Weight** | `weight.value` · `water/weight` · `water/weight-error` · `water/zero` | 连续、**高频**（依赖 `weight.enable` 见 §3.3） |
| **4** | **Water（水位 / 水量）** | **当前无独立传感器** ⇒ 由 Weight 派生 | 连续、高频（若存在） |
| **5** | **Temperature / Humidity** | `climate/temperature` · `climate/humidity`（Mijia `LYWSD03MMC`） | 连续、中高频 |
| **6** | **Online state** | `$state`（§12.3）· `system/mqtt-connected` · 连接生命周期 | 状态迁移、低频 |
| **7** | **Heartbeat** | 周期性保活 / 心跳 | 周期、**高频** |
| **8** | **Log** | LogManager 结构化日志批次（`§8.2` log Topic 预留） | 可抑制批量流、级别相关 |
| **9** | **★ System health** | `system/wifi-rssi` · `wifi-signal` · `time-valid` · `event-queue` · `mqtt-retries` | 低频诊断指标（**仅异常落库**） |

### 2.1 边界声明（`F-3`）—— telemetry 与 control event 的区分

| 归属 | 定义 | 例 |
|---|---|---|
| **✅ 纳入 telemetry / event** | **设备侧观测** —— **执行结果** · **设备事件** · state 变化 · 传感器读数 | `water/valve` 的**实际开合结果**、`weight` 读数、`$state` 迁移 |
| **❌ 排除（control event）** | **客户端下行命令本身**（`/set` 帧 · `down` 命令帧）**不是 telemetry** | `homie/5/<id>/water/valve/set` 的**入站帧**、`c:"action"` 命令 |
| **❌ 排除（元数据）** | 设备元数据 / 静态标识 | `climate/battery` · `climate/scan-enabled` |

> **判据**：**"谁发起"决定归属** —— **云端发起 = control event（不入历史库）**；**设备侧观测到的结果/事件 = telemetry / event**。
> `control/computer-reset` 属**控制面**：仅记录其**执行结果**（若有），**不记录命令帧本身**。

### 2.2 `system/*` 属性归类（`F-2` 补全）

| 属性 | 归属 | 处置 |
|---|---|---|
| `system/mqtt-connected` | 类别 **6** Online state | 随连接生命周期迁移记录（§3.6） |
| `system/wifi-rssi` · `wifi-signal` | 类别 **9** System health | **仅异常落库**（§3.9） |
| `system/time-valid` | 类别 **9** System health | **仅异常落库**（翻转计入异常） |
| `system/event-queue` | 类别 **9** System health | **仅异常落库**（高水位计入异常） |
| `system/mqtt-retries` | 类别 **9** System health | **仅异常落库**（增长计入异常） |

### 2.3 关于「Water」的现状（**不得臆造**）

`§7.3` 列出「水位/温湿度」；但**当前 Device Model 的 `water` node 只有 `valve` / `weight` / `weight-error` / `zero`**（`cloud_protocol.md` §12.5）—— **没有独立水位属性/传感器**。
⇒ 本冻结**不假设存在水位传感器**；「水量」**由 Weight 派生**（避免重复落库）。若未来引入独立水位传感器，**归入类别 4** 并按 §3.4 处理。

## 3. 逐类策略定义（**9 类 × 5 维**）

> **通用口径**：下表**频率/行数均为「理论估算」**（**非实测**）；**实际消耗须由 WP-6 实测确认**。
> 单设备目标 **< 1200 行/天**（**保留**）。**各类"日行数"为类别上限，不可直接相加** —— 见 §4 注。

### 3.1 EVENT / ERROR

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是（100%）** |
| **采样频率** | **事件驱动**（非周期）；低频 |
| **降频方式** | **不做阈值降频**（本身稀疏）；**但必须做「去重 / 边沿」**（见注） |
| **生命周期倾向** | **长**（故障诊断 / 安全追溯） |
| **成本影响** | **低**（理论 **< 100 行/天**） |

> **注**：`issues:R-3` 已登记「跳变源导致 `dispense_guard` 反复强制关阀」（成对 ×2、峰值 6 次/s）
> ⇒ 事件类**若直接全量落库会产生风暴**。⇒ **去重 / 边沿策略**是本类的**前置设计项**（属设备侧决策层）。

### 3.2 Valve action

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是（100%）** |
| **采样频率** | **动作驱动**；中低频 |
| **降频方式** | **不降频**（每次开/关都是有意义的动作）；可考虑 **open/close 配对**为一条（**待定，不预设**） |
| **生命周期倾向** | **长**（供水行为追溯） |
| **成本影响** | **中低**（理论 **< 500 行/天**） |

### 3.3 Weight

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（仅"有意义的变化"） |
| **采样频率** | **高频**（连续采样） |
| **降频方式** | **变化阈值 + 抽样兜底**：变化 **> `X` g** 才记；或**每 `N` = 15 min** 至少一条（见 §5 `H-W1-1` / `H-W1-2`） |
| **生命周期倾向** | **短**（高频运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**）—— 依赖 `X` 取值 |

> **★ 前置依赖（`F-4` 冻结项）**：本类**依赖 `weight.enable = true`**。
> **`weight.enable = false` ⇒① 不产生 weight telemetry；② 不产生 weight error history** ——
> 依据 `cloud_protocol.md` §12.4：`water/weight` · `water/weight-error` · `water/zero` **同时不出现在 `$description`**（16 → 13 属性）⇒ **本类无任何数据**。
> ⚠️ 当前设备端 `weight.enable` 存疑（`P2-8-KI-2` 三方不一致，**未修复**）⇒ **WP-6 实测前须先确认真机取值**。

### 3.4 Water（水位 / 水量）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（若独立水位传感器存在）；**当前无该传感器** ⇒ 由 Weight 派生，**避免重复落库** |
| **采样频率** | **高频**（若存在） |
| **降频方式** | **每 5–15 分钟一条** 或 **变化超阈值** |
| **生命周期倾向** | **短**（高频运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**，若存在）；**当前 = 0（无传感器）** |

### 3.5 Temperature / Humidity

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（Mijia `LYWSD03MMC` 可用时） |
| **采样频率** | **中高频**（Mijia 广播采集） |
| **降频方式** | **每 5–15 分钟一条** 或 **变化超阈值** |
| **生命周期倾向** | **短**（环境运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**） |

> 注：`climate/battery` / `scan-enabled` 属**设备元数据** ⇒ **不落库**（§2.1）。

### 3.6 Online state

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（**仅状态迁移时**） |
| **采样频率** | **状态驱动**；低频 |
| **降频方式** | **仅记录 `$state` 迁移点** —— **记录**：`init` · `ready` · `disconnected` · `lost`（见 §5 `H-W1-4`） |
| **生命周期倾向** | **中 / 长**（可用性审计） |
| **成本影响** | **低**（理论 **< 50 行/天**） |

> **★ 统一状态词表（`F-5` 冻结项）**：**`init` / `ready` / `disconnected` / `lost` / `stale`**（`cloud_protocol.md` §12.3 + P1-6）。
> - **记录的迁移** = `init` → `ready` · `disconnected` · `lost`（`lost` 由 broker LWT 表达）。
> - **`stale`** = **存活探针投影标记**（P1-6：`last_seen` 超时只标 `stale`）⇒ **不是状态迁移，一律不记录**。
> - **`sleeping` / `alert`**（Homie 5 其余两态）**本设备不使用 ⇒ 显式排除**。
> - **⛔ 禁止周期性 `offline` event**：**不得**用"周期 online / heartbeat-timeout offline"当在线历史（见 §5 `H-W1-4`）。

### 3.7 Heartbeat

| 维度 | 定义 |
|---|---|
| **是否落库** | ❌ **否**（见 §5 `H-W1-3`） |
| **采样频率** | **高频（周期）** |
| **降频方式** | **不落库**（"降频到 0"）—— **不产生 D1 history row** |
| **生命周期倾向** | **N/A**（不进入历史库） |
| **成本影响** | **0**（**把总量压到 < 1200 行/天的关键一项**） |

> 在线态由 §3.6 的迁移点表达；心跳本身**不入库**。

### 3.8 Log

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是**，**但受 `BT-1` 门禁**（`G-4` / `B-2`，**未解除**） |
| **采样频率** | **可抑制的批量流**（`§8.2`：批 ≤16 条 / 单条 ≤4096 B） |
| **降频方式** | **级别过滤** + 设备侧**发送限流**（`LOG_TX_MIN_INTERVAL_MS = 500 ms` ⇒ 上限 2 Hz） |
| **生命周期倾向** | **长**（故障诊断）；**`payload` 须有体积上限**（`P3-History-D1-Plan.md` WP-2） |
| **成本影响** | **高**（`P3-plan-§6:R-4`：修 `BT-1` 后上行升至 **2 Hz（×30）**，日志量可能远超预估） |

> **★ 双级别分离（`F-6` 冻结项）** —— 两者是**独立策略项**，**不得混为一谈**：
>
> | 级别 | 取值（当前冻结） | 说明 |
> |---|---|---|
> | **① 设备 Flash Log 保存级别** | **`{WARN, ERROR, CRITICAL}`**（INFO 不落 Flash） | 源：`cloud_protocol.md` **§8.2**；**设备侧**行为 |
> | **② 云端 `LogHistory` 存储级别** | **`{WARN, ERROR, CRITICAL}`**（**默认与设备一致**，但**独立可调**） | **本冻结项**；**云端**行为；**不因设备 Flash 级别变化而自动跟随** |
>
> **⇒ 规则**：**调整任一级别须独立裁决并重新冻结**（例如未来将云端级别放宽至含 INFO，属独立变更，**不等于**放开设备 Flash）。

> **⇒ `Log` 是本设计中唯一"落库前必须等前置修复"的类别**（`BT-1`）。

### 3.9 ★ System health（`F-2` 新增 · §5 `H-W1-6` 冻结）

| 维度 | 定义 |
|---|---|
| **是否落库** | ❌ **正常 runtime health 不落库**；**仅异常进入 EVENT / ERROR**（§5 `H-W1-6`） |
| **采样频率** | **低频**（诊断参考；**不产生稳态历史行**） |
| **降频方式** | **异常触发** —— `wifi-rssi` 低于阈值 · `time-valid` 翻转 · `mqtt-retries` 增长 · `event-queue` 高水位 ⇒ **转为类别 1（EVENT/ERROR）** |
| **生命周期倾向** | **随类别 1**（长，故障诊断） |
| **成本影响** | **≈ 0 稳态**（正常不落库）；**异常时计入类别 1** |

> **⇒ 本类不产生独立的稳态历史流**：`system/*` 五项属性只在**异常**时以 **EVENT / ERROR** 形式落库（§2.2）。

## 4. 汇总矩阵（**9 类 × 5 维**）

| # | 类别 | 落库 | 采样频率 | 降频方式 | 生命周期倾向 | 理论成本（行/天） |
|---|---|---|---|---|---|---|
| 1 | **EVENT / ERROR** | ✅ 100% | 事件驱动 / 低 | 无阈值；**去重/边沿** | **长** | **< 100** |
| 2 | **Valve action** | ✅ 100% | 动作驱动 / 中低 | 不降频（或配对，待定） | **长** | **< 500** |
| 3 | **Weight** | ⚠️ 条件（依赖 `weight.enable`） | 高频 | **阈值 `X` + 抽样 `N` = 15 min** | **短** | **< 300** |
| 4 | **Water** | ⚠️ 条件（当前无传感器） | 高频 | 5–15 min 或超阈值 | **短** | **< 300 / 当前 0** |
| 5 | **Temp / Humidity** | ⚠️ 条件 | 中高频 | 5–15 min 或超阈值 | **短** | **< 300** |
| 6 | **Online state** | ⚠️ 条件（仅迁移点） | 状态驱动 / 低 | 仅记录迁移点 | **中 / 长** | **< 50** |
| 7 | **Heartbeat** | ❌ 否 | 周期 / 高 | **不落库** | N/A | **0** |
| 8 | **Log** | ✅ 是（**受 `BT-1` 门禁**） | 可抑制批量流 | 级别过滤 + 限流 | **长** | **高** |
| 9 | **★ System health** | ❌ 稳态否（**异常→类别 1**） | 低频 | 异常触发 | **随类别 1** | **≈ 0** |

> **⇒ 目标**：单设备 **< 1200 行/天**（**保留**）。
> **⚠️ 全部数字为「理论估算」**：11 台合计与免费额度占比**只能作数量级预测**，**实际须由 WP-6 实测确认**（**不得据估算下"安全"结论**）。
