## 4. ★ 观测面缺口矩阵（本计划最关键的约束）

> 结论先行：**当前固件缺少"设备侧负载"的直读仪器**。
> 纯云端手段只能测"速率"，测不到"CPU / `loop` 节奏"。这是本计划必须显式承认的边界。

| 指标 | 可得性 | 载体 | 缺口说明 |
|---|---|---|---|
| **上行帧速率** | ⚠️ **半可观测** | `log_history` 行数 + EMQX `recv_cnt` 采样 | `/log` 自 `10-16` 起**不写 `mqtt_messages`**（`DT:WP-4` 选择 B）⇒ 无法用帧表计数 |
| **重发次数** | ⚠️ 仅串口 | `[Log Cloud] ack timeout retry=…` | `s_stats.cloud_retx` **无导出命令** |
| **CPU / `loop` 耗时** | ❌ **无** | — | 全仓**无** `loop_ms` / `vTaskGetRunTimeStats` / 循环占空比埋点 |
| **任务栈高水位** | ⚠️ 仅串口，且仅 `workflow.create` | `uxTaskGetStackHighWaterMark` 打印 | 非命令返回字段；无通用入口 |
| **堆内存** | ✅ **可用** | `system.memory`（只读） | 含 `min_free`（起转以来最小值）⇒ 可作**峰值压力代理** |
| **Flash / LittleFS** | ✅ **可用** | `system.flash`（只读） | 可看段文件占用趋势 |
| **队列丢弃计数** | ❌ **不可得** | 固件把 `meta.drop_ring/drop_overflow/drop_unacked` 放**批次头** | **云端 ingest 不落库**：`log_history` 仅 8 列（`device_id/ts/level/code/boot_seq/seq/message/payload`），**无任何 `drop_*` 列** ⇒ 侧信道虽上行却**未持久化** |
| **WDT / 复位原因** | ✅ 可用 | `system.restart_status`（只读） | 可发现"负载导致的看门狗复位" |
| **Wi-Fi 质量** | ⚠️ 间接 | EMQX 客户端信息 / 设备重连 | 无 RSSI 直读命令 |

**⇒ 直接后果**：

- 只靠云端，可测 **速率 + 内存 + Flash + 复位原因**（4 项）；
- **不可测** CPU 占空比、`loop` 抖动、队列丢弃；
- 要测这些，**必须**走 §6 的方案 B（固件补命令）或方案 C（DDL 落库），**均属生产变更**。

## 5. 负载模型（先算清楚，再决定测什么）

### 5.1 三档速率

| 档 | 速率 | 触发条件 | 设备侧含义 |
|---|---|---|---|
| **日常稳态** | **≈57 行/天 ≈ 0.00066 条/s** | 正常运行 | 每 ~25 min 一帧 ⇒ **负载可忽略** |
| **突发** | 上限 **2 条/s** | 故障洪泛（如 `VALVE-6` 0.6 条/s、`WF-1` 39-40 次/s 但被门控） | **唯一有风险档**：每 500 ms 一次 TLS publish |
| **积压排空** | 受 `cloud_replay_step()` **每轮 1 步** + I/O 有界 | 离线后重连 / 长时间积压 | 排空时长**必须实测**（`BT1-T18`），**禁止**用"记录数 ÷ 2 条/s"估算 |

### 5.2 容量边界（决定"突发能撑多久"）

| 队列 | 容量 | 耗尽后果 |
|---|---|---|
| RAM 环 | **64** 条 | 淘汰最旧（`ring_drop++`） |
| 云待发队列 | **128** 条 | FIFO 淘汰 + 空洞登记（`cloud_q_drop++`） |
| Flash 段环 | **496** 条（16×31） | **仅 `WARN+` 落盘**；优先淘汰已确认段 |
| 空洞表 | **8** 个区间 | 溢出 ⇒ `hovf` ⇒ **本 Boot 停止回收**（保守） |

### 5.3 为什么"2 条/s"是唯一需要验证的场景

日常 **0.00066 条/s** 与上界 **2 条/s** 相差 **≈3,000×**。
若只测日常，测不出任何东西；若只在实验室跑上界，又不代表现场。
⇒ **必须构造"可控突发"**（§7.2），且必须测**排空时间**而非瞬时速率。

## 6. 三个候选方案（推荐 A，B/C 需单独授权）

| | **方案 A：全只读 + 可控突发**（推荐） | **方案 B：补只读命令** | **方案 C：落库侧信道** |
|---|---|---|---|
| 做法 | 云端只读查询 + `memory`/`flash`/`restart_status` + 串口采集 + 受控命令触发突发 | 新增 `system.stats`（暴露 `s_stats` + 栈高水位 + `loop` 计数） | migration 给 `log_history` 加 `drop_*` 列，ingest 落库 |
| 能答 | 速率、排空时长、内存/Flash 趋势、复位原因、**间接** `loop` 健康度（并发命令延迟） | **直读** `cloud_retx`/`ring_drop`/`cloud_q_drop`/栈高水位 | 长期趋势，无需串口 |
| 不能答 | CPU 占空比、队列丢弃**精确值** | CPU 占空比（仍需额外埋点） | 实时性差（需等下一批） |
| 生产变更 | **无代码/无 DDL**；仅**产生消息与日志**（需授权下发命令） | 改固件 + **烧录**（高影响） | **DDL**（migration）+ 改 ingest + 部署 |
| 授权级别 | **低**（一次只读测试窗口） | **高** | **高** |
| 建议 | ✅ **先做** | 仅在 A 结论为 `CONDITIONAL` 且缺口致命时申请 | 不作为 `G-4` 手段（属 `WP-5`/P4 观测建设） |

## 7. 方案 A 实施细则

### 7.1 阶段划分

| 阶段 | 内容 | 生产副作用 | 授权 |
|---|---|---|---|
| **A-0 前置核验** | 固件版本/设备在线/串口可用/时钟正确；确认 `ack` 已正常（无 `ack timeout retry`） | 无（只读） | 无需 |
| **A-1 稳态采样（24 h）** | 每 30 min 一次：`log_history` 增量、EMQX `recv_cnt`、`memory`、`flash` | 极低（约 48 次只读命令） | **需授权**（下发只读命令） |
| **A-2 可控突发** | 见 §7.2 | 产生约 **10~30 条**日志 + 对应消息 | **需授权** |
| **A-3 排空测量** | 突发后观察 `log_history` 增量与 EMQX `recv_cnt` 收敛 | 无 | 随 A-2 |
| **A-4 并发健康度** | 突发期间叠加 1 条 `config_query`，测响应延迟是否退化（`loop` 健康度**代理**） | 低 | 随 A-2 |
| **A-5 报告与裁决** | 汇总 + 判据对照 + **候选阈值**（待人工批准） | 无 | — |

### 7.2 可控突发设计（关键，且必须无硬件副作用）

**触发手段**：生产 `cloud_api`（`/api/command`）下发 **`system.config_query`**（只读）。

- **已验证**：每次 `config_query` 会设备侧产生 **1 条 `LOG_CMD_APPLIED`（INFO）** 并上行（`BT-1` 验收两轮均如此，seq `5174`/`5175`）。
- **无副作用**：不写配置、不动阀门/电机、不重启。
- **突发配方**（候选，需批准）：

| 批次 | 命令数 | 间隔 | 期望产生日志 | 目的 |
|---|---|---|---|---|
| `B-1` | 1 | — | 1 条 | 基线单帧延迟 |
| `B-2` | **10** | **1 s** | 10 条 | 中等突发（≈0.9 条/s，接近上界一半） |
| `B-3` | **20** | **0.6 s** | 20 条 | 逼近上界（≈1.5 条/s） |

> ⚠️ **风险与止损**：`B-3` 的 20 条会把云队列（128）占用 16%，**不构成压力**；但会产生 **20 条生产消息记录**。
> 若 `B-3` 期间出现任何异常（复位、`ack timeout retry`、响应延迟 >3×基线）⇒ **立即停止**，不再加批次。
> ⚠️ **禁止**：不用 `config_set` / `config_save` / `restart` 制造日志；不构造畸形 payload。

### 7.3 测量项与仪器

| 指标 | 仪器 | 采样方式 |
|---|---|---|
| 上行速率（条/s） | `log_history` 行数增量 | 按 `created_at`（**秒**）分桶 |
| 上行总量（含未落库帧） | EMQX `GET /clients/dev_…` → `recv_cnt` | 每 30 s 采样（**已实证可用**） |
| 排空时长 | 突发最后一条命令 → `log_history` 最后一条新增的时间差 | 事后 SQL |
| 内存压力 | `system.memory` → `internal.min_free` / `max_alloc` | 阶段前后各 1 次 |
| Flash 占用 | `system.flash` → `external.used` | 阶段前后各 1 次 |
| 复位/WDT | `system.restart_status` | 阶段前后各 1 次 |
| `loop` 健康度（**代理**） | 并发 `config_query` 的 ACK→终帧延迟（对比 §A-1 基线） | 每批 1 条 |
| 重发（可选） | 串口 `[Log Cloud] ack timeout retry` 计数 | 需物理接串口 |

### 7.4 判据（**候选，阈值须人工批准** —— `BT1-Q-9` 未裁决）

| ID | 判据 | 候选阈值 | 状态 |
|---|---|---|---|
| `L-1` | 突发期无 `ack timeout retry`（ACK 链路不退化） | **0 次** | 待批 |
| `L-2` | 排空时长 | **`≤ 突发条数 × 2 s`**（留 4× 余量） | 待批 |
| `L-3` | `loop` 健康度代理：并发命令终帧延迟 | **`≤ 3× 阶段基线`** | 待批 |
| `L-4` | 内存：`min_free` 不因突发下降超过 | **`5%`** | 待批 |
| `L-5` | 无 WDT / 无异常复位 | **`restart_status` 不变** | 待批（客观） |
| `L-6` | 日常稳态速率与 `WP-6`（57 行/天）同量级 | **`≤ 3×`（≤171 行/天）** | 待批 |
| `L-7` | 队列丢弃（`drop_*`） | ❌ **当前不可测**（§4）⇒ 只能由串口定性 | **已知盲区** |

**判定规则**：

- `L-1`/`L-5` 任一失败 ⇒ **`FAIL`**，`G-4` 条件② 不通过；
- `L-2`/`L-3`/`L-4` 失败 ⇒ **`CONDITIONAL`**（需方案 B 补测或降级 `WP-5` 范围）；
