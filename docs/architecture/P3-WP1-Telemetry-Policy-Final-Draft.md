## 1. Telemetry Policy 唯一权威位置（**架构铁律**）

> **铁律**：**降频规则只能有一套，且位于「唯一权威位置」。**
> **禁止**设备侧 / EMQX / Worker **三层同时实现**降频规则 —— 三层各写一套必然导致**口径漂移、难以排障、无法验证**。

| 层 | **唯一职责** | **不做什么** |
|---|---|---|
| **设备侧（★ 唯一权威位置）** | **采样决策**：决定**采样频率**、**阈值**、"**何时算变化**"、"**是否值得上报**" | 不做存储、不做转发过滤 |
| **EMQX** | **只执行过滤**：按数据集成规则 SQL `WHERE` 做**转发前过滤** | **不重新定义阈值语义**（只应用设备侧已定口径） |
| **Worker（ingest）** | **只负责存储**：接收 → 边界校验 → 批量写入 → 幂等 → 持久化 | **不判断"该不该存" / 不做任何业务语义判断 / 不实现降频** |

**⇒ 定稿结论**：**哪一层负责采样决策 = 设备侧**；**哪一层负责过滤 = EMQX**；**哪一层只负责传输与存储 = Worker**。
（与 `P3-History-D1-Plan.md` WP-1「★★ 架构约束」· WP-4 边界**逐条一致**。）

**禁止的反模式**：

| 反模式 | 后果 |
|---|---|
| 设备侧按阈值上报 **＋** EMQX 又按自己的阈值过滤 | 双重阈值 ⇒ 实际口径 = 两者交集，**不可解释** |
| Worker 内再判一次"重量变化是否有效" | **第三套 policy** ⇒ 三层不一致，且 Worker CPU 预算被业务逻辑吃掉 |
| 三层都实现"变化检测" | 排障时**无法定位**是哪一层丢的数据 |

## 2. 数据分类（**9 类**；`R1` 新增第 9 类）

> 与 `§7.3` 表的 6 行 + `cloud_protocol.md` §12.5 属性映射对齐；`R1` 补入 `system/*` 遥测属性（`F-2`）。

| # | 类别 | 典型来源 | 数据性质 |
|---|---|---|---|
| **1** | **EVENT / ERROR** | `EVENT_*` · `VALVE_ERROR` · 安全事件 | 事件驱动、低频、**高价值** |
| **2** | **Valve action** | `VALVE_OPEN` / `VALVE_CLOSE` · `0x0505` · `water/valve` | 动作驱动、中低频 |
| **3** | **Weight** | `weight.value` · `water/weight` · `water/weight-error` · `water/zero` | 连续、**高频**（依赖 `weight.enable`） |
| **4** | **Water（水位 / 水量）** | **当前无独立传感器** ⇒ 由 Weight 派生 | 连续、高频（若存在） |
| **5** | **Temperature / Humidity** | `climate/temperature` · `climate/humidity`（Mijia `LYWSD03MMC`） | 连续、中高频 |
| **6** | **Online state** | `$state`（§12.3）· `system/mqtt-connected` · 连接生命周期 | 状态迁移、低频 |
| **7** | **Heartbeat** | 周期性保活 / 心跳 | 周期、**高频** |
| **8** | **Log** | LogManager 结构化日志批次（`§8.2` log Topic 预留） | 可抑制批量流、级别相关 |
| **9** | **★ System health（`R1` 新增）** | `system/wifi-rssi` · `wifi-signal` · `time-valid` · `event-queue` · `mqtt-retries` | 低频诊断指标 |

**边界声明（`R1` 新增 · 依 `F-3`）—— telemetry 与 control event 的区分**：

| 归属 | 定义 | 例 |
|---|---|---|
| **✅ 纳入 telemetry** | **设备侧观测**（action 结果 · state 变化 · 传感器读数） | `water/valve` 的实际开合、`weight` 读数、`$state` 迁移 |
| **❌ 排除（control event）** | **客户端下行指令本身**（`/set` 帧 · `down` 命令帧） | `homie/5/<id>/water/valve/set` 的**入站帧**、`c:"action"` 命令 |
| **❌ 排除（元数据）** | 设备元数据 / 静态标识 | `climate/battery` · `climate/scan-enabled`（`R1` 沿用草案 §3.5 处置） |

> **说明**：`control/computer-reset` 属**控制面**；仅记录其**动作结果**（若有），**不记录命令帧本身**。

**关于「Water」的现状（**不得臆造**）**：
`§7.3` 列出「水位/温湿度」；但**当前 Device Model 的 `water` node 只有 `valve` / `weight` / `weight-error` / `zero`**（`cloud_protocol.md` §12.5）—— **没有独立水位属性/传感器**。
⇒ 本候选**不假设存在水位传感器**；「水量」**由 Weight 派生**。若未来引入独立水位传感器，**归入本类**并按 §3.4 处理。

## 3. 逐类策略定义（**9 类 × 5 维**）

> **通用口径**：下表**频率/行数均为「理论估算」**（**非实测**）；**实际消耗须由 WP-6 实测确认**。
> 单设备目标 **< 1200 行/天**（**保留**）。
> **⚠️ 各类"日行数"为**类别上限**，**不可直接相加** —— 见 §4 注。

### 3.1 EVENT / ERROR

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是（100%）** |
| **采样频率** | **事件驱动**（非周期）；低频 |
| **降频方式** | **不做阈值降频**（本身稀疏）；**但必须做「去重 / 边沿」**（见注） |
| **生命周期倾向** | **长**（故障诊断 / 安全追溯） |
| **成本影响** | **低**（理论 **< 100 行/天**） |

> **注（既有登记）**：`issues#R-3` 已登记「跳变源导致 `dispense_guard` 反复强制关阀」（成对 ×2、峰值 6 次/s）
> ⇒ 事件类**若直接全量落库会产生风暴**。⇒ **去重 / 边沿策略**是本类的**前置设计项**（属设备侧决策层）。

### 3.2 Valve action

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是（100%）** |
| **采样频率** | **动作驱动**；中低频 |
| **降频方式** | **不降频**（每次开/关都是有意义的动作）；可考虑 **open/close 配对**为一条（**待定，不预设**） |
| **生命周期倾向** | **长**（供水行为追溯） |
| **成本影响** | **中低**（理论 **< 500 行/天**） |

### 3.3 Weight

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（仅"有意义的变化"） |
| **采样频率** | **高频**（连续采样） |
| **降频方式** | **阈值 + 抽样**：变化 **> `X` g** 才记；或**每 `N` 分钟**至少一条 |
| **生命周期倾向** | **短**（高频运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**）—— **强烈依赖 `X` / `N` 取值** |

> **★ 前置依赖（`R1` 新增 · 依 `F-4`）**：本类**依赖 `weight.enable = true`**。
> 若 `weight.enable=false` ⇒ `water/weight` · `water/weight-error` · `water/zero` **不出现在 `$description`**（`cloud_protocol.md` §12.4，16→13 属性）⇒ **本类无数据**。
> ⚠️ 当前设备端 `weight.enable` 存疑（`P2-8-KI-2` 三方不一致，**未修复**）⇒ 冻结时须**先确认真机取值**。
> **★ `X` / `N` = `HUMAN_REQUIRED`**（见 §5 `H-W1-1` / `H-W1-2`）。

### 3.4 Water（水位 / 水量）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（若独立水位传感器存在）；**当前无该传感器** ⇒ 由 Weight 派生，**避免重复落库** |
| **采样频率** | **高频**（若存在） |
| **降频方式** | **每 5–15 分钟一条** 或 **变化超阈值** |
| **生命周期倾向** | **短**（高频运行数据） |
| **成本影响** | **中**（理论 **< 300 行/天**，若存在）；**当前 = 0（无传感器）** |

### 3.5 Temperature / Humidity

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（Mijia `LYWSD03MMC` 可用时） |
| **采样频率** | **中高频**（Mijia 广播采集） |
| **降频方式** | **每 5–15 分钟一条** 或 **变化超阈值** |

| **成本影响** | **中**（理论 **< 300 行/天**） |

### 3.6 Online state

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（**仅状态迁移时**） |
| **采样频率** | **状态驱动**；低频 |
| **降频方式** | **仅记录 `$state` 迁移点**：`init` → `ready`；**`disconnected` / `lost`**（`lost` 由 broker LWT 表达） |
| **生命周期倾向** | **中 / 长**（可用性审计） |
| **成本影响** | **低**（理论 **< 50 行/天**） |

> **★ 术语（`R1` 依 `F-5` 校正）**：规范状态名 = **`init` / `ready` / `disconnected` / `lost`**（`cloud_protocol.md` §12.3）。
> **`sleeping` / `alert`**（Homie 5 其余两态）**本设备不使用 ⇒ 显式排除**。
> **★ `HUMAN_REQUIRED`**（见 §5 `H-W1-4`）。
> **⚠️ 不要**用"周期性 `offline` 事件"当作在线状态历史 —— P1-6 已确立「**`last_seen` 超时不再产生 `offline`，只标 `stale`**」⇒ **唯一可信的迁移点 = `$state` / 连接事件**。

### 3.7 Heartbeat

| 维度 | 定义 |
|---|---|
| **是否落库** | ❌ **否**（仅内存 / 在线态） |
| **采样频率** | **高频（周期）** |
| **降频方式** | **不落库**（"降频到 0"） |
| **生命周期倾向** | **N/A**（不进入历史库） |
| **成本影响** | **0**（**把总量压到 < 1200 行/天的关键一项**） |

> **★ `HUMAN_REQUIRED`**（见 §5 `H-W1-3`）。在线态由 §3.6 的迁移点表达。

### 3.8 Log

| 维度 | 定义 |
|---|---|
| **是否落库** | ✅ **是**，**但受 `BT-1` 门禁**（`G-4` / `B-2`）；**云端 `LogHistory` 落库级别 = `{WARN, ERROR, CRITICAL}`**（`R1` 依 `F-6` 明确，与设备 Flash 落盘级别一致 —— `cloud_protocol.md` §8.2） |
| **采样频率** | **可抑制的批量流**（`§8.2`：批 ≤16 条 / 单条 ≤4096 B） |
| **降频方式** | **级别过滤**（INFO 不落）+ 设备侧**发送限流**（`LOG_TX_MIN_INTERVAL_MS = 500 ms` ⇒ 上限 2 Hz） |
| **生命周期倾向** | **长**（故障诊断）；**`payload` 须有体积上限**（`P3-History-D1-Plan.md` WP-2） |
| **成本影响** | **高**（`P3-plan§6#R-4`：修 `BT-1` 后上行升至 **2 Hz（×30）**，日志量可能远超预估） |

> **⇒ `Log` 是本设计里**唯一**"落库前必须等前置修复"的类别**（`BT-1`）。

### 3.9 ★ System health（`R1` 新增）

| 维度 | 定义 |
|---|---|
| **是否落库** | ⚠️ **条件落库**（`R1` 建议：**仅异常 / 显著劣化时落库**，稳态不落） |
| **采样频率** | **低频**（`R1` 建议每 15–30 分钟采样一次） |
| **降频方式** | 临界值触发（如 `wifi-rssi` 低于阈值 · `time-valid` 翻转 · `mqtt-retries` 增长 · `event-queue` 高水位） |
| **生命周期倾向** | **短 / 中**（诊断用，非业务追溯） |
| **成本影响** | **低**（理论 **< 100 行/天**） |

> **★ `R1` 说明**：本类为**补齐分类完整性**（`F-2`）而新增；其**是否落库 / 频率 / 阈值**属**新增待裁决项** ⇒ 见 §5 **`H-W1-6`**。
> **备选**：若人工决定**不落库**，则须在 §2 将本类**显式排除**（并注明理由）。
