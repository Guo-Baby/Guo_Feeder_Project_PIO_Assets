# P4-3 配置失败与回滚路径 —— 演练结论与配置写入门禁最终方案（2026-10-26）

> 对应任务书第六节。**结论先行**：
> 10 个场景里 **6 个可以安全自动化**（已写成脚本、可复跑），**4 个是破坏性场景**
> （Flash 写失败 / 启动失败 / 非计划重启回滚 / 提交卡 PENDING）—— 它们**不能**在
> 唯一的生产设备上自动制造，本文件给出**可由用户执行的人工步骤 + 风险 + 恢复流程 + 判定标准**。
> 门禁的最终策略见 §4，**本轮不静默改动生产门禁**。

### 1.1 为什么 S1–S4 不能自动做（不是"没做"，是"不能这么做"）

| 场景 | 为什么不能自动 | 能不能用固件已有测试接口替代 |
|---|---|---|
| S1 Flash 写失败 | 需要介质级故障（只读分区 / 满盘 / 擦写错误） | **无**。固件没有"故意写失败"的开关，且**不得**在生产固件里加默认开启的故障注入入口 |
| S2 启动失败 | 需要让启动阶段崩（坏配置 / 资源缺失） | **无**。但 CFG-ROLLBACK 链（Active/Backup/`.bootok` + commit）已在固件里实现并可静态审计 |
| S3 非计划重启回滚 | 需要物理断电 / 看门狗复位 | **无**。固件无"模拟掉电"入口 |
| S4 提交卡 PENDING | 需要在 Flash 事务窗口断电 | **无**。事务窗口很窄，需要可编程断电 |

> ★ **明确不做的事**：不为了"跑出 PASS"而往生产固件里加故障注入开关，
> 不在唯一设备上制造无法可靠恢复的故障。这四项的**未执行**是**有理由的风险接受项**，
> 不是"测试通过"。

## 2. 演练脚本（`scripts/hw_config_fault_drill.mjs`）

| 能力 | 说明 |
|---|---|
| 只跑指定设备 | 必须 `--device <12hex>`；**不枚举、不批量** |
| 双重确认 | `--confirm-gate`（承认写通道会被临时打开）+ `--confirm-fault`（承认会真的改配置） |
| 前置检查 | 设备在线 / 写门禁已开 / 设备在白名单 / 键在白名单 / 管理令牌存在 —— **任一不满足立即停** |
| 前置取证 | 原值、version、boot_seq 全部落证（**不知道原值就不许开始**） |
| 分项记录 | 每项记录：请求受理（http）/ 命令终态 / 设备回帧 / 设备回读值 / 时间线 |
| 判定 | **202=受理；ACK=收到；`s=1`=入队；只有设备 result 帧 `s=0` 才算成功**；无回帧 = **UNKNOWN** |
| 恢复 | 可自动恢复的场景测完**写回原值并复核**（值 + version + boot_seq） |
| 停止条件 | 任何 **FAIL** 或恢复失败 ⇒ 立刻停止后续测试并输出告警 |
| 防重复执行 | 同设备 30 分钟内只允许跑一次（`.p43-drill.lock`） |
| 输出 | 机器可读 `result.json` + 人读 `report.md`（含破坏性场景的人工步骤） |
| 只读演练 | `--dry-run` 只做前置检查与计划输出，**不写设备** |

**实跑（2026-10-26，用户授权后）**：**6 PASS / 0 FAIL / 0 UNKNOWN / 4 NOT RUN**
（证据 `Cloudflare_Assets/docs/evidence/p4-3-fault-drill-2026-10-26/{result.json,report.md}`）。
演练后**独立复核**（另发一条 `config_query` 回读）：`time.sync_interval_sec = 86400`（原值）·
`versions.time = 5` · 最新日志 `boot_seq = 103` ⇒ **原值已还原，设备状态正常**。

> ★ 演练脚本本身在实跑前抓到并修掉两个**真 bug**：
> ① `curlJson` 少了 `-w "\n%{http_code}"` ⇒ 把 JSON 末行当状态码 ⇒ body 解析失败
>    ⇒ "设备在线"被误判成"离线"；
> ② `preVal` 声明在 `try` 块内、场景块作用域不可见 ⇒ `ReferenceError` 崩掉。
> 另外给 `curl` 加了失败兜底（记 UNKNOWN + 打印 exit code，不再让整个演练崩）。

## 3. 临时写窗口的开启/关闭步骤（供授权后执行）

| 步骤 | 动作 | 验证 |
|---|---|---|
| 1 | 部署 Worker，附 `CONFIG_WRITE_ENABLED=1`、`CONFIG_WRITE_DEVICES=288485896ce4`、`CONFIG_WRITE_KEYS=time.sync_interval_sec` | 目录 `config_write.enabled=true` 且 `scope` 精确到 1 设备 1 键 |
| 2 | 跑 `node scripts/hw_config_fault_drill.mjs --device 288485896ce4 --confirm-gate --confirm-fault --evidence-dir docs/evidence/p4-3-<date>` | `result.json` / `report.md` |
| 3 | **立即**关闭窗口：重部署去掉三个环境变量 | 目录 `enabled=false`；写命令实测 **403 `config_write_disabled`** + **零下行帧** |

> ★ 三个变量是**最窄窗口**：只 1 台设备、只 1 个键（`time.sync_interval_sec`，

> ★ 默认常量 `CONFIG_WRITE_ENABLED_BY_DEFAULT` **始终 false**，不因演练而改。

## 4. 配置写入门禁的最终方案（待授权）

### 4.1 现状

| 项 | 值 |
|---|---|
| `CONFIG_WRITE_ENABLED_BY_DEFAULT` | **false**（从未改成 true） |
| 生产目录 `config_write.enabled` | **false** |
| 生产写命令实测 | **403 `config_write_disabled`** + **零下行帧** |
| 服务端校验 | `validateConfigParams`（模块/键/类型/范围/枚举/占位符/`expect_version`）+ `configWriteAllowed`（开关→设备→键 三级） |

### 4.2 三个可选方案（**请选一个**）

| 方案 | 内容 | 优点 | 风险 |
|---|---|---|---|
| **A. 保持关闭**（现状） | 门禁维持 false，等破坏性场景有人工结论 | 零风险 | R30 永久 🚫；用户无法自行改配置；写通道能力从未被真实用户使用 |
| **B. 开放"受限配置写入"**（**推荐**） | 常开 `CONFIG_WRITE_ENABLED=1`，但**永久**保留：① 设备白名单（先只放 `288485896ce4`）② 键白名单（先只放 `time.*` 这类低风险键）③ 类型/范围/枚举校验 ④ `expect_version` 乐观锁 ⑤ 全量审计落 `command_audit` | 用户能自行改**低风险**配置；所有安全校验仍在；随时可按键收敛 | 中低：用户可能误改仍会造成行为变化；**破坏性故障注入能力与普通配置编辑必须分离**（不提供任何故障注入入口） |
| **C. 全开** | `CONFIG_WRITE_ENABLED=1` 且不加键白名单 | 最自由 | 高：可改 `valve.gpio_pin` / `stepper.*` 等**物理执行器**参数 ⇒ 失控/常开风险；且**当前协议无法在故障时区分"已生效"与"已接收"** |

### 4.3 推荐 B 的具体形态（**破坏性注入与普通编辑严格分离**）

| 层 | 内容 |
|---|---|
| 常开 | `CONFIG_WRITE_ENABLED=1` |
| 设备 | `CONFIG_WRITE_DEVICES=288485896ce4`（新增设备须显式加） |
| 键 | `CONFIG_WRITE_KEYS=time.sync_interval_sec,time.timezone`（**只放不驱动物理执行器的时间类键**） |
| 保留 | 鉴权（Bearer/会话）、设备白名单、键白名单、类型/范围/枚举校验、`expect_version` 乐观锁、`command_audit` 全量审计 |
| **分离** | **不提供任何故障注入入口**；`CONFIG_WRITE_KEYS` 里永远不放 `valve.*` / `stepper.*` / `vibration.*` / `weight.*`（这些要么留在关闭态，要么需要单独的、更严格的授权） |
| 回滚 | 把 `CONFIG_WRITE_ENABLED` 去掉（或清空 `CONFIG_WRITE_KEYS`）重新部署 ⇒ 立刻回到只读 |
| 观测 | 每次写入都在「记录 → 审计」可见（cmd_id / 操作者 / 前后值 / 终态） |

### 4.4 仍需人工验收的破坏性场景（无论选哪个方案都保留为风险接受项）

| 场景 | 人工步骤 | 判定标准 | 恢复 |
|---|---|---|---|
| S1 Flash 写失败 | 用 df/量产工具把目标分区写满或置只读 → `config_set` + `config_save` | 设备回 `s=3/s=4`，**RAM 值不变、version 不变** | 解除只读后重新 save ⇒ version +1 且回读一致 |
| S2 保存成功但启动失败 | 写入语义致命但语法合法的配置 → save → restart | 重启后**无 0x0B Registry 段日志 / 无 heartbeat** | bootloader 或复位 ⇒ 触发 CFG-ROLLBACK 回落 Backup |
| S3 非计划重启回滚 | save 后**不**正常重启，5 分钟窗口内物理断电再上电 | 启动日志出现 **0x0102**（回滚证据） | 确认用 Backup（落盘前值）启动后再正常 save |
| S4 提交卡 PENDING | 在 `config_save` 落盘阶段立刻断电（需可编程断电或串口卡点） | 启动校验到 **PENDING** ⇒ 拒绝启动 | 按 CFG-ROLLBACK 走 Active/Backup 回落链（`config_manager.cpp:1115-1196`） |

> ★ 这四项需要**物理接触设备**与**可恢复的 bootloader 手段**。本项目只有一台设备、
> 且没有第二台可当"实验品" ⇒ **在当前硬件条件下无法自动化**。这是**硬件约束**，
> 不是流程疏忽。建议：在拿到第二台设备前，这四项按"**未执行 · 风险接受**"记录，
> 并在用户使用写配置时**优先使用可随时还原的低风险键**。
