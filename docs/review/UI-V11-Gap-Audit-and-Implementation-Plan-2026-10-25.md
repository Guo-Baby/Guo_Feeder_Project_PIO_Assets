## 0. 结论：当前 UI 距离 V1.1 原型还差什么、按什么顺序做、怎么证明做完

### 0.1 差距一句话总结

V1.1 原型共 **24 屏**（`docs/ui-v1/prototype.html`，纯静态设计稿）。生产 UI **完整落地 6 屏、部分落地 11 屏、未做 7 屏**；另外有 **2 个生产阻断缺陷**（审计页 403、日志事件列全 NULL）与 **1 处生产状态不一致**（EMQX 已有 5 个池账号而 D1 侧 0010 迁移在本次审计前未应用）。

用户本次提出的 11 项工作里，**9 项在生产有部分或完整实现**（可增量补齐），**2 项必须先有协议/后端能力**（单 Workflow 精确强停 = 固件缺口；跨控制端操作历史 = 数据来源缺口）。

### 0.2 实施顺序（依赖驱动，不是按 UI 好看程度）

```
P0 修正生产阻断（不动架构）        ← 先做，否则「审计页」根本打不开
   └─ 补 Pages 白名单 history/command

P1 状态可见性三件套（用户最在意"能不能信"）
   ├─ 操作来源标注（HTTP/MQTT 逐条可见）
   ├─ Unknown 出口：迟到回帧改判可见 + 「重新查询状态」按钮
   └─ 日志去噪（查询层过滤 + 中文名映射）  ← 不落库、不动 SQL

P2 快捷操作与首页布局（纯前端 localStorage，零后端）
   ├─ 数量 1..12 自由 + ↑↓ 排序 + 折叠
   └─ 首页布局管理（显隐/排序/锁定安全四要素/恢复默认/按设备隔离）

P3 自动化（流程→自动化）改名 + 执行详情页 + 独立编辑器
   └─ 前置：先出「流程运行态可读性」方案（query_workflows 有态、workflow.list 无态）

P4 配置 UI 化（最高风险，最高价值）—— 必须分三步走
   ├─ 4a 读：模块详情页 + Config 分类页（只读→可编辑的骨架，含中文名/范围/依赖）
   ├─ 4b 写：RAM 改 + 落盘 + 重启 三段式（含 5 分钟倒计时 UI，固件已实现）
   └─ 4c 失败演练：保存失败/重启失败/设备离线/非计划重启 的回滚与复核

P5 多设备（设备列表 + 切换 + 别名跨端）
   └─ 前置：设备清单端点（Worker 已有 /api/admin/user/:uid/devices，但无在线状态）

P6 EMQX 动态账号池（可选，取决于 §6 决策）
```

### 0.3 怎么证明每项真正完成（验收判据的通用形态）

| 类型 | 判据 |
|---|---|
| 可见性类 | **真实浏览器**（chromium）里能点到、能看见；不是"代码里写了" |
| 状态类 | **必须引用设备侧真实字段**（`s/c/i/o` 压缩帧、`last_result` 枚举、`boot_seq`），缺字段就标"未取到"，不推断成功 |

| 回归 | 既有 17 套件 1238 断言 + 本轮新增断言全绿；生产部署后按 §5.1 复验脚本实测 |

## 1. 审计原则与本轮纪律

- **原型优先**：以 `docs/ui-v1/prototype.html` 24 屏为 UI 事实源；生产 UI 只作"现状"，不作"需求"反推依据。
- **区分状态**：已实现且有证据 / 已实现但未充分验证 / 部分实现 / 尚未实现 / 与原型不一致 / 需要固件或后端能力 / 存在安全或数据一致性风险 / 原型或需求信息不足。
- **测试通过 ≠ 功能完整 ≠ 生产已验证**。
- **不得把 MQTT 命令确认当物理动作成功**：固件无执行器电气回读（`safety.h:29-32`），UI 只能表述"设备报告已停止"，不能表述"已确认物理停止"。
- **不绕过固件配置安全机制**：ConfigManager 的 Active/Backup + `.bootok` + Critical 闸门是既有契约。
- **不改已应用迁移**；本轮不提出任何迁移需求（若未来需要，须说明原因/兼容/回滚）。
- **不触碰生产**：本轮仅做只读 GET 探测 EMQX（未发任何 POST/PUT/DELETE）。

- 设备页改造：10 个模块入口 → 模块详情页（状态 / 全部参数 / 含义 / 范围 / 依赖 / 只读标识）。

#### P4-2 · 写侧（RAM → 落盘 → 重启，3–4 天）

- 放行链路：Worker family 白名单加 `config` + 目录登记 `system.config_set`/`config_save`/`config_restart`（**必须新增目录条目 + 参数规格**）。
- 三段式交互：
  1. 编辑 → **仅写 RAM**（`config_set`；带 `expect_version` 乐观锁；带 Critical 冲突提示）
  2. 第二次明确确认 → **落盘**（`config_save`；回显 `saved/dirty`）
  3. 「立即重启」→ `config_restart`（= 落盘 + 请求重启）；或选择"稍后" ⇒ **显示固件真实剩余倒计时**
- ★ **协议缺口**：`config_restart_pending()` 无云端命令入口 ⇒ **倒计时剩余时间目前读不到**。两条路：
  (a) 新增只读命令 `system.config_restart_status`（固件小改，1–2 天）；(b) UI 只显示"设备将在 5 分钟内自动重启（固件行为）"，**不显示秒级倒计时**。
  ⇒ 建议先 (b) 上线，(a) 作为固件增量单独排期（原型屏 20 的"4 分 12 秒"需 (a) 才能真实还原）。
- 可编辑范围按 **D-6：一次性开放**全部固件实际支持且可改的项。规格表里 `editable:false`（只读/废弃/无生效路径）的项一律禁用并说明原因；**不再分批**。
  - 前提：规格表必须先完成（P4-0），且每一项都有固件映射证据；没有证据的键默认 `editable:false`。

#### P4-3 · 失败演练与回滚指引（1–2 天，**门禁**）

必须演练并产出可执行指引：
1. 落盘失败（Flash 写失败）→ `config_save` 返回 IO 失败 ⇒ UI 提示"数据可能下次启动回滚"。
2. 重启失败 / 设备不在线。
3. **非计划重启**（panic/wdt）→ 固件自动用 Backup 覆盖 Active ⇒ UI 需能读到 `0x0102 LOG_SYS_BOOT_INCOMPLETE_PREV`（CRITICAL）并提示"配置已回滚到上一版本"。
4. `commit` 状态停在 PENDING（`config_manager.cpp:846-875`）⇒ 启动时 recover 路径。
