**结构性结论**：

1. **读的 84% 集中在 4 条"分页/统计"查询**（#1 46% + #2 20% + #3 17% + #4 5%）——根因同一类：**缺 `(device_id, id)` / `(device_id, msg_id)` 覆盖索引**。
2. **写的 92% 来自设备日志链路**：`log_history` INSERT（43%）+ `log_boot_watermark` upsert（36%）+ `log_conflict`（5%）。
3. `INSERT log_history` 每次写 3.25 行（表行 + 2 索引项）、读 6.4 行（唯一索引冲突探测）⇒ 单条日志真实成本 ≈ 10 个配额单位。
4. **10-24（今日）写量 79,268，93% 仍是上述两条**（log_history 40,055 + watermark 33,702）——与 UI 无关，是**设备持续产生日志**（≈850 批/小时 ≈ 每 4 秒 1 批）。结合"`HX711 未接但 weight.enable=true` ⇒ 每 5 s `WEIGHT_ERROR`"的已知缺陷，**这是当前写消耗的第一驱动**。

| 湿度（%）          | `climate.humidity`                       | snapshot | 高                    | 保留，**名称前置**（"湿度 62 %"），不要只显示百分号 |
| 固件版本           | `device.fw_version`                      | snapshot | 中                    | **下沉**到设备页                      |
| 最后上报（"xx 前"）   | `device.last_seen`                       | snapshot | 中（与状态重复）             | **合并**进状态副文案                    |
| 日志/遥测/事件条数     | snapshot `counts.*`                      | snapshot | **低（用户明确无用）**        | **删除**（同时消灭 §3 #2 20% 读）        |
| 快捷操作 4 钮       | 硬编码                                      | 无        | 高                    | 保留，后续可配置（S3-04）                 |


### 5.2 信息架构建议（精简后）

```
[状态卡] 在线（EMQX 权威）· 最后数据 12 秒前 · 固件 v0.7
[数值卡] 重量 — g（未连接警示） | 温度 24.3 ℃ | 湿度 62 %
[快捷]   开阀 / 关阀 / 急停 / 解除锁存
[注意]   告警摘要（最近 1 条 WARN+，链接到记录页）
[刷新]   ↻ 手动刷新 + 明确数据时间
```

原则落实：① 每个数值带**名称+单位+时刻**；② 状态（在线）与数据新鲜度（最后上报）**分开表达**；③ 旧值必须显示"数据时间"，不得伪装实时；④ 无价值统计删除。

### 5.3 请求变化

| 项                    | 现状                   | 建议                                                   |
| -------------------- | -------------------- | ---------------------------------------------------- |
| snapshot `?recent=5` | 含 3 COUNT（每次 13K 行读） | 新增 `?counts=0`（默认不带 COUNT）；首页不再请求                    |
| snapshot 频率          | 本会话 1 次 + 手动         | 保持                                                   |
| 在线状态                 | 由 snapshot 推断        | 改 `GET /api/presence/emqx/:device`（30 s 缓存）或浏览器 MQTT |
| 遥测最新值                | 由 snapshot 取         | 保持（一次取全）                                             |

**预估收益**：首页读消耗 13K 行/次 → ~50 行/次（**−99.6%**）；配合 D1-2 全站 −1.47M/日。

## 6. 浏览器端 MQTT 与设备实时在线状态

### 6.1 可行性（逐项核实）

| 问题                                  | 结论                                                                                           | 证据                                                        |
| ----------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Serverless 是否支持 MQTT over WebSocket | ✅ 支持                                                                                         | `[文档]` 定价页协议矩阵含 WebSocket；官方博客示例 `wss://<host>:8084/mqtt` |
| 本实例 WebSocket 地址                    | `wss://n302933b.ala.cn-hangzhou.emqxsl.cn:8084/mqtt`（**端口 8084 待实测**，实例仅文档给出 8443 REST）      | `[文档]`+`[未验]`                                             |
| 免费套餐是否允许                            | ✅ 允许（同套餐含 WebSocket）                                                                         | `[文档]` 定价页                                                |
| 免费额度                                | 1,00`0,000 session minutes/月 · 1 GB 流量/月 · 1,000,000 rule actions/月 · 最多 1,000 连接 · 消息 1 MB` | `[文档]` 官方定价/免费额度页                                         |
| 浏览器端限制                              | WSS 可用；**不支持浏览器双向证书**（只能用用户名密码/JWT）                                                          | `[文档]` EMQX 官方博客                                          |
| ACL 能否限制网页端 Topic                   | ✅ 按 username 配 ACL 规则（项目已在用该 API）                                                            | `[代码]` emqx-admin.js + `[生产探针]`                           |
| 凭据如何下发                              | Worker 签发（见 §7）                                                                              | —                                                         |
| 断线/刷新/过期                            | MQTT.js 自动重连 + Worker 凭据租约；页面隐藏即断开                                                           | 设计项                                                       |

**关键约束**：**session minutes 是共享额度**——网页端每条连接每分钟都消耗。当前免费额度 1M/月 ≈ 23 台设备全月在线；若网页端 24/7 常开，会与设备抢额度。⇒ **网页端必须"按需连接、离开即断"**。

### 6.2 在线状态三种口径对比

| 口径                      | 可信度            | 延迟       | 成本                | 适用         |
| ----------------------- | -------------- | -------- | ----------------- | ---------- |
| **EMQX `/clients` API** | 高（Broker 真实连接） | 秒级（查询即时） | 1 次 REST/查询（无 D1） | **首页状态首选** |
| 浏览器 MQTT 订阅 `$SYS`/LWT  | 高              | 实时       | session minutes   | 实时场景       |
| `last_seen` 推断          | 中（受心跳/日志节流影响）  | 分钟级      | 0                 | 数据新鲜度、离线诊断 |

- **生产探针证据**：`GET /clients?limit=3` → **200**（可用）；`/status` `/stats` `/nodes` `/monitor_current` → **403**（Serverless 受限）。⇒ 只能走 `/clients`（含 `username`/`clientid` 过滤，**过滤参数待实测**）。
- 建议：**状态与新鲜度分开表达**——"在线（MQTT 连接）" + "最后数据 12 秒前（遥测）"。不要用 `last_seen` 单独判在线，也不要用在线状态代替数据新鲜度。

### 6.3 职责划分建议

| 功能        | 通道                                     | 理由                                                 |
| --------- | -------------------------------------- | -------------------------------------------------- |
| 实时在线状态    | Worker 代理 `/clients`（30 s 缓存）或浏览器 MQTT | 权威、无 D1                                            |
| 实时遥测/告警推送 | 浏览器 MQTT 订阅 `.../up`（只读 ACL）           | 免轮询                                                |
| 设备控制命令    | **仍走 Worker**（`/api/command`）          | 需 registry 版本校验、审计、去重、ACL 与限流；直接 MQTT 会绕过 §8 的全部保障 |
| 历史日志/统计   | Worker + D1                            | 需要查询与聚合                                            |
| 身份认证/会话   | Worker + D1                            | 不可下放                                               |
| MQTT 凭据签发 | Worker（持管理 API 密钥）                     | 密钥绝不下前端                                            |

**明确不做**：不让浏览器直发控制命令；不让浏览器持管理 API 凭据；不为省请求而绕过设备隔离与审计。

## 7. 认证、授权与临时凭据方案

### 7.1 现状（[代码] + [生产探针]）

- 认证方式：**`password_based:built_in_database`**（内置库），认证器 id 固定常量。
- 已可用管理端点：`POST/PUT/GET/DELETE /authentication/password_based:built_in_database/users[/{id}]`；ACL：`PUT/DELETE /authorization/sources/built_in_database/rules/users/{username}`；`DELETE /clients/{clientid}`（P0 实测 204）。
- 受限端点：`GET /authentication` 列表 **403**（Serverless 限制，代码注释已记录）；`/status`、`/stats`、`/nodes` 等 403。

### 7.2 候选方案对比

**方案 A：固定 10 个用户 + Worker 轮换密码**（用户提出）

| 维度     | 评估                                                                        |
| ------ | ------------------------------------------------------------------------- |
| 可行性    | 🟡 部分可行：创建/改密/删用户 API 均可用 [代码+探针]                                         |
| 关键缺陷 1 | **改密码不会断开已建立连接**（`[未验]`，EMQX 通行行为；官方文档未明示）⇒ 旧凭据持有者若已连接，仍可继续收发 ⇒ **轮换≠撤销** |
| 关键缺陷 2 | 需额外 `DELETE /clients/{clientid}` 才能撤销 ⇒ 变成"轮换 + 踢线"两步，任一失败即留活口            |
| 关键缺陷 3 | 10 个用户**共享** ⇒ 同一用户名可被多标签页复用 ⇒ **无法识别是谁**；若同时被两处占用，轮换会踢掉另一处的合法连接          |
| 安全     | 密码明文经 Worker → 浏览器；须 HTTPS + 短 TT；泄漏窗口 = 连接存续期                            |
| 复杂度    | 高（租约表、占用状态、冷却期、并发锁、失败补偿、重试幂等）                                             |
| 额度     | 每条 REST 调用 = 1 次管理 API；无明显配额限制 [未验]                                       |

**方案 B：每会话一次性用户 + ACL 收窄（推荐候选）**

| 维度  | 评估                                                                                                                                                  |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 做法  | Worker 为每个**已通过 UI 会话校验**的浏览器创建/复用一个用户 `web_<sid8>`，ACL 仅允许该设备 topic；连接建立后 Worker 记录 `clientid`；登出/到期时 `DELETE /clients/{clientid}` + `DELETE user` |
| 安全  | 可精确撤销（踢线 + 删用户）；无共享身份；单一设备隔离                                                                                                                        |
| 复杂度 | 中（无密码轮换队列，但仍需清理与并发幂等）                                                                                                                               |
| 额度  | 需实测用户数上限（Serverless 认证信息上限 **2,000 条** [文档]）；每会话 1 用户 ⇒ 需定期清理                                                                                       |
| 缺陷  | 仍依赖 `DELETE /clients` 才能即时撤销                                                                                                                        |

**方案 C：不引入浏览器 MQTT，仅用 Worker 代理 `/clients`（最小改动）**

| 维度  | 评估                                                                                |
| --- | --------------------------------------------------------------------------------- |
| 做法  | 首页状态改 `GET /api/presence/emqx/:device`（30 s isolate 缓存 + 限频）；遥测仍走 snapshot（手动/低频） |
| 安全  | **零新增攻击面**（不下发任何 MQTT 凭据）                                                         |
| 复杂度 | 低                                                                                 |
| 收益  | 状态变权威；读数几乎不变（1 REST + 0 D1）；不消耗 session minutes                                   |
| 缺陷  | 无实时推送（轮询间隔 30–60 s）                                                               |

**评估结论**：**先 C 后 B**。A 不推荐（共享身份 + 轮换≠撤销）。B 需在 C 稳定后再做，且必须先以**只读探针**验证：① `:8084` WSS 可达；② `GET /clients?username=` 过滤生效；③ 改密对已连接客户端的真实影响（用测试用户 + 本地客户端验证，**不动线上 ACL**）。

### 7.3 必须的人工决策 / 未验事项

- 改密是否断开既有连接 → 需实测（用**新建测试用户**，不碰现有设备用户）。
- `DELETE /clients/{clientid}` 在 Serverless 的生效时延 → 需实测。
- 认证信息上限（2,000）与清理策略。
- 管理 API 密钥保管：现状在 Worker Secret，**不得**下发前端（已满足 [代码]）。
