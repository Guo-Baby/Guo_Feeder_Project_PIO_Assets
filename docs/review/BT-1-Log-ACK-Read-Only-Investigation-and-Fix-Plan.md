## §0 术语与指标定义（**`rev.2` 新增 · 全文统一口径**）

> **为什么需要本节**：`rev.1` 曾把"最小发送间隔（**时间**）"与"吞吐率（**速率**）"混用（例如写作"≤ 500 ms 节流上限"），
> 并把**理论最大速率**与**正常稳态速率**混同。本节为全文唯一口径来源；§6 的各表必须与本节一致。

| 术语 | 定义 | 单位 | 典型值 | **不得**被误用为 |
|---|---|---|---|---|
| **最小发送间隔** | 相邻两次**上行业务发送**之间的最小时间间隔（设备侧节流闸门 ⑤，`log_manager.cpp:2913-2918`） | **ms** | `LOG_TX_MIN_INTERVAL_MS = 500` | 吞吐率 / 验收目标 |
| **理论最大速率** | 由最小发送间隔 + 每消息记录数推出的**上界**（`1 / 0.5 s × 1 条`） | **条/s** | **2 条/s**（= 172,800 条/天） | 日常稳态验收目标 |
| **正常稳态速率** | 设备**实际日志产出**速率（受事件频率支配） | **条/时间** | 实测 `≈1 条 / 3.5 min`（单机、当前负载） | — |
| **实测受限吞吐** | 因 `BT-1`（无 ACK）导致重试阶梯占满发送窗口后的**实际**吞吐 | **条/时间** | `≈1 条 / 152 s` | 设计吞吐能力 |
| **重试周期** | 单条记录从首发到 GIVE_UP 的**总时长**（1 首发 + 5 重试） | **s** | **152 s** | 发送间隔 |
| **积压排空时长** | 积压 N 条记录从"开始排空"到"排空完成"的**实测**时长 | **s / min** | **待测**（**不得**用理论最大速率反推替代） | 理论推算值 |
| **ACK 发布尝试次数** | 调用发布接口的**次数**（含失败） | 次 | — | 成功次数 |
| **ACK 发布成功次数** | 发布接口返回**判定为成功**的次数（判定规则见 §5.2.1） | 次 | — | 尝试次数 |

### 2.4 ★ 新发现的跨链路副作用（`mqtt_messages` 会被 ACK 污染）

`mqtt_messages` 现有 topic 分布（D1 实测）：

| kind | 行数 |
|---|---|
| `up` | **2,048** |
| **`log`** | **867**（`/log` 被 Rule A 加谓词**之前**的噪音残留） |
| **`down`** | **571** ⇒ 证明 **Rule B 确实收录 `down` 流量** |
| `other` | 9 |
| **合计** | **3,495** |

⇒ 一旦实现 `log_ack`（发布到 `down`），**每条 ACK 都会产生 1 行 `mqtt_messages`**。成本量级：
- **理论上界 = 172,800 行/天**（按 §0「理论最大速率」2 条/s，仅当持续有 ≥1 条待发；**上界，非稳态**）；
- **正常稳态量级 = ⚠️ 待核实**（`rev.2.1` 更正）：`rev.1`/`rev.2` 曾写"按**正常稳态速率**约 **2,500–5,000 行/天**"，但该数与 §6.1 的实测口径**不能同时成立**，而其**时间窗口 / 设备数 / 重试计数 / 样本来源均未载明** ⇒ 详见 **§6.1 的速率口径核对**；**在该项核实前，不得把 2,500–5,000 作为 `N1-C` 的量化成本依据**（`BT1-Q-5` 裁决须以此为前提）。
**这正是 `mqtt_messages` 867 行 `/log` 历史噪音的同一机制**（Rule B 的谓词边界问题）。

**★ `rev.2` 更正**：`rev.1` 曾在此处直接把「Rule B 排除整个 `guo_feeder/+/down`」写成倾向性方案。该写法**不是已批准裁决**。
⇒ 现改为 **三方案并列比较**（`N1-A` / `N1-B` / `N1-C`），见 **§5.12**；最终选择保留人工裁决（`BT1-Q-5`）。

> **★ 关键澄清（防止"过滤历史记录 ⇒ ACK 送不到设备"的误判）**：
> **`log_ack` 送达设备走的是 MQTT 投递路径**（broker → 设备对 `guo_feeder/<id>/down` 的订阅），
> **`mqtt_messages` 落库走的是 Rule B（数据集成）→ HTTP Action → Pages → Worker/webhook 的历史记录路径**。
> **两条路径彼此独立** ⇒ 在 Rule B 的 `WHERE` 上做过滤**只影响历史收录，不影响设备投递**。
> （唯一共享点是 topic 字面量；规则引擎的过滤发生在**转发**阶段，不改变 broker 对订阅者的投递。）

### 5.3 ACK 触发条件与发送时机（**精确规则**）

```
对每一条通过 validation 的记录 r（当前 count = 1 ⇒ 一条 ingest 请求 = 一条记录）：

  条件 P（已持久化）：
      r 被 INSERT 成功（accepted）
      ∨  r 命中 ux_lh_dedup 被忽略（duplicate）      ← ★ 必须包含！
  条件 ¬P 时一律**不发 ACK**：
      · level = 0（filtered/DEBUG）  → 未落库 ⇒ 不发（设备实际不会发 DEBUG）
      · validation 拒收（rejected）  → 未落库 ⇒ 不发（设备 6 次后自行 give-up，有界）

  发送：publishToDevice(env, `guo_feeder/${deviceId}/down`,
                        {c:"log_ack", i:"<唯一>", p:{b:boot_seq, f:seq, t:seq}},
                        {qos:1})
  ⚠️ f = t = r.seq（**不得**用 batch 的 min/max —— 若中间有 rejected，
     区间 ACK 会让设备把未落库的记录当作已确认 ⇒ 违反不变量 ①）
```

> **★ `duplicate` 必须 ACK（本条是本次调查最重要的设计点）**
> 若"仅 accepted 才 ACK"，则设备**重启后重放**的历史记录（云端必然 `duplicate`）**永远拿不到 ACK** ⇒ 直接复现 `BT-1` 的原始症状。`log_ack` 语义 = "**云端已持久化该 seq 区间**"（`log_ack.h` 顶部冻结注释），duplicate **同样满足**该语义。

| 场景 | ACK 策略 |
|---|---|
| 正常首次投递 | `accepted=1` ⇒ 发 1 条 ACK |
| 重投（设备重试 / 重启重放） | `duplicate=1` ⇒ **仍发** ACK ⇒ 设备判 `LOG_ACK_DUPLICATE`（无副作用）并推进水位 |
| `level=0` | 不发（设备侧不发生） |
| `rejected` | 不发；由设备 `MAX_RETRY` 收敛；**记 `console.warn`**（可观测） |
| D1 写入失败（`5xx`） | **不发**（保持 `persist_failed` 503，让上游重投） |
| 设备已被 REVOKED | `200 ignored` ⇒ **不发**（未落库） |

### 5.3.1 ★★ 核心不变量与 `accepted` / `duplicate` 的严格判定（`rev.2` 新增 · **✅ 已批准 `R-1…R-6`**）

> ## **★ 核心不变量（Iron Law）**
> **ACK 只能确认"已经持久化的数据"。**
> **绝不能仅凭"数据库语句没有抛出异常"或"语句被执行过"就发送 ACK。**

**为什么必须写死这条**：设备侧收到 ACK 后会**推进水位并据此删除 Flash 段**（§5.7）。一旦对**未落 D1** 的记录发 ACK，该记录的**唯一物理副本**会被删除 ⇒ **不可恢复的数据丢失**（重启也补不回）。

#### （a）两个结果量的**严格定义**（二者语义不同，不得互相推导）

| 量 | **严格定义** | 判定依据 |
|---|---|---|
| **`accepted`** | 本条记录**已由本次请求成功写入 D1**（新增了一行） | `INSERT` 的 `meta.changes == 1` |
| **`duplicate`** | **D1 中确实已存在**与 `(device_id, boot_seq, seq)` 对应的记录（**幂等冲突**） | 见 (c)：**必须独立证明存在性**，**不得**由"未新增行"反推 |

#### （b）`rev.1` 口径的**缺陷（必须修正）**

现有实现（`history-ingest.js:636-666`）的返回值是：

```
inserted = Σ(每条语句的 meta.changes)          // 只统计"真新增"
duplicate = rows.length − inserted              // ← ★ 由"减法"反推
```

⇒ **`duplicate = rows.length − inserted` 是"未被插入"的条数，不是"已存在"的条数。**
`INSERT OR IGNORE` 会**静默忽略任何约束冲突**，其中包括：
1. 幂等冲突（`ux_lh_dedup` 命中）—— **这才是 duplicate**；
2. **其他约束冲突**（如 `NOT NULL` / `CHECK` / 类型约束失败）—— 这是**写入未成功**，**不是 duplicate**；
3. 其他 D1 层面的忽略原因（**待核实**：D1 对 `OR IGNORE` 的具体语义覆盖范围）。

⇒ **"未新增行" ≠ "记录已存在"。** 若按 `rev.1` 的口径直接对 `duplicate` 发 ACK，
**存在对"因其他约束冲突而未落库"的记录误发 ACK 的风险** ⇒ **违反核心不变量**。

#### （c）`rev.2` 设计要求（判定规则 · 待人工批准）

| # | 要求 | 说明 |
|---|---|---|
| **R-1** | `accepted` 判定 = **单条语句 `meta.changes == 1`**（**逐条**，不是 chunk 求和） | 现有实现按 `PERSIST_CHUNK` 求和 ⇒ **必须改为逐条返回结果**（属**实施需求**，本文件不改代码） |
| **R-2** | `duplicate` 判定 **必须独立证明存在性** —— 在"未新增行"时，对同一 `(device_id, boot_seq, seq)` 执行 **`SELECT 1 … WHERE` 存在性查询**；命中 ⇒ `duplicate`；**未命中 ⇒ 既非 `accepted` 也非 `duplicate`** | 唯一能让 ACK 判定**可证明**的方式；代价 = 每条未新增记录 **+1 次 D1 查询**（§5.4.3 预算） |
| **R-3** | 存在性**无法证明**（查询异常 / 超时 / 结果不确定）⇒ **不发 ACK**，且**不得**把该条计入 `duplicate` | 保守优先：宁可让设备重投（有界），也不误发 ACK |
| **R-4** | 其他约束冲突 / 形状异常 ⇒ 归入 **`rejected`**（或新增独立计数），**不发 ACK** | 与 `F-C2-8` 的三态（`null` / `LOG_FILTERED` / 数组）**不得混同** |
| **R-5** | D1 **写入失败**（`db.batch()` 抛错）⇒ 维持既有语义：**`503 persist_failed`**，**不发 ACK**，**不得**被 ACK 逻辑掩盖 | 见 §5.4 (c) |
| **R-6** | 响应体**保持现有四字段**（`accepted` / `duplicate` / `rejected` / `filtered`）**语义不变**；ACK 统计**不进入响应体**（仅日志 / 测试桩可观测） | 不改变既有契约与调用方 |

> **⇒ 实施需求（记入 §5.11，不在本文件改代码）**：
> `persist()` 必须由"返回求和后的行数"改为"**返回逐条结果**"，并在未新增行时执行**存在性校验**；
> 判定结果需区分 `accepted` / `duplicate` / `unpersisted` 三态，**只有前两态允许 ACK**。

#### （d）与 ACK 的映射（**唯一合法映射**）

| 判定结果 | D1 实际新增行 | 是否发 ACK |
|---|---|---|
| `accepted` | **+1** | ✅ **发** |
| `duplicate`（**存在性已证明**） | **0** | ✅ **发** |
| `unpersisted`（未新增且**未能证明存在**） | **0** | ❌ **不发**（保守） |
| `rejected` / `filtered` | **0** | ❌ **不发** |
| 写入失败（`5xx`） | — | ❌ **不发**（响应 503） |

### 5.4 ★ ACK 发布与 HTTP 响应的**时序契约**（`rev.2` 重写 · 待人工批准）

> **来源**：审阅第 1 项。`rev.1` 只用一张 5 行表描述"关系"，**未定义等待方式、超时预算、后台执行的生命周期约束**，
> 且"ACK 发布超时 ⇒ 放弃本次 ACK，**不阻塞响应**"这一表述**隐含了未经验证的保证** ⇒ `rev.2` 全部显式化。

#### （a）硬性时序不变量（**不可协商**）

| ID | 不变量 | 违反后果 |
|---|---|---|
| **T-1** | **ACK 的触发时刻严格晚于"本条记录被确认持久化 / 确认已存在于 D1"**（判定规则见 §5.3.1） | 对未落库记录发 ACK ⇒ 设备删除唯一副本 ⇒ **不可恢复丢失** |
| **T-2** | **ACK 的任何失败（throw / 非 2xx / 超时 / 未执行）都不得把"已成功持久化"的请求改判为失败** | 5xx 会让 EMQX 重投 ⇒ 重复处理 + 放大；更糟的是掩盖"其实已落库"的事实 |
| **T-3** | **`try/catch` 只能隔离异常，不能自动保证"不阻塞响应"** | 若发布调用**同步等待**且耗时长，请求仍会被拖住（超时、放大）⇒ 必须由 **§5.4.1 的等待方式**保证 |
| **T-4** | ACK 发布**不得**改变 `persist()` 的既有失败语义（写入失败仍 `503 persist_failed`） | 见 §5.3.1 R-5 |
| **T-5** | ACK 失败**必须**产生**可检索**且**不含敏感值**的日志（§5.2.1 P-5） | 否则线上无法定性 |
| **T-6** | **不假设**任何"后台任务一定完成"的保证（§5.4.1 W-3） | 见下 |

#### 5.4.1 发布等待方式（**三个候选 · ✅ 已裁决 = `W-2`**）

> **★ 前置事实（实测 · 来自 EMQX 配置存档）**：EMQX HTTP Action —— **请求超时 `5 s`** · **请求模式 `异步`** · **最大重试 `1`** · **缓存队列 `4 MB`** · **飞行队列窗口 `50`** · 健康检查 `30 s`。
> （来源：`EMQX_Assets/config/data-integration/P3-WP4C-V2V4-Config-After.md` §0 第 7 项）
> ⇒ **ingest 请求的整个处理时长必须显著短于 `5 s`**，否则 Action 判失败 ⇒ 重投（重试 1）⇒ **重复记录 + ACK 重复发布**。

| 候选 | 机制 | 优点 | 缺点 / 风险 | **必须验证** |
|---|---|---|---|---|
| **W-1 · 同步等待（有界）** | `await` 发布调用，但用**有界超时**包裹（建议预算 **≤ 1.5 s**，见 §5.4.3） | · 语义最清晰：**"发不出去"可立即记账**<br>· 实现最简单（无生命周期依赖）<br>· 与 `EMQX 5 s` 超时留有余量 | · 每条 ingest **增加最长 1.5 s 的延迟**（当前 Worker CPU 实测 1–4 ms，属**纯 I/O 等待**）<br>· 若 EMQX 侧偶发变慢 ⇒ 请求逼近 5 s 上限 | `publishToDevice()` 的 P99 延迟；`AbortSignal` 行为 |
| **W-2 · 同步等待 + 严格有界（推荐候选）** | 同 W-1，但预算**强制**（用有界超时包裹发布调用；**具体实现载体见 §5.4.4 路径 A / 路径 B**），**超时即放弃并记账** | · 消除"无限等待"的可能 ⇒ 请求时长**上界可证**（此为**设计预算**，**不等于**平台已保证） | · 同 W-1（延迟）<br>· **实现载体未定**：是否允许改 `src/emqx-admin.js` ⇒ **待人工裁决 `BT1-Q-17`** | 同上 + **超时后是否真的释放连接**（§5.4.4：**路径 A 可保证**；**路径 B 不可**，仅停止等待） |
| **W-3 · 响应后后台执行** | 先返回 200，再在 `ctx.waitUntil()` 中发布 | · 不给 ingest 增加任何延迟 ⇒ 对上游 `5 s` 最友好 | · **Cloudflare Worker 生命周期约束**：`waitUntil` 只保证"在响应返回后继续执行**一段时间**"，**不保证完成**，且**失败无重试、无回溯**<br>· 失败时**无任何补偿**（设备仍会重投 ⇒ 靠 `duplicate` 再试，属**被动**恢复）<br>· 观测性更差（tail 时序与请求分离）<br>· **不得**写成"一定会完成" | `waitUntil` 在该平台/该计划下的**实际时限与保证级别**（`rev.2` **标记为待实测**） |

**⇒ `rev.2` 建议**：**首选 W-2**（有界同步等待），理由 = 请求时长**上界可证**（**设计预算**）+ 失败可立即记账 + 不依赖未验证的生命周期保证；
**★ `rev.2.1` 补充（实现边界）**：**`W-2` 的"强制有界"在当前代码上无法凭空成立** —— 现有 `publishToDevice()` 是**直通调用**，其底层 `emqxRequest()` 的 `fetch` **未接收 `AbortSignal`**（静态事实，§5.4.4）⇒ 必须二选一（**路径 A** 修改 `src/emqx-admin.js` / **路径 B** 调用层 `Promise.race`），见 **§5.4.4**，裁决项 **`BT1-Q-17`**。**`1.5 s` 仅为设计预算，不代表已具备平台级超时保证。**
**W-3 仅在实测证明"`waitUntil` 具备可接受保证 + 失败可观测"后才考虑**。
**若最终选 W-3，则必须同时定义**（否则不得采用）：① 后台任务的**实际时限**；② 失败后的**恢复机制**（当前唯一可用恢复 = 设备重投 ⇒ 必须在计划中写明这是**被动**恢复，且依赖 `duplicate` 路径仍会 ACK）；
③ 后台执行的**可观测出口**（日志能否被 `tail` 捕获）。

#### 5.4.2 时序（**唯一合法顺序**）

```
EMQX Action ──POST──▶ Pages 中转 ──▶ Worker /api/history/ingest
                                          │
   ① requireWebhookKey ──失败──▶ 4xx（不发 ACK）
                                          ▼
   ② 信封解析 / domain / device_id 一致性 ──失败──▶ 400（不发 ACK）
                                          ▼
   ③ REVOKED 守卫 ──命中──▶ 200 ignored（不发 ACK）
                                          ▼
   ④ validation（三态）──rejected / filtered──▶ 计入各自计数（不发 ACK）
                                          ▼
   ⑤ persist() ──抛错──▶ 503 persist_failed（不发 ACK · 维持既有语义）
                                          ▼
   ⑥ ★ 持久化判定（§5.3.1）：accepted / duplicate(存在性已证) / unpersisted
            ├─ accepted | duplicate  ⇒ 允许 ACK
            └─ unpersisted           ⇒ 不发 ACK（保守）
                                          ▼
   ⑦ ★ ACK 发布（§5.4.1 W-2：有界等待 ≤ 1.5 s · 全捕获 · 不 rethrow）
            ├─ 成功  ⇒ console.log("[log-ack] published …")   （计数：尝试+1 · 成功+1）
            └─ 失败  ⇒ console.warn("[log-ack] publish failed …")（计数：尝试+1 · 成功+0）
                        ★ 不得改变 HTTP 状态
                                          ▼
   ⑧ 返回既有响应体 {accepted, duplicate, rejected, filtered}（**零变更**）
```

> **★ 顺序铁律**：`⑦` 之前**必须**完成 `⑥`。**不得**把 ACK 发布提前到 `⑤` 之前、**不得**并入 `checkpoint ②③④`，
> **不得**由 EMQX 侧 republish 代替（§5.2 方案 C 已禁止 —— 无法保证"仅落库后"）。

#### 5.4.3 超时预算、D1 查询预算与请求放大分析（**待验证项已标注**）

| 预算项 | 值 | 说明 |
|---|---|---|
| EMQX Action 请求超时 | **5 s**（实测配置） | **上游硬预算** —— Worker 端总耗时必须显著低于它 |
| Worker `fetch` 处理耗时（当前实测） | **CPU 1–4 ms**（`tail` 实测 9 次） | ACK 发布属**纯 I/O 等待**，不计 CPU |
| **ACK 发布有界预算（建议）** | **≤ 1.5 s** | 留 ≥ 3.5 s 余量给 Pages 中转 + D1 + 网络抖动 |
| D1 **存在性校验**查询增量 | **+1 查询 / 条"未新增行"的记录** | §5.3.1 R-2 的代价。**逐条口径**：`accepted` 条**无需**校验（`changes == 1` 已自证）；**仅**"未新增行"的条各 **+1** 校验查询 |
| D1 写入尝试（现状 · 不变） | **6 / 记录** | 1 成功 + 5 忽略（`rowid` 步长实证） |
| **单记录 D1 查询总数（修复后 · 推算）** | **≈ 12 / 记录**（每条 6 次投递 × 2 查询：`getDevice` 1 + `persist` 1）**＋ 最多 5**（存在性校验，仅重投条） | 现状为 **12 / 记录** ⇒ 增量**最多 +5**（≈ +42%）；**待实测确认**（`BT1-T20` 一并观察） |

**请求放大分析（`rev.2` 新增）**：

| 情形 | 是否放大 | 机制 |
|---|---|---|
| ACK 发布**成功** | 否 | 1 次 ingest + 1 次 EMQX publish |
| ACK 发布**失败**（有界超时内） | **轻度** | 1 次 ingest + 1 次失败的 publish；**响应仍 200** ⇒ 上游**不重投** ⇒ 放大 = **0 次 ingest**（仅多 1 次失败的 publish 调用）。设备侧 15 s 后重发同一记录 ⇒ 下次 ingest 覆盖 |
| ACK 发布**拖长请求超过 5 s** | **★ 严重（必须避免）** | EMQX 判失败 ⇒ **重试 1** ⇒ **重复 ingest 请求** ⇒ 每条记录再走一遍 persist + 发布 ⇒ **请求与发布双放大**。W-2 的**严格有界**预算即为消除此风险 |
| 采用 W-3 且后台任务未执行 | 中度 | 响应 200 但无 ACK ⇒ 设备重投 ⇒ 下次可能再次后台未执行 ⇒ **可能持续无 ACK**（= 功能退化为 `BT-1`）⇒ 必须实测 `waitUntil` 保证后才可采用 |

> **★ 标记为待验证（不得编造保证）**：
> 1. EMQX Action 的**实际**请求超时是否仍为 `5 s` —— 存档为 **`2026-10-12` 的动作配置**（`2026-10-16` 只改**规则 SQL**、动作未动 ⇒ **很可能仍有效**），但**数据集成 API `403` ⇒ 不可回读** ⇒ 须控制台核实；
> 2. Worker → EMQX `/api/v5/publish` 的**典型与 P99 延迟**（当前**无实测数据**）；
> 3. `AbortSignal.timeout()` 在 Cloudflare Workers 运行时的**行为与资源释放**；
> 4. `ctx.waitUntil()` 在本账号 / 本计划下的**时限与失败语义**。
> ⇒ 以上 4 项**必须在编码阶段的 P1/P2 实测**（见 §8），**不得**在计划中被当作已成立的前提。

### 5.5 ACK 丢失 / 重复 / 延迟 / 乱序 / 断线 / 重启的处理规则

> **★ `rev.2` 更正**：`rev.1` 曾写「ACK 一旦生成即为**最新**，不会乱序」—— 这是**过强的绝对表述**，已删除。
> **正确表述见下方"乱序 / 并发"行与其后的"顺序假设"小节。**

| 场景 | 设备侧既有行为（**无需改动**） | 云端应做 |
|---|---|---|
| ACK 丢失 | 15 s 超时 → 重发（≤5 次）→ 若无 ACK 则 GIVE_UP（不推进水位、登记空洞） | 保持幂等；下次重投时再 ACK |
| ACK 重复 | `log_ack_classify` 判 `DUPLICATE` ⇒ 无变化 | 无需特殊处理 |
| ACK 延迟 / 乱序 | `ack_to <= gc_seq` ⇒ DUPLICATE；`ack_to < tx_from` ⇒ IGNORE；部分覆盖 ⇒ PARTIAL | **不得把"生成顺序 = 投递顺序"当作事实**；依赖设备侧既有分类逻辑安全吸收；云端只需保证**单条 ACK 只覆盖该条自身** |
| **并发 ingest（同一设备）** | 设备侧只有**一个在途批次**（`s_cloud_inflight`），但云端可能**同时**处理多条（不同 `seq`） | 每条 ACK **独立**：`f = t = 该条自身 seq`；`b = 该条自身 boot_seq`。**不得**合并成区间 |
| **并发 ingest（多设备）** | 各设备独立水位 | ACK 主题按 `device_id` 隔离（`guo_feeder/<id>/down`）⇒ 天然隔离 |
| 断线重连 | 离线不消费记录（`cloud_poll` ④）；重连后补发 | — |
| 设备重启 | `acked_seq/gc_seq/gc_floor` 归 0，全量重放；云端 `duplicate` | **`duplicate` 必须 ACK**（§5.3） |
| Boot 变更 | `ack_boot != tx_boot` ⇒ IGNORE | ACK 的 `b` 必须回**该记录自身的 `boot_seq`**（**不是**当前请求的 boot） |
| 云端不可用 | 超时 → 重试 → GIVE_UP（不推进水位） | — |

#### 5.5.1 ACK 的顺序假设（**`rev.2` 新增 · 必须遵守**）

| # | 规则 | 理由 |
|---|---|---|
| **O-1** | **单条 ACK 必须使用 `f = t = seq`**（该条日志自身的 `seq`） | 保证一次 ACK **只确认一条**，不会顺带确认同批其他记录 |
| **O-2** | **`boot_seq` 必须取自对应日志记录本身**（`rec.boot_seq`），**不得**取"当前请求上下文 / 当前 boot / 会话变量" | 设备侧 `ack_boot != tx_boot ⇒ IGNORE`；错误的 `b` 会让 ACK 被静默丢弃 |
| **O-3** | **并发 ingest、发布完成顺序、MQTT 投递顺序不得被默认视为一致** | 三条链路各有独立调度：EMQX Action **异步 + 缓存队列 4 MB + 飞行窗口 50**；Worker 并发执行；MQTT 投递顺序不保证。⇒ 完全可能出现"seq 较大的 ACK 先于 seq 较小的 ACK 到达" |
| **O-4** | **重复 / 延迟 / 乱序 ACK 由设备侧既有分类逻辑安全处理**（`log_ack_classify`：`DUPLICATE` / `IGNORE` / `PARTIAL`），**云端无需（也不应）自行排序** | 设备侧已在真机验证（Board Report §6）；`rev.1` 的"不会乱序"假设不成立 |
| **O-5** | **不得**为"避免乱序"而引入云端侧的排序 / 缓冲 / 补齐逻辑 | 会显著增加复杂度与延迟，且违反"ACK ⊆ 已持久化"（补齐会确认未落库记录） |
| **O-6** | **单条 ACK 不会（也不得）确认其他未持久化记录** —— 这是 `f = t` 的直接推论，须由 §7 `BT1-T17` **并发/乱序集成测试**证明 | 核心不变量的可验证化 |

### 5.6 `boot_seq` / `seq` / `acked_seq` 的比较、推进与持久化规则（**现状即正确，不改**）

| 量 | 语义 | 推进 | 持久化 |
|---|---|---|---|
| `boot_seq` | 本次开机标识（`meta.bin`） | 每次 init 分配 | ✅ 落 `meta.bin` |
| `seq` | 记录序号（**跨 boot 单调**；DEBUG 不消耗；区间预留 256） | `log_emit_internal` 临界区内 `++` | ✅ 随记录落 Flash / 落云 |
| `acked_seq` | 云端确认过的**最大** seq（观测用） | `max(旧值, 本次覆盖末条 seq)` | ❌ **仅 RAM**；重启归 0（at-least-once 语义） |
| `gc_seq` | **连续**可回收水位 = `min(acked_seq, gc_floor − 1)` | **单调不降**（`if (gc > s_cloud_gc_seq)`） | ❌ 仅 RAM |
| `gc_floor` | 补发 backlog 下界（未确认 Flash 记录最低 seq） | `cloud_replay_arm()` 时设置；补发消费完后清 0 | ❌ 仅 RAM |
| `give_up_seq` | 本 Boot 已放弃重发的水位（单点） | GIVE_UP 时置 | ❌ 仅 RAM（**`BT-11` 残留：单点而非区间**） |

**比较顺序**（`log_ack_classify`，顺序即语义）：区间非法 → 无在途 → boot 不匹配 → `ack_to ≤ gc_seq`(DUPLICATE) → `ack_to < tx_from`(IGNORE) → 完整覆盖(ACCEPT) → 部分(PARTIAL)。

### 5.7 如何避免 ACK 使设备**提前删除**尚未安全确认的日志（4 道防线，均已存在）

1. **`gc_seq` ≠ `acked_seq`**（`BT-9` 修复）：水位只能推进到"补发 backlog 下界之前"，防止 live 记录的高水位**跨过**仍躺在 Flash 的旧记录；
2. **空洞表**（`FIX-2`/`FIX-H2`）：GIVE_UP / 队列淘汰的区间被显式登记，段回收**必须与之不相交**；
3. **段回收 4 条件**（`log_ack.h:384`）：整段 ≤ `gc_seq` ∧ 无空洞相交 ∧ 空洞表未溢出 ∧ 段非空；
4. **`gc_floor` 钳制**（`FIX-BT9`）：补发未完成前水位被压在 backlog 下界之下。

⇒ **`BT-1` 修复只需提供 ACK 输入，回收安全性由既有 4 道防线承担**（`BT-10` / `BT-11` / `BT-H1` 为**已知残余**，见 §9）。

### 5.8 重复 ACK / 重复上传不导致序号倒退、错误回收或数据丢失

| 机制 | 效果 |
|---|---|
| `log_ack_classify` ④ `ack_to ≤ gc_seq` ⇒ DUPLICATE | 水位**单调不降**（`if (gc > s_cloud_gc_seq)`） |
| `log_ack_segment_reclaimable` 要求 `last_seq ≤ gc_seq` | 只删**完整已确认**的段 |
| `INSERT OR IGNORE` + `ux_lh_dedup` | 重复上传不产生重复行 |
| 空洞表 | GIVE_UP / 淘汰区间**永不**被回收 |

### 7.0 计数定义（`rev.2` 新增 · **`rev.2.1` 更正强制清单为 `T02 / T03 / T14`**）

> **★ `rev.2.1` 口径更正（`P2-6`）**：强制报告**四类计数**的集成项 = **`BT1-T02` / `BT1-T03` / `BT1-T14`**（与修订记录 ⑤ 一致）。

> 计数仅在其自身断言需要时报告（如 `T19` 的失败分支可体现"尝试 +1 / 成功 +0"，其断言见 §5.11 `BT1-U-4a…4c`）。
> **本次更正只统一文本口径，未改变任何测试的目的、通过标准或状态。**

| 计数 | 含义 | 观测来源 |

### 7.1 `BT1-T13` 回归夹具**重设计原则**（`rev.2` 新增 · 强制）

| **① 依赖"云端永不发 ACK"的旧故障断言** | **删除或改写** | 改写时应重定义为"**在受控无 ACK 条件下**"的场景（例如用桩抑制 ACK），而**不是**删除整段 |
