## §0 一句话结论

> **`ts=0` 不是"脏数据"，是"设备还不知道现在是几点"的如实表达**。而 `retention` 的判据把
> "未知"当成了"很久以前"，于是**每轮清理都会把它删掉**。`2026-10-18 03:00Z` 已经实删一次
> （`ts=0` 行 **26 → 0**，其中 **3 条 `CRITICAL`**）。
> 要止血只能改**保留判据**（B/C，需复议冻结裁决）；**修固件（D）治不了这一类**——
> 只要"设备从未同步过时间"，`ts=0` 就必然出现。

## §1 设备时间同步路径（代码取证）

### 1.1 `time_get()` 是唯一出口，也是 `ts=0` 的唯一来源

```c
// src/services/time_manager.cpp:912
time_t time_get()
{
    if (!state_get_bool(STATE_TIME_VALID)) return 0;   // ① 未置有效
    time_t now = time(nullptr);
    if (!time_validate(now)) return 0;                 // ② < 2026-07-01Z
    return now;
}
```

- `TIME_VALID_START_TIMESTAMP = 1782864000` ⇒ **`2026-07-01T00:00:00Z`**（`time_manager.cpp:35`）。
  即：RTC 里哪怕有 2025 年的时间，也判无效。
- 因此 `time_get() == 0` 有**两种**成因：① `STATE_TIME_VALID = false`；② 系统时钟落在下界之前。
  两者在**日志记录层不可区分**（都写 `timestamp = 0`）。

### 1.2 时间有效性的三个来源（分支表）

| 阶段 | 分支 | 结果 | 代码位置 |
|---|---|---|---|
| **启动 `time_init()`** | `rtc.enable=true` **且** `rtc_init()` 成功 **且** `rtc_read_time()` 通过 `time_validate()` | ✅ **`STATE_TIME_VALID=true`** · `time_source="RTC"` · 埋点 `LOG_TIME_RTC_BOOT_RESTORE` | `time_manager.cpp:706-731` |
| 同上 | RTC 在位但时间无效（**VL 置位** = 电池掉过） | ❌ `INVALID`，等 SNTP | `:733-737` |
| 同上 | RTC 初始化失败 / `rtc.enable=false` | ❌ `INVALID`，等 SNTP（`LOG_TIME_RTC_PROBE` 区分两者） | `:740-770` |
| **运行期 `time_task()`** | **WiFi 未连** ⇒ SNTP **根本不会启动**（`if (wifi && !sntp_started)`） | ❌ 一直 `INVALID` | `:795-801` |
| 同上 | WiFi 连上 ⇒ SNTP 启动；回调 → `sntp_sync_seq++` → loop 侧「回调通知 + 延迟确认」收敛 | ✅ `time_source="SNTP"` · 埋点 `LOG_TIME_NTP_OK` | `:826-886` |
| 同上 | 每轮 `time_validate(time(nullptr))` 维护 `STATE_TIME_VALID` | 有效区间内 = true | `:888-897` |
| **失败可观测性** | ⚠️ **`LOG_TIME_NTP_FAIL` 冻结 EventId 但"无宿主、未实现"**（SDK 只提供**成功**通知回调，`sntp_sync_status_t` 无 FAIL 态） | **"同步失败"在日志里没有正面证据**，只能靠"没有 `LOG_TIME_NTP_OK`"反推 | `time_manager.cpp:104-120` |

> **关键推论**：`ts=0` 的充分必要条件 = **本次启动至今既没有从 RTC 恢复、也没有 SNTP 成功**。
> 设备 `2026-10-17 10:38–16:45Z` 那 26 条即落在这一状态（RTC 未提供有效时间 + 当时 SNTP 未成功/未收敛）。

### 1.3 为什么**修 `HD-3` 不能消除这一类**

| 假设的"修复" | 后果 | 评价 |
|---|---|---|
| **D-1：未同步 ⇒ 暂缓上传**（沿用"不伪造时间"原则） | 开机期记录**永远不进云**（本地环 496 条写满后被覆盖） | ❌ **比现状更差**：连"曾经有过这条 CRITICAL"都看不到 |
| **D-2：强制依赖 RTC** | RTC 电池耗尽 / VL 置位 / `rtc.enable=false` 时**照旧 `ts=0`** | ❌ 只缩小概率，不消除 |
| **D-3：信封新增"boot 相对时间"字段** | 需改**已冻结**的 6 字段信封契约（`LOG_ENV_*`），并让 Worker 解码 CBOR | ⚠️ 治本但**属架构变更**，成本最高 |
| **D-4：云端用 `payload_base64` 里的 `uptime_ms` 反推** | 技术上可行（CBOR 批次含完整 128 B 记录，**已含 `uptime_ms`**），但需 Worker 解码 CBOR + 找同 `boot_seq` 的锚点行 | ⚠️ 新解码路径 + CPU 成本，非最小改动 |

> 结论：**`ts=0` 是"设备确实不知道时间"的正确表达，不可能被固件消灭**。
> 真正要决定的是：**云端拿这条记录怎么办**。

## §2 `ts=0` 的完整生命周期（链路图）

```
   ┌──────────────── 设备侧 ────────────────────────────────┐
   │ log_emit(event, level=CRITICAL)                        │
   │        │                                                │
   │        ├─ time_get() ──► 0（未同步）                    │
   │        │      └─ rec.timestamp = 0                     │
   │        │         rec.flags **不置** LOG_FLAG_TIMESTAMP_VALID
   │        │         rec.uptime_ms = millis()   ← 本机仍有时序信息
   │        ▼                                                │
   │  128 B LogRecord → s%07u.log（16 段 × 31 条 = 496）      │
   │        │                                                │
   │        ▼  （需 ACK 才回收，见 BT-1 / WP-5）               │
   │  Cloud Log Envelope: {device_id,boot_seq,seq,**ts:0**,   │
   │                       level,payload_base64}             │
   └────────┼────────────────────────────────────────────────┘
            ▼  HTTPS POST /api/history/ingest
   ┌──────────────── Worker（Cloudflare）───────────────────┐
   │ normalizeLog(): ts = asInt(rec.ts) = **0**（非 null ⇒ 收）
   │ INSERT INTO log_history(device_id,ts,level,boot_seq,seq,…)
   │        created_at 由 D1 生成 = unixepoch()  ← 唯一"可信"时间
   └────────┼────────────────────────────────────────────────┘
            ▼  每天 03:00Z（Cron `0 3 * * *`）
   ┌──────────────── retention.js ───────────────────────────┐
   │ cutoff = now − 180 d                                    │
   │ DELETE FROM log_history WHERE device_id=? AND ts < ?     │
   │                                  LIMIT 1000              │
   │        ts = 0  <  cutoff  ⇒ **必然命中**                  │
   └────────┼────────────────────────────────────────────────┘
            ▼
       **永久删除**（无归档、无回收站）
```

**三条不可逆的语义断裂**：

1. **`ts=0` 与 `ts=1792297533` 在同一个数值轴上比较** —— "未知"被当成"极早"。
2. **`created_at`（写入时刻）就在同一行里，却没被用于判定** —— 兜底材料一直都在，只是没被采用。
3. **删除前没有任何"这条是 CRITICAL"的优先级** —— `level` 不参与判据（`D-3` 要求谓词只含 `device_id + ts`）。

## §4 四种方案比较（本轮**不实施**其中任何一种）

### 4.0 共同前提（任何方案都必须面对）

| 约束 | 内容 | 出处 |
|---|---|---|
| **`Q-2`（已裁决）** | "**`ts <= 0` 按现有谓词参与 retention**，保持 `WHERE device_id=? AND ts<?`，**不得增加 `AND ts > 0`**" | `P3-WP7-Implementation-Record.md:53` |
| **`D-3`（已冻结）** | 删除谓词**只依赖 `device_id + ts`**（无 rowid/随机/now 竞态） | `P3-WP3-…Design.md:420` |
| **`D-5`（已冻结）** | retention **不执行任何 DDL**（无新增索引 / 无 migration） | `retention.js` 头注释 |
| **`I-P*`（预算）** | 单表 DELETE ≤ 20 次 · `HARD_STOP=45` 不可达 | 同上 |

⇒ **B/C 都同时触碰 `Q-2` 与 `D-3`**（两个**冻结/已裁决**项），**不是纯编码改动**。
⇒ **A/D 不触碰**这两项。

### 4.1 方案 A：维持现状（零改动）

| 维度 | 评价 |
|---|---|
| 收益 | 零风险、零改动、零部署；`Q-2`/`D-3` 原样成立 |
| 代价 | **每次冷启动的 `CRITICAL` 在 ≤ 24 h 内必删** → 已实证丢失 3 条 |
| 适用 | 仅当"开机期日志不被需要"被**明确接受** |
| 验收 | 无需验收（现状） |
| 一句话 | **技术上最省事，运维上最贵的选项** —— 故障复盘时永远缺第一现场 |

### 4.2 方案 B：`created_at` 兜底（✅ **`2026-10-18` 人工已选**）

**判据改为**：`ts>0` 用 `ts`，`ts=0` 用 `created_at` 判超窗。

**实现形态（关键）**：必须写成 **OR 形式**，不能写 `COALESCE(NULLIF(ts,0),created_at) < ?`。
生产 `EXPLAIN QUERY PLAN` 实测（`2026-10-18` · 只读）：

| 谓词形态 | 执行计划 | 判定 |
|---|---|---|
| 现状 `device_id=? AND ts<?` | `SEARCH … USING **COVERING INDEX ix_lh_device_ts** (device_id=? AND ts<?)` | ✅ 最优 |
| `COALESCE(NULLIF(ts,0),created_at) < ?` | `SEARCH … USING INDEX **ux_lh_dedup** (device_id=?)` | ❌ **丢失 `ts` 收窄**，退化为"该设备全扫" |
| `((ts>0 AND ts<?) OR (ts=0 AND created_at<?))` | `SEARCH … USING **INDEX ix_lh_device_ts** (device_id=? AND ts>?)` | ⚠️ 保住索引与收窄，但**非 covering** |

| 维度 | 评价 |
|---|---|
| 收益 | ① 直接止血；② **安全方向单调**：`created_at ≥ 事件时刻`（上传延迟 ⇒ 只会**延长**保留，**绝不提前删除**）；③ 单点改动 + 可测试；④ 容量影响可忽略（见下） |
| 代价 | ① **修订 `Q-2`**（改判据 = 改裁决）；② **修订 `D-3`**（谓词不再"只依赖 `ts`"）；③ 需 `wrangler deploy`；④ 已删的 3 条**不会回来** |
| 容量 | `26 行/天 × 180 d × ≈378 B ≈ **1.7 MiB/设备**`；11 台 ≈ **19 MiB**（`5 GB` 的 **0.4%**）⇒ 不构成约束 |
| 风险 | ① 若设备离线 30 天后补传 ⇒ 该批 `ts=0` 行从 `created_at` 起算 ⇒ 保留期实际**多 30 天**（方向安全，但需知情）；② 谓词变复杂 ⇒ 必须补 L1 矩阵 + L2 真实 D1（`DELETE … LIMIT` 在 OR 形态下的行为） |
| 验收 | ① L1：`ts=0`/`ts>0`/`ts=cutoff` 三边界；② L2 真 D1：构造 `ts=0` 行 × 批次上限，断言"`ts=0` 不被误删、`ts>0` 超窗仍删、预算 `≤42`"；③ 生产首跑观察 `deleted` 与 `ts=0` 存量不再归零 |

#### 4.2.1 `created_at` 实测证据（本轮 · 只读 · 166 行）

| 项 | 值 | 判读 |
|---|---|---|
| 列定义 | `INTEGER NOT NULL DEFAULT (unixepoch())` | 不改 migration |
| NULL / `<=0` | **0 / 0** | 非空成立、无异常值 |
| 轴与单位 | **UTC Unix 秒**，与 `ts` 同轴 | 无时区换算 |
| 生成方 | **D1（服务端）** | 与 `cutoff`（`scheduledTime`）**同钟** |
| `created_at < ts` 行数 | **0** | **无负滞后**（不会提前删） |
| 滞后分布 | `<60 s` 97 · `60–600 s` 46 · `600–3600 s` 12 · **`≥1 d` 11** | `max = 770,260 s ≈ **8.9 d**`（离线补传）· `avg ≈ 7.1 h` |

**结构论证（不依赖样本）**：`created_at` 是入库时刻，入库必然晚于事件 ⇒ 删除时刻 ≥ 事件 + 180 d ⇒
**保留只会更长**。⇒ 「只会延长」= **`PROVEN（逻辑）`**；「最多延 ~9 d」= **`PROXY`**（单设备样本）。

#### 4.2.2 `ts<0` 处置（★ `H-RET-2` 已裁决 = **B-1** · 详见 §7.3）

| 事实 | 结论 |
|---|---|
| 生产 `ts<0` 行数 | **0** |
| 固件能力 | `LogRecord.timestamp` = `uint32_t` ⇒ **本固件不可能产生负数** |
| 入口未拦 | Worker `asInt()` 接受负整数 ⇒ 畸形请求可写入 |
| 候选 B-1（**✅ 已裁决**） | 并入 `ts <= 0` 一支（`created_at` 兜底）⇒ 谓词不遗漏、仍命中索引 |
| 候选 B-3（**❌ 已否决**） | 独立 `OR (ts<0)` ⇒ 实测计划**退化**为 `ux_lh_dedup` |

> **禁令**：任何实现形态都**不得**让 `ts<0` 落进"两支都不匹配"的空隙 —— 那等于**永久保留**。

### 4.3 方案 C：`ts=0` 隔离保留 N 天（B 的有界变体）

**判据**：`ts=0` 且 `created_at < now − N d` 才删（例如 `N = 7`）。

| 维度 | 评价 |
|---|---|
| 收益 | 同 B 的止血能力，但**保留期可调、有界**（不会因长期离线而被拉长到 180 d） |
| 代价 | ① 同样触碰 `Q-2` / `D-3`；② **新增 1 个可注入参数**（`RETENTION_TS0_DAYS`）⇒ 与 `Q-5`「生产 `[vars]` 不设置 `RETENTION_*`」的纪律要重新对齐；③ 多一套边界测试 |
| 容量 | `26 × 7 × 378 ≈ 69 KiB/设备`（几乎为零） |
| 适用 | 若人工认为"开机期日志只看近一周"够用 |
| 相对 B | **更"克制"但更复杂**：B 不需要新参数（沿用 180 d），C 需要 |

### 4.4 方案 D：修 `HD-3` 根因（固件侧）

**先厘清 `HD-3` 到底是什么**（见 `Phase-C-C1-Telemetry-Publisher-Implementation-Review.md:206`）：

> `HD-3` 原问题 = **"`ts` 无效时：仍发 `ts=0`，还是暂缓发送？"** —— 现状 = 发 `ts=0`（"不伪造时间"）。
> 附加面（`P-4`）= `ts=0` + 重启后 `seq` 归零 ⇒ **telemetry** 幂等键 `(device_id,type,ts,seq)` **碰撞**。
> （`log_history` 的唯一键含 `boot_seq`，故 log 域不受该碰撞影响。）

| 维度 | 评价 |
|---|---|
| 收益 | 消除"`ts=0` 记录存在"的**成因之一**（不等于消除成因） |
| 代价 | ① **改固件 + 刷机**（需单独授权）；② "暂缓发送" ⇒ 开机期记录**根本不进云**（比现状更差）；③ "加 boot 相对时间字段" ⇒ **动已冻结的 6 字段信封**，且 Worker 需解码 CBOR（`D-4`） |
| 对 `RET-1` 的作用 | **不解决**：只要"设备从未同步过时间"，`ts=0` 仍会产生 ⇒ 仍需 B/C 兜底 |
| 建议 | **不作为本轮首选**；若日后要做，先做"**协议边界决策**"，而不是直接改代码 |

### 4.5 已评估并**排除**的方案 E：云端用 `uptime_ms` 反推 `ts`

- **技术可行**：`payload_base64` 解出的是 CBOR 批次，内含完整 128 B `LogRecord`，**已带 `uptime_ms`**
  （`log_events.h:465`，`LOG_OFF_UPTIME_MS`）。用同 `boot_seq` 的任一 `ts>0` 行作锚点
  （`boot_epoch ≈ ts − uptime_ms/1000`）即可估算。
- **为何排除**：① 需 Worker **新增 CBOR 解码**（CPU + 代码面）；② 估算值带上传抖动，**不是真值**；
  ③ 属于"改数据"而非"改判据"，与"不伪造时间"的项目纪律冲突。
- **保留用途**：**离线分析**（人工排查已落库的 `ts=0` 行）可以这么做，但**不得进 ingest 路径**。
