## §2 生产变更纪律

> **适用于每一次变更**（EMQX / Worker / D1 均适用）。**一次变更 = 一组「前 → 中 → 后」记录。**

### 2.1 变更**前**（必须全部完成）

| # | 动作 | 产出 |
|---|---|---|
| 1 | **保存当前配置基线** | 变更前配置快照（EMQX 规则 SQL / Action / Connector；Worker 版本） |
| 2 | **保存版本状态** | 平台版本 ID（如 Worker deployment version）+ 时间 |
| 3 | **保存 migration 状态** | 远端已应用清单（`migrations list --remote`） |
| 4 | **保存回滚信息** | 明确的回滚步骤 + 回滚判据 + 回滚后校验点 |

> **无基线不得变更**（尤其 EMQX：其配置 **API 不可回读**，基线**只能人工导出**）。

### 2.2 变更**中**

| # | 规则 |
|---|---|
| 1 | **一次只执行一个明确步骤**（禁止批量合并不同性质的变更） |
| 2 | **每一步必须记录执行结果**（命令 / 操作 / 原始输出 / 时间 / 操作者） |
| 3 | **失败立即停止**（不得带病继续下一步；不得"先做完再一起修"） |

### 2.3 变更**后**

| # | 动作 |
|---|---|
| 1 | **必须验证**（按 §3 的验证步骤，结果标注 `PASS / FAIL / BLOCKED`） |
| 2 | **必须更新仓库存档**（EMQX 控制台配置**必须回写** `EMQX_Assets/config/data-integration/`） |
| 3 | **必须提交实施记录**（变更对象 / 原因 / 前后状态 / 验证结论；**代码与文档分离提交**） |

## §3 不可跳过步骤纪律（**顺序固定**）

```
        ① 0003 migration
              ↓
        ② Worker deployment
              ↓
        ③ EMQX baseline export
              ↓
        ④ EMQX Rule creation
              ↓
        ⑤ Existing Rule narrowing
              ↓
        ⑥ Validation V-1 ~ V-7
              ↓
        ⑦ Archive update
```

> **★ ④ 与 ⑤ 必须同处一个变更窗口**（冻结设计 `-S2`）—— 只新增不收窄 ⇒ **telemetry 双投**。

### 3.1 明令禁止

| # | 禁止 | 原因 |
|---|---|---|
| 1 | **先建 Rule 后部署 Worker** | 规则目标不存在 ⇒ 投递落在 catch-all，**静默丢弃** |
| 2 | **先切 Action 后准备数据库** | 远端无表 ⇒ 全量 **`503` + 上游重投风暴** |
| 3 | **未导出基线直接修改 EMQX** | **不可回滚、不可审计**（配置 API 不可回读） |
| 4 | **未验证直接宣布完成** | 违反 `V-1…V-7` 判据 |

> **顺序铁律**：`0003` → Worker → EMQX 变更。**禁止调整顺序**（`H-WP4C-06` 已确认）。

## §4 回滚纪律

### 4.1 必须**停止并评估**的情形（触发条件）

| # | 触发 |
|---|---|
| 1 | **Rule predicate 命中异常**（误判 / 漏判） |
| 2 | **Action 失败**（非 2xx / 超时 / 重试放大） |
| 3 | **D1 写入失败**（`503` / `persist_failed` / 约束异常） |
| 4 | **Worker endpoint 异常**（非预期状态码 / 异常响应） |
| 5 | **双投 telemetry**（同一记录同时进 `telemetry_history` 与 `mqtt_messages`） |
| 6 | **`mqtt_messages` 污染**（命令链路被 telemetry 写入 / 记账断链） |

### 4.2 回滚**优先级**（**严格自上而下**）

```
        停止新增流量
              ↓
        恢复旧 Rule
              ↓
        恢复 Action
              ↓
          分析原因
```

> **★ 关键**：**先止损（停流）再回滚配置，最后才分析根因** —— 禁止"先查原因再决定是否止损"。
> **回滚基线来源** = §2.1 保存的**变更前配置基线**（EMQX 侧须人工导出）。

## §5 报告要求（**每一步之后必须输出**）

| # | 报告 | 必含字段 |
|---|---|---|
| 1 | **Commit / Change Report** | 修改对象 · 修改原因 · **是否超范围** |
| 2 | **Production Change Report** | **平台** · **操作时间** · **操作者** · **前后状态** |
| 3 | **Validation Report** | **`V-0`…`V-7`** 逐项 `PASS / FAIL / BLOCKED` |
| 4 | **Risk Report** | **新风险** · **偏离冻结设计** · **环境差异** —— **必须新增记录，不允许隐藏** |

## §6 纪律执行与冲突处置

| 场景 | 处置 |
|---|---|
| 纪律与冻结设计冲突 | **以冻结设计为准** ⇒ `STOP` + 新 `HUMAN_REQUIRED` |
| 环境与冻结设计不符（如平台限制） | **记录为风险（`R-*`）** + `STOP` + 新 `HUMAN_REQUIRED`，**不得自行绕过** |
| 授权范围外 | **不做** ⇒ 报告"超范围"并请求授权 |
| 验证未通过 | **不得宣布完成**；按 §4 评估回滚 |

## §6A `EMQX Console Boundary Rule` —— **EMQX 控制台边界规则**（**2026-10-12 增补** · 适用于 `WP4C` 及后续）

> **增补原因**：`WP4C` 实施在**步骤 ③（EMQX 基线导出）**受阻于平台限制（数据集成 API **读 + 写全 `403`**、**无 CLI**）⇒ 依 §6 **`STOP`**。
> 为避免后续任何形式的**代办 / 推测 / 绕过**，本节把**边界**写成**强制规则**。与冻结设计冲突时，**以冻结设计为准**（§1）。

### EMQX Console Boundary Rule

#### 6A.1 定性 —— Console-only 操作 = **生产人工变更**

| # | 规则 |
|---|---|
| 1 | EMQX **规则 / 连接器 / 动作**（数据集成）在现有平台上**只能通过控制台配置**（`D-1`：API `403` · 无 CLI） |
| 2 | ⇒ **凡控制台所做的每一处配置，性质均为「生产人工变更」** —— **不因「点了鼠标」而降级** |
| 3 | ⇒ 须**完整套用** §2（变更前 / 中 / 后）· §4（回滚）· §5（四类报告），**不得以"手工操作无法留痕"为由豁免** |
| 4 | 变更后**必须回写** `EMQX_Assets/config/data-integration/`（存档 = 唯一可审计来源 · `R-WP4C-6` / `R-WP4C-13`） |
| 5 | **密钥（`X-Webhook-Key` / secret）禁入仓** —— 只记录「**已配置 / 未配置**」与轮换方式（`H-WP4C-07`） |

#### 6A.2 自动代理**禁止**清单（**硬禁 · 无例外**）

| # | 禁止 | 理由 |
|---|---|---|
| 1 | **猜测 Rule SQL** | SQL **非冻结**，须以部署版本**实测**（`V-1`）为准；猜测值**不可回滚、不可审计** |
| 2 | **猜测 Action 配置** | Action 的 URL / 方法 / 请求头 / Body 模板**只能取自 `V-0` 导出**；推断值 = **伪造基线** |
| 3 | **以历史文档替代 `V-0` 导出** | 存档是**观测推断**（且**已知与 `D-2` 矛盾**，`R-WP4C-12`）⇒ **不能**充当"变更前的字节" |
| 4 | **在无法验证权限时尝试绕过 API** | 权限不足（`403`）⇒ **只读探测为止**；**禁**换凭据 / 换端点 / 猜参数 / 反复重试写请求去"试出来" |
| 5 | （推论）**代填控制台 / 代抄 SQL 并宣称已完成导出** | 代理**可**交付**规格草案**（须标注 `⚠️ 未执行 · 待 V-1`），但**不得**宣称已导出 / 已验证 |

> **代理允许做的事**：**只读**探测（状态码即证据）· 撰写**人工操作规格**（`P3-WP4C-Implementation-Plan.md` §8）· 汇总**待人工裁决项**。
> **代理不允许做的事**：任何形式的"据推断，基线应该是…"并据此推进实施。

#### 6A.3 EMQX 变更**准入序列**（`V-0…V-5` · **每一步都是前置门**）

> **★ 命名空间说明**：本序列的 `V-0…V-5` = **EMQX 变更准入序列（Change Admission Sequence）**；
> 它与冻结设计的**验证集** `V-1…V-7`（`P3-WP4C-EMQX-Rule-Design.md` §7 / `Decisions.md` §5.2）是**两个命名空间** ——
> 前者约束「**能不能做这一步**」，后者判定「**做完对不对**」。**两者都不得省略。**
> 映射：准入 `V-3` ≡ 冻结 `V-2`（telemetry positive）· 准入 `V-5` ≡ 冻结 `V-3`（command negative）。

```
V-0  人工导出当前 Rule / Action / Connector 基线      ← 无基线 ⇒ 不得变更
 ↓
V-1  确认目标 Action 可达（endpoint 实测可达）        ← 不可达 ⇒ 不得建 Rule
 ↓
V-2  创建新 Rule（guo_feeder_history_ingest）
 ↓
V-3  验证 telemetry 分流（history +1 / mqtt_messages +0）
 ↓
V-4  收窄旧 Rule（WHERE 改为 NOT 谓词）
 ↓
V-5  验证 command 不受影响（history +0 / mqtt_messages +1）
```

| 步 | 内容 | 判据 | 当前（`2026-10-12`） |
|---|---|---|---|
| `V-0` | **人工导出** Rule SQL / Action / Connector **三份基线** | 三份快照**全文入库**（secret 脱敏） | ✅ **已完成**（`2026-10-12` · `H-WP4C-09-A = CLOSED WITH GUARD`）—— 连接器 2/2 · 规则 3/3（SQL 全文）· 动作 3/3（含高级设置）· D1 计数 · 回滚已签署；**guard = TLS 明细不可回读**（`R-WP4C-16`） |
| `V-1` | **确认目标 Action 可达** | **实测**可达；**不得**以"应该能通"代替 | 🟢 **`PASS`（带说明）**（`2026-10-12`）—— **①** 形态已裁决（方案 A = Pages 域名）· **②** **Pages 中转已部署并验证**（`H-WP4C-11 = CLOSED`；`61b4938e-…`；中转层 + 鉴权边界 **7/7 `PASS`**）· **③** **同 host 由 EMQX 生产投递作证**（既存 presence 连接器 `c-n302933b-291200` → 同一 `*.pages.dev`，`device_event` 近 7 d **114** 次）⇒ **`D-2` / 方案 A 获现场证据**。**✅ 已补齐（`2026-10-12` 22:20 · 第五轮终测）**：新连接器（`CB` + presence 重建体）5 请求全 200（tail 实证） |
| `V-2` | **创建新 Rule** | `guo_feeder_history_ingest` 已保存并**启用** | ✅ **已完成**（`2026-10-12` · 人工控制台：规则 A/B 已保存并启用 —— `r-n302933b-cf0cf2` / `r-n302933b-f731cf`） |
| `V-3` | **验证 telemetry 分流** | `telemetry_history` **+1** 且 `mqtt_messages` **+0** | ✅ **已完成**（冻结 `V-2` 实证：`th+1` / `mm+0` · 第五轮 `th+1` seq `91301`） |
| `V-4` | **收窄旧 Rule** | 旧规则 WHERE 已改为 **`NOT`（冻结谓词）** | ✅ **已完成**（`R3` 形态：规则 B 新建即带 `NOT 谓词` · 与 `V-2` 同批达成） |
| `V-5` | **验证 command 不受影响** | `telemetry_history` **+0** 且 `mqtt_messages` **+1** | ✅ **已完成**（冻结 `V-3` 实证：`th+0` / `mm+1`） |

> **★ 顺序铁律（与 §3 一致）**：`V-2`（新增）与 `V-4`（收窄）**必须同处一个变更窗口** —— 只做其一 ⇒ **telemetry 双投**。

#### 6A.4 `STOP` 条款（**任一不满足 ⇒ 立即 `STOP`**）

> **若以下任一条件不满足，立即 `STOP`，并登记 / 更新 `HUMAN_REQUIRED`：**

| # | 条件 | 不满足时的动作 |
|---|---|---|
| 1 | **Action endpoint 未确认** | **`STOP`** —— **不得**创建 Rule（否则投递必然失败或静默丢弃） |
| 2 | **Rule baseline 未保存**（`V-0` 未完成） | **`STOP`** —— **不得**修改任何既有规则（不可回滚 / 不可审计） |
| 3 | **回滚方案不存在** | **`STOP`** —— **不得**开始变更（须先明确回滚步骤 + 判据 + 校验点，§2.1） |

> **★ 本条 = §6「环境与冻结设计不符 ⇒ `STOP`」在 **EMQX 控制台作业**上的具体化**。
> `STOP` 后**唯一**合法动作 = **登记 `HUMAN_REQUIRED` + 等待人工**；**禁止**任何形式的绕过或降级。

> **当前实际状态 —— ✅ 三个 `STOP` 条件均不成立（`2026-10-12` 起）**：
> **条件 1（Action endpoint 未确认）= 已解除** —— Pages 中转**已部署并端到端验证**（`H-WP4C-11 = CLOSED`），且**同一 host** 已由既存 presence 连接器在生产上**持续投递成功**；
> **条件 2（`V-0` 未完成）= 已解除** —— `V-0` = ✅ `CLOSED WITH GUARD`（`H-WP4C-09-A`）；
> **条件 3（无回滚方案）= 已解除** —— 回滚方案已签署（`V0` §5.2）。
> **⇒ EMQX 侧变更当前无纪律层面阻塞**；剩余阻塞 = **人工执行能力**（`H-WP4C-09-B` 须在控制台操作；代理无控制台 / 数据集成 API 权限，`D-1…D-6`）。
> **★ 注意**：`STOP` 解除**不等于**授权变更 —— 变更仍须按 **§6A.3 准入序列**逐步执行，且 `V-2` 与 `V-4` **必须同批**。
