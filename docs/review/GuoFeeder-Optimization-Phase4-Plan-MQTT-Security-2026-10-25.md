### P4-2 三方案对比与选型（必须在 P4-1 之后）

| 方案 | 描述 | 预判断 |
|---|---|---|
| A | Worker 代理命令（现状） | ✅ 现状，全保障 |
| B | 浏览器 MQTT 直接发命令 | ❌ 丢失 registry 校验/审计/去重/限流；且需浏览器用户有**发布**权限 |
| C | 浏览器 MQTT 只读（状态/遥测），命令仍走 Worker | 需浏览器用户有**订阅**权限 |

选型必须回答的核心问题：**浏览器用户如何获得受限制的 pub/sub 权限？**
由于 ACL API 不可用，只能依赖控制台预置的**静态账号 + 静态 ACL**。
⇒ 这与现有的 `GuoFeederDevice` 共享账号是同一模式，会**复现 P1 风险**（账号共享、无按会话隔离）。
⇒ **若 P4-1 证明无法做到按会话/按用户的最小权限，方案 C 的安全前提不成立。**

- session minutes 预算：网页端 1 连接 ≈ 1,440 分钟/日·常开 ⇒ 必须「按需连接、隐藏即断」。
- 结论写入报告，**不擅自实施 B/C**（规划明确：UI 命令迁移到 MQTT 待用户在全阶段结束后提出）。
