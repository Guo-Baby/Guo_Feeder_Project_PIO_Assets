## §1 触发：Serverless 配额实测（**不可调整**）

| 配额 | 上限 | **当前占用** | 余量 | 备注 |
|---|---|---|---|---|
| **连接器数** | **2** | **2 / 2**（`c-…291200` presence · `c-…b12100` 消息流） | **0** ❌ | 人工在控制台核实：**不可调整** |
| **规则数** | **4** | **3 / 4** | **1** ✅ | 足够（本次只需 +1） |
| **动作数** | **4** | **3 / 4** | **1** ✅ | 足够（本次只需 +1） |
| 单条规则关联动作数 | **1** | 1（既有 3 条规则均 1 动作） | 0 | ✅ 本设计天然满足（1 规则 : 1 动作） |

> **交叉核对（官方文档）**：EMQX Cloud 文档《数据集成简介》给出同一组限制 ——
> **"可创建的连接器数量 2 · 可创建的规则数量 4 · 单条规则关联的动作数量 1"**。
> 与人工在控制台读到的「连接器 2 / 规则 4 / 动作 4（**不可调整**）」一致（"动作 4" 为控制台侧表述，本设计两种口径下均满足）。

**⇒ 结论：`R1` 冻结设计所依赖的"**新建独立连接器**（`guo_feeder_history_http`）"**在配额上不可能实现**。**

## §2 为什么这不是"可绕过的实施细节"，而是**设计修订**

`R1` 的关键前提是**一个端点一个连接器**：

| `R1` 假设 | 现实 |
|---|---|
| 连接器 = **端点（URL 含路径）** 的载体 | ✅ 成立（连接器 URL `…/api/webhook` · `…/api/presence/event`） |
| 因此"新端点 ⇒ **新连接器**" | ❌ **配额 0 余量** ⇒ 不可能 |
| 动作用**空** URL 路径（`V-0` 实测三条动作路径**全空**） | ⚠️ 这只说明**既有配置如此**，**不是**平台约束 |

**⇒ 必须变更的是"如何把两个不同路径指向同一端点族"的**形态**，而不是分流**语义**。**

## §4 采纳方案 `R-A′` —— **单连接器 + 动作级路径分流**

### 4.1 核心机制（**已由官方文档确认**）

> EMQX HTTP Server 数据集成：**连接器承载 base URL**，**动作承载 `URL Path`**；
> 「**The final request URL will be constructed by combining the Connector URL and this path.**」
> （来源：EMQX 官方文档《Ingest MQTT Data into HTTP Server》· 连接器步骤 5 与动作步骤 3）

```
                  ┌──────────────────────────────────────────────┐
                  │  连接器 c-n302933b-b12100（复用 · 仅改 URL）   │
                  │  base URL = https://guo-feeder-pagesdev.pages.dev │
                  │  headers  += X-Webhook-Key（见 §4.4）          │
                  └───────────────┬──────────────────────────────┘
                                  │
          ┌───────────────────────┴────────────────────────┐
          │                                                │
  动作 a-…921e22（既有）                          动作 <新>（第 4 个）
  URL Path = /api/webhook                        URL Path = /api/history/ingest
          │                                                │
          ▼                                                ▼
  https://…pages.dev/api/webhook                 https://…pages.dev/api/history/ingest
  （= 逐字等于今日生效 URL）                        （= R1 冻结的同一端点，未变）
          │                                                │
     Worker 根路径                                  Worker /api/history/ingest
          ▼                                                ▼
   mqtt_messages                                  telemetry_history
```

> **★ 为什么 base 取「裸主机」（不带路径）**：
> `https://guo-feeder-pagesdev.pages.dev` 是**唯一**对两种拼接语义都成立的选择 ——
> 若平台是「**追加**」（文档口径）：`base` + `/api/webhook` = `…/api/webhook` ✅
> 若平台是「**替换路径**」：`base`（无路径）被替换为 `/api/webhook` = `…/api/webhook` ✅
> ⇒ **两种语义下结果一致**，消除唯一的不确定性。

### 4.4 鉴权头落位的选择（**为什么放在连接器**）

`/api/history/ingest` 是**鉴权端点**（`requireWebhookKey()`；无 key ⇒ `401`）。
`c-…b12100` **当前无任何鉴权头**，故**必须补**。落位选择：

| 落位 | 说明 | 采用 |
|---|---|---|
| **连接器 `c-…b12100` 的 Headers** | **官方文档确认**的请求头位置（连接器创建步骤 6）；对 `/api/webhook`（**无鉴权根路径**）**无副作用** | ✅ **主选** |
| 动作层 Headers | `V-0` 实测动作层**确有** Headers 字段（三条动作均配了头）⇒ 控制台若在动作页提供，可作为**备选** | ⚠️ 备选（**不要两处同时配同名头**） |

> **★ 副作用声明**：加上后，消息流请求也会带上 `X-Webhook-Key`。因 `/api/webhook` → Worker **根路径**（P0 无鉴权）⇒ **无行为变化**；仅"多一个头"。

### 4.5 ★ 一处**未采纳**的"顺带清理"（**纪律约束**）

`c-…b12100` 是**消息流链路**的连接器（`R-WP4C-15`：≈90% 失败）。
**本次只改 URL 与补鉴权头**，**不动**请求体 / `SELECT *` / 超时参数 —— 修 `R-WP4C-15` 属**超出 WP-4 范围**，人工已裁示**暂不追修**。

### 5.2 阶段 3 与 4 的"双投窗口"（**冻结设计已预告 · 按冻结顺序执行**）

冻结设计 §5.3 规定 **`①新增` → `②收窄`** 的顺序。照此执行时，阶段 3-1（启用新规则）到阶段 4-1（收窄旧规则）之间存在**双投窗口**：

| 影响 | 评估 |
|---|---|
| telemetry 同时进 `telemetry_history`（**正确**）与 `mqtt_messages`（**多余**） | 窗口目标 **≤30 s** ⇒ 预计多出 **0–1 行** `mqtt_messages` |
| 是否破坏 `V-3` 判据？ | ❌ 不破坏 —— `V-3` 判 `mqtt_messages` **+1**（命令结果），与 telemetry 行无关；且为**窗口内一次性** |
| 是否需清理？ | 可选（按 `device_id` + `ts` 定点删）；**建议不清理**（保留原始证据，且 `mqtt_messages` 本就 best-effort） |

> **若把窗口也压到零**：可改为 **②收窄 → ③启用** 的顺序（先收窄旧规则，再启用新规则）—— 此时无"双投"，代之以 ≤30 s 的"telemetry 不落任何表"。
> **本文档按冻结顺序（①→②）执行**；上述变体作为**可选优化**，须在执行报告中注明实际采用哪种。

## §6 ★ 顺带修正：**动作请求体**与**规则 SQL** 的对齐缺陷（**同一窗口内一并处理**）

> 审查 `P3-WP4C-Implementation-Plan.md` §8.1 时发现 **`R1` 规格内部不自洽** —— 若照原样施工，**V-2 必然失败**。
> 该两处属**未被冻结**的部分（冻结设计 §4.5 明示「SQL 形态**非冻结契约**，以 `V-1` 实测为准」），故**可修正**，但须留痕。

### 6.1 缺陷 1：动作请求体与规则 SELECT 输出**字段不匹配**

| `R1` §8.1 原样 | 问题 |
|---|---|
| 规则 SQL：`SELECT json_encode(… 'payload' …) AS body` | 规则**只输出 `body` 一个字段** |
| 动作请求体：`{"topic":"${topic}","clientid":"${clientid}","payload":"${payload}"}` | `${topic}` / `${clientid}` / `${payload}` **在规则输出中不存在** ⇒ 模板变量取空 |

**对比既有生产配置**（`V-0` 实测，**已验证可用**）：
- presence 两条：规则 `SELECT json_encode(…) AS body` + 动作体 **裸 `${body}`** ✅（字段匹配）
- 消息流一条：规则 `SELECT *` + 动作体 **三键模板** ✅（字段匹配）

⇒ **两处必须成对选择其一。**

### 6.2 缺陷 2：`${payload}` **加引号**会让 Worker 直接 `400`

`Cloudflare_Assets/guo-feeder-api/src/history-ingest.js` 的 `extractRecords()`：
telemetry 域要求 `body.payload` 是**非数组对象**（或数组）；**若 `payload` 是字符串 ⇒ 返回 `null` ⇒ `400 {"error":"unparsable_payload"}`**。

⇒ 请求体写 `"payload": "${payload}"`（**带引号**）⇒ payload 变成**字符串** ⇒ **V-2 必失败**。

### 6.3 🔒 修正后的定案（**采用既有生产模式 ②**）

| 项 | 定案值 |
|---|---|
| **规则 SQL** | `SELECT * FROM "guo_feeder/+/up" WHERE <冻结谓词>` |
| **动作请求体** | `{"topic":"${topic}","clientid":"${clientid}","payload": ${payload}}` ← **`${payload}` 不加引号** |
| **理由** | ① **与已在生产验证的消息流动作同构**（同为 `SELECT *` + 三键体 + 不加引号）② 保证 `payload` 以**对象**落到 Worker ⇒ 满足 `history-ingest.js` 契约 ③ `FROM` 与冻结谓词**逐字不变** |

**冻结谓词（`R2` 原字面写法 · 存档留存）**：

```
      payload.schema_version  != 'undefined'
  AND payload.seq             != 'undefined'
  AND payload.ts              != 'undefined'
  AND payload.type            != 'undefined'
  AND payload.value           != 'undefined'
  AND payload.c               == 'undefined'
  AND payload.cmd             == 'undefined'
```

> 🔄 **`R3.1`（`2026-10-12` · 控制台实测）**：上述**字面写法已被否决** ——
> ① **`==` 不存在**（EMQX 规则 SQL 的"相等"只有单 `=`）⇒ 保存报 **`11: syntax error before: '='`**；
> ② "键是否存在"应使用官方内置函数 **`is_null()` / `is_not_null()`**。
> ⇒ **施工以 `R3.1` 写法为准**（**语义逐字不变**，仅改写法）：
>
> ```
>       is_not_null(payload.schema_version)
>   AND is_not_null(payload.seq)
>   AND is_not_null(payload.ts)
>   AND is_not_null(payload.type)
>   AND is_not_null(payload.value)
>   AND is_null(payload.c)
>   AND is_null(payload.cmd)
> ```
>
> **最后备选**（仅当 `is_null` 报"未知函数"）：回到 `'undefined'` 字符串比较，但**相等必须单 `=`**。
> 权威施工规格 = `P3-WP4C-Console-Task-Sheet.md`（照抄版）+ `…-Console-Build-Guide-R3.md`；冻结设计 §4.5 / §10.4 已同步。

> **★ 语义铁律不变**：`value` 用「**键存在**」语义（**禁**"值非空 / ≠ 0"）· 谓词**不涉及** `device_id`（身份只来自 topic）· **禁只判 `type`/`value`/`topic`**。
> ✅ **`R3.1`（`2026-10-12`）已定稿部分**：函数名 = 官方内置 **`is_null` / `is_not_null`**（控台实测 `==` 报错后核实官方文档定案）；`'undefined'` 字符串比较**降级为最后备选**（必须单 `=`）。
> ⚠️ **仍待控制台实测确认**：`payload.x` 是否自动解码 —— 规则保存后用页面调试功能试跑（`{"msg":"hello"}` ⇒ 规则 A **不匹配** / 规则 B **匹配**；见 `P3-WP4C-Console-Task-Sheet.md` §7.0）。若 `payload` 不自动解码 ⇒ 就地改用 `json_decode(payload)` 方案，并回写存档（属 §4.5 允许范围）。
